## Анализ результатов

### Что хорошо ✅

1. **0 ошибок** на всех тестах до 1000 пользователей
2. **Стабильный рост RPS** — система масштабируется линейно
3. **Все ответы 200 OK** — ни одного таймаута или 500-й ошибки
4. **NATS работает стабильно** — все 6000+ событий опубликованы и доставлены

### Узкие места 🎯

1. **Латентность растёт с 30ms до 940ms** при увеличении нагрузки с 10 до 1000 пользователей
   - P95 latency на 1000 пользователях: 940ms (цель была <500ms)
   - **Причина:** У каждого запроса Game → NATS → Leaderboard → Billing (синхронная цепочка)

2. **RPS колеблется** (2271 → 2309 → 3060 → 3496)
   - Нестабильность из-за NATS ack и PostgreSQL записи в Billing
   - **Причина:** Billing пишет в PostgreSQL синхронно (без batch)

3. **Память растёт** с 50MB до 220MB при 1000 пользователях
   - В пределах нормы (~220KB на пользователя)

### Рекомендации по оптимизации

#### 1. Billing: добавить batch записи в PostgreSQL
Сейчас каждая транзакция пишется отдельно. Переделать на batch writer:

```go
// Буферизированный канал
dbChan := make(chan Transaction, 10000)

// Отдельный воркер для batch insert
go func() {
    batch := make([]Transaction, 0, 100)
    ticker := time.NewTicker(1 * time.Second)
    
    for {
        select {
        case tx := <-dbChan:
            batch = append(batch, tx)
            if len(batch) >= 100 {
                flushBatch(batch)
                batch = batch[:0]
            }
        case <-ticker.C:
            if len(batch) > 0 {
                flushBatch(batch)
                batch = batch[:0]
            }
        }
    }

}()
```

#### 2. Leaderboard: убрать лишние обращения к Redis

Сейчас каждый запрос делает ZADD и ZREVRANK. Можно делать только ZADD и раз в N секунд пересчитывать топ.

#### 3. Добавить кеш для /api/game/submit

На уровне Gateway можно кешировать частые запросы одного пользователя (TTL 1-2 секунды).
