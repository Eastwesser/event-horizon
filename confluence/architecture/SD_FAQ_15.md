🧠 Твой пример с Кафкой → Перенос на NATS (Event Horizon)
Ты сказал:

«Producer привозит кирпичи → склад (топик) → Consumer забирает»

В Event Horizon это выглядит так:

Роль в Кафке	Роль в NATS	В проекте
Producer (кто привозит)	Publishers	Game, Auth, Billing
Склад (топик)	Subject / Stream	score.updated, user.registered
Consumer (кто забирает)	Subscribers	Leaderboard, Billing, Analytics
Consumer Group	Queue Group	Несколько инстансов Leaderboard (чтобы не дублировать обработку)
Offset	Sequence / Ack	JetStream хранит позицию, если подписчик упал
Главное отличие:
Кафка — для долгого хранения (days/weeks).
NATS JetStream — для быстрой доставки (минуты/часы), но тоже с персистентностью.

📝 Официальные ответы на 15 вопросов (с пояснениями)
Вопрос 1 (Самый важный): Куда Gateway отправляет gRPC-запрос?
Ответ:
Gateway → напрямую в сервисы (Auth/Game/Billing/Leaderboard) по gRPC.
НЕ в NATS.

Пояснение:
Gateway — это входная дверь. Он не знает про NATS. Он просто принимает HTTP, проверяет JWT, конвертирует в gRPC и вызывает нужный метод сервиса.

А уже сервис (например, Game) решает:

«Мне нужно оповестить других?» → тогда Game публикует событие в NATS.

Как это связано с твоим примером про Кафку:
Gateway — это не Producer и не Consumer. Это просто шлюз, который пропускает запрос внутрь.
А Producer — это Game, который после сохранения рекорда говорит: «Эй, NATS, передай это Лидерборду!»

Вопрос 2: Если Game обработал рекорд, куда он публикует событие?
Ответ:
Game публикует событие score.updated в NATS (JetStream).

Подписчики:

Leaderboard (обновляет топ)

Billing (начисляет валюту)

(в будущем) Analytics (собирает метрики)

Пояснение:
Game не знает, кто подписан. Он просто кидает событие в «эфир» (NATS). А NATS уже доставляет всем, кому нужно.

Вопрос 3: Как клиент получает обновление топа?
Ответ:
Через WebSocket (постоянное соединение).

Пояснение:
Когда Leaderboard обновляет Redis, он пушит изменения через WebSocket всем подключённым клиентам. Клиенты не опрашивают сервер (не polling). Сервер сам присылает обновление.

Вопрос 4: Что делает Балансировщик?
Ответ:
Балансировщик (:8079) выбирает Gateway с наименьшим количеством активных соединений (Least Connections).

Пояснение:
Он смотрит на ActiveConns у каждого Gateway. Выбирает тот, у которого меньше всего.
НЕ round-robin.

Вопрос 5: Какой сервис для /api/billing/balance?
Ответ:
Gateway вызывает Billing (:50053) по gRPC.

Пояснение:
Gateway смотрит на путь:
/api/billing/* → отправляет в Billing.
/api/auth/* → отправляет в Auth.
Это маршрутизация по пути.

Вопрос 6: Billing пишет сначала в Redis или PostgreSQL?
Ответ:
При записи (списание/начисление) — сначала PostgreSQL, потом инвалидация Redis.
При чтении (просмотр баланса) — сначала Redis, если нет → PostgreSQL.

Пояснение:
Баланс — критичные данные. Нельзя полагаться на Redis, потому что он может упасть.
Сначала сохраняем в надёжную БД, а потом уже обновляем кеш.

Вопрос 7: Что при cache miss?
Ответ:
Сервис идёт в PostgreSQL.

Если данные есть → возвращает и кладёт в Redis (с TTL).

Если данных нет → возвращает 404 (для GET) или создаёт запись (для POST).

Пояснение:
Это стандартный паттерн Cache-Aside.

Вопрос 8: Порты NATS?
Ответ:

4222 — клиентский (для сервисов).

8222 — мониторинг (JSON).

Почему не используем 8222 в Prometheus?
Прометей ждёт формат /metrics (plain text).
А NATS отдаёт JSON. Это несовместимо.
Нужен NATS Exporter, чтобы переводить JSON в Prometheus-формат.

Вопрос 9: Как реплицируются 3 ноды NATS?
Ответ:
Через RAFT-консенсус.

Флаги:

bash
-cluster nats://0.0.0.0:6222 \
-routes nats://nats-2:6222,nats://nats-3:6222
Одна нода — лидер (пишет), остальные — фолловеры (читают).
Если лидер падает — выбирается новый.

Пояснение:
Это как в Кафке: один брокер — контроллер, остальные — реплики.

Вопрос 10: Кто выбирает Gateway?
Ответ:
Балансировщик (:8079).

Как именно:

Приходит запрос.

Балансировщик смотрит на ActiveConns у всех Gateway.

Выбирает с минимальным числом.

Увеличивает счётчик на 1, проксирует запрос.

После ответа — уменьшает счётчик на 1.

Вопрос 11: Как Leaderboard обновляет топ?
Ответ (пошагово):

Игрок завершает игру → Game получает рекорд.

Game → NATS (публикует score.updated).

Leaderboard подписан на это событие → получает.

Leaderboard обновляет Redis Sorted Set (порт 6382).

Leaderboard → WebSocket → отправляет обновление всем клиентам.

Важно: Leaderboard пишет в Redis, а не в PostgreSQL для топа.
PostgreSQL (5463) — для истории, а Redis — для быстрого топа.

Вопрос 12: Rate Limiter — какие лимиты?
Ответ:

AllowSubmit — 10 запросов/сек на пользователя.

AllowLogin — 5 запросов/сек с IP.

AllowWebSocket — 100 соединений/мин с IP.

Когда включать: на проде, при нагрузке > 100 RPS.

Вопрос 13: Есть ли защита при падении Auth?
Ответ:
Сейчас нет. Gateway будет пытаться отправлять запросы, пока не получит timeout.

В планах:

Circuit Breaker — если Auth не отвечает 3 раза, Gateway перестаёт слать запросы на 30 секунд.

Health Checks — Kubernetes будет проверять /health и перезапускать упавший под.

Вопрос 14: Где лежат миграции?
Ответ:
В папках services/auth/migrations, services/game/migrations и т.д.

Как применять:
Сейчас — руками через goose.
План: автоматически при старте контейнера (через entrypoint.sh).

Вопрос 15 (Финальный): Стрелка NATS → WebSocket?
Ответ:
Да, но пунктирная (асинхронная).

Итоговая цепочка:
NATS → Leaderboard → WebSocket → Клиент.

Важно: Это только для Leaderboard.
Auth/Game/Billing не используют WebSocket для ответов клиенту.
