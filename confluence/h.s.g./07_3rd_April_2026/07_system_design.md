Тема 1: Введение в System Design & Требования (Requirements)

Что важнее: трейдоффы или цифры?
Функциональные требования (business API, действия системы).
Нефункциональные требования (метрики): Reliability, Availability (uptime %), Scalability, Latency (задержка), Durability (сохранность данных).
Процентили (95, 99).

Тема 3: Сбор требований и расчет нагрузки

Определение User (B2B/B2C) и DAU.
Расчет RPS (Request Per Second): как считать от 100 млн пользователей.
Расчет объема данных (сообщения по 200 байт, хранить 5 лет → 450 ТБ).
Правило 80/20 (кэширование 20% данных для 80% запросов).
Расчет кэша (50 ГБ -> 1 инстанс Redis).

Тема 4: Базовая архитектура и Компоненты (Квадратики)

Схема: Client -> LB (Load Balancer) -> Gateway -> Service -> DB.
Балансировщики: L4 (сетевые угрозы, DDoS) vs L7 (бизнес логика, JWT, агрегация).
WebSockets: secure, двунаправленное соединение, почему это не HTTP.

Тема 5: Авторизация и JWT (JSON Web Token)

Проверка токена на Gateway (+10 мс).
Проблема инвалидации токена (Blacklist в Redis).
Проблема 5000 RPS на авторизацию.

Тема 6: WebSocket Connection Management (Самое сложное)

Sticky Sessions (липкие сессии) на ALB.
Что если пользователь отвалился? Перебалансировка.
Как сервис узнает, каких клиентов он обслуживает? (ID клиента).
Сценарий: сервис упал, потом поднялся. Как вернуть клиентов?

Тема 7: Асинхронная коммуникация (Redis Pub/Sub)

Событие -> Persistent Storage -> Redis PubSub.
Consumer (WS-сервис) получает событие, проверяет "мой ли это клиент?", отправляет в канал.
Разница между: открыть коннект (стабильно) vs отправить сообщение (публикация).

Тема 8: Базы данных (Database) для чата

SQL (Postgres) vs NoSQL (MongoDB).
Почему для чата может подойти MongoDB: удобное шардирование, репликация, нет жесткой связанности.
Хранение: Пользователи -> Чаты -> Сообщения (коллекции).
Прокси слой (Citrus от Microsoft) — нужен ли?

Тема 9: Защита от перегрузок и Recovery

Что если все 10к сокетов упали и поднялись одновременно? (Thundering herd problem).
Rate limiter.
Single flight (чтобы не дублировать запросы в БД).
Как не задудосить чат-сервис при массовом переподключении.
