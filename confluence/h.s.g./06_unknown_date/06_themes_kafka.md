Тема С2: Consistent Hashing (Консистентное хэширование)
Вводная: в чём проблема обычного хэширования?
Из твоего конспекта (ты упоминал шардирование, но не углублялся):

«Нужно заниматься шардированием — по какому ключу разделять данные?»

Проблема классического подхода hash(key) % N:

Количество нод (N)	Куда попадает hash("user_123") % N
3 ноды	12345 % 3 = 0 → нода 0
4 ноды (добавили одну)	12345 % 4 = 1 → нода 1
В чём катастрофа: При добавлении или удалении всего одной ноды — почти все данные (≈ (N-1)/N, то есть ~75-90%) перекладываются на другие ноды.

Для БД на 1 ТБ это значит: переложить 750 ГБ данных. Это часы или дни простоя.

Фраза для интервью:

«Классический hash(key) % N не годится для распределённых систем, потому что при изменении N почти все данные перекладываются. Нужен механизм, который минимизирует перемещения — это Consistent Hashing.»

1. Как работает Consistent Hashing
Главная идея (запомни наизусть):

Вместо хэширования ключа в «номер ноды» — мы хэшируем ключ и ноды в общее кольцо (hash ring). Кольцо — это числовая окружность от 0 до 2³²-1 (или до 2⁶⁴-1).

Схема кольца (пример с 3 нодами):

text
                    (hash("node_1") = 1000)
                           │
                           ▼
    ┌─────────────────────────────────────────────────────────────┐
    │                                                             │
    │   2³²-1 ● ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ● 0    │
    │         ╲                                               │    │
    │          ╲                                              │    │
    │           ╲                                             │    │
    │            ● (hash("node_2") = 5000)                    │    │
    │           /                                             │    │
    │          /                                              │    │
    │         /                                               │    │
    │    ● ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ●    │
    │   (hash("node_3") = 4000000000)                         │    │
    └─────────────────────────────────────────────────────────────┘
Как ищем, на какой ноде лежит ключ:

text
1. key = "user_123"
2. hash(key) = 2500
3. Идём по кольцу ПО ЧАСОВОЙ СТРЕЛКЕ от hash(key)
4. Находим ПЕРВУЮ ноду, у которой hash(node) >= hash(key)
5. В примере: hash("node_2") = 5000 → это наша нода
Что даёт кольцо:

Сценарий	Что происходит
Добавили ноду	Перекладывается только часть данных с соседних нод (не все)
Удалили ноду	Её данные перекладываются на соседнюю ноду
Фраза для интервью:

*«В Consistent Hashing и ключи, и ноды хэшируются в одно кольцо. Ключ попадает на первую ноду по часовой стрелке. При добавлении/удалении ноды перекладывается только ≈1/N часть данных, а не почти всё.»*

2. Проблема неравномерного распределения
Из твоего конспекта (про виртуальные ноды):

«Виртуальные ноды (virtual nodes) для баланса.»

Проблема: Если нод всего 3-5, они могут распределиться по кольцу неравномерно. Одна нода получает 50% данных, другая — 5%.

Решение: Виртуальные ноды (Virtual Nodes / VNodes)

Что это	Как работает
Одна физическая нода	Представлена 100-200 виртуальными нодами на кольце
Хэши	Каждая виртуальная нода получает свой хэш (node_id + replica_number)
Распределение	Данные равномернее распределяются по физическим нодам
Схема виртуальных нод:

text
Физическая нода 1 (Node A):
    ├── виртуальная нода A_1 (hash = 123)
    ├── виртуальная нода A_2 (hash = 45678)
    ├── виртуальная нода A_3 (hash = 1234567)
    └── ... (всего 200 штук)

Физическая нода 2 (Node B):
    ├── виртуальная нода B_1 (hash = 789)
    ├── виртуальная нода B_2 (hash = 34567)
    └── ...
Фраза для интервью:

*«Для балансировки нагрузки используют виртуальные ноды: каждая физическая нода представлена 100-200 точками на кольце. Это даёт равномерное распределение данных даже при небольшом количестве физических нод.»*

3. Добавление и удаление нод (что перекладывается)
Исходное состояние (3 ноды):

text
Кольцо: [Node_A] --- [Node_B] --- [Node_C] --- (обратно к Node_A)

Ключи распределены между Node_A, Node_B, Node_C
Добавляем Node_D:

text
До добавления:
    Ключи между Node_B и Node_C → принадлежали Node_C

После добавления Node_D (между Node_B и Node_C):
    Ключи между Node_B и Node_D → теперь принадлежат Node_D
    Ключи между Node_D и Node_C → остались у Node_C

Переместилось: только ключи из сегмента [Node_B, Node_D]
≈ 1/N часть всех данных (при равномерном распределении)
Фраза для интервью:

*«При добавлении ноды перекладываются только данные из сегмента между предыдущей нодой и новой. Это ~1/N часть всех данных, а не (N-1)/N, как в обычном хэшировании.»*

4. Применение в реальных системах
Система	Где используется Consistent Hashing
Cassandra	Распределение данных по нодам кластера
DynamoDB (Amazon)	Шардирование ключей
Redis Cluster	Распределение ключей по мастер-нодам
Akamai CDN	Распределение запросов по кэш-серверам
Kafka	Распределение партиций по брокерам (частично)
Применительно к твоему проекту (GIFTS.ru / чат):

Твой компонент	Можно ли применить Consistent Hashing
MongoDB шардирование	MongoDB использует range-based sharding (по умолчанию) или hash-based (можно настроить). Hash-based близок к consistent hashing
WebSocket сервисы	Sticky sessions — можно через consistent hashing по user_id (чтобы не держать session table в Redis)
Кэш (Redis)	Redis Cluster использует consistent hashing для распределения ключей
Фраза для интервью:

«Consistent Hashing используется в Cassandra, DynamoDB, Redis Cluster. В MongoDB мы используем hash-based шардирование — это похожий принцип. Для WebSocket sticky sessions можно реализовать consistent hashing на уровне балансировщика, чтобы не хранить session mapping в Redis.»

5. Важный нюанс: Consistent Hashing ≠ Sharding
Многие путают эти понятия. Запомни разницу:

Понятие	Что это
Sharding	Разбиение данных на части (шарды), которые хранятся на разных серверах
Consistent Hashing	Алгоритм как именно решать, какой ключ на каком шарде лежит
Фраза для интервью:

«Sharding — это стратегия горизонтального масштабирования. Consistent Hashing — это один из алгоритмов для реализации шардирования с минимальным перемещением данных при изменении числа шардов.»

6. Плюсы и минусы Consistent Hashing
Плюсы	Минусы
Минимальное перемещение данных при добавлении/удалении нод	Сложность реализации (виртуальные ноды, поддержка кольца)
Равномерное распределение (с виртуальными нодами)	Не учитывает разную мощность нод (можно добавить веса)
Хорошо работает для кэшей и БД	Не подходит для range-запросов (только point lookup)
Масштабируется горизонтально	—
7. Сравнение методов распределения данных
Метод	При добавлении ноды	Сложность	Примеры
hash(key) % N	Перекладывается почти всё (75-90%)	Простая	Не используется в распределённых БД
Range-based	Зависит от диапазона (может быть много)	Средняя	MongoDB (default), HBase

Твои ключевые фразы (запомни для интервью):

Тема С5: Rate Limiting — алгоритмы (детально)
Вводная: зачем нужен rate limiter
Из твоего конспекта (ты упоминал, но не углублялся):

*«Rate limiter на Nginx + Redis (30 в минуту для генераций + защиты от спама).»*

Что такое rate limiting:

Ограничение количества запросов от одного клиента за единицу времени.

Защита от: DDoS, брутфорса, спама, перегрузки бэкенда.

Где живёт rate limiter:

L7 (прикладной уровень): API Gateway, Nginx, сам сервис (Redis + Lua)

L4 (транспортный уровень): iptables, CloudFlare, AWS Shield (для DDoS)

Фраза для интервью:

«Rate limiting защищает систему от перегрузки, спама и злоупотреблений. L7 лимитер работает на уровне HTTP (по user_id, IP), L4 — на уровне сети (по IP, портам).»

1. Алгоритм: Fixed Window (Фиксированное окно)
Как работает:

Время разбито на окна (например, 1 минута).

В каждом окне счётчик запросов обнуляется.

Схема:

text
Время:   0:00          0:01          0:02          0:03
         │             │             │             │
Окно 1   [##### 10/10] │
Окно 2                [##### 10/10] │
Окно 3                             [##### 10/10] │
Проблема (границы окон):

text
Запросы:
   0:00:59 → окно 1 (9/10)
   0:01:00 → окно 2 (1/10)
   
Итого за 2 секунды: 10 запросов (прошли оба, хотя лимит 10 в минуту)
Плюсы: Простота, мало памяти.
Минусы: Провалы на границах окон (burst в 2x лимита).

Фраза для интервью:

«Fixed window — самый простой алгоритм, но у него есть недостаток: на границе окон можно сделать 2 лимита за короткое время. Например, лимит 10 в минуту — в конце минуты и начале следующей можно отправить 20 запросов.»

2. Алгоритм: Sliding Window (Скользящее окно)
Как работает:

Храним временные метки всех запросов (или агрегируем в счётчики).

Окно «скользит» непрерывно.

Схема (точный вариант, с хранением меток):

text
Текущее время: 0:01:30
Окно: от 0:00:30 до 0:01:30

Запросы в окне: 8 штук
Лимит: 10 → пропускаем
Схема (приближённый вариант, с логарифмической ошибкой — Redis реализация):

text
Redis хранит:
    window_start = текущее_окно (минута)
    counter = количество запросов в этом окне
    previous_counter = количество в предыдущем окне

Текущий счётчик = previous_counter * (1 - weight) + counter
Плюсы: Точно соблюдает лимит, нет провалов на границах.
Минусы: Требует больше памяти (если хранить все метки).

Фраза для интервью:

«Sliding window решает проблему границ окон. Точная версия хранит временные метки всех запросов — точна, но дорога. Приближённая версия (через два счётчика в Redis) даёт погрешность ~10% при малом количестве памяти.»

3. Алгоритм: Token Bucket (Ведро с токенами) — САМЫЙ ПОПУЛЯРНЫЙ
Как работает:

В ведре есть токены (максимум N штук).

Токены добавляются со скоростью R токенов в секунду.

Каждый запрос забирает 1 токен.

Если токенов нет — запрос отклоняется (429).

Схема:

text
     +─────────────────────────────────────────────────────────────────+
     │                      TOKEN BUCKET                                │
     │                                                                 │
     │   ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐                       │
     │   │  T  │ │  T  │ │  T  │ │  T  │ │  T  │  (токены)            │
     │   └─────┘ └─────┘ └─────┘ └─────┘ └─────┘                       │
     │       │       │       │       │       │                         │
     │       └───────┴───────┴───────┴───────┘                         │
     │                           │                                     │
     │                           ▼                                     │
     │                   ┌───────────────┐                            │
     │                   │   Запрос      │                            │
     │                   │   берёт токен │                            │
     │                   └───────────────┘                            │
     │                                                                 │
     │   ┌─────────────────────────────────────────────────────────┐   │
     │   │  Токены добавляются со скоростью R токенов/сек          │   │
     │   │  (например, 10 токенов в секунду)                       │   │
     │   └─────────────────────────────────────────────────────────┘   │
     │                                                                 │
     └─────────────────────────────────────────────────────────────────┘
Параметры:

Параметр	Что значит	Пример
bucket_size	Максимум токенов в ведре	100 (можно сделать 100 запросов подряд)
refill_rate	Токенов в секунду	10 (в среднем 10 RPS)
Плюсы: Сглаживает bursts (можно отдать 100 запросов сразу, потом ждать).
Минусы: Нужно хранить состояние (последнее обновление, количество токенов).

Реализация на Redis + Lua (атомарно):

lua
-- Ключ: rate_limit:{user_id}
-- Аргументы: max_tokens, refill_rate, now

local key = KEYS[1]
local max_tokens = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local bucket = redis.call('hmget', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1])
local last_refill = tonumber(bucket[2])

if tokens == nil then
    tokens = max_tokens
    last_refill = now
end

local elapsed = now - last_refill
local new_tokens = math.min(max_tokens, tokens + elapsed * refill_rate)

if new_tokens >= 1 then
    new_tokens = new_tokens - 1
    redis.call('hmset', key, 'tokens', new_tokens, 'last_refill', now)
    redis.call('expire', key, 60)
    return {1, new_tokens}  -- разрешить
else
    return {0, new_tokens}  -- отклонить
end
Фраза для интервью:

*«Token bucket — самый популярный алгоритм. Он позволяет небольшие bursts (например, 100 запросов сразу), но в среднем ограничивает до R токенов в секунду. Реализуется через Redis + Lua для атомарности. Используется в AWS API Gateway, Nginx (ngx_http_limit_req_module).»*

4. Алгоритм: Leaky Bucket (Дырявое ведро)
Как работает:

Запросы поступают в очередь (ведро).

Обработчик забирает запросы с фиксированной скоростью (как вода вытекает через дыру).

Если очередь переполнена — запросы отбрасываются.

Схема:

text
    ┌─────────────────────────────────────────────────────────────────┐
    │                      LEAKY BUCKET                               │
    │                                                                 │
    │   Запросы ──► ┌─────────────────────────────────────────────┐   │
    │               │                    ОЧЕРЕДЬ                   │   │
    │               │  [req] [req] [req] [req] [req] [req] ...    │   │
    │               └─────────────────────────────────────────────┘   │
    │                           │                                     │
    │                           │ (фиксированная скорость)            │
    │                           ▼                                     │
    │                    ┌───────────────┐                           │
    │                    │  Обработчик   │                           │
    │                    └───────────────┘                           │
    │                                                                 │
    └─────────────────────────────────────────────────────────────────┘
Token Bucket vs Leaky Bucket:

Характеристика	Token Bucket	Leaky Bucket
Bursts	Разрешает (за счёт накопленных токенов)	Не разрешает (очередь заполняется)
Сглаживание	Меньше	Больше (фиксированный output)
Популярность	Очень высокая	Средняя
Пример	AWS API Gateway	QoS в сетях
Фраза для интервью:

«Leaky bucket отличается от token bucket тем, что не разрешает bursts — запросы выходят с фиксированной скоростью. Он лучше сглаживает нагрузку, но хуже подходит для API, где клиент ожидает быстрого ответа на burst запросов.»

7. Распределённый rate limiting (через Redis)
Проблема: Если у тебя 5 инстансов сервиса, каждый считает свои запросы. Злоумышленник может стучать в разные инстансы и набрать 5× лимит.

Решение: Redis как центральное хранилище счётчиков.

Схема:

text
[User] → [LB] → [Service #1] ──┐
              → [Service #2] ──┼──→ [Redis] (общий счётчик)
              → [Service #3] ──┘
Атомарность: Redis + Lua скрипт (как в примере выше) или INCR + EXPIRE.

Проблемы распределённого лимита:

Проблема	Решение
Race condition	Lua-скрипты (атомарно)
Redis недоступен	Fallback — локальный rate limiter или отказ
Латентность	Асинхронная проверка или локальный кэш счётчиков
Фраза для интервью:

*«В распределённой системе rate limiter должен быть централизованным, иначе клиент может обойти лимит, стуча в разные инстансы. Redis с Lua-скриптами даёт атомарное обновление счётчика. Минус — задержка на сетевой вызов (~0.5-2 мс), но это обычно приемлемо.»*

Тема С6: Kafka глубоко — внутренности, которые убивают новичков
Вводная: Kafka проста снаружи, сложна внутри
Из твоего конспекта:

Снаружи (что видит разработчик):

go
producer.Send(&sarama.ProducerMessage{

consumer.ConsumeClaim(session, claim) {

}
Внутри (о чём молчат туториалы):

Партиции, сегменты, ISR, лидер/фолловеры

Consumer group rebalance (stop-the-world)

Compaction, retention, tombstone records

__consumer_offsets топик

Фраза для интервью:

«Kafka даёт простой API — publish в топик, subscribe с offset. Но под капотом: партиции, сегменты, ISR, ребаланс consumer groups, compaction. Это не «просто очередь». Это распределённый лог с гарантиями, и за эту мощность платишь сложностью.»

1. Партиции (Partitions) — основа параллелизма
Что такое партиция:

Физическая очередь внутри топика.

Сообщения внутри партиции строго упорядочены (по offset).

Между партициями — порядок не гарантирован.

Схема топика с партициями:

text
TOPIC: "orders"
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│  PARTITION 0:  [msg0] [msg1] [msg2] [msg3] [msg4] ...  offset: 0...N       │
│  PARTITION 1:  [msg0] [msg1] [msg2] [msg3] [msg4] ...                      │
│  PARTITION 2:  [msg0] [msg1] [msg2] [msg3] [msg4] ...                      │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
Как сообщение попадает в партицию:

Стратегия	Формула	Когда использовать
По ключу	hash(key) % num_partitions	Нужен порядок по ключу (order_id)
Round-robin	По кругу	Порядок не важен
Sticky partitioner	Балансировка + батчинг	Высокая производительность
Важно для интервью:

*«Количество партиций = максимальный уровень параллелизма. Если у вас 10 партиций, вы можете запустить до 10 консьюмеров в группе. Больше партиций — больше параллелизма, но и больше накладных расходов (файловые дескрипторы, лидеры).»*

Сколько партиций нужно (правило большого пальца):

Фактор	Рекомендация
Пропускная способность	1 партиция ≈ 10-20 МБ/сек записи
Количество консьюмеров	Партиций ≥ количество консьюмеров
Количество брокеров	Распределить партиции равномерно
Максимум	Не более 4000 партиций на брокер
2. Сегменты (Segments) — как Kafka хранит данные на диске
Что такое сегмент:

Партиция физически разбита на сегменты — файлы на диске.

Каждый сегмент — это два файла: .log (данные) и .index (индекс для быстрого поиска по offset).

Схема хранения партиции:

text
PARTITION 0 (на диске брокера):
/var/kafka/data/orders-0/
    ├── 00000000000000000000.log   (сегмент 0: offsets 0-9999)
    ├── 00000000000000000000.index
    ├── 00000000000000100000.log   (сегмент 1: offsets 10000-19999)
    ├── 00000000000000100000.index
    ├── 00000000000000200000.log   (сегмент 2: offsets 20000-29999)
    └── 00000000000000200000.index
Параметры сегментов:

Параметр	Значение по умолчанию	Что значит
segment.bytes	1 ГБ	Размер сегмента (логирует ротацию)
segment.ms	7 дней	Время жизни сегмента до ротации
Как это работает (важно для интервью):

Kafka пишет сообщения в активный сегмент.

Когда сегмент достиг segment.bytes или истёк segment.ms — он закрывается.

Создаётся новый активный сегмент.

При удалении данных (по retention) удаляются целые сегменты, а не отдельные сообщения.

Фраза для интервью:

«Партиция физически состоит из сегментов — файлов на диске по 1 ГБ. Запись идёт в активный сегмент. При удалении данных по retention Kafka удаляет целые сегменты, что делает удаление очень эффективным (O(1), а не O(N)).»

3. ISR (In-Sync Replicas) — как Kafka гарантирует надежность
Из твоего конспекта:

«ISR (In-Sync Replicas) — кто считается синхронизированным.»

Что такое ISR:

Множество реплик (фолловеров), которые успели синхронизироваться с лидером.

Только реплики из ISR могут стать новым лидером при падении текущего.

Схема лидер + фолловеры + ISR:

text
┌─────────────────────────────────────────────────────────────────────────────┐
│  PARTITION 0                                                                │
│                                                                             │
│    LEADER (Broker 1) ──(запись)──► [сообщение]                              │
│         │                                                                   │
│         │ (репликация)                                                      │
│         ├──────────────────────────────────────────┐                        │
│         │                                          │                        │
│         ▼                                          ▼                        │
│    FOLLOWER (Broker 2) ── ISR? ✅ (успел)      FOLLOWER (Broker 3) ── ISR? ❌│
│    (данные актуальные)                          (отстаёт)                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
Параметры ISR:

Параметр	Значение по умолчанию	Что значит
replication.factor	3	Сколько всего реплик
min.insync.replicas	2	Минимум реплик в ISR для подтверждения записи
unclean.leader.election.enable	false	Можно ли выбрать лидера не из ISR
Почему ISR важен:

Сценарий	Что происходит
Лидер упал, есть ISR-фолловер	Новый лидер из ISR → 0 потерь
Лидер упал, ISR пуст	Новый лидер из не-ISR (unclean election) → потеря данных
min.insync.replicas=2, запись	Должны подтвердить 2 реплики (лидер + 1 фолловер)
Фраза для интервью:

«ISR — это фолловеры, которые не отстают от лидера. При acks=all и min.insync.replicas=2 запись считается успешной только после подтверждения от лидера и минимум одного ISR-фолловера. Если ISR пуст, Kafka может либо выбрать лидера не из ISR (потеря данных), либо ждать (потеря доступности).»

4. Compaction (уплотнение) — хранение только последнего состояния
Из твоего конспекта:

«Compaction — как оставить только последнее значение по ключу.»

Что такое compaction:

Механизм, который оставляет только последнее сообщение для каждого ключа.

Остальные удаляются (компактируются).

Включение: cleanup.policy=compact.

Схема compaction:

text
ДО COMPACTION (все сообщения по ключу user_123):
    offset 0: {key: user_123, balance: 100}
    offset 1: {key: user_123, balance: 150}
    offset 2: {key: user_123, balance: 200}
    offset 3: {key: user_456, balance: 500}
    offset 4: {key: user_123, balance: 250}

ПОСЛЕ COMPACTION:
    offset 0: {key: user_456, balance: 500}   (последнее по user_456)
    offset 1: {key: user_123, balance: 250}   (последнее по user_123)
Когда использовать compaction:

Use case	Почему compaction
Хранение текущего состояния	Баланс пользователя, статус заказа
CDC (Change Data Capture)	Последнее состояние записи в БД
Таблица ключ-значение	Kafka как источник правды
Важный нюанс — Tombstone records:

java
// Чтобы удалить ключ из compacted топика:
producer.send(new ProducerRecord<>("topic", key, null));
Фраза для интервью:

«Compaction оставляет только последнее сообщение для каждого ключа. Это удобно для хранения текущего состояния (баланс, статус). Чтобы удалить ключ, нужно отправить сообщение с value=null — это tombstone.»

5. Consumer Group Rebalance — как партиции распределяются
Что такое ребаланс:

Процесс перераспределения партиций между консьюмерами в группе.

Вызывается при: добавлении/удалении консьюмера, добавлении/удалении партиции.

Схема ребаланса:

text
ДО РЕБАЛАНСА (3 партиции, 2 консьюмера):
    Consumer 1: Partition 0, Partition 1
    Consumer 2: Partition 2

ДОБАВИЛИ Consumer 3:
    Consumer 1: Partition 0
    Consumer 2: Partition 1
    Consumer 3: Partition 2

(во время ребаланса — stop-the-world, никто не читает)
Алгоритмы ребаланса:

Стратегия	Как работает	Плюсы	Минусы
Range (по умолчанию)	Партиции разбиваются на диапазоны	Просто	Может быть неравномерно
RoundRobin	По кругу	Равномерно	Больше ребалансов
Sticky (Cooperative)	Минимальные перемещения	Меньше стоп-мира	Сложнее
Cooperative Sticky	Постепенный ребаланс	Почти без стоп-мира	Требует новых версий
Проблемы ребаланса:

Проблема	Что происходит	Решение
Stop-the-world	Во время ребаланса консьюмеры не читают	Cooperative rebalance (инкрементальный)
Rebalance storm	Частые ребалансы (консьюмер падает, переподключается)	Увеличить session.timeout.ms
Лишняя нагрузка	При ребалансе перечитываются партиции	Хранить состояние в Redis, а не в памяти
Фраза для интервью:

«Consumer group rebalance — это stop-the-world событие, когда партиции перераспределяются между консьюмерами. В старых версиях это приводило к паузам в обработке. Современные стратегии (Cooperative Sticky) делают ребаланс постепенным, без полной остановки.»

6. __consumer_offsets — топик для хранения offset'ов
Что это:

Внутренний топик Kafka, где хранятся коммиты offset всех consumer групп.

По умолчанию: 50 партиций, репликация 3.

Схема хранения offset'ов:

text
__consumer_offsets (внутренний топик):
    Partition 0: {group=g1, topic=orders, partition=0} → offset=12345
    Partition 1: {group=g1, topic=orders, partition=1} → offset=12346
    Partition 2: {group=g2, topic=users, partition=0} → offset=789
    ...
Что нужно знать (для интервью):

Offset'ы хранятся в compacted топике (только последний коммит по каждому ключу).

Если __consumer_offsets повреждён — все consumer группы теряют позицию.

При миграции кластера нужно переносить этот топик вручную.

Фраза для интервью:

«Kafka хранит коммиты offset в специальном внутреннем топике __consumer_offsets. Это compacted топик, поэтому для каждой группы и партиции хранится только последний коммит. При рестарте консьюмер продолжает чтение с последнего закоммиченного offset.»

7. Idempotent Producer (Exactly-Once Semantics)
Что это:

Гарантия, что сообщение не будет продублировано при retry.

Включение: enable.idempotence=true.

Как работает:

text
ПРОДЮСЕР:
    producer_id = уникальный ID (при старте)
    sequence_number = 0, 1, 2... (для каждой партиции)

БРОКЕР:
    Хранит (producer_id, sequence_number) последнего успешного сообщения
    Если приходит сообщение с тем же sequence_number → игнорирует (дубль)
Параметры для exactly-once:

Параметр	Значение	Зачем
enable.idempotence=true	Включить идемпотентность	Не дублирует сообщения при retry
acks=all	Подтверждение от всех реплик	Не теряем сообщения
max.in.flight.requests.per.session=1	1 запрос в полёте	Порядок не нарушается
Фраза для интервью:

«Idempotent producer использует sequence number на каждое сообщение. Брокер запоминает последний sequence number для каждого producer_id и отбрасывает дубликаты. Это даёт exactly-once в пределах одной партиции. Для глобального exactly-once нужны транзакции (производитель + несколько топиков).»

8. Kafka для твоего проекта (Roolz)
Из твоего конспекта:

*«Настроил асинхронную обработку событий поставок через Kafka (~1М+ событий/час), обеспечив гарантию доставки и возможность реплея.»*

Компонент	Настройка	Зачем

Итог по ТЕМЕ С6 (шпаргалка для конспекта)

Твои ключевые фразы (запомни для интервью):

«Партиции — основа параллелизма. Запись по ключу гарантирует порядок внутри партиции.»

«Сегменты — файлы на диске по 1 ГБ. Retention удаляет целые сегменты, а не отдельные сообщения.»

«ISR — фолловеры, которые не отстают от лидера. При min.insync.replicas=2 запись считается успешной только после подтверждения от лидера и одного фолловера.»

«Compaction оставляет только последнее сообщение по ключу. Tombstone (value=null) удаляет ключ.»

«Consumer group rebalance — перераспределение партиций. Cooperative rebalance почти не вызывает пауз.»

Тема С7: REST vs GraphQL vs gRPC — API дизайн
Вводная: как клиент общается с сервером
Из твоего конспекта (нет прямого упоминания, но важно для твоего проекта):

«Go (Gin, gRPC)» — в твоём стеке есть оба.

Три основных подхода:

Подход	Протокол	Формат данных	Типизация
REST	HTTP/1.1, HTTP/2	JSON, XML, plain	Слабая (OpenAPI)
GraphQL	HTTP/1.1, HTTP/2	JSON	Сильная (Schema)
gRPC	HTTP/2	Protobuf (бинарный)	Сильная (.proto)
Фраза для интервью:

«REST, GraphQL и gRPC — это три основных подхода к построению API. REST — классика для публичных API, GraphQL — для сложных клиентов с разными потребностями в данных, gRPC — для внутренних сервисов с высокими требованиями к производительности.»

1. REST (Representational State Transfer) — классика
Основные принципы:

Принцип	Что значит	Пример
Ресурсы	Всё — это ресурс (существительное)	/users, /orders/123
HTTP методы	GET, POST, PUT, PATCH, DELETE	GET /users/123
Stateless	Каждый запрос содержит всю нужную информацию	JWT в заголовке
Кэшируемость	HTTP-кэширование	Cache-Control, ETag
HATEOAS	Гиперссылки в ответе	"links": {"self": "...", "next": "..."}
Пример REST API:

http
GET /users/123
GET /users/123/orders
POST /orders
GET /orders/456

POST /users/123/orders/favorites
DELETE /favorites/789
Плюсы REST:

Плюс	Почему хорошо
Простота	HTTP — понятен всем
Кэширование	На уровне CDN, браузера, nginx
Инструментарий	Postman, Swagger, curl — всё работает
Idempotency	GET, PUT, DELETE — идемпотентны
Минусы REST:

Минус	Проблема
Over-fetching	При GET /users получаешь все поля, даже если нужно только имя
Under-fetching	Нужно делать несколько запросов: /users/123 + /users/123/orders
Версионирование	/v1/users, /v2/users — костыль
Слабая типизация	JSON — нет схемы на уровне протокола
Фраза для интервью:

«REST хорош для публичных API, где важна простота, кэшируемость и идемпотентность. Но у него есть проблемы: over-fetching (получаешь лишние данные) и under-fetching (нужно много запросов).»

2. GraphQL — клиент сам решает, какие поля нужны
Основная идея:

Клиент отправляет запрос (query) с указанием какие поля нужны.

Сервер возвращает ровно эти поля (ни больше, ни меньше).

Пример GraphQL запроса:

graphql
query GetUserWithOrders($userId: ID!) {
  user(id: $userId) {
    id
    name
    email
    orders(limit: 5) {
      id
      total
      status
      items {
        name
        price
      }
    }
  }
}
Ответ (ровно то, что запросили):

json
{
  "data": {
    "user": {
      "id": "123",
      "name": "Denis",
      "email": "denis@example.com",
      "orders": [
        { "id": "456", "total": 100, "status": "delivered", "items": [...] }
      ]
    }
  }
}
Ключевые концепции:

Концепция	Что значит
Query	Чтение данных (аналог GET)
Mutation	Изменение данных (аналог POST/PUT/DELETE)
Subscription	Real-time (WebSocket)
Schema	Типизированное описание API
Resolver	Функция, которая достаёт данные для поля
Плюсы GraphQL:

Плюс	Почему хорошо
No over-fetching	Получаешь только нужные поля
No under-fetching	Один запрос — все связанные данные
Сильная типизация	Schema — контракт между клиентом и сервером
Introspection	Клиент может сам узнать, какие поля доступны
Versioning	Не нужно — добавляешь поля, старые клиенты их игнорируют
Минусы GraphQL:

Минус	Проблема
Сложность	Нужно проектировать schema и resolvers
N+1 проблема	Resolver для списка вызывает resolver для каждого элемента
Кэширование	Сложнее, чем REST (нет URL как ключа)
Атаки	Глубокие вложенные запросы могут убить сервер (нужен complexity analysis)
Решение N+1 в GraphQL (DataLoader):

text
Без DataLoader:
    Query: users(limit=100)
        → user resolver: 1 запрос на 100 пользователей
        → orders resolver: 100 запросов (по одному на каждого) → N+1

С DataLoader:
    Query: users(limit=100)
        → user resolver: 1 запрос
        → orders resolver: собирает все user_id, делает 1 запрос
        → всего 2 запроса вместо 101
Фраза для интервью:

*«GraphQL даёт клиенту контроль над данными — никакого over-fetching. Но он сложнее REST: нужно думать о N+1 проблеме (решается DataLoader) и защите от глубоких запросов (complexity analysis). Идеален для сложных клиентов (мобилки, дашборды).»*

3. gRPC (gRPC Remote Procedure Calls) — бинарный протокол от Google
Основная идея:

Вызов удалённых процедур как локальных.

Protobuf (Protocol Buffers) для сериализации.

HTTP/2 как транспорт.

Пример .proto файла:

protobuf
syntax = "proto3";

service UserService {
    rpc GetUser (GetUserRequest) returns (User);
    rpc ListUsers (ListUsersRequest) returns (stream User);  // server streaming
    rpc CreateUser (stream CreateUserRequest) returns (User); // client streaming
}

message GetUserRequest {
    string user_id = 1;
}

message User {
    string id = 1;
    string name = 2;
    string email = 3;
}
Типы gRPC вызовов:

Тип	Что значит
Unary	Один запрос → один ответ (как REST)
Server streaming	Один запрос → поток ответов
Client streaming	Поток запросов → один ответ
Bidirectional streaming	Поток запросов ↔ поток ответов
Плюсы gRPC:

Плюс	Почему хорошо
Производительность	Protobuf бинарный (меньше данных, быстрее парсинг)
Сильная типизация	.proto — строгий контракт
HTTP/2	Мультиплексирование, server push, стриминг
Code generation	Генерация клиента на Go, Java, Python, JS...
Deadlines / Timeouts	Встроенная поддержка
Минусы gRPC:

Минус	Проблема
Браузеры	Не поддерживают gRPC напрямую (нужен grpc-web)
Сложность	Нужен .proto, генерация кода, специальные инструменты
Человекочитаемость	Бинарный протокол — curl не поможет
Балансировка	Требует специальный load balancer (L7, понимающий gRPC)
Фраза для интервью:

«gRPC — высокопроизводительный RPC-фреймворк с бинарной сериализацией (Protobuf). Он отлично подходит для внутренних сервисов (backend-to-backend), где нужны скорость, стриминг и строгий контракт. Но для браузерных клиентов и публичных API он неудобен — там лучше REST или GraphQL.»

4. REST vs GraphQL vs gRPC — прямое сравнение
Характеристика	REST	GraphQL	gRPC
Протокол	HTTP/1.1, HTTP/2	HTTP/1.1, HTTP/2	HTTP/2
Формат данных	JSON, XML, plain	JSON	Protobuf (бинарный)
Типизация	Слабая (OpenAPI)	Сильная (Schema)	Сильная (.proto)
Over-fetching	Есть	Нет	Нет (методы под задачу)
Under-fetching	Есть	Нет	Нет
Кэширование	Отличное (HTTP)	Сложное	Нет (не предназначен)
Стриминг	Нет (Server-Sent Events)	Да (Subscriptions)	Да (native)
Браузерная поддержка	Отличная	Хорошая	Плохая (grpc-web)
Человекочитаемость	Отличная	Хорошая	Плохая (бинарный)
Производительность	Средняя	Средняя	Высокая
Code generation	Swagger/OpenAPI	GraphQL Codegen	Да (.proto → всё)
Сложность	Низкая	Средняя	Высокая
5. Когда что выбирать (главное для интервью)
Выбираем REST, если:

Публичное API (для внешних разработчиков)

Нужно кэширование на уровне CDN / браузера

Простота важнее производительности

Клиенты — браузеры, мобилки (без сложных требований)

Выбираем GraphQL, если:

Клиенты с разными потребностями (мобилка vs веб vs дашборд)

Сложные графы данных (много связанных сущностей)

Хочешь избежать over-fetching / under-fetching

Готов к сложности (DataLoader, complexity analysis)

Выбираем gRPC, если:

Backend-to-backend коммуникация (микросервисы)

Нужна максимальная производительность

Стриминг данных (большие объёмы)

Строгий контракт между сервисами

Есть возможность использовать HTTP/2

Примеры из реальных компаний:

Компания	Что используют	Почему
GitHub	REST	Публичное API, простота
GitHub (внутренние)	gRPC	Микросервисы, производительность
Netflix	GraphQL (Falcor)	Сложные клиенты, разные устройства
Uber	gRPC + REST	gRPC для бэкенда, REST для публичного API
Slack	REST + GraphQL (эксперименты)	REST для стабильности

7. Дополнительно: WebSocket vs HTTP/2 (для чата)
Из твоего конспекта (про WebSocket в чате):

«Настроил WebSockets для уведомлений о новых сообщениях.»

Сравнение WebSocket и HTTP/2:

Характеристика	WebSocket	HTTP/2 + SSE
Двунаправленность	Да	SSE — только от сервера к клиенту
Заголовки	Только при handshake	Каждое сообщение
Бинарные данные	Да	Да (через ArrayBuffer)
Кэширование	Нет	Нет
Балансировка	Sticky sessions	Можно без sticky
Простота	Средняя	Выше (SSE)
Когда WebSocket, а когда HTTP/2 + SSE:

Use case	Что выбрать
Чат (двусторонний обмен)	WebSocket
Real-time уведомления (только от сервера)	HTTP/2 + SSE (проще)
Стриминг больших данных	gRPC (или WebSocket)
Фраза для интервью:

*«Для чата я выбрал WebSocket, потому что нужна двунаправленная связь — клиент отправляет сообщения, сервер их доставляет другим клиентам. Для односторонних уведомлений (например, алерты) хватило бы Server-Sent Events (SSE) поверх HTTP/2, но они не двунаправленные.»*
