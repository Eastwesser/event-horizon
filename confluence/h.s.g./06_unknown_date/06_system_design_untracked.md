Тема С1: CAP Theorem и PACELC
Коротко: почему нельзя иметь всё (Consistency, Availability, Partition Tolerance) одновременно.

Что разберём:

CAP Theorem: C, A, P — что каждый означает

Почему при network partition (P) приходится выбирать между C и A

Kafka — AP (доступность и терпимость к разделению)

PostgreSQL — CP (консистентность и терпимость к разделению)

PACELC — уточнение CAP (если нет Partition → выбираем между C и A; если есть Partition → выбираем между C и A)

Твой конспект (если есть): пока нет, разберём с нуля.

Тема С2: Consistent Hashing
Коротко: как добавить новый шард в БД, не перекладывая все данные.

Что разберём:

Проблема: hash(key) % N — при изменении N всё перекладывается

Решение: кольцо (hash ring)

Виртуальные ноды (virtual nodes) для баланса

Добавление/удаление шарда — перемещается только K/N данных

Твой конспект (есть): ты упоминал шардирование, но не consistent hashing.

Тема С3: Индексы в БД (B-tree, LSM-tree)
Коротко: как БД находит данные за O(log N), а не O(N).

Что разберём:

B-tree (PostgreSQL, MySQL) — хорош для чтения, плох для записи (random I/O)

LSM-tree (Cassandra, RocksDB, LevelDB) — хорош для записи (sequential I/O), плох для чтения (merge)

Какой индекс для чата? (chat_id, timestamp) — составной

Твой конспект (есть): ты говорил про индексы, но не про B-tree vs LSM.

Тема С4: Паттерны кэширования
Коротко: как кэшировать данные, чтобы они не рассинхронизировались с БД.

Что разберём:

Cache-aside (lazy loading) — самый популярный

Write-through — пишем в кэш + БД синхронно

Write-behind (write-back) — сначала в кэш, потом асинхронно в БД

Read-through — кэш сам ходит в БД при промахе

Cache stampede problem — как много запросов одновременно бьют в БД (single flight — решение)

Твой конспект (есть): ты говорил про кэш в чате, но не про паттерны.

Sliding window — точный, но дорогой

Fixed window — простой, но резкие границы

Реализация на Redis + Lua (atomic)
