RPS (Requests Per Second) — это сколько запросов в среднем сервер обрабатывает за одну секунду.

Как обычно считают на практике
Шаг 1. Оцениваем суточные запросы

Важный нюанс из книги (чтоб не спалили)
RPS ≠ QPS (Queries Per Second) — если один запрос пользователя делает 3 SQL-запроса в БД, то QPS будет в 3 раза выше.

Никогда не считай по часам (час пик = 20% трафика за день — это другой расчёт, для кэшей и очередей).

Лайфхак для интервью/проектирования
Если задача звучит «миллион пользователей в день» — бери:

RPS средний ≈ 12–15 (при 100 запросах на юзера в день).

Пиковый RPS ≈ 50–100.

1. Про реплики БД (твой первый вопрос) — ты понял абсолютно верно
Ведущая (master) — только на запись. Ведомые (replicas) — только на чтение.

✅ Да. Веб-сервер отправляет запись → мастер.
✅ Чтение → любая реплика (чтобы мастер не захлебнулся).

🔸 Нюанс (который ты дальше сам нащупал):
Репликация не мгновенна (асинхронная). Если пользователь только что написал пост и тут же перезагрузил страницу — он может не увидеть свой пост, потому что читает из реплики, куда данные ещё не пришли.

Решение:

Для критичных чтений («мой только что созданный пост») — читать из мастера.

Для остальных — реплики.

2. Куда воткнуть кэш (твой любимый вопрос)
Ты правильно нарисовал:
Пользователь → LB → Web Server → Cache → DB

🔸 Кэш ставится ПЕРЕД БД (между сервисом и базой).

Два сценария:
При чтении:

Сервис сначала идёт в кэш (Redis/Memcached).

Если есть (cache hit) → отдаёт клиенту, БД не трогает.

Если нет (cache miss) → идёт в БД, забирает, кладёт в кэш на будущее.

При записи:
Есть две стратегии, и тут ты запутался — распутаю:

Стратегия	Что делаем	Плюсы	Минусы
Write-through	Сначала в БД (master), потом в кэш	Кэш всегда свежий	Запись медленнее
Cache-aside	Сначала в БД, кэш инвалидируем (удаляем старую запись)	Быстрая запись	При следующем чтении — cache miss
Твой случай (новостная лента) — обычно cache-aside, потому что посты пишут редко, а читают часто.

3. Липкие сеансы (sticky sessions) — ты правильно прочитал, это зло
Ты сказал: «проблема в том, что каждый запрос клиента надо отправлять на тот же сервер».

✅ Да. Но это антипаттерн для горизонтального масштабирования.

Почему плохо:

Сервер упал → сессия потеряна → пользователь вылетел.

Добавили сервер → перебалансировка → липкость ломается.

Правильно:
Хранить состояние вне серверов — в Redis или БД. Тогда любой сервер может обработать любой запрос.

4. Разделяемое хранилище (shared storage)
Ты спросил: «разделяемое хранилище — это типа MongoDB?»

🔸 Не совсем.
MongoDB — это база данных, которая сама по себе может быть shared storage для серверов.

А в контексте sticky sessions разделяемое хранилище — это Redis или база данных, где лежат сессии.

Пример:
Сервер А получил запрос → проверил сессию в Redis → обработал.
Сервер Б получил следующий запрос → тоже пошёл в тот же Redis → всё ок.

5. Очередь сообщений (Kafka vs RabbitMQ)
Ты спросил: «это Kafka или RabbitMQ?»

Оба, но под разные задачи:

RabbitMQ	Kafka
Задача	Задачи между сервисами (один раз обработал и забыл)	Поток событий, логи, аналитика
Сохранение	Удалил после обработки	Хранит долго (days/weeks)
Повторная обработка	Нет	Да (можно перечитать)
Скорость	Высокая	Очень высокая
В твоей схеме (новостная лента, уведомления) — обычно Kafka, потому что:

Пост пользователя → событие в Kafka → несколько сервисов читают (лента, уведомления, аналитика).

Запрос ленты → проверка кэша (1 QPS к Redis)

Cache miss → читаем из replica БД (1 QPS к PostgreSQL)

Если постов нет → читаем графовую БД (1 QPS к Neo4j)

Итоговый QPS к БД ≈ RPS × 2–3.
