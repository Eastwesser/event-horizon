Базы данных
PostgreSQL
MVCC (Multi-Version Concurrency Control) обеспечивает конкурентный доступ к данным. В PostgreSQL для этого используются системные столбцы xmin (создавшая транзакция) и xmax (удалившая или изменившая транзакция).При выполнении UPDATE запись не меняется на месте: система помечает старую версию как удалённую и создаёт новую строку. Старые версии строк остаются на диске, что приводит к «раздуванию» (bloat) таблиц. Чем чаще происходят обновления, тем сильнее проявляется этот эффект.
Команда VACUUM сканирует данные, находит строки, у которых xmax старше текущей транзакции, и помечает их как доступные для повторного использования. Важно понимать: VACUUM освобождает место только для новых записей внутри базы, но не возвращает его операционной системе.
В механизме MVCC используются 32-битные идентификаторы транзакций. Если база обрабатывает миллиарды транзакций, а xmin/xmax не сбрасываются (процесс Wraparound), PostgreSQL может выйти из строя.AutoVacuum можно настраивать. Также существует режим Read Only, когда база данных временно не принимает записи.
WAL (Write-Ahead Log) — журнал упреждающей записи. Необходимо следить за его размером. Сначала изменения вносятся в определённую область памяти, одновременно формируя запись в журнале. При коммите БД сбрасывает изменения из журнала на диск. Это необходимо для восстановления: если произойдёт сбой, система сможет воспроизвести действия из WAL-файла с момента последней контрольной точки.В репликации (slave в режиме read only) ведомый сервер считывает данные именно из WAL.
Кэш ОС (Cash DB)Ядро Linux агрессивно использует кэш файловой системы для данных БД.PostgreSQL сначала ищет нужную страницу в своём внутреннем кэше (shared_buffers). Если не находит, то обращается к ОС с запросом на чтение файла. Linux, в свою очередь, отдаёт данные либо из своего кэша (page cache), либо читает с диска.Кэш должен быть ограничен по размеру, так как бесконтрольный рост данных может привести к проблемам с управлением памятью. Для этого существуют специфические алгоритмы вытеснения.
TimeScaleDB
Проблема масштабирования времени. Представим датчики, отправляющие метрики каждую секунду. В обычной таблице PostgreSQL со временем накопится огромный объём данных, и B-Tree индекс перестанет помещаться в кэш. База начнёт работать медленно из-за постоянных чтений с диска и записи обновлённых страниц («задохнётся от собственных индексов»).
Решение: TimeScaleDBЭто расширение (аддон) для PostgreSQL, работающее с гипертаблицами. Для пользователя это обычная таблица, но внутри она состоит из чанков (chunks).В отличие от стандартного партиционирования, чанки создаются автоматически. Это решает проблему записи: новые INSERT летят в последний активный чанк, а старые остаются статичными и не мешают производительности.
TimeScaleDB умеет сжимать чанки, преобразуя данные из строкового формата в массивы (колоночный формат), что даёт сжатие в 10–20 раз.Для дашбордов можно создавать вьюхи для чтения данных в реальном времени.Удаление старых данных сводится к удалению целых таблиц-чанков, что позволяет вернуть место операционной системе.Существуют аналоги, например, VictoriaMetrics или InfluxDB.
ClickHouse
Если есть огромная таблица логов (например, 100 млрд записей) и нужно посчитать уникальных пользователей за интервал, PostgreSQL будет сканировать все эти 100 млрд строк.ClickHouse подходит для таких задач лучше благодаря своей колоночной архитектуре и сжатию данных.
Данные в ClickHouse хранятся принципиально иначе. Главная структура — семейство движков MergeTree. При создании таблицы обязательно указывается ключ сортировки (sorting key), по которому данные режутся на гранулы (granules).ClickHouse использует другой тип индекса (primary index или sparse index), который позволяет хранить индекс на миллиарды строк в оперативной памяти.
MergeTree
MergeTree — это фоновый процесс слияния данных. Так как в ClickHouse нет нормального UPDATE/DELETE, движки решают разные задачи: аналитика, интеграции, взаимодействие с Kafka или PostgreSQL (например, непрерывная выкачка данных).
Как выбрать БД правильно

Гигантская корзина (e-commerce): В PostgreSQL каждая запись — это изменение в журнале и много обращений к диску. Инстанс станет дорогим по операциям ввода-вывода. Лучше подойдёт Cassandra, где операции записи менее нагружены (вместо классических B-деревьев используются свои структуры). У Cassandra нет мастера и слейва — все узлы равны. Аналогом является более современный ScyllaDB (написан на C++).
Система рекомендаций: Задача «найти друзей моих друзей». В реляционной БД это будет многоэтажный JOIN, что неэффективно при миллионах связей. Для этого существуют графовые СУБД (например, Neo4j), где узел физически хранит ссылки на соседние узлы, обеспечивая минимальное время перехода.
Поиск по тексту: У PostgreSQL есть мощный полнотекстовый поиск. Но для большого маркетплейса с неточными запросами и сложной фильтрацией лучше использовать специализированные движки, такие как ElasticSearch, изначально спроектированный для шардирования больших объёмов данных.
Антипаттерны в архитектуре
•    Dual writes: Попытка писать данные одновременно в две разные системы из кода приложения. Это ненадежно из-за возможных сбоев сети между бэкендом и БД.
•    2PC (Two-Phase Commit): Протокол распределённых транзакций. В современных реалиях не работает или работает крайне медленно из-за блокировок.
Best Practices
•    Outbox-паттерн: Вместо прямой отправки бизнес-события, выполняется два INSERT: в основную таблицу и в таблицу outbox. Далее Kafka читает событие и отправляет его дальше.
o    Проблемы: Как понять, что задача обработана? Как защититься от дублей?
•    CDC (Change Data Capture): Используется для переноса огромных объёмов данных (например, из PostgreSQL в ClickHouse). Писать через Outbox накладно.
o    Debezium притворяется read-only репликой, читает из WAL PostgreSQL, превращает события в сообщения и помещает их в Kafka. Debezium запоминает свою позицию при сбоях.
•    CQRS (Command Query Responsibility Segregation): Разделение ответственности на чтение и запись. При этом могут использоваться разные базы данных для этих операций.
