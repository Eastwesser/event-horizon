📁 Архитектура БД, паттерны интеграции и Highload (Конспект)
1. PostgreSQL: Внутренности и проблемы
MVCC (Multi-Version Concurrency Control)
Механизм: Каждая строка имеет служебные колонки xmin (ID транзакции, которая создала версию) и xmax (ID транзакции, которая удалила или обновила версию).

Как работает UPDATE: Старая версия не меняется. Ей проставляется xmax, и создается новая строка. Это приводит к раздуванию (bloat) таблиц.

VACUUM: Сканирует таблицы, находит строки с xmax старше текущей транзакции и помечает их как свободное место внутри БД. ОС место не возвращается.

Wraparound: Из-за 32-битных идентификаторов транзакций при миллиардах операций может произойти переполнение. PostgreSQL аварийно остановится, если не настроить AutoVacuum или не перевести БД в READ ONLY.

WAL (Write-Ahead Log)
Суть: Сначала изменения пишутся в журнал (WAL), потом — в data files. Нужен для Point-in-Time Recovery и репликации.

Репликация: Slave (Read-Only) тянет данные именно из WAL мастер-сервера.

Кэширование
Уровень 1 (Shared Buffers): Внутренний кэш PostgreSQL.

Уровень 2 (Page Cache): Кэш операционной системы (Linux). Если данных нет в shared_buffers, Postgres идет в Page Cache ОС.

Правило: Нужно балансировать память (20-30% ОС под Page Cache, остальное — shared_buffers и процессы).

2. TimeScaleDB (Временные ряды / IoT)
Проблема: Обычный PostgreSQL задыхается, если B-Tree индекс растет быстрее, чем кэш. База начинает "дохнуть от размера индексов".

Решение:

Аддон к PostgreSQL. Пользователь работает с "гипертаблицей" (как с обычной).

Чанки (Chunks): Гипертаблица внутри состоит из "чанков" — это обычные таблицы Postgres, но создаются автоматически под капотом (в отличие от ручного партиционирования).

Сжатие: Данные старше N дней из строкового формата превращаются в колоночный массив (сжатие до 20 раз). Место возвращается ОС при удалении чанка (не VACUUM!).

Аналоги: VictoriaMetrics, InfluxDB.

3. ClickHouse (OLAP / Логи / Аналитика)
Проблема: "Мне нужно прочитать 100 млрд строк логов за вчера, чтобы посчитать уникальных пользователей". В PostgreSQL это займет час. Это отстой.

Архитектура ClickHouse:

Колоночное хранение. Ты читаешь только нужные колонки, а не целые строки.

Движок MergeTree:

Данные физически сортируются на диске по ORDER BY ключу.

Режутся на гранулы (обычно 8192 строки).

Вместо индексации каждой строки — разреженный (sparse) индекс. Индекс хранит одну запись на гранулу (похоже на BRIN индекс в Postgres).

Отсутствие UPDATE/DELETE: Только мутации (ALTER TABLE ... UPDATE), которые тяжелые и переписывают целые партиции.

Работа с Kafka: ClickHouse может быть полноценным консьюмером Kafka (парсит JSON на лету). Exactly-once не гарантирован — при падении данные перетрутся. Но для логов это OK (идемпотентность не нужна).

Легенда для собеса (твой опыт):

"Мы использовали ClickHouse в проекте для аналитики по событиям (3M+/час). Это OLAP с возможной потерей данных. Debezium стримил логи из PG в Kafka, а ClickHouse забирал. Для дашбордов 99.9% точности хватало. Exact write — в PostgreSQL."

4. Паттерны интеграции БД (Надежно vs Антипаттерны)
🚫 АНТИПАТТЕРНЫ (Не использовать в проде)
Паттерн	Почему плохо
Dual Writes	Пишем в БД, потом пытаемся отправить в Elasticsearch/Kafka. При сбое сети данные теряются. Чинить приходится костылями-сверками ("сверялками"), а это — признак плохой архитектуры.
2PC (Two-Phase Commit)	Протокол распределенных транзакций. Блокирует все ресурсы, пока самый медленный узел не скажет "готов". В современных микросервисах это самоубийство (медленно, ненадежно).
✅ РАБОЧИЕ ПАТТЕРНЫ
A. Outbox / Inbox (Де-факто стандарт)
Как работает: В одной SQL транзакции делаем INSERT в бизнес-таблицу и в таблицу outbox. Отдельный воркер читает outbox и отправляет в Kafka.

Плюсы: Атомарность. Нет распределенных блокировок.

Вопросы реализации:

Как не потерять? Воркер удаляет запись из outbox только после ack от Kafka.

Как бороться с дублями? Consumer должен быть идемпотентным (хранить idempotency_key).

Недостаток: Воркер постоянно дергает БД (Polling). На миллиардах записей — нагрузка.

B. CDC (Change Data Capture) — Круче чем Outbox
Как работает: Ставится слушатель (например, Debezium), который подписывается на WAL PostgreSQL (или бинарный лог MySQL).

Почему это золотой стандарт:

Нет Polling. События приходят моментально.
Атомарность. Если транзакция закоммичена — CDC гарантированно увидит изменение.
Replay. Если ClickHouse упал, CDC перечитывает WAL за последние дни.
Ваша легенда (Roolz):

"Чтобы разгрузить Postgres и не делать лишних запросов, мы использовали CDC через Debezium. Он читал WAL Postgres, и как только появлялась запись в Outbox, моментально отправлял ее в Kafka. Это решило проблему Dual-Writes."

5. Когда какая БД нужна (Выбор инструмента)
Сценарий	Решение	Почему
E-commerce (корзина, заказы)	Cassandra / ScyllaDB	В Cassandra нет мастера/слейва, все узлы равны, линейный рост. В отличие от Postgres, запись не такая "дорогая" (нет тяжелых B-Tree индексов). Scylla — аналог на C++ (быстрее).
Система рекомендаций (граф)	Neo4j (графовая БД)	В реляционной БД "друзья друзей" = многоэтажные JOIN'ы, которые тормозят. В графовой БД узел физически хранит ссылки на соседей (переход за O(1)).
Полнотекстовый поиск	Elasticsearch	У PG есть gin индекс, но для маркетплейса с опечатками ("кроссовки" → "красовки") и сложной фильтрацией нужен специализированный движок.
Highload Кэш	Dragonfly (а не Redis)	Многопоточная in-memory БД. Совместима с API Redis (drop-in replacement). На многоядерных машинах быстрее Redis в 20-25 раз. Минус: менее обкатана в проде (детские болезни).
