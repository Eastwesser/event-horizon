1. Про миграцию с монолита на микросервисы
Твоя заметка:

«Какой-то подход душитель существует, когда распиливаешь монолит. То есть когда мы говорим про миграцию старых данных, нам нужно говорить, что типа вот мы создавали новый сервис, да, вот... Маршрутизация трафика, куда базы шли, потом куда запись шла, это про secure.»

Что ментор хочет услышать:

Ты не можешь просто сказать «я переписал монолит на микросервисы». Это звучит как «я переписал Excel на Google Sheets».

Правильный ответ (легенда про миграцию):

«Мы мигрировали с монолита на микросервисы постепенно, без даунтайма.

1. Strangler Fig Pattern (паттерн «душитель»): новый сервис писался рядом со старым. Трафик сначала шёл в монолит.
2. Постепенное переключение: 5% трафика → на новый сервис, 95% → на монолит. Смотрели метрики (error rate, latency).
3. Двунаправленная синхронизация данных: пока шла миграция, старый и новый сервисы писали в обе БД (или через Kafka).
4. Полное отключение монолита: только когда 100% трафика стабильно шло на новый сервис в течение 2 недель.»

Фраза для интервью:

«Мы использовали Strangler Fig Pattern: новый сервис «душил» старый монолит. Трафик переключали постепенно (5% → 20% → 50% → 100%), смотрели на error rate и latency. Данные синхронизировали двунаправленно через Kafka, чтобы не потерять ни одного события при переключении.»

2. Про CI/CD и окружения (dev → stage → prod)
Твоя заметка:

«Зайти в окружение в тестовое, тестики, подтянуть пайплайн ветка, запуск на машине, потом в д ветку либо напрямую раскатывать... там типа dev-stage-prod ветки.»

Что ментор хочет услышать:

Ты знаешь, как устроен процесс доставки кода — это база для любого инженера.

Правильный ответ (CI/CD flow):

text
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                         CI/CD PIPELINE (GIFTS.ru)                                   │
└─────────────────────────────────────────────────────────────────────────────────────┘

1. DEV (разработка):
   - Разработчик пишет код в feature-ветке
   - Поднимает сервисы через docker-compose локально
   - Прогоняет unit-тесты

2. CODE REVIEW + MERGE:
   - Pull Request в develop
   - Автоматические проверки (линтеры, тесты)
   - Ревью от 2 коллег

3. STAGE (тестовое окружение):
   - Автоматический деплой после мержа в develop
   - Интеграционные тесты
   - Ручное тестирование (тестировщики)
   - Нагрузочное тестирование (если нужно)

4. PROD (боевое окружение):
   - Деплой из stage в main (release-ветка)
   - Canary deployment (5% → 20% → 50% → 100%)
   - Мониторинг метрик (latency, error rate, RPS)

5. ROLLBACK (если что-то пошло не так):
   - Откат на предыдущую версию (30 секунд)
   - Анализ инцидента через логи и трейсы
Фраза для интервью:

*«У нас был стандартный пайплайн: feature-ветка → code review → develop (авто-деплой на stage) → main (деплой на prod через canary). На проде сначала пускали 5% трафика, смотрели на метрики, потом увеличивали. Откат занимал меньше минуты.»*

3. Про профилирование и техдолг
Твоя заметка:

«Профилирование нужно для выявления проблем. Просто так, по своему желанию, профилированием люди не занимаются. Берётся задачи из бэклога, там идём профилировать.»
«То, что не несёт денег бизнесу, обосновать очень тяжело. Если бизнес не получит за 2 недели, пока ты пальцем не ткнёшь, что мы потеряем столько, они думают.»

Что ментор хочет услышать:

Ты понимаешь, что инженерные решения нужно обосновывать бизнесу деньгами, а не «это красиво».

Правильный ответ (про профилирование и техдолг):

«Профилирование мы проводили по запросу:

Когда latency выходила за SLA

После инцидентов (чтобы найти корень проблемы)

Перед планированием capacity (чтобы понять, где узкое место)

*Техдолг мы оценивали в деньгах: «Если мы не перепишем этот сервис сейчас, через 3 месяца нагрузка вырастет на 30%, и нам придётся докупить серверов на $2000/мес. Переписывание стоит 2 недели разработчика — $3000. Окупится за 2 месяца». Бизнес понимает только такие аргументы.»*

Фраза для интервью:

*«Техдолг мы обосновывали через TCO (total cost of ownership). Если переписывание стоило 2 недели, а экономия на серверах — $2000/мес, бизнес соглашался. Профилировали после инцидентов или когда latency выходила за SLA. Просто так — никто не профилирует, это не приносит ценности бизнесу.»*

4. Про уровни глубины в System Design
Твоя заметка:

«Главное, что у тебя идёт, да, необязательно там прописывать до каждого сервиса. То есть, условно говоря, если у тебя целый проект, квадратики раскидал по сервисам и всё. Базово это сильно помогает, фундамент такой верхнеуровневый строить.»

Что ментор хочет услышать:

На интервью по System Design не нужно рисовать до каждого сервиса. Достаточно верхнеуровневой схемы, чтобы показать, что ты понимаешь потоки данных.

Правильный подход (уровни глубины):

Уровень	Что рисуем	Когда
L1 (High-level)	Клиент → LB → Gateway → Service → DB	Первые 5 минут интервью
L2 (Components)	Добавляем кэш, брокеры, реплики БД	Когда спрашивают про масштабирование
L3 (Details)	Конкретные индексы, партиции, настройки	Только если интервьюер копает глубоко
Фраза для интервью:

«Я начинаю с высокоуровневой схемы (Client → LB → Gateway → Service → DB), чтобы показать основные потоки данных. Потом, если нужно, углубляюсь до конкретных компонентов: кэш, брокеры, шардирование. Не нужно рисовать каждый микросервис — это убивает время и запутывает.»

5. Про метрики (что смотрели)
Твоя заметка:

*«Какие метрики смотрели? Загрузка по таскам, по RPS, стандартные метрики процентили p95, p99. Бизнес-метрики также можно в зависимости от проекта.»*

Что ментор хочет услышать:

Ты знаешь разницу между техническими метриками (RPS, latency, error rate) и бизнес-метриками (конверсия, количество заказов, выручка).

Правильный ответ (метрики):

Тип метрик	Примеры	Кто смотрит
Технические	RPS, p95/p99 latency, error rate, CPU, memory	Инженеры
Бизнес-метрики	Конверсия (запрос → генерация), количество заказов/час, выручка	Продакты, бизнес
SLA / SLO	99.9% доступности, p95 < 100 мс	И те, и другие
Фраза для интервью:

*«Мы смотрели стандартные технические метрики: RPS, p95/p99 latency, error rate. Для бизнеса показывали конверсию (сколько запросов на генерацию превратилось в заказы) и количество заказов в час. Если latency росла, но конверсия не падала — бизнес не парился. Если конверсия падала — это был триггер для срочного фикса.»*
