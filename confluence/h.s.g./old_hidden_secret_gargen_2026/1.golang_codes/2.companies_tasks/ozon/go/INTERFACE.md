# Интерфейсы в Go

## Грейд
17-18

## Вопрос
Что такое интерфейс в Go? Как он устроен?

## Ответ

**Интерфейс** — это абстракция поведения других типов. Он определяет набор методов, которые должен реализовать тип, чтобы удовлетворять интерфейсу (duck-typing).

### Внутреннее устройство (рантайм)

```go
type iface struct {
    tab  *itab          // информация о типе и таблице методов
    data unsafe.Pointer // указатель на данные
}

type eface struct {
    _type *_type        // информация о типе
    data  unsafe.Pointer
}
```

- interface{} (пустой интерфейс) — eface (нет методов)

- Интерфейс с методами — iface (таблица методов)

## Дополнительные вопросы

### Что произойдёт в этом коде?
```go
type Foo struct{}
func (f *Foo) A() {}
func (f *Foo) B() {}
func (f *Foo) C() {}

type AB interface { A(); B() }
type BC interface { B(); C() }

func main() {
    var f AB = &Foo{}
    y := f.(BC)  // сработает ли type assertion?
    y.A()        // а этот вызов?
}
```

Ответ:

y := f.(BC) — сработает, потому что *Foo реализует и AB, и BC.
y.A() — вызовется, но тип y — BC, у которого нет метода A. 
Однако y хранит конкретный тип *Foo, 
поэтому вызов возможен (но небезопасно полагаться на это)

### Что такое "пустой интерфейс" (interface{})?
Интерфейс без методов. Любой тип удовлетворяет пустому интерфейсу.

```go
var anything interface{}
anything = 42
anything = "hello"
anything = struct{}{}
```

### Когда использовать пустой интерфейс?

- Функции типа fmt.Print (работают с любым типом)
- Хранилище разнотипных данных (с последующей проверкой типа)

### Отличия интерфейсов в Go от классических ООП-языков
```text
ООП (Java/C#)	                    Go
Явная реализация (implements)	    Неявная реализация (duck-typing)
Интерфейс — контракт	            Интерфейс — поведение
Наследование интерфейсов	    Встраивание (embedding)
```

## Что важно сказать на собеседовании

Интерфейс в Go — это два слова: тип + указатель на данные

### Nil-интерфейс ≠ интерфейс с nil-данными

```go
var p *int = nil
var i interface{} = p
fmt.Println(i == nil)  // false! (i имеет тип *int)
```

### Метод с pointer receiver — интерфейсу удовлетворяет только указатель

```go
type Stringer interface { String() string }
type MyInt int
func (m *MyInt) String() string { return fmt.Sprint(*m) }

var s Stringer = MyInt(5)   // ОШИБКА!
var s Stringer = &MyInt(5)  // OK
```

Пустой интерфейс полезен, но лучше использовать дженерики (Go 1.18+), если тип известен

Интерфейсы в Go (понятное объяснение)
Что такое интерфейс?
Интерфейс — это набор методов, которые описывают поведение.

Он НЕ содержит данных (как структура). Он говорит: «Тот, кто меня реализует, умеет делать вот эти действия».

Коротко и просто
Структура (struct)	Интерфейс (interface)
ДАННЫЕ (поля)	УМЕНИЯ (методы)
"Кто я"	"Что я умею"
var d Dog — в d лежит собака	var s Speaker — в s лежит ТОТ, кто умеет говорить
Как объявить интерфейс
go
type Speaker interface {
Speak() string
}
Любой тип, у которого есть метод Speak() string, автоматически удовлетворяет интерфейсу Speaker (duck typing — «если ходит как утка и крякает как утка, значит утка»).

Как реализовать интерфейс (на примере структуры)
go
type Dog struct{ Name string }
func (d Dog) Speak() string { return "Гав, я " + d.Name }

type Cat struct{ Name string }
func (c Cat) Speak() string { return "Мяу, я " + c.Name }
Обе структуры реализуют Speaker. Никакого implements писать не нужно.

Зачем нужен интерфейс?
Проблема без интерфейса
go
func GreetDog(d Dog)   { fmt.Println(d.Speak()) }
func GreetCat(c Cat)   { fmt.Println(c.Speak()) }
// для каждого нового животного — новая функция
Решение с интерфейсом
go
func Greet(s Speaker)  { fmt.Println(s.Speak()) }
// одна функция для всех, кто умеет Speak()
Интерфейс как тип переменной
go
var s Speaker           // переменная типа интерфейс
s = Dog{Name: "Шарик"}  // в неё можно положить Dog
s = Cat{Name: "Мурка"}  // а теперь Cat
s.Speak()               // вызывается метод того, кто внутри
Важно: переменная интерфейса НЕ имеет полей. Она хранит только указатель на данные и указатель на методы.

Главная сила интерфейса — слайс разных типов
go
animals := []Speaker{Dog{}, Cat{}, Human{}, Phone{}}

for _, a := range animals {
fmt.Println(a.Speak())
}
БЕЗ интерфейса такой код невозможен. В слайс можно положить только один конкретный тип.

Пустой интерфейс interface{}
Не имеет методов. Ему удовлетворяет любой тип.

go
var anything interface{}
anything = 42
anything = "hello"
anything = Dog{}
Обычно используется:

В fmt.Print и подобных функциях

Когда тип действительно неизвестен (с последующей проверкой)

❗ С появлением дженериков (Go 1.18+) пустой интерфейс стал нужен реже.

Проверка типа (type assertion)
Для пустого интерфейса (или когда нужно узнать конкретный тип внутри):

go
var x interface{} = 42

// Вариант 1: если не уверены
val, ok := x.(int)
if ok {
fmt.Println("Это int:", val)
}

// Вариант 2: type switch
switch v := x.(type) {
case int:
fmt.Println("int:", v)
case string:
fmt.Println("string:", v)
default:
fmt.Println("неизвестный тип")
}
Распространённые ошибки новичков
1. «Методы всё равно писать, зачем интерфейс?»
   Ответ: Интерфейс нужен не чтобы не писать методы, а чтобы не писать GreetDog, GreetCat, GreetPhone...

2. Интерфейс принимает любой тип данных
   Нет. Интерфейс с методами принимает только те типы, у которых ЕСТЬ эти методы. Только interface{} принимает всё.

3. Путают интерфейс с type assertion
   x.(int) — это не интерфейс, это проверка типа. Работает только с пустым интерфейсом.

Опасный вопрос с собеседования (для сеньоров)
go
type Foo struct{}
func (f *Foo) A() {}
func (f *Foo) B() {}
func (f *Foo) C() {}

type AB interface { A(); B() }
type BC interface { B(); C() }

func main() {
var f AB = &Foo{}
y := f.(BC)  // сработает (у Foo есть B() и C())
y.A()        // ❗ вызовется! (у Foo есть A(), хотя y типа BC)
}
Почему работает: y хранит конкретный тип *Foo, а не абстракцию.
Почему опасно: компилятор не обязан это пропускать, полагаться на такое — плохая практика.

Для новичка: забудь этот пример до уровня middle. В реальном коде так не пишут.

Главное, что нужно запомнить
Структура — данные. Интерфейс — умения.

Интерфейс как тип позволяет хранить разные конкретные типы в одной переменной или слайсе.

Главная польза: один слайс + один цикл вместо 10 слайсов и 10 циклов.

Методы писать всё равно придётся. Интерфейс избавляет от дублирования функций, а не методов.

Код для практики (запусти и поиграй)
go
package main

import "fmt"

type Speaker interface {
Speak() string
}

type Dog struct{}
func (Dog) Speak() string { return "Гав!" }

type Cat struct{}
func (Cat) Speak() string { return "Мяу!" }

type Phone struct{}
func (Phone) Speak() string { return "Бип!" }

func main() {
// Разные типы в одном слайсе
things := []Speaker{Dog{}, Cat{}, Phone{}}

    for _, t := range things {
        fmt.Println(t.Speak())
    }
}
Попробуй удалить Speak() у Dog — код не скомпилируется. Вот что значит «не удовлетворяет интерфейсу».
