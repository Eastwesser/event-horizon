# Scaling

## Грейд
18

## Вопрос
Есть два сервиса A и B. Сервис A отправляет запросы в сервис B по HTTP. Какие существуют варианты для масштабирования сервиса B?

## Ответ

### 1. Server-side balancing
Добавляем промежуточный балансировщик (nginx / haproxy).

### 2. Client-side balancing
Используем DNS / Consul / etcd, из которого A узнаёт, где запущен B.

## Дополнительные вопросы

### Сколько балансировщиков будет в первой схеме?
Как минимум два (чтобы избежать SPOF).

### Если их больше, чем один, как приложение узнает, где они запущены?
Балансировщики можно находить через DNS.

### Как именно будет выглядеть discovery через DNS?
A-записи или SRV-записи.

## Что важно сказать на собеседовании

1. **Server-side balancing:**
   - L4 (TCP) — HAProxy, AWS NLB
   - L7 (HTTP) — Nginx, AWS ALB, Traefik
   - Плюс: просто для клиента
   - Минус: дополнительный hop, возможен SPOF

2. **Client-side balancing:**
   - Consul, etcd, ZooKeeper, Eureka
   - Плюс: нет дополнительного hop'а
   - Минус: сложнее реализовать, каждый клиент должен знать о discovery

3. **Service Mesh (например, Istio):**
   - Позволяет делать client-side balancing без изменения кода
   - Sidecar proxy (Envoy) рядом с каждым сервисом

4. **DNS-based balancing:**
   - Просто, но нет health checking на уровне DNS
   - Работает с TTL, но не быстро переключается
