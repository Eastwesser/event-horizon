# Slow Service (Медленный сервис аналитики)

## Грейд
18

## Вопрос
На примере создания заказа. Есть запрос на сервис и есть ответ. Между этими двумя действиями мы отправляем данные в аналитику (например, для подсчёта популярности товаров). Сервис аналитики периодически работает медленно или вовсе таймаутит, и мы не успеваем ответить — теряем заказы.

Что делать, чтобы перестать терять заказы и деньги?

## Ответ
Нужно **отвязать** обработку заказа от отправки в аналитику. Сделать это асинхронно.

## Схема решения

Order Service                    Analytics Service
│                                  │
│  1. Create Order                 │
├─────────────────────────────────►│
│                                  │
│  2. Save order to DB             │
│                                  │
│  3. Send to queue (Kafka/RMQ)    │
├─────────────────────────────────►│ (Queue)
│                                  │
│  4. Return response to client    │
│◄─────────────────────────────────┤
│                                  │
│                     5. Worker consumes from queue
│                                  │
│                     6. Send to Analytics
│                                  │


## Дополнительные вопросы

### Как организовать воркеры, чтобы они не брали в работу одни и те же данные?
Использовать мастер-процесс, который будет раздавать задачи, или использовать очередь с exclusivity (например, Redis с `BLPOP`, Kafka с partition key).

### Сервис аналитики не будет читать данные из нашей очереди. Что будем делать?
Придумать способ самим пушить данные в аналитику из своей очереди (сделать reverse-proxy для аналитики или адаптер).

### Отдел аналитики жалуется на высокий RPS от нас, когда они под нагрузкой. Как решить проблему?
Нужно придумать **адаптивный rate limiter** с экспоненциальным понижением нагрузки в зависимости от состояния аналитики (например, на основе HTTP-статусов или времени ответа).

### Проблема с аналитикой решена. Теперь проблема с местом, занимаемым нашей очередью. Что делать?
Нужно просеивать данные в зависимости от квоты на ресурсы:
- Вытеснение (eviction) — удалять старые или наименее приоритетные события
- Прореживание (sampling) — отправлять только каждый N-ый заказ

## Что важно сказать на собеседовании

1. **Асинхронная обработка** через очередь — основной паттерн
2. **Технологии:** Kafka, RabbitMQ, Redis Streams, AWS SQS
3. **Patience:** Circuit Breaker для аналитики (чтобы не ждать таймаут)
4. **Bulkhead:** выделить отдельный пул потоков/горутин для аналитики
5. **Fallback:** при недоступности аналитики — логировать или сохранять в БД

## Пример (Go с каналом)

```go
func CreateOrder(w http.ResponseWriter, r *http.Request) {
    order := parseOrder(r)
    saveToDB(order)
    
    // Асинхронная отправка в аналитику
    // ВАЖНО: при завершении программы нужно дождаться таких горутин
    // Или использовать очередь (Kafka/RMQ) для надёжности
    go func() {
        // В реальном коде — через очередь (Kafka/RMQ)
        sendToAnalytics(order)
    }()
    
    w.WriteHeader(http.StatusOK)
    json.NewEncoder(w).Encode(order)
}
```
