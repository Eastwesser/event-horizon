# Медленный сервис**
### **Асинхронная обработка**

Отправлять данные в аналитику **асинхронно**, не дожидаясь ответа перед формированием ответа клиенту.

- **Варианты реализации:**
    
    - **Message Queue (Kafka, RabbitMQ, SQS)** – кладем событие о заказе в очередь, а отдельный воркер отправляет в аналитику.
### **Устойчивость к ошибкам (Retry + Circuit Breaker)**

- **Retry** – повторять запрос при временных сбоях (но с экспоненциальной задержкой, чтобы не перегружать сервис).
    
- **Circuit Breaker** (Hystrix, Resilience4j) – если аналитика не отвечает, временно отключать запросы к ней, чтобы не блокировать основной поток.
    

### **3. Локальное кеширование + отложенная отправка**

- Сохранять данные о заказах **локально** (в БД или файл), а потом отправлять пачками.

Если аналитика **не может или не хочет** потреблять данные напрямую из вашей очереди
**Берёт данные из вашей очереди** → **Отправляет в API аналитики** (с retry-логикой).
### **Отправка пачками (Batching)**

Если аналитика **не принимает частые запросы**, но готова к большим batch-обновлениям:

- Воркер **накапливает N сообщений** или ждёт **X секунд** → отправляет одним запросом.

### **Резервное хранилище + ручной импорт**

Если аналитика **только берёт данные из БД**:

- Пишите заказы в свою **резервную БД** (например, `orders_for_analytics`).
    
- Аналитика периодически **забирает данные через ETL-процесс**

# Scaling**
## **Горизонтальное масштабирование (Horizontal Scaling)**

**Суть:** Запуск нескольких инстансов сервиса B за балансировщиком нагрузки.  
**Технологии:**

- **Kubernetes (K8s) + HPA** – автоматическое масштабирование по CPU/RPS.
    
- **Docker Swarm** – проще, но менее гибко, чем K8s.
    
- **VM + Load Balancer (Nginx, HAProxy, AWS ALB)** – ручное или автоскейлинг групп виртуальных машин.
    

**Плюсы:**  
✅ Простота реализации.  
✅ Автоматическое масштабирование под нагрузку.

**Минусы:**  
⚠ Нужна shared-nothing архитектура (сессии в Redis, общее хранилище).

## **2. Асинхронная обработка через очередь (Message Queue)**

**Суть:** Сервис A кладёт запросы в очередь, а сервис B обрабатывает их в фоне.  
**Технологии:**

- **Kafka** – для высоконагруженных систем с гарантированной доставкой.
    
- **RabbitMQ** – проще, но менее масштабируемо.
    
- **AWS SQS / Google PubSub** – managed-решения для облака.
    

**Плюсы:**  
✅ Развязка сервисов (B может отставать в обработке без влияния на A).  
✅ Возможность буферизации и retry.

**Минусы:**  
⚠ Усложнение архитектуры (нужны воркеры, DLQ, мониторинг).  
⚠ Задержки (не подходит для real-time).

---

## **3. Кеширование ответов (Caching)**

**Суть:** Если запросы повторяются, можно кешировать ответы B.  
**Технологии:**

- **Redis / Memcached** – in-memory кеш.
    
- **CDN (Cloudflare, Fastly)** – для статичных данных.
    
- **HTTP-кеш (Nginx, Varnish)** – кеширование на уровне прокси.
    

**Плюсы:**  
✅ Снижает нагрузку на B.  
✅ Уменьшает задержки для повторяющихся запросов.

**Минусы:**  
⚠ Не подходит для уникальных запросов.  
⚠ Нужна инвалидация кеша.

---

## **4. Шардирование (Partitioning / Sharding)**

**Суть:** Разделение данных между разными инстансами B (например, по userId).  
**Технологии:**

- **Базы данных (PostgreSQL, MongoDB)** – шардирование на уровне хранилища.
    
- **Сервис B + Consistent Hashing** – запросы распределяются по нодам.
    

**Плюсы:**  
✅ Уменьшает конкуренцию за ресурсы.  
✅ Позволяет обрабатывать больше данных.

**Минусы:**  
⚠ Сложность маршрутизации запросов.  
⚠ Неравномерная нагрузка (если шарды не сбалансированы).

## **Сколько балансировщиков нужно?**

Зависит от нагрузки и требований к отказоустойчивости:

### **Вариант 1: Один балансировщик (Single Load Balancer)**

- Подходит для **некритичных сервисов** с умеренной нагрузкой.
    
- **Риск:** Если балансировщик упадёт, весь трафик к сервису B остановится.
    
- **Примеры:**
    
    - Один **Nginx/HAProxy** на отдельной VM.
        
    - Один **AWS ALB** (Application Load Balancer).
        

### **Вариант 2: Несколько балансировщиков (High Availability)**

- Для отказоустойчивости используют **2+ балансировщика** в разных AZ (зонах доступности).
    
- **Как работает:**
    
    - **DNS-балансировка (Round Robin)** – у одного домена (например, `b-service.example.com`) несколько IP-адресов балансировщиков.
        
    - **Anycast (AWS Global Accelerator, Cloudflare)** – один IP маршрутизируется на ближайший балансировщик.
        
- **Примеры:**
    
    - **AWS ALB + Route53** (с health checks).
        
    - **Kubernetes Ingress + Cloud Load Balancer** (GCP/AWS).

## **2. Как сервис A узнаёт адреса балансировщиков или нод сервиса B?**

Есть несколько подходов:

### **Вариант 1: DNS + Load Balancer (Самый простой)**

- Сервис B регистрируется под доменным именем (например, `b-service.example.com`).
    
- DNS возвращает IP балансировщика (или несколько IP, если балансировщиков много).
    
- **Плюсы:**
    
    - Простота.
        
    - Балансировщик скрывает внутреннюю структуру сервиса B.
        
- **Минусы:**
    
    - DNS-кеширование может задерживать обновления.
        

### **Вариант 2: Service Discovery (Для сложных систем)**

- **Используется в Kubernetes, Consul, Eureka.**
    
- Сервис B регистрируется в Service Discovery (например, **etcd, Consul**).
    
- Сервис A запрашивает у Service Discovery актуальные адреса сервиса B.
    
- **Плюсы:**
    
    - Динамическое обновление при масштабировании.
        
    - Поддержка health checks (отсекает нерабочие ноды).
        
- **Минусы:**
    
    - Усложняет архитектуру.
        

### **Вариант 3: API Gateway (Для микросервисов)**

- Все запросы идут через **Gateway (Kong, Apigee, AWS API Gateway)**.
    
- Gateway знает, куда маршрутизировать запросы.
    
- **Плюсы:**
    
    - Единая точка входа.
        
    - Можно добавить аутентификацию, rate limiting.
        
- **Минусы:**
    
    - Gateway становится узким местом (нужно масштабировать и его).

## **3. Как балансировщик узнаёт о новых инстансах сервиса B?**

Зависит от технологии:

### **Kubernetes (K8s)**

- **Ingress-контроллер (Nginx, Traefik)** автоматически обновляет конфиг при добавлении подов.
    
- **Service (ClusterIP)** балансирует трафик между подами.
    

### **Cloud Load Balancer (AWS ALB, GCP LB)**

- Интегрируется с **Auto Scaling Group (AWS)** или **Managed Instance Group (GCP)**.
    
- Новые VM автоматически регистрируются в балансировщике.
    

### **Nginx/HAProxy + Consul**

- **Consul Template** динамически обновляет конфиг Nginx при изменении списка сервисов.

### **DNS (Domain Name System)**

**DNS** — это система, которая преобразует удобные для человека доменные имена (например, `google.com`) в IP-адреса (например, `142.250.185.206`), которые понимают компьютеры.

#### **Как работает DNS?**

1. **Пользователь** вводит `b-service.example.com` в браузере или API-запросе.
    
2. **DNS-резолвер** (например, Google DNS `8.8.8.8`) ищет IP-адрес этого домена:
    
    - Сначала проверяет локальный кеш.
        
    - Если нет — запрашивает корневые DNS-серверы, затем серверы домена `.com`, потом `example.com`.
        
3. **Возвращает IP** (например, `10.0.0.5`), который принадлежит балансировщику нагрузки или серверу.
    

#### **Зачем DNS в масштабировании?**

- Балансировщик (например, AWS ALB) привязан к домену.
    
- Если сервис масштабируется, DNS может возвращать несколько IP-адресов (Round Robin).
    
- **Пример:**
    
    bash
    
    Copy
    
    Download
    
    $ dig b-service.example.com
    b-service.example.com. 300 IN A 10.0.0.5
    b-service.example.com. 300 IN A 10.0.0.6
    

#### **Проблемы DNS**

- **Кеширование**: DNS-клиенты (ОС, браузеры) кешируют IP, что замедляет обновление.
    
- **Нет health checks**: DNS не проверяет, жив ли сервер.

### **Service Discovery (Сервис-дискавери)**

**Service Discovery** — это механизм, позволяющий сервисам автоматически находить друг друга в динамической среде (например, в Kubernetes или облаке).

#### **Как работает?**

1. **Сервис B регистрируется** при запуске (например, в **Consul, etcd, Eureka, Kubernetes Service**).
    
2. **Сервис A запрашивает** "Где сейчас находится сервис B?" у Service Discovery.
    
3. **Получает актуальный список IP:порт** и выбирает один (с балансировкой).
    

#### **Примеры технологий**

|Технология|Где используется|Особенности|
|---|---|---|
|**Kubernetes Service**|K8s|Встроен, работает с `kube-dns`.|
|**Consul**|On-premise/Cloud|Поддержка health checks.|
|**Eureka**|Spring Cloud|Для Java-микросервисов.|
|**Zookeeper**|Kafka, Hadoop|Хранит метаданные.|

#### **Плюсы Service Discovery**

✅ **Динамическое обновление**: Если сервис B упал или масштабировался, клиент узнает об этом.  
✅ **Балансировка**: Можно распределять запросы между инстансами (Round Robin, Least Connections).  
✅ **Health checks**: Отсеивает нерабочие ноды.

#### **Минусы**

⚠ **Сложнее, чем DNS**: Нужна инфраструктура (Consul, etcd).  
⚠ **Задержки**: Клиент должен интегрировать SDK или делать дополнительные запросы.
