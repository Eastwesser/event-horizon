## ЧАСТЬ 1: GOLANG — ОСНОВЫ И CONCURRENCY

### 1.1. Указатели (Pointers)

**Что такое указатель?**
- Указатель хранит **адрес переменной** в памяти
- Синтаксис: `*T` — тип указателя, `&x` — взять адрес переменной `x`
- Разыменование: `*ptr` — получить значение по адресу

**Пример:**
```go
x := 10
ptr := &x         // ptr содержит адрес x
fmt.Println(ptr)  // 0xc000012345 (адрес)
fmt.Println(*ptr) // 10 (значение по адресу)

*ptr = 20         // изменяем значение через указатель
fmt.Println(x)    // 20 (x изменился!)
```

**Указатели на структуры:**
```go
type User struct {
    Name string
    Age  int
}

func updateAge(u *User, newAge int) {
    u.Age = newAge  // автоматическое разыменование
}

func main() {
    user := User{Name: "Alice", Age: 25}
    updateAge(&user, 30)
    fmt.Println(user.Age) // 30
}
```

**Когда использовать указатели:**
- Когда нужно изменить значение внутри функции
- Когда структура большая (избегаем копирования)
- Когда нужен `nil` как значение (например, `var ptr *int = nil`)

**Zero value:**
- Zero value для указателя — `nil`

### 1.2. Слайсы (Slices)

**Что такое слайс?**
- **Структура**: три поля — `pointer` (указатель на базовый массив), `len` (текущая длина), `cap` (вместимость)
- **Динамический массив**, может изменяться в размере
- **Ссылочный тип** (так как есть указатель на базовый массив)

**Операции:**
- `append(slice, value)` — добавление элемента:
  - Если `len < cap` → элемент добавляется в существующий массив
  - Если `len == cap` → происходит **реаллокация**: создаётся новый массив (обычно в 2 раза больше до cap=1024, потом линейное увеличение на 25%), копируются старые значения + новый элемент, возвращается новый слайс с новым указателем
  - **Важно:** после реаллокации старый слайс и новый слайс указывают на разные массивы!

**Пример реаллокации:**
```go
slice := make([]int, 4)  // len=4, cap=4
fmt.Println(cap(slice), &slice[0])  // 4, 0xc0000b4000

slice = append(slice, 3)  // len=5, cap=8 (удвоение!)
fmt.Println(cap(slice), &slice[0])  // 8, 0xc0000b8000 (адрес изменился!)
```

**Размер слайса не всегда увеличивается в 2 раза:**
- Слайсы разных типов могут расширяться по-разному
- До cap=1024 элементов: удвоение (cap × 2)
- После 1024: линейное увеличение (~25%)

**Слайсинг (нарезка):**
- Синтаксис: `slice[start:end:cap]`
  - `start` — начальный индекс (включительно)
  - `end` — конечный индекс (не включительно)
  - `cap` — новая вместимость (третья цифра — **не шаг**, а максимальный cap для нового слайса)
- Пример: `mySlice[2:3:3]` → слайс от индекса 2 до 3 с cap=3

**Передача слайса в функцию:**
- Слайс передаётся **по значению** (копируется структура `pointer, len, cap`)
- Но `pointer` всё ещё указывает на тот же базовый массив → изменения элементов **по индексу** видны вне функции
- Если внутри функции происходит `append` → может произойти реаллокация → новый слайс не затронет исходный
- **Итого:** изменения по индексу видны, расширение слайса (append) — не видно (если не вернуть новый слайс)

**Copy:**
- `copy(dst, src)` — копирует элементы из `src` в `dst`
- Используется для переиспользования памяти (вместо создания нового слайса)

### 1.3. Мапы (Maps)

**Что такое мапа?**
- Под капотом: **хеш-таблица** с бакетами
- Порядок итерации **случайный** и не гарантируется (специально рандомизирован в Go)
- Операции: `make(map[K]V)`, `map[key] = value`, `value, ok := map[key]`
- **Comma-ok идиома:** `if v, ok := m[key]; ok { ... }` — проверяет наличие ключа

---

#### Объявление мапы:

**Два способа:**
```go
// 1. Без инициализации (nil map)
var m map[string]int
// При записи → PANIC: assignment to entry in nil map
// При чтении → возвращает zero value (0 для int, "" для string и т.д.)

// 2. С инициализацией (make)
m := make(map[string]int)
// Можно писать и читать безопасно
```

**ВАЖНО:** в неинициализированную мапу писать **нельзя** (runtime panic)!

---

#### Структура мапы под капотом:

**Мапа состоит из бакетов (buckets):**
- Каждый бакет хранит до 8 пар ключ-значение
- В бакете данные хранятся **сначала все ключи, потом все значения** (для оптимизации выравнивания памяти)
- При коллизиях (когда несколько ключей попадают в один бакет) используется цепочка переполнения (overflow buckets)

---

#### Эвакуация (расширение) мапы:

**Когда происходит эвакуация?**
- Когда мапа заполняется (load factor > 6.5, т.е. в среднем > 6.5 элементов на бакет)
- Мапа создаёт новый массив бакетов (в 2 раза больше)
- Данные **перемещаются постепенно**, по кусочкам (incremental rehashing), а не все сразу

**Как перемещаются данные?**
- Не все сразу, а по 2 бакета за операцию записи/удаления
- Это делается для того, чтобы избежать долгих пауз при больших мапах

---

#### Конкурентная запись в мапу:

**Что будет, если 2 горутины пишут в одну мапу?**
- **FATAL ERROR:** `concurrent map writes`
- Эту ошибку **нельзя отловить** с помощью `recover()` (это не panic, а fatal)
- Программа завершится

**Что будет, если в двух горутинах начнётся эвакуация мапы?**
- **FATAL ERROR** — Go детектирует это и убивает программу

**Решение:** использовать `sync.Mutex` или `sync.RWMutex` для защиты мапы, или использовать `sync.Map` (см. раздел 1.10)

---

#### Память и удаление элементов:

**Была огромная мапа (10 млн элементов), удалил все элементы — освободилась ли память?**
- **Нет!**
- Количество бакетов в мапе **не уменьшается** при удалении элементов
- Если мапа разрослась до 1 GB, она останется в этом объёме даже после удаления всех элементов
- **Решение:** пересоздать мапу (`make(map[K]V)`) и скопировать нужные элементы → старая мапа будет собрана GC

---

#### Ключи мапы:

**Может ли структура быть ключом мапы?**
- Да, **если все поля структуры сравниваемые** (comparable)
- Нельзя использовать структуры с полями типа `slice`, `map`, `func` (несравниваемые типы)
- Можно: `int`, `string`, `bool`, `pointer`, `struct` (если все поля сравниваемые), `array` (если элементы сравниваемые)

---

#### Range и адреса:

**Гарантирует ли `range` порядок обхода?**
- **Нет**, порядок случайный и специально рандомизирован (starting offset randomized)

**Можно ли взять адрес значения в мапе?**
```go
addr := &m["key"]  // ОШИБКА КОМПИЛЯЦИИ
```
- **Нельзя!** Потому что при эвакуации мапы элементы перемещаются в памяти (бакеты меняют адреса)
- Если бы взяли адрес, он стал бы невалидным после эвакуации

### 1.4. Каналы (Channels)

**Что такое канал?**
- Канал — механизм для передачи данных между горутинами
- Типы: **буферизированный** и **небуферизированный**

---

#### Небуферизированный канал:

```go
ch := make(chan T)
```

- **Синхронизация:** `send` блокируется до тех пор, пока не придёт `recv` (и наоборот)
- Если нет читателя → отправитель блокируется (и наоборот)
- Под капотом: очередь ожидающих горутин (`sendq`, `recvq`)

---

#### Буферизированный канал:

```go
ch := make(chan T, N)  // N — размер буфера
```

- **Очередь:** `send` блокируется только если буфер заполнен
- `recv` блокируется только если буфер пуст
- Буфер канала = макс количество "билетов", которые могут быть одновременно в обращении
- Под капотом: две очереди (`sendq`, `recvq`) + **буфер** (кольцевой массив для хранения значений)

---

#### Алгоритмическая сложность:

- Чтение из канала: **O(1)**
- Запись в канал: **O(1)**

---

#### Обмен данными через небуферизированный канал:

- Берём значение из **стэка** отправителя и записываем в **стэк** получателя (прямая передача без копирования в буфер)

---

#### SELECT:

**Что такое `select`?**
- Конструкция для работы с несколькими каналами одновременно
- Позволяет ждать на нескольких каналах и выбрать первый готовый

```go
select {
case msg := <-ch1:
    fmt.Println("Получено из ch1:", msg)
case msg := <-ch2:
    fmt.Println("Получено из ch2:", msg)
case <-time.After(1 * time.Second):
    fmt.Println("Таймаут")
default:
    fmt.Println("Ничего не готово")
}
```

**Что будет, если в `select` несколько кейсов станут `true` одновременно?**
- Go выбирает **случайный** кейс из готовых (uniform random selection)
- Если это `for + select` → будет выбирать по принципу **математического ожидания** (каждый кейс имеет равный шанс)
- Пример: 2 кейса готовы одновременно → каждый имеет шанс 50%

---

#### Паники с каналами:

**Паники, которые нельзя отловить с помощью `recover()`:**
- Запись в **неинициализированный** канал (`var ch chan int; ch <- 1` → FATAL)
- Закрытие уже закрытого канала
- Отправка в закрытый канал

### 1.5. Горутины и WaitGroup

**Что такое WaitGroup?**
- Счётчик для ожидания завершения группы горутин
- Работает по принципу **семафора** (или буферизированного канала)

**Как работает?**
```go
var wg sync.WaitGroup

for i := 0; i < 10; i++ {
    wg.Add(1)  // Увеличиваем счётчик перед запуском горутины
    go func(i int) {
        defer wg.Done()  // Уменьшаем счётчик при завершении
        // ... работа ...
    }(i)
}

wg.Wait()  // Ждём, пока счётчик не станет 0
```

**Под капотом:**
- WaitGroup состоит из **трёх полей:**
  1. **Счётчик** — 64-битное число, где:
     - **Старшие 32 бита** — количество вызовов `Add()` (сколько горутин ещё работают)
     - **Младшие 32 бита** — количество горутин, ожидающих на `Wait()`
  2. **Семафор** — для блокировки горутин, вызвавших `Wait()`

**Как WaitGroup понимает, что счётчик стал пустым?**
- При каждом `Done()` уменьшается счётчик
- Когда счётчик становится 0 → WaitGroup разблокирует все горутины, ожидающие на `Wait()` (пробуждает их через семафор)

### 1.6. Mutex и RWMutex

---

#### Mutex:

**Что происходит при вызове `mutex.Lock()`?**
1. Горутина пытается захватить мьютекс (несколько попыток через atomic CAS)
2. Если не получилось → горутина **уходит в очередь ожидания**
3. Горутина **открепляется от выполнения** и меняет статус на **WAITING**
4. Когда мьютекс освобождается → одна из ожидающих горутин пробуждается

**Что происходит, если мьютекс уже заблокирован?**
- Горутина несколько раз пытается получить доступ через спин-лок (spin-lock)
- Если не получилось → уходит в очередь ожидания (FIFO)

---

#### Starvation Mode (режим голодания):

**Что это?**
- Механизм, который предотвращает ситуацию, когда одна горутина долго не может получить блокировку из-за постоянной конкуренции

**Два режима работы мьютекса:**

**1. Нормальный режим (Normal Mode):**
- Конкурирующие горутины стоят в очереди (FIFO)
- Пробуждающаяся горутина **должна бороться за мьютекс** с новыми горутинами (которые только что вызвали `Lock()`)
- Даёт лучшую производительность, но может вызвать **голодание** (starvation) — когда горутина долго не может получить мьютекс

**2. Starvation Mode (режим голодания):**
- Включается, если горутина ждёт мьютекс **больше 1 мс**
- Мьютекс передаётся **ПРЯМО** следующей горутине в очереди (FIFO), без борьбы
- Новые горутины **не могут "ворваться"** перед ждущими
- Гарантируется **справедливость** (fairness) — все получат доступ по очереди

---

#### RWMutex:

**Read-Write Mutex:**
- Позволяет **нескольким горутинам читать** одновременно (`RLock()`)
- Но **только одна горутина может писать** (`Lock()`)
- Писатель блокирует всех (и читателей, и других писателей)

**Когда использовать:**
- Когда **чтение происходит гораздо чаще, чем запись**
- Если запись частая → обычный `Mutex` может быть быстрее

---

#### Sync.Cond:

**Что это?**
- Условная переменная для синхронизации горутин
- Используется для **разблокировки** горутин по сигналу

**Методы:**
- `Wait()` — блокирует горутину до получения сигнала
- `Signal()` — пробуждает **одну** ожидающую горутину
- `Broadcast()` — пробуждает **все** ожидающие горутины

**Когда использовать:**
- Когда нужно, чтобы горутины ждали определённого события
- Пример: producer-consumer pattern с несколькими consumers

---

#### Sync.Once:

**Что это?**
- Гарантирует, что функция будет выполнена **только один раз**, даже если вызывается из нескольких горутин

**Пример:**
```go
var once sync.Once
var instance *Singleton

func GetInstance() *Singleton {
    once.Do(func() {
        instance = &Singleton{}  // Выполнится только один раз
    })
    return instance
}
```

**Когда использовать:**
- Инициализация синглтонов
- Ленивая инициализация (lazy initialization) в многопоточной среде

---

#### Sync.Pool:

**Что это?**
- Пул объектов для **переиспользования** (object pooling)
- **Не гарантирует**, что объекты останутся в пуле (GC может их почистить)

**Для чего нужен?**
- Для уменьшения нагрузки на GC при обработке большого количества запросов
- Переиспользуем объекты вместо создания новых

**Пример:**
```go
var bufferPool = sync.Pool{
    New: func() interface{} {
        return new(bytes.Buffer)  // Создаём новый объект, если пул пуст
    },
}

// Получаем объект из пула
buf := bufferPool.Get().(*bytes.Buffer)
buf.Reset()  // ВАЖНО: обнуляем перед использованием!

// Используем...
buf.WriteString("Hello")

// Возвращаем в пул (после обнуления!)
buf.Reset()
bufferPool.Put(buf)
```

**Правила работы с Sync.Pool:**
1. **Всегда обнуляй объект перед возвратом в пул** (иначе следующая горутина получит "грязный" объект)
2. **Всегда проверяй состояние объекта после получения из пула**
3. GC может почистить пул при определённых обстоятельствах

**Когда использовать:**
- High-load сервисы (обработка большого количества запросов)
- Когда создание объекта дорогое (например, большие буферы, сложные структуры)
- Когда хотим снизить нагрузку на GC

**Разница с обычным созданием объектов:**
- Без пула: на каждый запрос создаётся новый объект → линейный рост потребления памяти → GC часто чистит
- С пулом: 100 объектов создаются один раз, переиспользуются → на следующие 100 запросов новые объекты не создаются

---

#### Sync.Map:

**Что это?**
- **Конкурентно-безопасная мапа** (можно писать и читать из нескольких горутин без мьютексов)

**Под капотом:**
- Sync.Map состоит из **двух мап:**
  - Одна для **чтения** (read-only map)
  - Другая для **записи** (dirty map)
- Есть особые политики согласованности данных между ними

**Разница в скорости:**
- **Sync.Map vs обычная map + Mutex:**
  - Sync.Map **быстрее** на чтении (если чтение >> записи)
  - Sync.Map **медленнее** на записи (из-за дополнительной синхронизации)
- **Sync.Map vs обычная map + RWMutex:**
  - Sync.Map может быть быстрее при очень частом чтении и редкой записи

**Когда использовать Sync.Map:**
- Когда **чтение происходит гораздо чаще, чем запись**
- Когда ключи стабильны (пишутся один раз, потом только читаются)
- Когда нужна конкурентно-безопасная мапа без явных мьютексов

**Когда НЕ использовать:**
- Когда запись частая → обычная `map + Mutex` будет быстрее
- Когда нужна типизация → Sync.Map работает с `interface{}` (нет дженериков в старых версиях Go)

### 1.7. Контекст (Context)

**Что такое Context?**
- **Механизм отмены** — сигнал для остановки операций
- **Таймауты и дедлайны** — ограничение времени выполнения
- **Передача значений** — передача метаданных через цепочку вызовов (traceID, userID, токены)

**Интерфейс:**
```go
type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done() <-chan struct{}
    Err() error
    Value(key any) any
}
```

**Основные методы создания:**
```go
// 1. Отмена
ctx, cancel := context.WithCancel(parent)
defer cancel()  // ОБЯЗАТЕЛЬНО вызывать!

// 2. Таймаут
ctx, cancel := context.WithTimeout(parent, 5*time.Second)
defer cancel()

// 3. Дедлайн
ctx, cancel := context.WithDeadline(parent, time)
defer cancel()

// 4. Передача значений
ctx := context.WithValue(parent, key, value)
val := ctx.Value(key)

// 5. Без отмены (Go 1.21+)
ctx := context.WithoutCancel(parent)
```

**Пример использования:**
```go
func worker(ctx context.Context, id int) {
    select {
    case <-ctx.Done():
        fmt.Printf("Worker %d: отменен, причина: %v\n", id, ctx.Err())
        return
    case <-time.After(2 * time.Second):
        fmt.Printf("Worker %d: работа завершена\n", id)
    }
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)
    defer cancel()

    go worker(ctx, 1)
    go worker(ctx, 2)

    time.Sleep(3 * time.Second) // Ждем, но контекст отменится через 1 секунду
}
```

**Ключевые принципы:**
- Context — **immutable** (неизменяемый), каждый `With*` создает новый контекст
- При отмене родителя отменяются **все потомки**
- Context должен быть **первым аргументом** функции (соглашение)
- `WithValue` — только для метаданных, **не для передачи аргументов**
- **ВСЕГДА** вызывай `defer cancel()` — освобождает ресурсы

**Когда использовать:**
- Graceful shutdown (остановка сервера)
- HTTP-запросы с таймаутом
- Работа с базами данных (отмена долгих запросов)
- Распределенный трейсинг (передача traceID)

### 1.8. Интерфейсы (Interfaces)

**Что такое интерфейс?**
- **Интерфейс** — набор методов, которые тип должен реализовать
- Go использует **Duck Typing**: если тип реализует все методы интерфейса, он удовлетворяет интерфейсу (явно указывать не нужно!)

**Пример:**
```go
type Writer interface {
    Write(p []byte) (n int, err error)
}

type FileWriter struct{}

func (fw FileWriter) Write(p []byte) (int, error) {
    // реализация
    return len(p), nil
}

// FileWriter автоматически удовлетворяет интерфейсу Writer!
```

**Пустой интерфейс `interface{}`:**
- Может принимать **любое значение** (любой тип)
- Используется для универсальных функций
```go
func Describe(i interface{}) {
    fmt.Printf("Type: %T, Value: %v\n", i, i)
}

func main() {
    Describe("Hello")  // Type: string, Value: Hello
    Describe(42)       // Type: int, Value: 42
    Describe(true)     // Type: bool, Value: true
}
```

---

#### Под капотом: как устроен интерфейс?

Интерфейс в Go — это **пара (type, value)**:
```go
type iface struct {
    tab  *itab        // информация о типе
    data unsafe.Pointer  // указатель на конкретное значение
}
```

**Важно:**
- Интерфейс содержит **два поля**: тип и данные
- Интерфейс считается `nil` только если **оба поля** равны `nil`

---

#### Ниловый интерфейс — подводные камни

**Проблема:**
```go
var a interface{} = nil
var b interface{} = (*int)(nil)

fmt.Println(a == nil) // true  (тип nil, данные nil)
fmt.Println(b == nil) // false (тип *int, данные nil)
```

**Почему `b != nil`?**
- `a`: тип = `nil`, данные = `nil` → интерфейс `nil`
- `b`: тип = `*int`, данные = `nil` → интерфейс **НЕ `nil`** (тип установлен!)

**Практический пример (типичная ошибка):**
```go
func getUser() *User {
    var user *User = nil
    return user  // вернули nil указатель
}

func main() {
    user := getUser()
    if user != nil {
        fmt.Println("User exists")  // ВЫПОЛНИТСЯ! Хотя user == nil
    }
}
```

**Решение:**
```go
func getUser() *User {
    return nil  // правильно: вернули nil значение напрямую
}

// Или возвращай интерфейс:
func getUser() interface{} {
    var user *User = nil
    if user == nil {
        return nil  // правильно
    }
    return user
}
```

**Правило:** Если функция возвращает интерфейс, не возвращай типизированный `nil`!

---

#### Type Assertion и Type Switch

**Type Assertion:**
```go
var i interface{} = "hello"

s := i.(string)       // паника, если i не string
s, ok := i.(string)   // безопасно: ok == true/false
```

**Type Switch:**
```go
func describe(i interface{}) {
    switch v := i.(type) {
    case int:
        fmt.Printf("Integer: %d\n", v)
    case string:
        fmt.Printf("String: %s\n", v)
    case nil:
        fmt.Println("Nil")
    default:
        fmt.Printf("Unknown type: %T\n", v)
    }
}
```

---

#### Error Group

**`errgroup.Group`** — пакет для управления группой горутин с обработкой ошибок:
```go
import "golang.org/x/sync/errgroup"

func main() {
    g := new(errgroup.Group)

    // Запускаем несколько горутин
    g.Go(func() error {
        return doWork1()
    })

    g.Go(func() error {
        return doWork2()
    })

    // Ждем завершения всех горутин
    if err := g.Wait(); err != nil {
        fmt.Printf("Ошибка: %v\n", err)
    }
}
```

**С контекстом:**
```go
g, ctx := errgroup.WithContext(context.Background())

g.Go(func() error {
    select {
    case <-ctx.Done():
        return ctx.Err()  // контекст отменен
    default:
        return doWork()
    }
})

if err := g.Wait(); err != nil {
    // Если хотя бы одна горутина вернула ошибку, контекст отменяется
    fmt.Println("Error:", err)
}
```

**Преимущества `errgroup`:**
- Автоматическое ожидание всех горутин
- Отмена контекста при первой ошибке
- Возврат первой ошибки из группы

### 1.9. Ошибки в Go

**Что такое ошибка в Go?**
- Ошибка — это **значение** типа `error` (интерфейс)
- `error` — интерфейс с одним методом: `Error() string`

---

#### errors.Is vs errors.As:

**errors.Is:**
- Проверяет, **является ли ошибка** определённым типом/значением (сравнивает ошибки)
- Работает с **обёрнутыми ошибками** (`fmt.Errorf("... %w", err)`)
- Возвращает `true`/`false`

```go
if errors.Is(err, io.EOF) {
    fmt.Println("Достигнут конец файла")
}
```

**errors.As:**
- Проверяет, **содержит ли цепочка ошибок** ошибку определённого типа, и **извлекает её**
- Позволяет **обращаться к полям** конкретной ошибки
- Принимает указатель на переменную, в которую записывает найденную ошибку

```go
var pathErr *os.PathError
if errors.As(err, &pathErr) {
    fmt.Println("Ошибка с файлом:", pathErr.Path)
}
```

**Итого:**
- `errors.Is` — **сравнение**: "это та же ошибка?"
- `errors.As` — **извлечение и приведение типа**: "есть ли в цепочке ошибка этого типа? Дай её мне"

---

#### Обработка ошибок в конкурентном коде:

**Варианты:**
1. `if err != nil` — классическая проверка
2. **Обёртка:** `fmt.Errorf("context: %w", err)` — добавляем контекст
3. **Error Group** (`golang.org/x/sync/errgroup`) — ждём несколько горутин, собираем первую ошибку
4. **Контекст:** передаём контекст с отменой, если произошла ошибка
5. **Канал с ошибками:** отдельный канал для передачи ошибок из горутин

---

#### Паники и recover:

**Что такое panic?**
- Аварийная остановка программы
- Можно отловить с помощью `recover()` (но только в `defer`)

**Как отловить панику?**
```go
defer func() {
    if r := recover(); r != nil {
        fmt.Println("Recovered:", r)
    }
}()
```

**Можно ли отловить панику в main() или на уровне выше?**
- Да, если `recover()` вызван в `defer` **в той же горутине**, где произошла паника
- **НО:** каждая горутина имеет свой стек → panic в горутине не может быть отловлен в main (нужен `recover` внутри горутины)

---

#### Паники, которые нельзя отловить с помощью recover():

**FATAL ошибки (не паники!):**
- **Конкурентная запись в мапу** (`concurrent map writes`)
- **Переполнение памяти** (out of memory)
- **Переполнение стека** (stack overflow)
- **Запись в неинициализированный канал**

**Глобально:**
- Невозможно отловить то, что в **Runtime** — память закончилась, стек/куча переполнились

---

#### Deadlock:

**Что такое deadlock?**
- Ситуация, когда все горутины заблокированы и ждут друг друга
- Go детектирует deadlock и выдаёт ошибку: `fatal error: all goroutines are asleep - deadlock!`

**Пример:**
```go
ch := make(chan int)
ch <- 1  // Блокируется, т.к. нет получателя → deadlock
```

### 1.10. Garbage Collector (GC)

**Как работает GC в Go?**
- Go использует **неблокирующий** (concurrent), **трёхцветный**, **маркировочно-подметальный** (mark-sweep) сборщик мусора
- Главная фишка: работает **параллельно** с программой, минимизируя паузы (stop-the-world)

---

#### Три цвета объектов:

**1. Белый (White) — "Кандидат на удаление"**
- Объект ещё не обработан сборщиком
- По умолчанию все объекты белые при старте GC
- **В конце цикла GC все белые объекты удаляются**

**2. Серый (Gray) — "Обрабатывается"**
- Объект обнаружен как живой (достижим из корней)
- Но его дочерние объекты ещё не проверены
- Находится в очереди на обработку

**3. Чёрный (Black) — "Обработан"**
- Объект точно живой (достижим)
- Все его дочерние объекты проверены и тоже серые/чёрные
- Больше не будет сканироваться в этом цикле GC

---

#### Фазы работы GC:

**Фаза 1: Маркировка (Marking) — Concurrent**

**Шаг 1:** Начало маркировки (STW — очень короткая пауза, обычно < 1ms)
- Все горутины приостанавливаются
- **Корни (roots)** помечаются как серые:
  - Глобальные переменные
  - Локальные переменные в стеке каждой горутины
  - Регистры процессора
- Пауза заканчивается

**Шаг 2:** Параллельная маркировка
```
Корни: [a] (серый)
Белые: [b]

1. Берём 'a' из серой очереди
2. Сканируем 'a', находим ссылку на 'b'
3. 'a' становится ЧЁРНЫМ (обработан)
4. 'b' становится СЕРЫМ (добавляем в очередь)
   Серые: [b], Чёрные: [a]
   
5. Берём 'b' из серой очереди  
6. Сканируем 'b' — нет дочерних ссылок
7. 'b' становится ЧЁРНЫМ
   Серые: [], Чёрные: [a, b]
```

**Шаг 3:** Завершение маркировки (ещё одна короткая STW)
- Проверяем, не добавились ли новые ссылки во время маркировки
- Обрабатываем оставшиеся серые объекты

**Фаза 2: Подметание (Sweeping) — Concurrent**
- Белые объекты (не помеченные) → **удаляются**
- Чёрные объекты (помеченные) → **остаются**

---

#### Особенности:

**Stop the World (STW):**
- Пауза, когда все горутины останавливаются
- В Go STW очень короткие (< 1ms)

**Можно ли остановить GC?**
- Нельзя полностью остановить
- Можно задать `GOGC=-1` чтобы **отключить автозапуск** GC (но можно вызвать вручную через `runtime.GC()`)

**Проблемы при использовании GC:**
- Если создаётся слишком много объектов → GC часто запускается → может снижать производительность
- Решение: использовать Sync.Pool для переиспользования объектов

**Освободит ли GC память, если в мапе `map[string][]byte` удалить ключ?**
- **Да**, но только если больше нет других ссылок на значение

**Mark Assist:**
- Если GC не успевает чистить память быстрее, чем горутины запрашивают место на новые данные → горутины **помогают маркировать элементы** для GC (замедляют свою работу)

**Стек и куча:**
- **Стек** — локальные переменные, которые живут только в рамках функции (автоматически освобождается при выходе из функции, GC не нужен)
- **Куча** — динамически выделяемая память (объекты, на которые есть ссылки извне функции) → **GC работает с кучей**

---

### 1.11. Make() vs New()

**make():**
- Используется для **инициализации** встроенных типов: **slice, map, channel**
- Возвращает **инициализированное значение** (не указатель)
- Пример: `s := make([]int, 10)`

**new():**
- Выделяет память для типа, **обнуляет** её и возвращает **указатель** на неё
- Работает с **любыми типами** (структуры, встроенные типы и т.д.)
- Пример: `p := new(int)` → `p` имеет тип `*int`

**Итого:**
- `make` → slice, map, channel (инициализирует)
- `new` → любой тип (выделяет память, возвращает указатель)

---

### 1.12. GMP Model

**Что это?**
- Модель планировщика горутин в Go
- **G** — Goroutine (горутина)
- **M** — Machine (OS thread, системный поток)
- **P** — Processor (логический процессор, контекст выполнения)

**Как работает:**
- Горутины (G) выполняются на OS threads (M)
- P связывает G и M (P хранит очередь горутин)
- Количество P = `GOMAXPROCS` (по умолчанию = количество CPU cores)
- M может переключаться между P, если горутина блокируется (например, на I/O)

---

### 1.13. CAP Теорема

**Что это?**
- Требования к **распределённым системам**
- Три свойства: **C**onsistency (согласованность), **A**vailability (доступность), **P**artition tolerance (устойчивость к разделению)

**CAP теорема гласит:**
- В распределённой системе можно обеспечить **только 2 из 3 свойств** одновременно

**Варианты:**
1. **CP (Consistency + Partition tolerance):**
   - Берём актуальные данные, но жертвуем доступностью
   - Пример: банковские операции (данные должны быть строго согласованы)

2. **AP (Availability + Partition tolerance):**
   - Без лагов, но страдает целостность данных
   - Пример: социальные сети (можно показать устаревшие данные, но система всегда доступна)

3. **CA (Consistency + Availability):**
   - Возможно только в **нераспределённых** системах (один узел)
   - В реальных распределённых системах не достижимо

**Когда нельзя использовать AP?**
- Когда данные должны строго соблюдаться (банковские операции, финансы)

---

### 1.14. Шардирование

**Что такое шардирование?**
- **Шардирование** — горизонтальное разделение данных на части (шарды), распределенные по разным серверам
- Каждый шард содержит **подмножество данных** (не копию, а свою часть)

**Зачем нужно?**
- **Масштабируемость на запись**: один сервер Postgres не справляется с нагрузкой
- Решение проблемы ограничений одного узла

**Проблема с Postgres:**
- Postgres — реляционная БД, данные **тесно связаны** между собой
- Шардировать реляционную БД — **нетривиальная задача**
- Postgres **не умеет шардироваться из коробки** (в отличие от MongoDB)

---

#### Как работает шардирование Postgres?

**Схема:**
```
[Приложение] → [Координатор/Балансировщик] → [Шард 1] [Шард 2] [Шард 3]
                   (например, Citus)
```

**Принцип:**
1. Приложение **не подключается напрямую к Postgres**
2. Приложение идет в **координатор** (балансировщик)
3. Координатор **анализирует запрос** и определяет, в какой шард отправить
4. Координатор **маршрутизирует запрос** в нужный шард

**Способы дробления:**
- По **схемам** (каждый шард — отдельная схема)
- По **таблицам** (разные таблицы на разных шардах)
- По **строкам** (например, user_id % 3 → шард 0/1/2)

---

#### Правило: избегать кросс-шард запросов!

**Кросс-шард запрос** — запрос, затрагивающий данные из разных шардов.

**Проблемы:**
- **Убивает производительность** (нужно собрать данные с разных серверов)
- **Сложность реализации** (JOIN между шардами требует сетевых запросов)
- **Транзакции не работают** (ACID не гарантируется между шардами)

**Принцип проектирования:**
- **Все данные для одной операции** должны находиться в **одном шарде**
- Например: если шардируем по `user_id`, все данные пользователя (заказы, корзина, профиль) должны быть в одном шарде

---

#### Пример стратегий шардирования:

**1. Range-based (по диапазону):**
```
user_id 1-10000   → Shard 1
user_id 10001-20000 → Shard 2
user_id 20001-30000 → Shard 3
```

**2. Hash-based (по хэшу):**
```
hash(user_id) % 3:
  0 → Shard 1
  1 → Shard 2
  2 → Shard 3
```

**3. Geographic (по географии):**
```
Пользователи из Европы → EU Shard
Пользователи из Азии   → ASIA Shard
```

---

#### Когда НЕ нужно шардирование?

- Данные помещаются на одном сервере
- Нагрузка не критическая
- Нет специалистов для настройки и поддержки
- Можно решить проблему **репликацией** (master-slave для чтения)

---

#### MongoDB vs Postgres:

| **Особенность**       | **Postgres**                     | **MongoDB**                   |
|-----------------------|----------------------------------|-------------------------------|
| Шардирование из коробки | ❌ Нет (нужен Citus, pg_shard) | ✅ Да, встроено                |
| Миграции              | Болезненные на больших таблицах | Не нужны (NoSQL)              |
| Кросс-шард запросы    | Сложные, медленные              | Поддерживаются (с ограничениями)|
| ACID транзакции       | ✅ Поддерживаются                | ⚠️ Ограничены между шардами   |

**Вывод:** Если нужно горизонтальное масштабирование, MongoDB проще. Если нужны строгие транзакции, Postgres с шардированием (но это сложно).

## ЧАСТЬ 2: БАЗЫ ДАННЫХ

### 2.1. Транзакции и уровни изоляции

**READ UNCOMMITTED** — все возможные аномалии (грязь одна).

**Аномалии:**
- **Dirty Read** — чтение незакоммиченных данных
- **Non-repeatable Read** — разные результаты в одной транзакции (неповторяющееся чтение)
- **Phantom Read** — новые строки появляются

**READ COMMITTED** (по умолчанию в Postgres) — видны все завершённые транзакции.

**REPEATABLE READ** (MySQL по умолчанию, в Postgres предотвращает фантомное чтение в отличие от стандарта SQL).

**Примеры:**

**Read Committed:**
```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1; -- 100

-- (другая транзакция обновляет balance на 200 и делает COMMIT)

SELECT balance FROM accounts WHERE id = 1; -- 200 (изменён)
COMMIT;
```

**Repeatable Read:**
```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1; -- 100

-- (другая транзакция обновляет balance на 200 и делает COMMIT)

SELECT balance FROM accounts WHERE id = 1; -- 100 (не изменился)
COMMIT;
```

**Serializable:**
```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
UPDATE balance FROM accounts WHERE id = 1; -- блокировка
-- Обновить не вышло из-за сериализуемости
COMMIT;
```

**Механизм в Postgres:**
- Строка хранит несколько состояний (кто создал, кто удалил)
- Работает только со своим снапшотом
- Может возникнуть конфликт записей: ошибка `could not serialize access`

**Разница между Phantom Read и Non-repeatable Read:**
- **Phantom** — видим (или не видим) новые строки; то же самое состояние, но либо меньше, либо больше строк
- **Non-repeatable** — один и тот же набор строк, но значения в них разные (в одной 100, в другой 200)

**SERIALIZABLE:**
- Очень медленный, крайне редко используется в проде
- На этапе коммита Postgres строит граф пересечений зависимостей
- Одна транзакция получит результат, остальные — ошибки
- Это **НЕ** пессимистичные блокировки (пессимистичные заставляют в очередь выстраиваться и ждать)
- При SERIALIZABLE все транзакции параллельны, потом граф строится → одна успешна, остальные с ошибками
- Дорого: ещё один сетевой поход в БД из-за ретраев, 99 новых транзакций сломаются

**Оптимистичные блокировки:**
- Используем, когда конфликты редки, много читающих, мало пишущих, не критично если операция иногда откатывается

---

### 2.2. Оптимистичные и пессимистичные блокировки

**Пессимистичная блокировка (SELECT FOR UPDATE):**
```sql
-- Блокируем строку для изменения
BEGIN;
SELECT * FROM products WHERE id = 1 FOR UPDATE;
-- Никто другой не может изменить эту строку до COMMIT
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;
```

**Оптимистичная (версионность):**
```sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100),
    stock INT,
    version INT DEFAULT 0
);

-- При обновлении проверяем версию:
BEGIN;
SELECT id, stock, version FROM products WHERE id = 1;
-- version = 5

UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;
-- Если version изменилась другой транзакцией, UPDATE вернёт 0 строк

COMMIT;
```

**SELECT FOR UPDATE с очередями (3 сервиса без конфликтов):**
```sql
-- SKIP LOCKED пропускает заблокированные строки

-- СЕРВИС 1, 2, 3 конкурируют за задачи
BEGIN;

SELECT * FROM tasks
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;

UPDATE tasks SET status = 'processing' WHERE id = ...;

COMMIT;
```

### 2.3. Индексы

**Индекс** — структура данных, ускоряющая поиск в таблице.

**Основные типы (поверхностно):**

1. **B-tree** (сбалансированное дерево, по умолчанию) — для операций `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `IN`, `IS NULL`
   - Высота дерева O(log N), каждый узел содержит множество ключей, все листья на одном уровне
   ```sql
   CREATE INDEX idx_users_email ON users(email);
   CREATE INDEX idx_users_age ON users(age);
   -- Составной индекс:
   CREATE INDEX idx_users_name_age ON users(last_name, first_name);
   ```

2. **Hash** — только для `=`
   ```sql
   CREATE INDEX idx_users_id_hash ON users USING HASH(id);
   ```

3. **GiST** (Generalized Search Tree) — для геоданных, полнотекстового поиска
   ```sql
   CREATE INDEX idx_users_metadata ON users USING GIST(metadata);
   ```

4. **GIN** (Generalized Inverted Index) — для JSONB, массивов, полнотекстового поиска
   ```sql
   CREATE INDEX idx_posts_tags ON posts USING GIN(tags);
   ```

5. **Частичный индекс:**
   ```sql
   CREATE INDEX idx_active_users ON users(email) WHERE is_active = true;
   ```

6. **BRIN** (Block Range Index) — для очень больших таблиц с сортированными данными
   ```sql
   CREATE INDEX idx_logs_created ON logs USING BRIN(created_at);
   ```

**Частота использования:**
- B-tree — 95% случаев
- GIN — для JSON-полей, массивов, полнотекстового поиска
- HASH — только для равенства, но B-tree обычно лучше
- GiST — геоданные (PostGIS)
- BRIN — огромные таблицы логов с естественной сортировкой

**Глубже (вопросы с собесов):**

**"КАКИЕ ТИПЫ ИНДЕКСОВ ВЫ ЗНАЕТЕ?"**

Нужно уметь рассказать разницу:
- **Кластерные** и **некластерные**
- **Составные** индексы

**Кластерный индекс** — определяет физический порядок строк в таблице.
- Пример: `id` если `PRIMARY KEY`. Нужен пользователь 124 — используем кластерный индекс.

**Некластерный индекс** — отдельные структуры, хранят ссылку на место, где лежит полная строка.
- Пример: ищем строку с названием транзакции → индекс говорит "см. на 32 стр" → переходим туда.

**Покрывающий индекс (Covering Index)** — индекс содержит все данные полей в рамках запроса.
- Поиск по некластерному индексу: перебираем, потом идём в кластерный индекс → достаём остальные данные.
- Если индекс уже содержит все нужные поля (например, `SELECT email FROM users WHERE email = '...'` и индекс включает `email`), то не нужно идти в базу — индекс сразу даст результат.

**Разница: частично vs полностью покрывающий:**
- **Частично покрывающий** — индекс содержит **часть** нужных полей, но не все. Нужен дополнительный поход в таблицу.
  - Пример: `CREATE INDEX idx ON users(email)`, запрос `SELECT email, name WHERE email = '...'` → индекс даст email, но name придется брать из таблицы.
- **Полностью покрывающий** — индекс содержит **все** поля из `SELECT` и `WHERE`. Не нужен поход в таблицу!
  - Пример: `CREATE INDEX idx ON users(email, name)`, запрос `SELECT email, name WHERE email = '...'` → всё берется из индекса.

**Можно ли создать индекс к несуществующему полю?**
- **Нет**, индекс можно создать только на **существующие** поля таблицы.
- Сначала нужно добавить поле через `ALTER TABLE`, затем создать индекс.

**Составные индексы:**
- Порядок колонок **важен**.
- Пример: `CREATE INDEX idx_users_name_age ON users(last_name, first_name)` — эффективен для запросов по `last_name` или `last_name + first_name`, но не для только `first_name`.

**Если индексов нет:**
- Будет перебираться все записи (Seq Scan).

**На собесах обычно хотят услышать:**
- Про саму структуру (B-tree, Hash и т.д.)
- Кластерный/некластерный
- Составной/несоставной

### 2.3.1. Lost Update (потерянное обновление)

**Что это?**
- Классическая проблема конкурентного доступа в БД, когда изменения одной транзакции полностью теряются из-за перезаписи другой транзакцией

**Сценарий Lost Update:**

| Время | Транзакция 1 (перевод 50$) | Транзакция 2 (начисление 10%) | Баланс в БД |
|-------|----------------------------|-------------------------------|-------------|
| 1 | Читает баланс: 100$ | | 100$ |
| 2 | | Читает баланс: 100$ | 100$ |
| 3 | Вычисляет: 100 - 50 = 50$ | | 100$ |
| 4 | | Вычисляет: 100 + 10 = 110$ | 100$ |
| 5 | Записывает: 50$ | | 50$ |
| 6 | COMMIT | | 50$ |
| 7 | | Записывает: 110$ | 110$ |
| 8 | | COMMIT | 110$ |

**Итог:** Перевод 50$ потерялся! Вместо правильного результата (100 - 50 + 10 = 60$) получили 110$.

**Как избежать Lost Update?**
1. Использовать **атомарные операции:**
   ```sql
   UPDATE accounts SET balance = balance - 50 WHERE id = 1;
   ```
   (вместо `SELECT → вычисление → UPDATE`)

2. Использовать **блокировки:**
   - Пессимистичные: `SELECT FOR UPDATE`
   - Оптимистичные: версионность (см. раздел 2.2)

3. Повысить **уровень изоляции транзакций** (REPEATABLE READ или SERIALIZABLE)

### 2.3.2. Нормализация и денормализация

**Нормализация:**
- Разделение данных по таблицам (избавление от дубликатов)
- **Плюсы:** меньше аномалий, избавление от избыточных данных, проще поддерживать целостность
- **Минусы:** больше JOIN'ов → медленнее запросы

**Денормализация:**
- Скидывание данных в одну таблицу (дублирование данных)
- **Плюсы:** быстрее запросы (меньше JOIN'ов)
- **Минусы:** больше аномалий, избыточность данных, сложнее поддерживать целостность

**Когда использовать?**
- **Нормализация** — для OLTP (transactional) систем, где важна целостность данных
- **Денормализация** — для OLAP (analytical) систем, где важна скорость чтения

### 2.3.3. DELETE vs TRUNCATE

**DELETE:**
- Удаляет строки **по условию** (`WHERE`)
- Можно откатить (работает в транзакции)
- **Ведёт лог действий** по удалению (медленнее)
- Триггеры срабатывают

**TRUNCATE:**
- Очищает **всю таблицу** (сохраняя структуру)
- **Без возможности отката** (не работает в транзакции в некоторых БД)
- Не ведёт лог → **очень быстрый**
- Триггеры **не срабатывают**

**Итого:**
- `DELETE` — для выборочного удаления с возможностью отката
- `TRUNCATE` — для полной очистки таблицы (быстро, но без отката)

---

### 2.3.4. UNION vs UNION ALL vs JOIN

**UNION:**
- Объединяет результаты двух запросов **в высоту** (добавляет строки)
- **Исключает дубликаты**
- Работает только с таблицами **одинаковой структуры** (одинаковое количество колонок и типы)

**UNION ALL:**
- То же, что UNION, но **не удаляет дубликаты** → быстрее

**JOIN:**
- Объединяет две таблицы **в ширину** (добавляет колонки)
- Может работать с таблицами разной структуры
- Типы: INNER JOIN, LEFT JOIN, RIGHT JOIN, FULL JOIN

**Итого:**
- `UNION` / `UNION ALL` → расширяет таблицу **в высоту** (строки)
- `JOIN` → расширяет таблицу **в ширину** (колонки)

### 2.4. Типы баз данных (CAP теорема?)

**Все мы знаем Postgres (стандарт). Зачем нам другие базы использовать? В 70% хватит Postgres.**

Но когда работаем под очень высокой нагрузкой:

#### Postgres — реляционная БД
- Все данные строго связаны между собой
- Полная транзакционная целостность (ACID)
- Нельзя потерять данные просто так

**Проблемы при высокой нагрузке:**
- Добавлять поле в таблицу на 1 млрд строк → проблема с блокировками и миграциями (накатить в рантайм новую колонку — больно)
- Масштабируемость на запись (сервер не резтновый)
- Шардировать реляционную БД — нетривиальная задача (данные тесно связаны)

**Шардирование:**
- Все данные должны идти в тот же шард
- Не допускать кросс-шард запросы (убивает производительность, сложно реализовать)
- Как работает? Появляется координатор (балансировщик): сервис открывает коннект не напрямую в Postgres, а на балансировщик → он сам понимает, в какой шард отправить запрос
- Дробление может быть по схемам или по таблицам (зависит от задачи)
- Подстроить логику сложно: нужна высокая нагрузка и специалисты

---

#### MongoDB — NoSQL (документная база)

**Что такое MongoDB:**
- **Документная NoSQL БД** (хранит данные в JSON-подобном формате BSON)
- Нет жёсткой схемы → можно менять структуру документов "на лету"
- Из коробки умеет **шардироваться** (горизонтальное масштабирование)
- Реплики для отказоустойчивости

**Структура:**
```javascript
// Коллекция "users" (аналог таблицы в SQL)
{
  "_id": ObjectId("507f1f77bcf86cd799439011"),
  "name": "Alice",
  "age": 30,
  "settings": {
    "theme": "dark",
    "notifications": true
  },
  "tags": ["admin", "premium"]
}

// В той же коллекции может быть документ с другой структурой!
{
  "_id": ObjectId("507f1f77bcf86cd799439012"),
  "name": "Bob",
  "email": "bob@example.com",
  "premium": true
  // Нет поля "age" и "settings" — это нормально!
}
```

**Основные операции:**
```javascript
// Вставка
db.users.insertOne({name: "Charlie", age: 25})

// Поиск
db.users.find({age: {$gt: 20}})  // age > 20
db.users.find({"settings.theme": "dark"})  // вложенные поля

// Обновление
db.users.updateOne(
  {name: "Alice"},
  {$set: {age: 31}}
)

// Удаление
db.users.deleteOne({name: "Bob"})
```

**Индексы в MongoDB:**
```javascript
// Обычный индекс
db.users.createIndex({name: 1})  // 1 = ascending

// Составной индекс
db.users.createIndex({name: 1, age: -1})

// Индекс по вложенному полю
db.users.createIndex({"settings.theme": 1})

// Текстовый индекс (полнотекстовый поиск)
db.articles.createIndex({content: "text"})
```

**Агрегация (аналог GROUP BY):**
```javascript
db.orders.aggregate([
  {$match: {status: "completed"}},  // WHERE
  {$group: {
    _id: "$user_id",               // GROUP BY user_id
    total: {$sum: "$amount"}       // SUM(amount)
  }},
  {$sort: {total: -1}},            // ORDER BY total DESC
  {$limit: 10}                     // LIMIT 10
])
```

**Транзакции в MongoDB (с версии 4.0):**
```javascript
const session = client.startSession();
session.startTransaction();

try {
  await db.accounts.updateOne(
    {_id: 1}, 
    {$inc: {balance: -100}}, 
    {session}
  );
  await db.accounts.updateOne(
    {_id: 2}, 
    {$inc: {balance: 100}}, 
    {session}
  );
  
  await session.commitTransaction();
} catch (error) {
  await session.abortTransaction();
  throw error;
} finally {
  session.endSession();
}
```

**Когда использовать MongoDB:**
- Хранение **неструктурированных данных**: новости, посты, комментарии, профили пользователей (где структура может часто меняться)
- Поиск по **вложенным полям** (JSON): `user.settings.theme`, `post.tags`
- Быстрое хранение логов, событий (где не важна строгая схема)
- Когда нужно горизонтальное масштабирование (шардирование) без сложной настройки
- Прототипирование (не нужно продумывать схему БД заранее)

**Когда НЕ использовать MongoDB:**
- Нужны сложные транзакции с множественными JOIN
- Критически важна строгая целостность данных
- Много связей между сущностями (лучше SQL с внешними ключами)
- Нужны сложные агрегации (SQL с оконными функциями удобнее)

---

#### ClickHouse — колоночная БД
- Для аналитических запросов на 1 млрд строк
- Пример: таблица платежей на 1 млрд строк, хотим узнать, сколько денег потратили за год
  - Postgres читала бы каждую строку → минуты и гигабайты данных
  - В ClickHouse данные каждой колонки лежат отдельно на диске → он прочитает только нужную колонку → 1 секунда или даже миллисекунды

**Особенности:**
- Аналитические операции очень быстрые
- UPDATE и DELETE **бьют сильно по производительности** → предпочитание append-only (пишем батчами)
- Сжатие данных (чтобы меньше места занимали)
- Когда не нужно постоянно что-то изменять — для аналитических запросов (OLAP)
- Пишем в ClickHouse батчами (проще, чем каждую строку гонять)

---

#### Time Series DB (TimescaleDB, Prometheus, VictoriaMetrics)
- Для метрик и логов
- Пример: 1000 серверов, каждый каждые 60 секунд посылает метрики → ~86 500 000 записей в сутки
- Postgres от такой нагрузки захлебнётся
- Специализация: пишут в конец, излишняя логика не нужна, специальная задача — сжимать данные
- Довольно специфичные, хранят данные N дней (например, 30)
- Сама будет хранить данные по timestamp
- Индексирование идёт, нет постоянных перестроений

---

#### Графовые БД (Amazon Neptune, Neo4j)
- Для задач с множественными связями: найти друзей друзей, которым нравятся котики, на 5 уровне вложенности
- В реляционной БД — 5 JOIN'ов → очень плохая сложность (O(N * K))
- Графовая БД: узлы и связи между ними. **Связь — не внешний ключ, а прямой указатель в памяти** (как ссылка в C++)
- Запрос с 4 JOIN'ами выполняется за константное время в графовых БД, а в Postgres — очень долго
- Идёшь по стрелочкам
- Актуально для антифрод-систем в финтехе: показывает, кто мошенник, а кто нет

---

#### Векторные БД
- Логика сложная
- Нужны для ML (машинного обучения)
- Рекомендательные системы, компьютерное зрение
- Вычисляем "на что это похоже"

---

**Итого: где какую БД юзать?**
- **Реляционные (Postgres, MySQL)** — где важны строгие связи между записями (банковские счета, логины)
- **Time Series** — для метрик
- **Графовые** — для построений (кто чей друг)
- **Векторные** — вычисляем "на что похоже" (компьютерное зрение)
- **Базовые случаи** — в 70% используют Postgres/MySQL

### 2.5. Redis и кэширование

**Redis и кэширование — сложная тема. Ошибка может стоить многих денег. Есть определённые паттерны.**

#### Паттерны чтения (Read)

**Cache-Aside (Lazy Loading):**
1. Хотим получить данные → идём в Redis, спрашиваем, есть ли значения
2. Если промахнулись → идём в Postgres, достаём данные, ставим в Redis
3. Это некий lazy loading

**Проблема: инвалидация кэша**
- В Postgres обновлено имя пользователя, а в Redis закэшировано старое
- Решение: в логике сервиса, который обновляет данные в Postgres, нужно **удалить данные из Redis по ключу** (или обновить значение)
- Если кэшируем состояние пользователя → при обновлении данных пользователя **выносить его из Redis** или обновлять значение

**Сквозное чтение (Read-Through):**
- Хотим получить данные из Redis, если их нет → заставляем Redis доставлять их из Postgres
- Redis нужно заставлять делать (сам он это не умеет из коробки)
- Любой механизм может ломаться → дополнительная точка отказа
- Дополнительная нагрузка на сам Redis (базовый Redis однопоточный)

---

#### Паттерны записи (Write)

**Write-Through (сквозная запись):**
- Пишем в Postgres и одновременно в Redis
- Redis синхронно складывает в Postgres
- Redis однопоточный

**Write-Behind (отложенная запись):**
- Для смелых в highload, где скорость записи важнее надёжности (лайки, счётчики просмотров)
- Приложение пишет в Redis → он отвечает "всё ок" → фоновый процесс переносит из Redis в БД
- Максимум скорости, но **минусы: потеря данных или рассинхрон** (в Redis 110, в БД 100)
- Настройки персистентности у Redis: есть дамп, есть форк

---

#### Проблемы с кэшированием

**1. Cache-Aside (Lazy Loading) — проблема с производительностью на холодном старте:**
- Изначально нет данных → первое время докидывать в базу приходится
- Решение: **прогрев кэша** — запросить наиболее востребованные данные

**2. Thundering Herd (гром стада):**
- 1000 запросов ломанулись в БД, а данных нет (сложный SELECT с 1000000 JOIN'ов)
- Решение 1 (элегантный, простой): **Singleflight** — библиотека
  - По ключу понимаем, что пришло за одними и теми же данными
  - Из 1000 запросов 1 запрос пойдёт в базу, остальные в очереди в ожидании будут стоять
  - Как только 1 ответ получает, все остальные 999 тоже получают
  - **Нюанс:** работает для 1 сервиса и 1 инстанса. Если 2 инстанса сервиса → будет 2 запроса (по одному на инстанс)
- Решение 2 (когда нужно гарантировать): **блокировки на уровне Redis**
  - Блокируем строку → пытаемся достать
  - Pulling в цикле — дёргать каждый раз
  - **Нюансы с отказоустойчивостью:** запрос пошёл и завис → все остальные запросы вместе с ним тоже зависли

---

### 2.6. ORM (когда нужен, когда не нужен)

**ORM** — штуковина, позволяющая оперировать с объектами БД как с полноценными объектами (`SELECT`, `Find`, `Update`).

**Когда ORM окей:**
- Маленькие проекты
- Небольшая нагрузка
- Написали SELECT → получили структуру → вызвали методы → они сходили в БД → всё замапилось на структуру

**Проблемы:**
- Работает через **рефлексию** → может быть дорого
- Из-за шаблонных запросов могут возникать неоптимальности: **N+1 запросы** O(N+1) → загружает БД

**Итого:**
- Нужен для небольших проектов, небольшой нагрузки
- Для highload лучше писать SQL руками

## ЧАСТЬ 3: ПАТТЕРНЫ CONCURRENCY

*Основные паттерны конкурентности в Go для построения надёжных систем*

### 3.1. Fan-Out / Fan-In

**Что это?**
- **Fan-Out** — распределение работы между множеством горутин (workers)
- **Fan-In** — сбор результатов от множества горутин в один канал

**Fan-Out (распределение):**
```go
func fanOut(in <-chan int, workers int) []<-chan int {
    outs := make([]<-chan int, workers)
    
    for i := 0; i < workers; i++ {
        out := make(chan int)
        outs[i] = out
        
        go func(workerID int) {
            defer close(out)
            for data := range in {
                // Обработка данных
                result := processData(data, workerID)
                out <- result
            }
        }(i)
    }
    
    return outs
}
```

**Fan-In (объединение):**
```go
func fanIn(channels ...<-chan int) <-chan int {
    var wg sync.WaitGroup
    out := make(chan int)
    
    // Функция для копирования из одного канала в out
    output := func(ch <-chan int) {
        defer wg.Done()
        for val := range ch {
            out <- val
        }
    }
    
    wg.Add(len(channels))
    for _, ch := range channels {
        go output(ch)
    }
    
    // Закрываем out когда все горутины завершатся
    go func() {
        wg.Wait()
        close(out)
    }()
    
    return out
}
```

**Полный пример:**
```go
func fanOutFanInExample() {
    // Источник данных
    source := make(chan int)
    go func() {
        for i := 1; i <= 20; i++ {
            source <- i
        }
        close(source)
    }()
    
    // Fan-Out: распределяем работу на 4 воркера
    workers := 4
    workerChannels := fanOut(source, workers)
    
    // Fan-In: собираем результаты
    results := fanIn(workerChannels...)
    
    // Обработка результатов
    for result := range results {
        fmt.Printf("Result: %d\n", result)
    }
}
```

**Когда использовать:**
- Когда задача может быть разбита на независимые подзадачи
- Когда нужно распараллелить обработку данных
- Когда важна скорость обработки большого объема данных

---

### 3.2. Worker Pool (Пул воркеров)

**Что это?**
- Фиксированное количество горутин (workers), обрабатывающих задачи из общей очереди
- Контролируемый параллелизм (не создаём миллион горутин)

**Простой пул воркеров:**
```go
func workerPoolExample() {
    jobs := make(chan int, 100)
    results := make(chan int, 100)
    
    // Создаем пул из 3 воркеров
    for w := 1; w <= 3; w++ {
        go worker(w, jobs, results)
    }
    
    // Отправляем задания
    for j := 1; j <= 10; j++ {
        jobs <- j
    }
    close(jobs)
    
    // Собираем результаты
    for r := 1; r <= 10; r++ {
        fmt.Println(<-results)
    }
}

func worker(id int, jobs <-chan int, results chan<- int) {
    for job := range jobs {
        fmt.Printf("Worker %d processing job %d\n", id, job)
        time.Sleep(time.Second)  // имитация работы
        results <- job * 2
    }
}
```

**Продвинутый Worker Pool с динамическим управлением:**
```go
type WorkerPool struct {
    workers   int
    jobQueue  chan func()
    semaphore chan struct{}
}

func NewWorkerPool(workers int) *WorkerPool {
    return &WorkerPool{
        workers:   workers,
        jobQueue:  make(chan func()),
        semaphore: make(chan struct{}, workers),
    }
}

func (wp *WorkerPool) Submit(task func()) {
    wp.jobQueue <- task
}

func (wp *WorkerPool) Run() {
    for i := 0; i < wp.workers; i++ {
        go wp.worker()
    }
}

func (wp *WorkerPool) worker() {
    for task := range wp.jobQueue {
        wp.semaphore <- struct{}{}  // захватываем слот
        task()
        <-wp.semaphore             // освобождаем слот
    }
}
```

**Когда использовать:**
- Когда нужно ограничить количество параллельных операций
- При работе с внешними API (ограничение на rate limit)
- При обработке пула соединений к БД

---

### 3.3. Rate Limiter (Ограничитель скорости)

**Что это?**
- Паттерн для ограничения количества операций в единицу времени
- Защита от перегрузки системы

**Реализация через канал:**
```go
type RateLimiter struct {
    interval time.Duration
    tokens   chan time.Time
    stop     chan struct{}
}

func NewRateLimiter(rate int, interval time.Duration) *RateLimiter {
    rl := &RateLimiter{
        interval: interval,
        tokens:   make(chan time.Time, rate),
        stop:     make(chan struct{}),
    }
    
    // Заполняем токены
    for i := 0; i < rate; i++ {
        rl.tokens <- time.Now()
    }
    
    // Запускаем пополнение токенов
    go rl.refill()
    
    return rl
}

func (rl *RateLimiter) refill() {
    ticker := time.NewTicker(rl.interval / time.Duration(cap(rl.tokens)))
    defer ticker.Stop()
    
    for {
        select {
        case <-ticker.C:
            select {
            case rl.tokens <- time.Now():
            default: // Пропускаем если полный
            }
        case <-rl.stop:
            return
        }
    }
}

func (rl *RateLimiter) Wait() {
    <-rl.tokens  // блокируется, если нет токенов
}

func (rl *RateLimiter) Stop() {
    close(rl.stop)
}
```

**Использование:**
```go
limiter := NewRateLimiter(5, time.Second)  // 5 запросов в секунду
defer limiter.Stop()

for i := 0; i < 20; i++ {
    limiter.Wait()  // ждем токен
    go makeAPICall(i)
}
```

**Когда использовать:**
- API с ограничением на количество запросов (rate limit)
- Защита от DDoS
- Контроль нагрузки на базу данных

### 3.4. Circuit Breaker (Предохранитель)

**Что это?**
- Паттерн для предотвращения каскадных сбоев
- При множественных ошибках "размыкает цепь" и перестаёт делать запросы

**Состояния:**
- **Closed** (закрыт) — запросы проходят нормально
- **Open** (разомкнут) — запросы блокируются, возвращается ошибка сразу
- **Half-Open** (полуоткрыт) — пробные запросы для проверки восстановления

**Упрощенная реализация:**
```go
type CircuitBreaker struct {
    maxFailures  int
    resetTimeout time.Duration
    failures     int
    lastFailTime time.Time
    state        string  // "closed", "open", "half-open"
    mu           sync.Mutex
}

func NewCircuitBreaker(maxFailures int, resetTimeout time.Duration) *CircuitBreaker {
    return &CircuitBreaker{
        maxFailures:  maxFailures,
        resetTimeout: resetTimeout,
        state:        "closed",
    }
}

func (cb *CircuitBreaker) Call(fn func() error) error {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    
    // Проверяем состояние
    if cb.state == "open" {
        if time.Since(cb.lastFailTime) > cb.resetTimeout {
            cb.state = "half-open"
        } else {
            return fmt.Errorf("circuit breaker is open")
        }
    }
    
    // Вызываем функцию
    err := fn()
    
    if err != nil {
        cb.failures++
        cb.lastFailTime = time.Now()
        
        if cb.failures >= cb.maxFailures {
            cb.state = "open"
        }
        return err
    }
    
    // Успех — сброс счетчика
    cb.failures = 0
    cb.state = "closed"
    return nil
}
```

**Когда использовать:**
- Вызовы внешних API (если они недоступны, не долбим их)
- Микросервисная архитектура (защита от каскадных сбоев)
- Работа с нестабильными сервисами

### 3.5. Health Checker (Проверка здоровья)

**Что это?**
- Периодическая проверка доступности сервиса
- Обычно endpoint `/health` для мониторинга

**Реализация:**
```go
type HealthChecker struct {
    checks   map[string]func() error
    interval time.Duration
    mu       sync.RWMutex
}

func NewHealthChecker(interval time.Duration) *HealthChecker {
    return &HealthChecker{
        checks:   make(map[string]func() error),
        interval: interval,
    }
}

func (hc *HealthChecker) RegisterCheck(name string, check func() error) {
    hc.mu.Lock()
    defer hc.mu.Unlock()
    hc.checks[name] = check
}

func (hc *HealthChecker) Start(ctx context.Context) {
    ticker := time.NewTicker(hc.interval)
    defer ticker.Stop()
    
    for {
        select {
        case <-ticker.C:
            hc.runChecks()
        case <-ctx.Done():
            return
        }
    }
}

func (hc *HealthChecker) runChecks() {
    hc.mu.RLock()
    defer hc.mu.RUnlock()
    
    for name, check := range hc.checks {
        if err := check(); err != nil {
            log.Printf("Health check failed: %s, error: %v", name, err)
        }
    }
}
```

**Использование:**
```go
hc := NewHealthChecker(10 * time.Second)

// Регистрируем проверки
hc.RegisterCheck("database", func() error {
    return db.Ping()
})

hc.RegisterCheck("redis", func() error {
    return redis.Ping()
})

ctx := context.Background()
go hc.Start(ctx)
```

**Когда использовать:**
- Мониторинг зависимостей (БД, кэш, внешние API)
- Kubernetes liveness/readiness probes
- Автоматическое восстановление сервисов

### 3.6. Retryer (Повторитель с backoff)

**Что это?**
- Автоматический повтор операции при ошибке
- С экспоненциальной задержкой (exponential backoff)

**Реализация:**
```go
func RetryWithBackoff(
    ctx context.Context,
    maxRetries int,
    initialDelay time.Duration,
    fn func() error,
) error {
    var err error
    delay := initialDelay
    
    for attempt := 0; attempt < maxRetries; attempt++ {
        // Проверяем контекст
        select {
        case <-ctx.Done():
            return ctx.Err()
        default:
        }
        
        // Пробуем выполнить
        err = fn()
        if err == nil {
            return nil  // Успех!
        }
        
        // Если не последняя попытка — ждем
        if attempt < maxRetries-1 {
            log.Printf("Attempt %d failed: %v, retrying in %v", attempt+1, err, delay)
            
            select {
            case <-time.After(delay):
                delay *= 2  // Экспоненциальный backoff
            case <-ctx.Done():
                return ctx.Err()
            }
        }
    }
    
    return fmt.Errorf("max retries exceeded: %w", err)
}
```

**Использование:**
```go
ctx := context.Background()

err := RetryWithBackoff(ctx, 5, time.Second, func() error {
    resp, err := http.Get("https://api.example.com/data")
    if err != nil {
        return err
    }
    defer resp.Body.Close()
    
    if resp.StatusCode != 200 {
        return fmt.Errorf("bad status: %d", resp.StatusCode)
    }
    return nil
})

if err != nil {
    log.Fatalf("Failed after retries: %v", err)
}
```

**Когда использовать:**
- HTTP-запросы к нестабильным API
- Работа с базой данных (временные сбои)
- Отправка сообщений в очередь
- Любые операции, которые могут временно не работать

### 3.7. Дополнительные паттерны

#### Pipeline (Конвейер)
```go
// Этап 1: генерация чисел
gen := func(nums ...int) <-chan int {

    go func() {
        for _, n := range nums {
            out <- n

// Этап 2: умножение
multiply := func(in <-chan int, factor int) <-chan int {

```

#### Семафор (ограничение параллелизма)
```go
sem := make(chan struct{}, 3)  // Максимум 3 горутины одновременно

for i := 0; i < 10; i++ {
    sem <- struct{}{}  // Захватываем слот
    
    go func(id int) {
        defer func() { <-sem }()  // Освобождаем слот
        
        fmt.Printf("Worker %d started\n", id)
        time.Sleep(time.Second)
        fmt.Printf("Worker %d done\n", id)
    }(i)
}
```

### Best Practices для Concurrency:

1. **Всегда используй `context.Context`** для отмены и таймаутов
2. **Закрывай каналы только отправителем** (producer)
3. **Используй `select` с `default`** для неблокирующих операций
4. **Ограничивай параллелизм** (не создавай миллион горутин)
5. **Используй `sync.Pool`** для переиспользования объектов
6. **Мониторь горутины**: `runtime.NumGoroutine()`
7. **Всегда используй `defer wg.Done()`** в горутинах с WaitGroup

## ЧАСТЬ 4: РАСПРЕДЕЛЁННЫЕ СИСТЕМЫ

### 4.1. API Gateway

**Что это?**
- Входной шлюз для всех запросов к микросервисам
- Работает как **балансировщик** и **роутер**

**Функции:**
- **Маршрутизация** — определяет, к какому микросервису направить запрос
- **Балансировка нагрузки** — распределяет запросы между копиями сервиса
- **Аутентификация и авторизация** — проверяет права доступа
- **Rate limiting** — ограничивает количество запросов
- **Агрегация** — может собирать данные от нескольких микросервисов в один ответ

**Примеры:** Kong, AWS API Gateway, NGINX, Traefik

---

### 4.2. Идемпотентность

**Что это?**
- Свойство операции, при котором **многократное выполнение** даёт тот же результат, что и однократное

**Простая аналогия:**
- **Неидемпотентная операция:** Нажать кнопку "купить" 5 раз → 5 одинаковых заказов
- **Идемпотентная операция:** Нажать кнопку "лайк" 5 раз → всё равно 1 лайк

**Зачем нужна?**
- В распределённых системах запросы могут дублироваться (сетевые проблемы, ретраи)
- Идемпотентность гарантирует, что операция выполнится **только один раз**, даже если запрос пришёл несколько раз

**Как реализовать?**
- **Идентификатор запроса** (idempotency key) — клиент генерирует уникальный ID для каждой операции
- Сервер сохраняет ID выполненных операций → если запрос с тем же ID приходит снова, возвращает результат первого выполнения

## ЧАСТЬ 5: БРОКЕРЫ СООБЩЕНИЙ

### 5.1. Зачем нужны брокеры?

**Что такое брокер сообщений?**
- Промежуточное программное обеспечение для **асинхронного взаимодействия** между сервисами

**Зачем использовать брокеры?**
- **Асинхронность:** можем закинуть сообщение в брокер и заниматься своими делами, а не ждать пока сервис что-то ответит
- **Буферизация:** брокер хранит сообщения, если получатель недоступен
- **Отказоустойчивость:** если получатель упал, сообщения не теряются

**Почему нельзя сразу перекинуть данные между сервисами?**
- Получатель может быть недоступен → данные потеряются
- Синхронная связь → отправитель блокируется, ждёт ответа
- Нет буферизации → при высокой нагрузке получатель может не справиться

**Минусы брокеров:**
1. **Дополнительная задержка** (latency)
2. **Усложнение логики** (overhead)
3. **Дополнительная точка отказа** (может упасть и сломать всё)
4. **Инструмент, который тоже нужно поддерживать** и сопровождать

---

### 5.2. RabbitMQ

**Модель:** **Push** (брокер **проталкивает** сообщения в consumers)

**Архитектура:**
- **Exchange** — принимает сообщения от producers и маршрутизирует их в очереди
- **Queue** — очередь сообщений, из которой consumers читают
- **Binding** — связь между exchange и queue (routing rules)

**Хранение сообщений:**
- Сообщения находятся в **оперативной памяти** (по умолчанию)
- Если RabbitMQ сдохнет → всё потеряется (если не настроить персистентность)

---

#### Exchange Types (типы обменников):

**1. Direct Exchange (прямой обменник):**
- Отправляет сообщения в очереди, чей `routing_key` **полностью совпадает** с ключом сообщения
- Аналогия: точно по адресу (как почтовый индекс)

**2. Fanout Exchange (веерный обменник):**
- Рассылает сообщения **во все** привязанные очереди (broadcast)
- Аналогия: радио-трансляция (всем кто слушает)
- `routing_key` игнорируется

**3. Topic Exchange (тематический обменник):**
- Маршрутизация по **шаблонам** с wildcards:
  - `*` (звёздочка) — заменяет **ОДНО** слово
  - `#` (хеш) — заменяет **НОЛЬ или более** слов
- Аналогия: подписка на тэги/категории
- Примеры шаблонов:
  - `payment.*` → `payment.success`, `payment.failed`
  - `*.processed` → `order.processed`, `user.processed`
  - `log.#` → `log`, `log.error`, `log.error.database`

**4. Headers Exchange (обменник по заголовкам):**
- Маршрутизация по **заголовкам сообщения** (headers), а не `routing_key`
- Аргументы:
  - `x-match: all` — **ВСЕ** заголовки должны совпасть
  - `x-match: any` — **ЛЮБОЙ** заголовок должен совпасть
- Аналогия: фильтр по свойствам/атрибутам

**5. Default Exchange (обменник по умолчанию):**
- Специальный встроенный exchange с именем `""` (пустая строка)
- Работает как Direct exchange, где `routing_key = имя очереди`

---

### 5.3. Kafka

**Модель:** **Pull** (consumers **сами тянут** сообщения из Kafka)

**Архитектура:**
- **Topic** — категория сообщений (аналог таблицы)
- **Partition** — раздел внутри топика (для распределения нагрузки)
- **Offset** — уникальный номер сообщения внутри партиции (позиция)
- **Consumer Group** — группа consumers, которые читают из одного топика

**Хранение сообщений:**
- Сообщения хранятся на **диске** (не в оперативной памяти)
- Можно настроить **retention policy** (как долго хранить)

---

#### Из чего состоит топик в Kafka?

**Топик состоит из партиций (partitions):**
- Каждая партиция — упорядоченная последовательность сообщений
- Партиции распределены по разным узлам (для масштабируемости)

**Зачем партиции?**
- **Масштабируемость:** разные партиции читаются разными consumers параллельно
- **Упорядоченность:** в рамках **одной партиции** порядок гарантируется

---

#### Гарантирует ли Kafka очередность сообщений?

- **В рамках одной партиции** — **ДА**
- **Между партициями** — **НЕТ**

**Итого:** если важен порядок сообщений → все сообщения одной категории должны идти в одну партицию (например, по ключу user_id)

---

#### Гарантии доставки:

**1. At most once (максимум один раз):**
- Сообщение может быть потеряно
- Дубликатов нет

**2. At least once (минимум один раз):**
- Сообщение гарантированно доставлено
- Могут быть дубликаты

**3. Exactly once (ровно один раз):**
- Сообщение доставлено ровно один раз, без дубликатов
- Самый сложный и дорогой режим

---

#### Оффсеты (Offsets):

**Что это?**
- Позиция consumer'а в партиции (какое сообщение он прочитал последним)

**Как работает?**
- Consumer читает сообщения и **сохраняет оффсет** (commit offset)
- При перезапуске consumer начинает читать с последнего сохранённого оффсета

**Consumer Lag:**
- Разница между последним сообщением в партиции и текущим оффсетом consumer'а
- Если lag большой → consumer не успевает обрабатывать сообщения

---

### 5.4. RabbitMQ — детальный разбор

**Модель:** **Push** (брокер **проталкивает** сообщения в consumers)

**Архитектура:**
- **Producer** — отправляет сообщения в **Exchange**
- **Exchange** — маршрутизирует сообщения в **Queue** по **Routing Key**
- **Queue** — хранит сообщения до обработки
- **Consumer** — получает сообщения из Queue

```
Producer → Exchange → Queue → Consumer
              ↓ (routing key)
```

---

#### Типы Exchange (4 типа)

**1. Direct Exchange:**
```
Routing Key = "error" → Queue "errors"
Routing Key = "info"  → Queue "logs"
```
- Сообщение идёт в Queue, где **routing key точно совпадает**
- Use case: логирование по уровням (error, warn, info)

**2. Topic Exchange:**
```
Routing Key = "user.created"  → Queue "notifications"
Routing Key = "user.deleted"  → Queue "analytics"
Routing Key = "order.created" → Queue "orders"

Pattern: "user.*"  → получит все события user
Pattern: "*.created" → получит все события created
```
- Поддерживает **wildcards**: `*` (одно слово), `#` (несколько слов)
- Use case: гибкая маршрутизация событий

**3. Fanout Exchange:**
```
Producer → Fanout Exchange → Queue 1 (emails)
                           → Queue 2 (SMS)
                           → Queue 3 (push)
```
- Отправляет сообщение **во ВСЕ** подключенные очереди (broadcast)
- Routing key игнорируется
- Use case: уведомления через несколько каналов

**4. Headers Exchange:**
```
Message headers: {type: "email", priority: "high"}
Queue binding: {type: "email"} → получит сообщение
```
- Маршрутизация по **заголовкам** сообщения (не по routing key)
- Use case: сложная логика маршрутизации

---

#### Queue (очереди)

**Параметры:**
```go
ch.QueueDeclare(
    "orders",    // name
    true,        // durable (сохраняется при рестарте RabbitMQ)
    false,       // autoDelete (удаляется когда нет consumers)
    false,       // exclusive (доступна только одному connection)
    false,       // noWait
    nil,         // arguments
)
```

**Durable Queue:**
- Очередь сохраняется при рестарте RabbitMQ
- **НО!** Сообщения теряются, если не помечены как persistent

**Persistent Messages:**
```go
err := ch.Publish(
    "",           // exchange
    "orders",     // routing key
    false,        // mandatory
    false,        // immediate
    amqp.Publishing{
        DeliveryMode: amqp.Persistent,  // ← сообщение на диск!
        ContentType:  "application/json",
        Body:         []byte(message),
    },
)
```

---

#### Acknowledge (подтверждение обработки)

**Auto Ack (автоматическое):**
```go
msgs, _ := ch.Consume(
    "orders",
    "",
    true,  // autoAck = true (RabbitMQ удаляет сразу после отправки)
    false,
    false,
    false,
    nil,
)
```
**Риск:** если consumer упал — сообщение потеряно!

**Manual Ack (ручное, рекомендуется):**
```go
msgs, _ := ch.Consume(
    "orders",
    "",
    false,  // autoAck = false
    false,
    false,
    false,
    nil,
)

for msg := range msgs {
    err := processOrder(msg.Body)
    if err != nil {
        msg.Nack(false, true)  // false = не multiple, true = requeue
    } else {
        msg.Ack(false)  // false = не multiple
    }
}
```

**Методы:**
- `Ack(multiple)` — подтвердить обработку (удалить из очереди)
- `Nack(multiple, requeue)` — отклонить (requeue = вернуть в очередь или в DLQ)
- `Reject(requeue)` — как Nack, но для одного сообщения

---

#### Prefetch Count (управление нагрузкой)

**Проблема:**
```
Consumer 1: обрабатывает 10 сек/сообщение (медленный)
Consumer 2: обрабатывает 1 сек/сообщение (быстрый)

Без prefetch: RabbitMQ отправит 50% сообщений Consumer 1 → узкое горлышко!
```

**Решение:**
```go
ch.Qos(
    1,     // prefetchCount (сколько сообщений отправить до получения Ack)
    0,     // prefetchSize (в байтах, 0 = без ограничений)
    false, // global (false = на канал, true = на connection)
)
```

**Эффект:**
- Consumer получит следующее сообщение **только после** `Ack` предыдущего
- Быстрый consumer будет обрабатывать больше сообщений

---

#### Dead Letter Queue (DLQ)

**Когда сообщение попадает в DLQ:**
1. Consumer отклонил (Nack/Reject) с `requeue = false`
2. Сообщение истекло (TTL)
3. Очередь переполнена (max length)

**Настройка:**
```go
// Создаём DLQ
ch.QueueDeclare("orders_dlq", true, false, false, false, nil)

// Основная очередь с DLQ
args := amqp.Table{
    "x-dead-letter-exchange":    "",            // пустой = default exchange
    "x-dead-letter-routing-key": "orders_dlq",  // routing key для DLQ
    "x-message-ttl":             60000,         // 60 сек TTL (опционально)
}
ch.QueueDeclare("orders", true, false, false, false, args)
```

**Обработка DLQ:**
```go
// Consumer для DLQ (логирование, алерты, ручная проверка)
msgs, _ := ch.Consume("orders_dlq", "", false, false, false, false, nil)

for msg := range msgs {
    log.Printf("Failed message: %s, reason: %v", msg.Body, msg.Headers["x-death"])
    // Логируем в Sentry, отправляем в Slack, сохраняем в БД
    msg.Ack(false)
}
```

---

#### RabbitMQ vs Kafka (сравнение)

| | RabbitMQ | Kafka |
|---|----------|-------|
| **Модель** | Push (брокер проталкивает) | Pull (consumers тянут) |
| **Хранение** | Оперативная память (+ диск при настройке) | Диск (по умолчанию) |
| **Порядок** | Не гарантируется (зависит от очередей) | Гарантируется в рамках партиции |
| **Масштабируемость** | Средняя | Высокая (партиции) |
| **Производительность** | Средняя (~20k msg/sec) | Высокая (~1M msg/sec) |
| **Сложность** | Проще | Сложнее |
| **Routing** | Гибкий (Exchange типы) | Простой (по ключу в партицию) |
| **Acknowledge** | Ack/Nack на каждое сообщение | Commit offset (батчами) |
| **Retention** | Удаляется после Ack | Хранится по времени (7 дней) |
| **Use case** | Задачи, очереди, RPC | Логи, события, стриминг |

**Когда RabbitMQ:**
- Сложная маршрутизация (Topic/Headers Exchange)
- RPC паттерн (request-reply)
- Нужны гарантии доставки каждого сообщения
- Приоритетные очереди

**Когда Kafka:**
- Высокая пропускная способность (миллионы событий)
- Event Sourcing (нужно хранить историю)
- Стриминг данных (real-time analytics)
- Replay сообщений (перечитать старые события)

### 5.5. Kubernetes (K8s) — основы для Backend разработчика

**Что такое Kubernetes:**
- **Система оркестрации контейнеров** (Docker, containerd)
- Автоматизирует деплой, масштабирование, управление приложениями
- Обеспечивает отказоустойчивость, балансировку нагрузки

**Основные компоненты:**

---

#### Pod — минимальная единица развёртывания

**Что такое Pod:**
- Группа из **одного или нескольких контейнеров**
- Контейнеры в Pod'е разделяют:
  - Сетевое пространство (localhost между контейнерами)
  - Volumes (общие диски)
  - IP-адрес

**Пример Pod:**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: go-api
  labels:
    app: api
spec:
  containers:
  - name: api-container
    image: myregistry/go-api:1.0.0
    ports:
    - containerPort: 8080
    env:
    - name: DB_HOST
      value: "postgres.default.svc.cluster.local"
    resources:
      requests:
        memory: "128Mi"
        cpu: "100m"
      limits:
        memory: "256Mi"
        cpu: "500m"
```

**Проблема Pod'ов:**
- Если Pod умер → нужно создавать новый вручную
- Решение → **Deployment**

---

#### Deployment — управление репликами

**Что делает:**
- Создаёт нужное количество реплик Pod'ов
- Автоматически пересоздаёт упавшие Pod'ы
- Rolling Update (постепенное обновление без downtime)

**Пример Deployment:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: go-api-deployment
spec:
  replicas: 3  # Запустить 3 экземпляра
  selector:
    matchLabels:
      app: api
  template:  # Шаблон Pod'а
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: api-container
        image: myregistry/go-api:1.0.0
        ports:
        - containerPort: 8080
        livenessProbe:   # Проверка "живой ли контейнер"
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 5
        readinessProbe:  # Проверка "готов ли принимать трафик"
          httpGet:
            path: /ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 3
```

**Rolling Update:**
```bash
# Обновить образ (новая версия)
kubectl set image deployment/go-api-deployment api-container=myregistry/go-api:2.0.0

# K8s автоматически:
# 1. Создаст новый Pod с версией 2.0.0
# 2. Дождётся readinessProbe (что он готов)
# 3. Убьёт старый Pod с версией 1.0.0
# 4. Повторит для всех реплик (постепенно)
```

**Откат (Rollback):**
```bash
kubectl rollout undo deployment/go-api-deployment
```

---

#### Service — сетевой доступ к Pod'ам

**Проблема:**
- Pod'ы динамические (их IP меняются при пересоздании)
- Как подключиться к ним?

**Решение — Service:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: go-api-service
spec:
  selector:
    app: api  # Выбирает все Pod'ы с label app=api
  ports:
  - protocol: TCP
    port: 80       # Порт Service
    targetPort: 8080  # Порт контейнера
  type: ClusterIP  # Доступен только внутри кластера
```

**Типы Service:**
1. **ClusterIP** (по умолчанию) — доступен только внутри K8s
2. **NodePort** — открывает порт на всех нодах кластера (30000-32767)
3. **LoadBalancer** — создаёт внешний Load Balancer (AWS ELB, GCP LB)

**Доступ к Service:**
```go
// Внутри кластера:
http.Get("http://go-api-service.default.svc.cluster.local/users")

// Короткая форма (если в том же namespace):
http.Get("http://go-api-service/users")
```


#### Probes (проверки здоровья)

**1. Liveness Probe** — "жив ли контейнер?"
```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 10  # Ждать 10 сек после старта
  periodSeconds: 5         # Проверять каждые 5 сек
  failureThreshold: 3      # 3 неудачи → убить Pod
```
**Если не прошёл:** K8s **рестартует** контейнер

**2. Readiness Probe** — "готов ли принимать трафик?"
```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 3
```
**Если не прошёл:** K8s **не отправляет** трафик на этот Pod (но не убивает)

**Реализация в Go:**
```go
http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
    // Проверка: работает ли приложение вообще
    w.WriteHeader(http.StatusOK)
    w.Write([]byte("OK"))
})

http.HandleFunc("/ready", func(w http.ResponseWriter, r *http.Request) {
    // Проверка: готово ли приложение (БД подключена, кэш работает)
    if db.Ping() != nil {
        w.WriteHeader(http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)
    w.Write([]byte("Ready"))
})
```

#### Resource Limits (ограничения ресурсов)

```yaml
resources:
  requests:      # Минимум (гарантированный)
    memory: "128Mi"
    cpu: "100m"  # 100 milliCPU = 0.1 CPU
  limits:        # Максимум (не может превысить)
    memory: "256Mi"
    cpu: "500m"
```

**Что происходит:**
- **CPU limit превышен** → throttling (замедление)
- **Memory limit превышен** → **OOMKilled** (Pod убит)

**Best practices:**
- requests = обычная нагрузка
- limits = пиковая нагрузка (в 2-3 раза больше requests)

#### Ingress — внешний доступ (HTTP/HTTPS)

**Проблема:**
- Service типа LoadBalancer создаёт отдельный LB для **каждого** сервиса → дорого

**Решение — Ingress:**
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
spec:
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /users
        pathType: Prefix
        backend:
          service:
            name: user-service
            port:
              number: 80
      - path: /orders
        pathType: Prefix
        backend:
          service:
            name: order-service
            port:
              number: 80
```

**Эффект:**
```
api.example.com/users  → user-service
api.example.com/orders → order-service
```
Один внешний IP для всех сервисов!

## ЧАСТЬ 6: SQL — ПРОФИЛИРОВАНИЕ И ОПТИМИЗАЦИЯ

*Инструменты для анализа и оптимизации SQL-запросов*

---

### 5.1. EXPLAIN — анализ плана выполнения запроса

**Что это?**
- `EXPLAIN` показывает, **как Postgres планирует выполнить запрос**
- Помогает найти узкие места: отсутствие индексов, неоптимальные JOIN'ы

**Основные варианты:**

#### EXPLAIN (базовый)
```sql
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
```
**Вывод:** план выполнения **без фактического выполнения** запроса

#### EXPLAIN ANALYZE (с выполнением)
```sql
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';
```
**Вывод:** план + **реальное время выполнения**

#### EXPLAIN (ANALYZE, BUFFERS)
```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM users WHERE age > 18;
```
**Вывод:** план + время + **использование кэша и дисковых операций**

#### EXPLAIN (ANALYZE, VERBOSE)
```sql
EXPLAIN (ANALYZE, VERBOSE) SELECT name, age FROM users WHERE id = 1;
```
**Вывод:** план + время + **детальная информация о каждом шаге**

---

### 5.2. Основные типы сканирования (Scan Types)

#### Seq Scan (Sequential Scan)
```
Seq Scan on users  (cost=0.00..15000.00 rows=1000000 width=32)
```
- **Полное сканирование таблицы** (построчное чтение)
- **Медленно** на больших таблицах (миллионы строк)
- **Когда используется:**
  - Нет подходящего индекса
  - Запрос выбирает > 10-20% таблицы (индекс не эффективен)
  - Таблица маленькая (быстрее, чем индекс)

**🔴 Красный флаг:** Seq Scan на таблице с 10 млн строк и малым результатом

---

#### Index Scan (Сканирование по индексу)
```
Index Scan using idx_users_email on users  (cost=0.29..8.31 rows=1 width=32)
  Index Cond: (email = 'test@example.com')
```
- **Использует индекс** для быстрого поиска
- **Быстро** для точечных запросов (`WHERE email = '...'`)
- **Когда используется:**
  - Есть индекс на поле
  - Запрос выбирает маленький процент строк

**✅ Хорошо:** Index Scan с низким `cost` и малым `rows`

---

#### Index Only Scan (Покрывающий индекс)
```
Index Only Scan using idx_users_email_name on users  (cost=0.29..8.31 rows=1 width=32)
  Index Cond: (email = 'test@example.com')
```
- **Все данные берутся из индекса** (не нужно читать таблицу!)
- **Самый быстрый** для запросов, где индекс содержит все поля из `SELECT`

**✅ Отлично:** Индекс полностью покрывает запрос

---

#### Bitmap Index Scan / Bitmap Heap Scan
```
Bitmap Heap Scan on users  (cost=4.31..100.00 rows=50 width=32)
  Recheck Cond: (age > 18)
  -> Bitmap Index Scan on idx_users_age  (cost=0.00..4.31 rows=50 width=0)
        Index Cond: (age > 18)
```
- **Комбинированный подход:** сначала создаёт bitmap по индексу, затем читает таблицу
- **Используется** для средних выборок (100-10000 строк)
- Эффективнее Seq Scan, но медленнее Index Scan

---

### 5.3. Типы JOIN'ов

#### Nested Loop (Вложенный цикл)
```
Nested Loop  (cost=0.29..100.00 rows=100 width=64)
  -> Seq Scan on orders  (cost=0.00..10.00 rows=10 width=32)
  -> Index Scan on users  (cost=0.29..9.00 rows=1 width=32)
        Index Cond: (users.id = orders.user_id)
```
- **Для каждой строки из первой таблицы** ищет совпадения во второй
- **Эффективен** для маленьких таблиц или когда одна таблица возвращает мало строк
- **Медленно** для больших таблиц без индексов

**🔴 Красный флаг:** Nested Loop на миллионах строк без индексов

---

#### Hash Join (Хэш-соединение)
```
Hash Join  (cost=50.00..200.00 rows=1000 width=64)
  Hash Cond: (orders.user_id = users.id)
  -> Seq Scan on orders  (cost=0.00..100.00 rows=1000 width=32)
  -> Hash  (cost=10.00..10.00 rows=100 width=32)
        -> Seq Scan on users  (cost=0.00..10.00 rows=100 width=32)
```
- **Создаёт хэш-таблицу** из меньшей таблицы, затем ищет совпадения
- **Эффективен** для больших таблиц с равными JOIN'ами (`=`)
- Требует **память** (может уйти в swap при недостатке RAM)

**✅ Хорошо:** Hash Join для средних/больших таблиц

---

#### Merge Join (Сортировка-слияние)
```
Merge Join  (cost=100.00..300.00 rows=1000 width=64)
  Merge Cond: (orders.user_id = users.id)
  -> Sort  (cost=50.00..60.00 rows=1000 width=32)
        Sort Key: orders.user_id
        -> Seq Scan on orders  (cost=0.00..100.00 rows=1000 width=32)
  -> Index Scan using idx_users_id on users  (cost=0.00..50.00 rows=100 width=32)
```
- **Сортирует обе таблицы** по JOIN-ключу, затем объединяет
- **Эффективен** когда обе таблицы уже отсортированы (индексы!)
- **Медленно** если нужна сортировка (высокий `cost` на `Sort`)

**✅ Хорошо:** Merge Join с использованием индексов (без сортировки)

---

### 5.4. Красные флаги в EXPLAIN

🔴 **Seq Scan на больших таблицах:**
```
Seq Scan on users  (cost=0.00..150000.00 rows=10000000 width=32)
```
**Решение:** Добавить индекс на поле в `WHERE`

---

🔴 **Большое количество строк (rows=10000000):**


---

🔴 **Nested Loop с большим количеством итераций:**


### 7.1. Репликация данных (Single-Leader Replication)

**Что такое репликация?**
- **Репликация** — хранение копий данных на нескольких серверах

**Зачем нужна репликация:**
- **Геораспределение** — данные ближе к пользователям
- **Отказоустойчивость** — система работает, даже если часть серверов упала
- **Масштабируемость** — распределение нагрузки на чтение

---

#### Алгоритмы репликации:

1. **Single-leader** (с одним ведущим узлом)
2. **Multi-leader** (с несколькими ведущими узлами)
3. **Leaderless** (без ведущего)

---

#### Single-Leader Replication

**Термины:**
- **Leader (Ведущий узел)** — единственный узел, принимающий запросы на **запись** и **чтение**
- **Followers (Ведомые узлы)** — узлы, принимающие запросы **только на чтение**

**Принципы:**
- Все записи идут **только через Leader**
- Чтение можно выполнять **с любого узла**
- Leader рассылает изменения Followers через **журнал репликации**

---

#### Типы репликации:

**1. Синхронная репликация:**
```go
type Cluster struct {
    leader   *Replica
    replicas []*Replica
}

type Replica struct {
    data map[string]string
}

// Синхронная репликация
func (c *Cluster) WriteDataSync(data NewData) {
    // 1. Запись в Leader
    c.leader.data[data.Key] = data.Value
    
    // 2. Синхронная запись во ВСЕ реплики
    for _, replica := range c.replicas {
        replica.data[data.Key] = data.Value
    }
}
```

**Плюсы:**
- Гарантия согласованности данных
- Все реплики содержат актуальные данные

**Минусы:**
- Медленная запись (ждём все реплики)
- При падении одной реплики запись блокируется

---

**2. Асинхронная репликация:**
```go
// Асинхронная репликация
func (c *Cluster) WriteDataAsync(data NewData) {
    // 1. Запись в Leader
    c.leader.data[data.Key] = data.Value
    
    // 2. Асинхронная запись в реплики (через горутины)
    for _, replica := range c.replicas {
        go func(r *Replica) {
            r.data[data.Key] = data.Value
        }(replica)
    }
}
```

**Плюсы:**
- Быстрая запись (не ждём реплики)
- Высокая производительность

**Минусы:**
- Возможна **потеря данных** при падении Leader'а до репликации
- Чтение с Follower может вернуть **устаревшие данные**

---

**3. Полусинхронная репликация:**
```go
// Полусинхронная репликация
func (c *Cluster) WriteDataSemiSync(data NewData) {
    // 1. Запись в Leader
    c.leader.data[data.Key] = data.Value
    
    // 2. Синхронная запись в ОДНУ реплику
    c.replicas[0].data[data.Key] = data.Value
    
    // 3. Асинхронная запись в остальные реплики
    for _, replica := range c.replicas[1:] {
        go func(r *Replica) {
            r.data[data.Key] = data.Value
        }(replica)
    }
}
```

**Плюсы:**
- Баланс между скоростью и надёжностью
- Минимум одна реплика гарантированно синхронизирована

**Минусы:**
- Сложнее в реализации

---

#### Возможные проблемы репликации:

**1. Актуальность данных (Replication Lag):**
- **Проблема:** Пользователь обновляет профиль → система подтверждает успех → но при проверке видит старые данные
- **Причина:** Чтение с **отстающей реплики** (запись прошла в Leader, но не дошла до читаемого Follower'а)

**Решение:**
- **Read-after-write consistency** — читать с Leader после записи
- **Monotonic reads** — всегда читать с одной и той же реплики

---

**2. Отказы узлов:**

**Отказ Leader'а:**
- Необходимо "повысить в ранге" один из Followers (failover)
- Перенаправить запросы на запись на новый Leader
- При восстановлении старого Leader'а — вернуть ранги узлов

**Отказ Follower'а:**
- При восстановлении получить **упущенные записи** от Leader'а
- Начать с последней операции, зафиксированной локально

---

#### Методы репликации:

**1. Операторная репликация (Statement-based):**
- Leader записывает SQL-операторы в журнал и отсылает их Followers
- **Проблема:** Недетерминированные функции (`RAND()`, `NOW()`) должны выполняться **до отправки**

**2. WAL (Write-Ahead Log):**
- Журнал содержит **результаты всех операций записи** в БД
- **Минус:** Сильно привязан к подсистеме хранения (версии СУБД должны совпадать)
- **Используется:** PostgreSQL, MySQL

**3. Логическая репликация:**
- Журнал содержит **логическую информацию** об изменениях (вставка, обновление, удаление)
- **Плюс:** Не привязан к подсистеме хранения, можно использовать **разные версии СУБД**

---

### 7.2. Redis: TTL и инвалидация ключей

**Что такое TTL?**
- **TTL (Time To Live)** — время жизни ключа в Redis
- После истечения TTL ключ считается **недействительным**

---

#### Механизмы инвалидации:

**1. Активная инвалидация (Lazy Expiration):**
- Проверка TTL **при обращении** к ключу
- Если TTL истёк → ключ **удаляется**

**2. Пассивная инвалидация (Active Expiration):**
- **Фоновый процесс** периодически проверяет ключи с TTL
- Удаляет просроченные ключи **без обращения к ним**

---

#### Активная инвалидация (Redis 7.2):

**Флаги:**
```c
#define EXPIRE_FORCE_DELETE_EXPIRED 1  // удалить, даже на read-only реплике
#define EXPIRE_AVOID_DELETE_EXPIRED 2  // не удалять, вернуть что ключ недействителен
```

**Функция `lookupKey`:**
```c
int is_ro_replica = server.masterhost && server.repl_slave_ro;
int expire_flags = 0;

if (flags & LOOKUP_WRITE && !is_ro_replica)  // проверка на Leader
    expire_flags |= EXPIRE_FORCE_DELETE_EXPIRED;
    
if (flags & LOOKUP_NOEXPIRE)  // игнорировать TTL
    expire_flags |= EXPIRE_AVOID_DELETE_EXPIRED;

if (expireIfNeeded(db, key, expire_flags)) {
    val = NULL;  // ключ удалён
}
```

**Возвращаемый результат:**
- ✅ Ключ существует и не просрочен → `robj*` (значение)
- ✅ Ключ просрочен, но удаление запрещено → `robj*` (значение)
- ❌ Ключ просрочен и удалён → `NULL`
- ❌ Ключ отсутствует → `NULL`

---

#### Активная инвалидация (Redis 8.2):

**Новый enum:**
```c
typedef enum {
    KEY_VALID,     // Ключ валиден
    KEY_EXPIRED,   // Просрочен но не удалён
    KEY_DELETED    // Удалён сейчас
} keyStatus;
```

**Новый флаг:**
```c
#define EXPIRE_ALLOW_ACCESS_EXPIRED 4  // разрешить доступ к просроченным ключам
```

**Возвращаемый результат:**
- ✅ Ключ существует и не просрочен → `kvobj*`
- ✅ Ключ просрочен, но удаление запрещено → `kvobj*`
- ✅ Ключ просрочен, но **разрешён доступ** → `kvobj*`
- ❌ Ключ просрочен и удалён → `NULL`

**Оптимизация в 8.2:**
- `kvobj` вместо `robj` — отдельные поля для ключа (`sds`) и значения
- **Повышение производительности** через переиспользование ссылок

---

#### Пассивная инвалидация:

**Функция `activeExpireCycle`:**
- Обходит все БД и запускает фоновые обработчики
- **Медленный цикл** — плановая уборка с частотой `server.hz`
- **Быстрый цикл** — запускается при пиковой нагрузке

**Параметры (redis.conf):**
- `hz` — частота вызова фонового процесса (по умолчанию 10 Hz)
- `active-expire-effort` — агрессивность очистки (1-10)

**Алгоритм:**
1. Берём батч ключей с TTL (размер зависит от `active-expire-effort`)
2. Проверяем каждый ключ на истечение TTL
3. Если > 25% ключей просрочены → **повторяем цикл**
4. Если < 25% → **завершаем**

```go
type basicAuth struct {

    password string

func (b *basicAuth) RawCredentials() string {
    return b.username + ":" + b.password
}
```

---

#### Внутреннее устройство строки:

**Структура `string`:**
```go
type stringStruct struct {
    str unsafe.Pointer  // указатель на данные
    len int            // длина строки
}
```

---

#### Порядок выполнения конкатенации:

**1. Выделение памяти:**
```asm
CMPQ    SP, 16(R14)    ; Проверка на переполнение стека
JLS     morestack      ; При переполнении → расширить стек
PUSHQ   BP             ; Сохранить base pointer
MOVQ    SP, BP         ; Обновить base pointer
SUBQ    $56, SP        ; Выделить 56 байт в стеке
```

**2. Загрузка полей структуры:**
```asm
MOVQ    (AX), BX       ; b.username.ptr
MOVQ    8(AX), CX      ; b.username.len
MOVQ    16(AX), R8     ; b.password.ptr
MOVQ    24(AX), R9     ; b.password.len
```

**3. Конкатенация:**
```asm
LEAQ    go:string.":"(SB), DI     ; указатель на строку ":"
MOVL    $1, SI                     ; длина строки ":" = 1 байт
CALL    runtime.concatstring3(SB)  ; вызов runtime оптимизации
```

**4. Очистка стека:**
```asm
ADDQ    $56, SP        ; освободить 56 байт
POPQ    BP             ; восстановить base pointer
RET                    ; вернуть результат
```

---

#### Runtime оптимизация:

**`runtime.concatstring3`:**
- Создаёт слайс переданных строк
- Вызывает `runtime.concatstrings`
- **Выделяет память один раз** для итоговой строки

**Бенчмарк:**
```

BenchmarkShortStr-12    80576389    14.76 ns/op      0 B/op    0 allocs/op
```

**Почему оптимизация возможна:**
- Строка помещается на **стек** (escape analysis)
- Известно **количество конкатенируемых строк** (compile time)
- Даже если вернуть указатель → оптимизация выполняется на стеке, затем перебрасывается в heap

### 8.1. Конкурентность vs Параллелизм

**Ключевое различие:**

- **Конкурентность** (Concurrency) — про **структуру программы**: задачи **как будто** выполняются одновременно, но могут по очереди делить одно ядро
- **Параллелизм** (Parallelism) — про **выполнение**: задачи **реально** работают одновременно на разных ядрах

**Аналогия:**
- Конкурентность — один повар готовит несколько блюд, переключаясь между ними
- Параллелизм — несколько поваров готовят блюда одновременно на разных плитах

**В Go:**
- Ты строишь **конкурентный код** через горутины
- Планировщик решает, станет ли он **параллельным** в зависимости от `GOMAXPROCS`

**Пример конкурентности:**
```go
func main() {
    go say("ping")  // Конкурентная задача
    go say("pong")  // Конкурентная задача
    time.Sleep(time.Second)
}

func say(msg string) {
    for i := 0; i < 3; i++ {
        fmt.Println(msg)
        time.Sleep(200 * time.Millisecond)
    }
}

// Вывод: ping, pong, ping, pong... (чередуются)
```

**Пример параллелизма:**
```go
func main() {
    runtime.GOMAXPROCS(2)  // Разрешаем 2 ядра
    go work("A")
    go work("B")
    select {}
}

func work(id string) {
    for {
        fmt.Println("working:", id)  // Реально выполняются одновременно
    }
}
```

**Когда что использовать:**
- **Concurrency** — для I/O операций (HTTP, БД, файлы)
- **Parallelism** — для CPU-intensive вычислений (кодирование, шифрование)

### 8.2. Идиома "comma ok"

**Что это?**
Проверка успешности операции через второе возвращаемое значение `bool`.

**Формат:**
```go
value, ok := someOperation()
if !ok {
    // обработать ошибку или ситуацию "не ok"
}
// использовать value
```

**Зачем?**
Безопасная работа с неопределенностью, чтобы избежать паники.

**Где встречается:**

#### 1. Чтение из map
```go
type UserRepository struct {
    cache map[int]*entity.User
}

func (r *UserRepository) FindByID(id int) (*entity.User, error) {
    user, ok := r.cache[id]  // comma ok!
    
    if !ok {
        // Нет в кэше — идем в БД
        userFromDB, err := r.fetchFromDB(id)
        if err != nil {
            return nil, err
        }
        r.cache[id] = userFromDB
        return userFromDB, nil
    }
    
    return user, nil
}
```

#### 2. Type Assertion
```go
func (uc *OrderUsecase) ProcessOrderPayment(orderID int, paymentData interface{}) error {
    cardPayment, ok := paymentData.(*entity.CardPayment)  // comma ok!
    
    if !ok {
        return errors.New("invalid payment data type")
    }
    
    if cardPayment.Amount <= 0 {
        return errors.New("payment amount must be positive")
    }
    return nil
}
```

#### 3. HTTP Query Parameters
```go
func (c *UserController) GetUser(w http.ResponseWriter, r *http.Request) {
    queryValues := r.URL.Query()
    
    userIDValues, ok := queryValues["user_id"]  // comma ok!
    
    if !ok || len(userIDValues[0]) == 0 {
        http.Error(w, "user_id parameter is required", http.StatusBadRequest)
        return
    }
    
    userIDStr := userIDValues[0]
    // дальше конвертация и вызов usecase
}
```

#### 4. Чтение из канала
```go
func (w *Worker) processJobs(jobs <-chan *entity.Job) {
    for {
        job, ok := <-jobs  // comma ok!
        
        if !ok {
            // Канал закрыт, больше данных не будет
            fmt.Println("Channel closed, stopping worker")
            return
        }
        
        w.executeJob(job)
    }
}
```

**Альтернатива с range:**
```go
// Вместо явного comma ok можно использовать range
for job := range jobs {
    w.executeJob(job)
}
// range автоматически выходит при закрытии канала
```

### 8.3. Опасный append() со срезами

**Проблема:**
Срезы в Go — это **окно** в общий массив. `append()` может **втихаря изменить оригинальный слайс**, если не создаёт новый массив.

**Когда происходит:**
- Два среза делят один базовый массив
- `append()` модифицирует элементы за пределами `len`, но внутри `cap`

**Пример:**
```go
func main() {
    s := []int{1, 2, 3, 4}
    t := s[1:3]        // t = [2, 3], но базовый массив тот же!
    
    t = append(t, 99)  // append может изменить s[3]!
    s[2] = 42          // меняем элемент исходного слайса
    
    fmt.Println("s:", s)  // [1, 2, 42, 99]
    fmt.Println("t:", t)  // [2, 42, 99]
}
```

**Схема:**
```
Исходный массив: [1, 2, 3, 4]
                  ↑     ↑  ↑
                  s     t  append(t, 99) изменяет s[3]!
```

**Решение 1: Явное копирование**
```go
t := make([]int, len(s[1:3]))
copy(t, s[1:3])
t = append(t, 99)  // Теперь безопасно
```

**Решение 2: Full slice expression**
```go
t := s[1:3:3]  // capacity ограничен до 3
// Теперь append() гарантированно создаст новый массив
```

**Когда опасно:**
- Передача среза в функцию, которая может его модифицировать
- Работа с подмножествами большого среза
- Concurrent access к разным срезам одного массива

### 8.4. errors.Join (Go 1.20+)

**Зачем?**
Объединить **несколько ошибок** в одну.

**До Go 1.20:**
```go
// Приходилось вручную собирать
var errs []error
if err1 != nil { errs = append(errs, err1) }
if err2 != nil { errs = append(errs, err2) }
```

**С Go 1.20:**
```go
err := errors.Join(err1, err2, err3)
```

**Пример использования:**
```go
func ValidateUser(user *User) error {
    var errs []error
    
    if user.Name == "" {
        errs = append(errs, errors.New("name is required"))
    }
    if user.Email == "" {
        errs = append(errs, errors.New("email is required"))
    }
    if user.Age < 18 {
        errs = append(errs, errors.New("age must be 18+"))
    }
    
    return errors.Join(errs...)  // Объединяем все ошибки
}

// Использование
if err := ValidateUser(user); err != nil {
    fmt.Println(err)
    // Output:
    // name is required
    // email is required
    // age must be 18+
}
```

**Проверка ошибок:**
```go
err := errors.Join(ErrNotFound, ErrUnauthorized)

// errors.Is работает с каждой ошибкой в цепочке
if errors.Is(err, ErrNotFound) {
    fmt.Println("Not found!")  // true
}
if errors.Is(err, ErrUnauthorized) {
    fmt.Println("Unauthorized!")  // true
}
```

**Различия:**
- `errors.Is` — проверяет, **является ли** ошибка конкретной ошибкой в цепочке
- `errors.As` — **достаёт** конкретный тип ошибки
- `errors.Join` — **объединяет** несколько ошибок в одну

### 8.5. Внутреннее устройство каналов (hchan)

**CSP модель:**
Каналы базируются на модели **Communicating Sequential Processes**: процессы не делят память напрямую, а обмениваются сообщениями.

**Структура hchan:**
```go
type hchan struct {
    qcount   uint           // Элементов в буфере
    dataqsiz uint           // Размер буфера
    buf      unsafe.Pointer // Указатель на кольцевой буфер
    elemsize uint16         // Размер элемента
    closed   uint32         // Флаг закрытия
    elemtype *_type         // Тип элемента
    sendx    uint           // Индекс отправки
    recvx    uint           // Индекс получения
    recvq    waitq          // Очередь горутин, ожидающих receive
    sendq    waitq          // Очередь горутин, ожидающих send
    lock     mutex          // Мьютекс для защиты
}
```

**Как работает:**
1. **Send (`ch <- value`)**:
   - Если есть ожидающий receiver → передаём напрямую (оптимизация)
   - Если буфер не заполнен → помещаем в буфер
   - Иначе → блокируемся, добавляемся в `sendq`

2. **Receive (`value := <-ch`)**:
   - Если есть ожидающий sender → берём у него напрямую
   - Если буфер не пуст → берём из буфера
   - Иначе → блокируемся, добавляемся в `recvq`

3. **Select**:
   - Горутина регистрируется сразу на нескольких каналах
   - Рантайм выбирает первый готовый
   - Снимает регистрацию с остальных

**Закрытие канала:**
- `close(ch)` устанавливает флаг `closed`
- Все ожидающие receivers **разблокируются** и получают zero value
- Все ожидающие senders **паникуют**

**Почему важно знать:**
- Понимание дедлоков
- Оптимизация производительности (размер буфера)
- Правильное проектирование concurrent систем

### 9.1. Load Balancer — алгоритмы распределения нагрузки

**Назначение:** Равномерно распределяет входящие запросы по серверам.

#### Основные алгоритмы:

**1. Round Robin (По кругу)**
- **Принцип:** Запросы распределяются по серверам **по очереди**
- **Пример:** Сервер A → Сервер B → Сервер C → Сервер A...
- **Плюсы:** Простота, равномерное распределение
- **Минусы:** Не учитывает нагрузку на серверы
- **Когда использовать:** Все серверы одинаковой мощности

**2. Least Connections (Наименьшее количество соединений)**
- **Принцип:** Запрос идёт на сервер с **наименьшим количеством активных соединений**
- **Пример:** Если Сервер A (5 соединений), Сервер B (10 соединений) → запрос идёт на A
- **Плюсы:** Учитывает текущую нагрузку
- **Минусы:** Требует отслеживания соединений
- **Когда использовать:** Долгоживущие соединения (WebSocket, long polling)

**3. Least Time (Наименьшее время ответа)**
- **Принцип:** Запрос идёт на сервер с **наименьшим временем ответа**
- **Пример:** Если Сервер A отвечает за 50ms, Сервер B за 100ms → запрос идёт на A
- **Плюсы:** Оптимизация latency
- **Минусы:** Требует мониторинга времени ответа
- **Когда использовать:** Критична скорость ответа

**4. Least Traffic (Наименьший трафик)**
- **Принцип:** Запрос идёт на сервер с **наименьшим количеством трафика**
- **Пример:** Если Сервер A обработал 1GB, Сервер B обработал 500MB → запрос идёт на B
- **Плюсы:** Равномерная нагрузка по сети
- **Минусы:** Требует мониторинга трафика
- **Когда использовать:** Ограничения по сетевым ресурсам

**Важно:**
- **Nginx для балансировки БД?** ❌ **НИКОГДА!** (для HTTP/HTTPS only)
- Для БД используют: PgBouncer, ProxySQL, HAProxy

### 9.2. Cache Eviction Policies — алгоритмы вытеснения из кэша

**Назначение:** Определяют, какие данные удалять при заполнении кэша.

#### Основные алгоритмы:

**1. LRU (Least Recently Used) — Вытеснение давно неиспользованных**
- **Принцип:** Удаляется элемент, к которому **дольше всего не обращались**
- **Структура данных:** HashMap + Двусвязный список (O(1) get/put)
- **Пример:** 
  ```
  Кэш [A, B, C, D] (capacity = 4)
  Обращение: B → D → A → E (нужно добавить)
  Вытесняется: C (самый старый)
  Результат: [B, D, A, E]
  ```
- **Когда использовать:** Временная локальность (недавно использованное будет использоваться снова)

**2. LFU (Least Frequently Used) — Вытеснение редко используемых**
- **Принцип:** Удаляется элемент с **наименьшей частотой обращений**
- **Структура данных:** HashMap + Min-Heap или HashMap + DoublyLinkedList per frequency
- **Пример:**
  ```
  Кэш [A(5), B(3), C(2), D(1)]  // (частота)
  Новый элемент E → вытесняется D (наименьшая частота)
  ```
- **Когда использовать:** Популярные данные (хиты) должны оставаться в кэше

**3. FIFO (First In First Out) — Очередь**
- **Принцип:** Удаляется элемент, который был **добавлен первым**
- **Структура данных:** Очередь (Queue)
- **Пример:**
  ```
  Кэш [A, B, C, D] (добавлены по порядку)
  Новый элемент E → вытесняется A (первый добавленный)
  ```
- **Когда использовать:** Простота важнее эффективности

**4. Random Replacement (RR) — Случайное вытеснение**
- **Принцип:** Удаляется **случайный** элемент
- **Пример:** Выбирается рандомный ключ для удаления
- **Когда использовать:** Простая реализация, нет предсказуемого паттерна доступа

**Главный алгоритм:** **LRU** (самый популярный на собесах!)

**Важно:**
- Выбирать вручную? ❌ **НИКОГДА!** (Redis/Memcached выбирают автоматически)
- Главная проблема кэширования: **консистентность** (актуальность данных)

### 9.3. InMemory Cache — реализация на Go

**Задача:** Реализовать потокобезопасный in-memory кэш.

```go
package main

import "sync"

type Cache interface {
    Set(k string, v string)
    Get(k string) (string, bool)
}

type InMemoryCache struct {
    data map[string]string
    mu   sync.RWMutex  // RWMutex быстрее обычного Mutex для чтения
}

func NewInMemoryCache() *InMemoryCache {
    return &InMemoryCache{
        data: make(map[string]string),
    }
}

func (c *InMemoryCache) Set(k string, v string) {
    c.mu.Lock()          // Блокируем запись
    defer c.mu.Unlock()
    c.data[k] = v
}

func (c *InMemoryCache) Get(k string) (string, bool) {
    c.mu.RLock()         // Блокируем только запись, не чтение
    defer c.mu.RUnlock()
    
    data, ok := c.data[k]
    return data, ok
}

func main() {
    cache := NewInMemoryCache()
    cache.Set("foo", "bar")
    
    wg := &sync.WaitGroup{}
    wg.Add(2)
    
    // Concurrent доступ
    go func() {
        defer wg.Done()
        cache.Set("foo", "updated_bar")
    }()
    
    go func() {
        defer wg.Done()
        value, ok := cache.Get("foo")
        if ok {
            println("Found:", value)
        }
    }()
    
    wg.Wait()
}
```

**Почему RWMutex?**
- **Много читателей** — не блокируют друг друга (`RLock`)
- **Один писатель** — блокирует всё (`Lock`)

### 10.1. Data Race vs Race Condition

#### Отличия:

| Аспект | Data Race | Race Condition |
|--------|-----------|----------------|
| **Определение** | Несинхронизированный доступ к памяти | Логическая ошибка в порядке выполнения |
| **Детектируется** | `go run -race` | Нет автоматической детекции |
| **Пример** | Несколько горутин пишут в `counter++` | Проверка условия + действие (не атомарно) |
| **Решение** | `sync.Mutex` или `atomic` | Правильная логика + синхронизация |

**Пример Data Race:**
```go
var counter int

func increment() {
    counter++  // Data Race!
}

func main() {
    for i := 0; i < 1000; i++ {
        go increment()
    }
    time.Sleep(time.Second)
    fmt.Println(counter)  // Не 1000!
}
```

**Решение:**
```go
var (
    counter int
    mu      sync.Mutex
)

func increment() {
    mu.Lock()
    counter++
    mu.Unlock()
}
```

### 10.2. Оптимальные практики работы с транзакциями

#### Когда использовать какой уровень изоляции:

**READ COMMITTED** (по умолчанию) — 95% случаев
```sql
BEGIN;
SELECT * FROM orders WHERE user_id = 1;
UPDATE orders SET status = 'shipped' WHERE id = 123;
COMMIT;
```
- Обычные операции
- CRUD с редкими конфликтами

**REPEATABLE READ** — отчёты и аналитика
```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM orders;  -- 100
-- Другая транзакция добавила заказ
SELECT COUNT(*) FROM orders;  -- Всё равно 100 (снапшот)
COMMIT;
```
- Генерация отчётов
- Экспорт данных
- Консистентное чтение

**SERIALIZABLE** — критические финансовые операции
```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```
- Переводы денег
- Продажа билетов
- Инвентаризация (остатки товаров)

**Важно:**  
- SERIALIZABLE может вернуть ошибку `could not serialize access`
- Нужен механизм **retry** с экспоненциальной задержкой
- Используй редко (< 5% транзакций)

### 10.3. SKIP LOCKED — работа с очередями

**Задача:** 3 воркера обрабатывают задачи из таблицы `tasks`

**Без SKIP LOCKED:**
```sql
BEGIN;
SELECT * FROM tasks WHERE status = 'pending' LIMIT 1 FOR UPDATE;
-- Воркер 1 блокирует строку
-- Воркеры 2 и 3 ЖДУТ
```

**С SKIP LOCKED:**
```sql
BEGIN;
SELECT * FROM tasks 
WHERE status = 'pending' 
LIMIT 1 
FOR UPDATE SKIP LOCKED;
-- Воркер 1 берёт строку 1
-- Воркер 2 берёт строку 2 (пропуская заблокированную)
-- Воркер 3 берёт строку 3
```

**Результат:** 
- Нет ожидания
- Максимальный параллелизм
- Идеально для распределённых очередей задач

### 10.4. Механизм работы SERIALIZABLE в PostgreSQL

**Не пессимистичная блокировка!**

1. **Все транзакции выполняются параллельно**
2. **При COMMIT строится граф зависимостей**
3. **Если есть циклы → одна транзакция успешна, остальные откатываются**

**Пример конфликта:**
```
T1: READ accounts(1) → 100
T2: READ accounts(1) → 100
T1: UPDATE accounts(1) = 50  (COMMIT ✅)
T2: UPDATE accounts(1) = 80  (ERROR: could not serialize access)
```

**Почему медленно:**
- Граф зависимостей для каждой транзакции
- 99 из 100 транзакций откатятся при конфликте
- Дополнительные сетевые походы из-за retry

### 10.5. Phantom Read vs Non-Repeatable Read (детально)

#### Non-Repeatable Read (одна строка, разные значения)

```sql
-- Транзакция 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- 100

-- В это время Транзакция 2:
UPDATE accounts SET balance = 200 WHERE id = 1;
COMMIT;

-- Продолжаем Транзакцию 1:
SELECT balance FROM accounts WHERE id = 1;  -- 200 (изменилось!)
COMMIT;
```

**Решение:** REPEATABLE READ

#### Phantom Read (количество строк изменилось)

```sql
-- Транзакция 1
BEGIN;
SELECT COUNT(*) FROM orders WHERE user_id = 1;  -- 10 строк

-- В это время Транзакция 2:
INSERT INTO orders (user_id) VALUES (1);
COMMIT;

-- Продолжаем Транзакцию 1:
SELECT COUNT(*) FROM orders WHERE user_id = 1;  -- 11 строк (фантом!)
COMMIT;
```

**Решение:** В PostgreSQL REPEATABLE READ **предотвращает** Phantom Read (отличие от стандарта SQL)

## ЧАСТЬ 12: МИГРАЦИЯ MySQL → PostgreSQL

*Источник: island_sql/turn_to_postgresql (лабораторная работа, 3175 строк)*

**⚠️ ВАЖНО:** При переезде с MySQL на PostgreSQL нужно знать **10 ключевых отличий**!

---

### 12.1. ТОП-10 ОТЛИЧИЙ MySQL → PostgreSQL

#### 1️⃣ AUTO_INCREMENT → SERIAL

**MySQL:**
```sql
CREATE TABLE пациент (
    пациент_ID int(6) NOT NULL AUTO_INCREMENT,
    пациент_ФИО varchar(20) NOT NULL,
    PRIMARY KEY (пациент_ID)
);
```

**PostgreSQL:**
```sql
CREATE TABLE пациент (
    пациент_ID SERIAL PRIMARY KEY,  -- или: BIGSERIAL для int8
    пациент_ФИО varchar(20) NOT NULL
);

-- Альтернатива (более современный способ):
CREATE TABLE пациент (
    пациент_ID INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    пациент_ФИО varchar(20) NOT NULL
);
```

**Ключевое отличие:**
- `SERIAL` = `INTEGER` + автоматическая sequence
- `BIGSERIAL` = `BIGINT` + sequence (аналог MySQL BIGINT AUTO_INCREMENT)

---

#### 2️⃣ Типы данных: int(6) → INTEGER

**MySQL:**
```sql
врач_ID int(6) NOT NULL  -- (6) = display width (игнорируется)
процент_скидки int NOT NULL
```

**PostgreSQL:**
```sql
врач_ID INTEGER NOT NULL  -- Нет display width!
процент_скидки INTEGER NOT NULL

-- Или точные типы:
врач_ID INT2  -- smallint (2 байта, -32768..32767)
врач_ID INT4  -- integer (4 байта, стандартный)
врач_ID INT8  -- bigint (8 байтов)
```

**Важно:** В PostgreSQL `int(6)` не существует! Используй `INTEGER`, `SMALLINT`, `BIGINT`.

---

#### 3️⃣ DATETIME → TIMESTAMP

**MySQL:**
```sql
дата_время_приема datetime NOT NULL
```

**PostgreSQL:**
```sql
дата_время_приема TIMESTAMP NOT NULL
-- или с временной зоной:
дата_время_приема TIMESTAMPTZ NOT NULL  -- рекомендуется!

-- Текущее время:
-- MySQL: NOW(), CURRENT_TIMESTAMP
-- Postgres: NOW(), CURRENT_TIMESTAMP (то же самое!)
```

**Типы дат в PostgreSQL:**
- `DATE` — только дата (2024-02-16)
- `TIME` — только время (14:30:00)
- `TIMESTAMP` — дата + время (без timezone)
- `TIMESTAMPTZ` — дата + время (с timezone, **рекомендуется!**)

---

#### 4️⃣ ENGINE = INNODB → убрать

**MySQL:**
```sql
CREATE TABLE deleted_пациенты (
    пациент_ID INT(20) NOT NULL
) ENGINE = INNODB;
```

**PostgreSQL:**
```sql
CREATE TABLE deleted_пациенты (
    пациент_ID INTEGER NOT NULL
);
-- ENGINE не нужен! В Postgres один движок.
```

---

#### 5️⃣ DELIMITER → убрать (не нужен!)

**MySQL:**
```sql
DELIMITER //
CREATE PROCEDURE procedure1 (n INT)
BEGIN
    SELECT * FROM пациент WHERE пациент_ID = n;
END//
DELIMITER ;
```

**PostgreSQL:**
```sql
CREATE OR REPLACE PROCEDURE procedure1 (n INT)
LANGUAGE plpgsql  -- обязательно указать язык!
AS $$
BEGIN
    -- Для SELECT в процедуре нужен курсор или RETURN QUERY
    RAISE NOTICE 'Patient ID: %', n;
    -- Или используй FUNCTION вместо PROCEDURE
END;
$$;

-- Вызов:
CALL procedure1(5);
```

**Ключевое отличие:**
- В PostgreSQL процедуры **не возвращают** результаты SELECT напрямую
- Для возвращения данных используй **FUNCTION** с `RETURNS TABLE` или `RETURN QUERY`

---

#### 6️⃣ Процедуры с возвратом → FUNCTION

**MySQL:**
```sql
CREATE PROCEDURE get_patient(n INT)
BEGIN
    SELECT * FROM пациент WHERE пациент_ID = n;
END;
```

**PostgreSQL (правильно — через FUNCTION):**
```sql
CREATE OR REPLACE FUNCTION get_patient(n INT)
RETURNS TABLE(
    пациент_ID INTEGER,
    пациент_ФИО VARCHAR(20),
    дата_рождения DATE,
    город VARCHAR(20)
)
LANGUAGE plpgsql
AS $$
BEGIN
    RETURN QUERY
    SELECT p.пациент_ID, p.пациент_ФИО, p.дата_рождения, p.город
    FROM пациент p
    WHERE p.пациент_ID = n;
END;
$$;

-- Вызов:
SELECT * FROM get_patient(5);  -- как обычная таблица!
```

---

#### 7️⃣ Триггеры: OLD/NEW синтаксис

**MySQL:**
```sql
CREATE TRIGGER trigger1
BEFORE DELETE ON пациент
FOR EACH ROW
BEGIN
    INSERT INTO deleted_пациенты VALUES (OLD.пациент_ID, OLD.пациент_ФИО, NOW());
END;
```

**PostgreSQL:**
```sql
CREATE OR REPLACE FUNCTION trigger1_func()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO deleted_пациенты VALUES (OLD.пациент_ID, OLD.пациент_ФИО, NOW());
    RETURN OLD;  -- обязательно для BEFORE DELETE
END;
$$;

CREATE TRIGGER trigger1
BEFORE DELETE ON пациент
FOR EACH ROW
EXECUTE FUNCTION trigger1_func();  -- PostgreSQL 11+
-- Или: EXECUTE PROCEDURE trigger1_func(); (старый синтаксис)
```

**Ключевое отличие:**
- В PostgreSQL триггер **вызывает функцию**, а не содержит код напрямую
- Функция должна возвращать `TRIGGER` тип
- Нужно `RETURN OLD` (для DELETE) или `RETURN NEW` (для INSERT/UPDATE)

---

#### 8️⃣ MODIFY COLUMN → ALTER COLUMN

**MySQL:**
```sql
ALTER TABLE пациент
MODIFY город VARCHAR(200),
MODIFY пациент_ФИО VARCHAR(200);
```

**PostgreSQL:**
```sql
ALTER TABLE пациент
ALTER COLUMN город TYPE VARCHAR(200),
ALTER COLUMN пациент_ФИО TYPE VARCHAR(200);
```

**Другие ALTER операции:**
```sql
-- Изменить DEFAULT
ALTER TABLE пациент ALTER COLUMN город SET DEFAULT 'Москва';

-- Добавить NOT NULL
ALTER TABLE пациент ALTER COLUMN город SET NOT NULL;

-- Убрать NOT NULL
ALTER TABLE пациент ALTER COLUMN город DROP NOT NULL;
```

---

#### 9️⃣ RENAME TO (таблица/столбец)

**MySQL:**
```sql
-- Переименовать таблицу:
ALTER TABLE пациент RENAME TO пациенты;

-- Переименовать столбец (старый синтаксис):
ALTER TABLE пациент CHANGE COLUMN старое_имя новое_имя VARCHAR(20);
```

**PostgreSQL:**
```sql
-- Переименовать таблицу:
ALTER TABLE пациент RENAME TO пациенты;  -- то же самое!

-- Переименовать столбец (проще):
ALTER TABLE пациент RENAME COLUMN старое_имя TO новое_имя;
```

---

#### 🔟 LOOP, REPEAT, WHILE синтаксис

**MySQL:**
```sql
DELIMITER //
CREATE PROCEDURE procedure6 (n INT, i INT)
BEGIN
a: LOOP
    IF (SELECT стоймость FROM обращение WHERE id = i) >= n THEN
        UPDATE обращение SET стоймость = стоймость - 100 WHERE id = i;
    ELSE
        LEAVE a;  -- выход из цикла
    END IF;
END LOOP;
END//
```

**PostgreSQL:**
```sql
CREATE OR REPLACE PROCEDURE procedure6 (n INT, i INT)
LANGUAGE plpgsql
AS $$
DECLARE
    current_cost INT;
BEGIN
    LOOP
        SELECT стоймость INTO current_cost FROM обращение WHERE id = i;
        
        IF current_cost >= n THEN
            UPDATE обращение SET стоймость = стоймость - 100 WHERE id = i;
        ELSE
            EXIT;  -- выход из цикла (вместо LEAVE)
        END IF;
    END LOOP;
END;
$$;
```

**Циклы в PostgreSQL:**
```sql
-- 1. LOOP (бесконечный цикл с EXIT)
LOOP
    EXIT WHEN условие;  -- выход
END LOOP;

-- 2. WHILE
WHILE условие LOOP
    -- код
END LOOP;

-- 3. FOR (по диапазону)
FOR i IN 1..10 LOOP
    RAISE NOTICE 'i = %', i;
END LOOP;

-- 4. FOR (по результату запроса)
FOR record IN SELECT * FROM users LOOP
    RAISE NOTICE 'User: %', record.name;
END LOOP;
```

### 12.2. ПОЛНАЯ КОНВЕРТАЦИЯ (пример из лабораторной)

**MySQL (оригинал):**
```sql
DROP DATABASE IF EXISTS pol;
CREATE DATABASE pol; 
USE pol;

CREATE TABLE пациент (
    пациент_ID int(6) NOT NULL AUTO_INCREMENT,
    пациент_ФИО varchar(20) NOT NULL,
    дата_рождения date NOT NULL,
    город varchar(20) NOT NULL,
    PRIMARY KEY (пациент_ID)
);

CREATE TABLE врач (
    врач_ID int(6) NOT NULL AUTO_INCREMENT,
    ФИО_врача varchar(20) NOT NULL,
    специальность varchar(20) NOT NULL,
    PRIMARY KEY (врач_ID)
);

CREATE TABLE обращение (
    обращение_ID int(6) NOT NULL AUTO_INCREMENT,
    дата_время_приема datetime NOT NULL,
    пациент_ID int(6) NOT NULL default '1',
    врач_ID int(6) NOT NULL default '1',
    стоймость_обращения varchar(100) NOT NULL,
    PRIMARY KEY (обращение_ID),
    FOREIGN KEY (пациент_ID) REFERENCES пациент(пациент_ID) ON DELETE CASCADE,
    FOREIGN KEY (врач_ID) REFERENCES врач(врач_ID) ON DELETE CASCADE
);
```

**PostgreSQL (конвертированный):**
```sql
DROP DATABASE IF EXISTS pol;
CREATE DATABASE pol;
\c pol;  -- подключение к БД (вместо USE)

CREATE TABLE пациент (
    пациент_ID SERIAL PRIMARY KEY,
    пациент_ФИО VARCHAR(20) NOT NULL,
    дата_рождения DATE NOT NULL,
    город VARCHAR(20) NOT NULL
);

CREATE TABLE врач (
    врач_ID SERIAL PRIMARY KEY,
    ФИО_врача VARCHAR(20) NOT NULL,
    специальность VARCHAR(20) NOT NULL
);

CREATE TABLE обращение (
    обращение_ID SERIAL PRIMARY KEY,
    дата_время_приема TIMESTAMP NOT NULL,
    пациент_ID INTEGER NOT NULL DEFAULT 1,
    врач_ID INTEGER NOT NULL DEFAULT 1,
    стоймость_обращения VARCHAR(100) NOT NULL,
    
    FOREIGN KEY (пациент_ID) REFERENCES пациент(пациент_ID) ON DELETE CASCADE,
    FOREIGN KEY (врач_ID) REFERENCES врач(врач_ID) ON DELETE CASCADE
);
```

### 12.3. БЫСТРАЯ ШПАРГАЛКА MySQL → PostgreSQL

| Операция | MySQL | PostgreSQL |
|----------|-------|------------|
| **AUTO_INCREMENT** | `INT AUTO_INCREMENT` | `SERIAL` или `GENERATED ALWAYS AS IDENTITY` |
| **Типы int** | `int(6)`, `int(11)` | `INTEGER`, `SMALLINT`, `BIGINT` |
| **Дата/время** | `DATETIME`, `TIMESTAMP` | `TIMESTAMP`, `TIMESTAMPTZ` |
| **Движок** | `ENGINE=InnoDB` | Не нужен |
| **Разделитель** | `DELIMITER //` | Не нужен (используй `$$`) |
| **Процедура с SELECT** | `PROCEDURE` | `FUNCTION RETURNS TABLE` + `RETURN QUERY` |
| **Триггер** | Код в `CREATE TRIGGER` | Создай функцию + `EXECUTE FUNCTION` |
| **MODIFY COLUMN** | `MODIFY column TYPE` | `ALTER COLUMN column TYPE` |
| **Переименовать столбец** | `CHANGE COLUMN old new` | `RENAME COLUMN old TO new` |
| **Выход из цикла** | `LEAVE label` | `EXIT` |
| **USE database** | `USE db_name` | `\c db_name` (в psql) |
| **Показать таблицы** | `SHOW TABLES` | `\dt` (в psql) или `SELECT * FROM pg_tables` |
| **LIMIT OFFSET** | `LIMIT 10 OFFSET 20` | То же самое! |

### 12.4. ТИПИЧНЫЕ ОШИБКИ ПРИ МИГРАЦИИ

#### ❌ Ошибка 1: Забыл убрать `int(6)`
```sql
-- MySQL
CREATE TABLE users (id int(6) PRIMARY KEY);

-- PostgreSQL (НЕПРАВИЛЬНО!)
CREATE TABLE users (id int(6) PRIMARY KEY);  -- ❌ синтаксическая ошибка!

-- PostgreSQL (ПРАВИЛЬНО)
CREATE TABLE users (id INTEGER PRIMARY KEY);  -- ✅
```

#### ❌ Ошибка 2: Процедура с SELECT
```sql
-- MySQL
CREATE PROCEDURE get_users()
BEGIN
    SELECT * FROM users;
END;

-- PostgreSQL (НЕПРАВИЛЬНО!)
CREATE PROCEDURE get_users()  -- ❌ PROCEDURE не вернёт SELECT
LANGUAGE plpgsql AS $$
BEGIN
    SELECT * FROM users;  -- результат потеряется!
END; $$;

-- PostgreSQL (ПРАВИЛЬНО)
CREATE FUNCTION get_users()  -- ✅ FUNCTION + RETURNS TABLE
RETURNS TABLE(id INT, name VARCHAR)
LANGUAGE plpgsql AS $$
BEGIN
    RETURN QUERY SELECT u.id, u.name FROM users u;
END; $$;
```

#### ❌ Ошибка 3: Триггер без функции
```sql
-- MySQL
CREATE TRIGGER log_delete
BEFORE DELETE ON users
FOR EACH ROW
BEGIN
    INSERT INTO logs VALUES (OLD.id, NOW());
END;

-- PostgreSQL (НЕПРАВИЛЬНО!)
CREATE TRIGGER log_delete  -- ❌ нет тела триггера в Postgres!
BEFORE DELETE ON users
FOR EACH ROW
BEGIN ...  -- синтаксическая ошибка

-- PostgreSQL (ПРАВИЛЬНО)
-- 1. Создаём функцию:
CREATE FUNCTION log_delete_func() RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO logs VALUES (OLD.id, NOW());
    RETURN OLD;
END; $$ LANGUAGE plpgsql;

-- 2. Создаём триггер, вызывающий функцию:
CREATE TRIGGER log_delete
BEFORE DELETE ON users
FOR EACH ROW
EXECUTE FUNCTION log_delete_func();  -- ✅
```

### 12.5. ИНСТРУМЕНТЫ ДЛЯ АВТОМАТИЧЕСКОЙ МИГРАЦИИ

**pgloader** — утилита для миграции MySQL → PostgreSQL:
```bash
# Установка (Ubuntu/Debian)
sudo apt install pgloader

# Миграция целой БД
pgloader mysql://user:pass@localhost/mydb postgresql://user:pass@localhost/newdb

# С конфигурационным файлом
pgloader mydb.load
```

**Пример конфига `mydb.load`:**
```
LOAD DATABASE
    FROM mysql://root:pass@localhost/mydb
    INTO postgresql://postgres:pass@localhost/mydb

WITH include drop, create tables, create indexes, reset sequences

SET work_mem to '256MB', maintenance_work_mem to '512 MB';
```

**Альтернативы:**
- **AWS DMS** (Database Migration Service)
- **Flyway** / **Liquibase** (для версионирования миграций)
- Ручная конвертация через дамп: `mysqldump` + правка SQL + `psql`
