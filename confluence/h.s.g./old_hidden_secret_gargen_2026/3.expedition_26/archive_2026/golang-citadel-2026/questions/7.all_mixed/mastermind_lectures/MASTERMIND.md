📦 Выжимка: sync.Pool в Go (за 2 минуты)
1. В чем суть?
   Это кэш для временных объектов. Вместо того чтобы создавать новый объект (выделять память) на каждый запрос, ты берешь старый из пула, используешь и кладешь обратно. Главная цель — снизить нагрузку на сборщик мусора (GC).

2. Почему он "ничего не гарантирует"?
   GC имеет право в любой момент незаметно выкинуть объекты из пула, чтобы освободить память.

Это фича, а не баг. sync.Pool оптимизирует пиковую нагрузку. Если пул пуст — pool.Get() просто создаст новый объект через функцию New. Если пул полон — часть объектов почистят. Сервис не упадет, а просто на секунду станет чуть медленнее создавать объекты заново.

3. Главное правило безопасности (Священный ритуал)
   Алгоритм работы должен быть жестким:

Get() — берем объект.

Используем — пишем данные.

Очищаем (Reset) — возвращаем в исходное состояние (самый частый баг, если забыть!).

Put() — кладем обратно.

Если забыть очистить, следующий получит объект с мусором (старыми данными).

4. Где применять (Идеальные кейсы)

Тяжелые объекты, которые создаются очень часто, но живут недолго.

Классика: bytes.Buffer (для JSON, шаблонов), большие срезы ([]byte).

НЕ применять для соединений (БД, HTTP-клиенты) — там нужны свои механизмы.

5. Ответ на собеседовании (Короткая схема)

"sync.Pool — это инструмент для переиспользования объектов. Мы кладем в него, например, bytes.Buffer, чтобы на каждый HTTP-запрос не создавать новый буфер, а брать старый. Это резко снижает количество аллокаций и давление на GC. Важно помнить: пул не хранит объекты вечно — GC может их почистить. Поэтому логика простая: Get, использовать, сбросить состояние (иначе будут гонки), Put обратно."


Блок 1: Массивы и Слайсы (Go)
Это, пожалуй, самая холиварная тема на джуниор-мидл собесах.

1. Массив vs Слайс

Массив: [4]int. Фиксированный размер, известный на этапе компиляции. Передается по значению (копируется).

Слайс: []int. Надстройка над массивом. Структура из трех полей: указатель на массив, длина (len), емкость (cap). Передается как ссылка (точнее, как структура, содержащая указатель).

2. Append и емкость (cap)

append() добавляет элементы.

Если len < cap: просто заполняет существующий массив.

Если len == cap: происходит реаллокация — создается новый массив (обычно в 2 раза больше, если cap < 1024, и на ~25% если больше), указатель в слайсе меняется на новый массив, старый массив уходит в GC, если на него никто не ссылается.

Важно: После реаллокации старый и новый слайсы смотрят в разные места.

3. Синтаксис [1:2:3] (Полный срез)

[low:high:max]

low (1) — начальный индекс (включительно).

high (2) — конечный индекс (не включительно) -> определяет len.

max (3) — индекс, до которого считается емкость -> определяет cap (cap = max - low).

Зачем? Чтобы ограничить емкость нового слайса и случайно не перезаписать данные в исходном массиве через append.

4. Пример с подвохом

go
slice := make([]int, 4) // len=4, cap=4, массив [0,0,0,0]
slice = []int{1, 2}     // Переприсвоили! Теперь len=2, cap=2 (новый массив)
slice = append(slice, 3) // len=2 < cap=2? Нет, равно. cap=2 -> не хватает.
// Происходит реаллокация: новый массив с cap=4. Адрес поменялся!
Вывод: Указатель на изначальный массив (где было 4 элемента) потерян навсегда после строки slice = []int{1, 2}.

Блок 2: Базы данных (PostgreSQL)
1. Уровни изоляции (ACID)
   4 уровня (от слабого к строгому):

Read Uncommitted: Грязное чтение (видит незакоммиченные данные). В Postgre нет, он работает как Read Committed.

Read Committed: Видит только закоммиченные данные (дефолт в Postgre). Защита от грязного чтения.

Repeatable Read: Гарантирует, что прочитанные данные не изменятся в рамках транзакции. Защита от неповторяющегося чтения.

Serializable: Транзакции идут строго по очереди. Защита от фантомов.

2. Нормализация vs Денормализация

Нормализация: Разбиение данных на связанные таблицы (как 3НФ). Минимум дублирования, целостность. Минус: много JOIN'ов.

Денормализация: Сознательное добавление дублирующих данных в одну таблицу или добавление избыточности. Ускорение чтения (быстрее, чем JOIN), но сложнее поддержка (обновлять в нескольких местах).

3. Индексы: B-tree vs Hash

B-tree: Стандарт. Работает с диапазонами (>, <, BETWEEN), порядком сортировки (ORDER BY), префиксным поиском. Сбалансированное дерево.

Hash: Только на точное равенство (=). Быстрее B-tree для точечных запросов, но бесполезен для диапазонов.

4. DELETE vs TRUNCATE

DELETE: DML (операция с данными). Можно с WHERE. Медленный, генерирует много WAL (журнала), срабатывают триггеры. Можно ROLLBACK.

TRUNCATE: DDL (операция с таблицей). Быстро чистит всю таблицу, сбрасывает счетчики последовательностей. Нельзя WHERE, откатить сложно (хотя можно в транзакции в Postgre). Не вызывает триггеры удаления.

Блок 3: Обработка ошибок и Паники (Go)
1. Ошибка (error) — это интерфейс

go
type error interface {
Error() string
}
Любая структура с методом Error() string — это ошибка.

2. Panic / Recover

panic — аварийное завершение (паника).

recover — перехват паники. Работает только внутри defer.

Отловить панику из main можно, обернув main() в функцию с defer и recover, но это сомнительный паттерн.

3. Какие паники нельзя отловить?

recover не спасает если программа действительно сломалась:

Конкурентная запись в map (data race) — это не recover, это аварийное завершение рантайма.

Запись в закрытый канал (но запись в неинициализированный (nil) канал — это deadlock, а панику? обычно блокировка).

Нехватка памяти (out of memory).

4. Ошибки в конкурентном коде

Канал ошибок: Создать канал и собирать ошибки из горутин.

errgroup (из golang.org/x/sync/errgroup): Удобно запустить горутины и получить первую ошибку или дождаться всех.

Контекст: Отмена по ошибке через context.WithCancel.

5. errors.Is vs errors.As

Is: Проверяет, является ли ошибка конкретным значением (сравнение). errors.Is(err, io.EOF)

As: Проверяет, можно ли привести ошибку к конкретному типу (чтобы достать поля). var myErr *MyErrorType; errors.As(err, &myErr)

Блок 4: Сборщик мусора (GC) в Go
1. Трехцветная маркировка

Белые: Непосещенные (кандидаты на удаление).

Серые: Посещенные, но ссылки на них еще не проверены (рабочая очередь).

Черные: Посещенные, все ссылки проверены. Выживают.

2. Stop the World (STW)

Моменты, когда программа полностью замораживается для GC. В Go их стараются минимизировать (происходят в основном в начале и конце цикла сборки).

3. GC и sync.Pool

GC очищает sync.Pool перед сборкой. Да, может почистить.

Словить панику в sync.Pool? Можно, если в функциях New, Get или Put вызывать panic.

4. GC и Map

Освободит ли GC память при удалении ключа из map[string][]byte?

Запись в мапе удалится.

НО! Если []byte был большой, и это единственная ссылка — память освободится.

Важно: Сама мапа не сжимается. Удаление ключей не уменьшает количество bucket'ов.

5. Mark Assist

Если горутина аллоцирует память быстрее, чем GC успевает маркировать, она сама помогает GC делать маркировку, прежде чем получить новую память. Это замедляет программу, но предотвращает нехватку памяти.

6. Стек vs Куча

Стек: Локальные переменные, вызовы функций. Живет пока работает функция. GC туда не лезет (очищается при выходе из функции).

Куча: Данные, которые живут дольше функции (переданные по указателю наружу). GC работает только с кучей.

Блок 5: Общие вопросы
1. GMP модель (Goroutine Scheduler)

G — Goroutine (легкий поток).

M — Machine (поток ОС).

P — Processor (контекст, отвечает за запуск G на M, имеет локальную очередь горутин).

2. make() vs new()

new(T): Выделяет память под тип T и возвращает указатель на нулевое значение (например, *int = 0). Работает для любых типов.

make(T): Работает только для слайсов, мап, каналов. Возвращает инициализированное значение (не указатель), готовое к использованию.

3. CAP-теорема

В распределенной системе можно выбрать только 2 из 3:

Consistency (Согласованность) — данные одинаковы на всех узлах.

Availability (Доступность) — любой запрос дает ответ (не ошибку).

Partition Tolerance (Устойчивость к разрыву) — система работает, если связь между узлами потеряна.

Выбор: CP (банки — важна целостность) или AP (соцсети — важна доступность). Жертвовать P нельзя, если система распределенная.

Разбор транскрибата: Пакет sync
1. sync.Map (оф. документ)

Что сказано: Состоит из двух карт (read и dirty).

Детализация: Да, это так. read — это атомарная карта (неблокирующая для чтения), dirty — карта для записи, требующая блокировки. Когда количество промахов в read достигает предела, dirty промотается в read. Нюанс: sync.Map эффективен только при паттерне "много чтений, мало записей" или когда разные ключи пишутся/читаются разными горутинами. Для обычных мап с мьютексом он может быть медленнее.

2. WaitGroup (оф. документ)

Что сказано: Работает как счётчик. Принцип работы основан на семафоре и буферизированном канале.

Детализация: Это не совсем так. Внутри WaitGroup использует атомарные операции (для счётчика) и семафор (syscall) для блокировки/пробуждения горутин. Буферизированный канал там не используется, это было бы слишком дорого.

3. Мьютексы и Starvation Mode (оф. документ)

Что сказано: Если мьютекс занят, рутина уходит в очередь. Starvation mode предотвращает "несанкционированный доступ".

Детализация: В Go мьютексы (начиная с версии 1.9) работают в двух режимах:

Normal mode: Горутины встают в очередь FIFO, но пробудившаяся горутина соревнуется с новой, которая пришла одновременно. Новая может выиграть (так как уже работает на CPU). Это может привести к "голоданию" (starvation) долго ждущих горутин.

Starvation mode: Если горутина ждет дольше 1 мс, мьютекс переходит в этот режим. Тогда пробудившаяся горутина получает мьютекс сразу, без соревнования с новыми. Новые встают в конец очереди.

Разбор транскрибата: Базы данных (SQL)
1. UNION vs JOIN (оф. документ)

Что сказано: UNION добавляет записи (в высоту), JOIN добавляет колонки (в ширину). UNION требует одинаковую структуру.

Детализация: ✅ Абсолютно верно. Добавлю про UNION ALL — он не удаляет дубликаты (работает быстрее UNION).

2. Уровни изоляции и Lost Update (оф. документ)

Что сказано: Описаны грязное, неповторяющееся, фантомное чтение и Lost Update. Упомянута пессимистичная блокировка.

Детализация:

Lost Update (Потерянное обновление): Классика — две транзакции читают одно значение (10), каждая уменьшает на 1. Первая пишет 9, вторая пишет 9 (поверх первой). Потеряли одно изменение.

Борьба: На уровне REPEATABLE READ в Postgre или SERIALIZABLE, либо через SELECT ... FOR UPDATE (пессимистичная блокировка — блокируем строку на время транзакции).

Разбор транскрибата: Брокеры сообщений (RabbitMQ vs Kafka)
1. Push vs Pull (оф. документ)

Что сказано: RabbitMQ — push, Kafka — pull.

Детализация: ✅ Верно. RabbitMQ сам "толкает" сообщения потребителю. Kafka — потребитель сам "тянет" сообщения из партиции, когда готов. Это дает Kafka возможность работать с большими потоками и реплицировать данные на диск.

2. Хранение данных (оф. документ)

Что сказано: В Kafka можно хранить на жестком диске, в RabbitMQ это менее развито.

Детализация: Да, Kafka пишет всё на диск (и активно использует кэш ОС для скорости), и сообщения хранятся заданное время (retention), даже если их прочитали. RabbitMQ обычно удаляет сообщение после подтверждения (ack).

3. Топики и партиции (оф. документ)

Что сказано: Kafka гарантирует очередность в рамках одной партиции.

Детализация: ✅ Ключевой момент. Если нужна строгая очередность событий по одному ключу (например, по ID пользователя), они должны попадать в одну партицию.

Разбор транскрибата: Каналы и слайсы в Go
1. Select с тремя кейсами (оф. документ)

Что сказано: Если все три кейса стали истинными одновременно.

Детализация: В спецификации Go сказано: если несколько кейсов могут быть выполнены без блокировки, select выбирает один из них псевдослучайно (рандомно). Нельзя полагаться на порядок.

2. Буфер канала (оф. документ)

Что сказано: Пример структуры буферизированного канала: две очереди и буфер.

Детализация: Структура канала (hchan) содержит циклический буфер (queue), счетчики отправки/получения и две очереди ждущих горутин (sendq и recvq).

3. Слайсы и изменение в функции (оф. документ)

Что сказано: Различие между изменением по индексу и расширением.

Детализация: Это святое.

f(s) — передаем слайс.

s[0] = 100 — изменится в вызывающей функции (так как массив общий).

s = append(s, 200) — внутри функции может создать новый массив (если не хватит cap). Внешний слайс этого не увидит. Важно: Нужно возвращать новый слайс из функции.

Разбор транскрибата: Кэширование и Redis
1. Singleflight (оф. документ)

Что сказано: Инструмент, объединяющий несколько запросов в один при пропадании ключа.

Детализация: Да, это пакет golang.org/x/sync/singleflight. Позволяет предотвратить эффект "стада" (thundering herd), когда 1000 запросов одновременно видят, что кэш пуст, и летят в БД.

2. TTL и лавины (оф. документ)

Что сказано: Одинаковый TTL ведет к неравномерной нагрузке. Нужно добавлять смещение.

Детализация: ✅ Верно. Это называется Кэш-лавина (cache avalanche). Решение: TTL = базовое время + случайное число (jitter).

Разбор транскрибата: Карты (map) и память
1. Освобождение памяти при удалении (оф. документ)

Что сказано: Удаление элементов не уменьшает количество бакетов. Если карта разрослась, она останется в этом объеме.

Детализация: Это чистая правда. Мапа в Go не сжимается (shrink). Если на пике нагрузки в мапе было 1 млн элементов, а потом стало 10, память ОС не вернется. Решение — пересоздать карту: newMap := make(map[T]U, len(oldMap)) и скопировать нужные элементы, старую отпустить для GC.

2. Эвакуация данных (оф. документ)

Что сказано: Данные перемещаются постепенно, по кусочкам.

Детализация: Это про рост мапы (когда идет рехеширование). В Go мапа растет не мгновенно, а постепенно (incremental). При вставке или удалении элементов пара бакетов переносится из старой структуры в новую. Это сделано, чтобы не было длительных пауз.

Блок: Устройство Go (GC, Слайсы, Мапы)
Часть 1: Трехцветная маркировка (GC)
1. Суть алгоритма
   GC в Go использует трехцветную маркировку для определения живых объектов.

Белый: Непосещенный. Кандидат на удаление (если останется белым к концу цикла).

Серый: Посещенный, но его ссылки еще не проверены. Рабочая очередь.

Черный: Посещенный, все его ссылки проверены. Точно живой.

2. Как это работает по шагам

Шаг 1: Начало маркировки (STW)

Программа ненадолго замирает (Stop The World).

GC находит корни (roots) — глобальные переменные и локальные переменные в стеках горутин.

Корни красятся в СЕРЫЙ и помещаются в очередь.

STW заканчивается (обычно < 1 мс).

Шаг 2: Параллельная маркировка (Concurrent)

Программа работает, но специальные worker-горутины GC параллельно разбирают серую очередь:

Берут серый объект A.
Смотрят, на какие объекты A ссылается (его поля-указатели).
Если B — белый, он становится СЕРЫМ (добавляется в очередь).
Сам A становится ЧЕРНЫМ (живой, проверен).
Так серая очередь постепенно становится черной, а белые объекты остаются не у дел.

Шаг 3: Завершение маркировки (STW)

Короткая пауза, чтобы проверить, не появились ли новые ссылки во время маркировки.

Шаг 4: Подметание (Sweep — Concurrent)

Память, занятая белыми объектами, помечается как свободная. Черные живут дальше.

Часть 2: Слайсы (поведение)
17. Передача слайса в функцию: изменение значений

Кейс 1: Изменение элемента по индексу (s[i] = x)

Изменится ли вне функции? ДА.

Почему? Слайс содержит указатель на массив. Функция получает копию структуры слайса, но указатель указывает на тот же массив.

Кейс 2: Добавление элементов (append)

Изменится ли вне функции? ЗАВИСИТ.

Почему? Если len < cap — append использует тот же массив, и изменения увидят оба слайса (если len внешнего слайса позволяет это увидеть).

Почему? Если len == cap — append создает новый массив (реаллокация). Внутри функции слайс начинает указывать на новый массив, а внешний слайс — на старый. Изменения теряются.

Вывод: Если функция может менять длину слайса, ее нужно возвращать.

Часть 3: Мапы (устройство и поведение)
18. Что такое map и как устроена?

Хэш-таблица. В Go это массив бакетов (корзин). Ключ хэшируется, младшие биты хэша определяют номер бакета.

Бакет: Хранит до 8 пар ключ-значение, у которых хэши попали в этот бакет. Если ключей больше 8, создается бакет переполнения (overflow bucket), связанный в список.

19. var m map[string]int vs m := make(map[string]int)

var m map[string]int

Объявляет переменную, но не инициализирует ее.

m == nil (нулевое значение для map).

Чтение: Работает, вернет zero-value для типа значения (0 для int).

Запись: m["key"] = 1 -> panic: assignment to entry in nil map.

m := make(map[string]int)

Создает пустую, готовую к использованию хэш-таблицу.

m != nil.

20. Range по map: порядок и адресация

Порядок: НЕ ГАРАНТИРУЕТСЯ. Более того, от запуска к запуску порядок будет разный (рандомизирован, чтобы программисты не привыкали).

Адрес значения: addr := &m["key"] — НЕЛЬЗЯ (ошибка компиляции).

Почему? Мапа в Go может перемещать значения при эвакуации (росте). Если бы Go отдал указатель на значение в бакете, а потом бакет переехал, указатель бы повис.

21. Что будет, если в двух горутинах начнется эвакуация?

Эвакуация (рост мапы) — это внутренний процесс. Но если две горутины одновременно пишут в мапу, вызывая ее рост, это приведет к data race. Go детектит это и выбрасывает fatal error: concurrent map writes. Отловить recover это нельзя — программа аварийно завершится.

22. Может ли структура быть ключом?

Да, может, если все поля структуры сравниваемы (comparable).

Несравниваемые типы: слайсы, мапы, функции. Если в структуре есть поле-слайс, такая структура не может быть ключом.

23. Что будет, если 2 горутины пишут в одну мапу?

Та же участь: fatal error: concurrent map writes. Go разработан так, что даже просто писать параллельно без синхронизации нельзя. Нужен sync.Mutex или sync.Map.

24. Освободится ли память, если удалить все элементы из огромной map?

НЕТ.

Почему? Мапа в Go не уменьшается (shrink). Количество бакетов, однажды выделенное под мапу, остается занятым.

Решение: Если мапа была огромной, а стала пустой, и память нужна — нужно пересоздать мапу: m = make(map[T]U). Старая мапа уйдет в GC, освободив бакеты.

25. Как хранятся данные внутри бакета?

Нюанс: Для оптимизации выравнивания (memory alignment) и уменьшения расхода памяти, ключи хранятся отдельным блоком, значения — отдельным.

Сначала идет массив из 8 "топ-хэшей" (первый байт хэша для быстрого сравнения).

Потом массив из 8 ключей.

Потом массив из 8 значений.

Потом указатель на overflow-бакет.

Такая структура позволяет, например, при map[int64]int8 не тратить память на padding.

26-27. Эвакуация данных (когда и как)

Когда возникает? Когда средняя загрузка бакетов (load factor) превышает ~6.5 (или слишком много overflow-бакетов). Мапа решает, что пора расти.

Как происходит?

Выделяется новый массив бакетов (в 2 раза больше).
Мапа переходит в состояние "роста".
Данные перемещаются НЕ СРАЗУ, а постепенно (incremental). При каждой вставке или удалении пару старых бакетов "эвакуируются" (переезжают) в новую память.
Это сделано, чтобы не было длительной "заморозки" программы на время копирования миллионов элементов. Хэш-таблица растет плавно.

Блок: Базы данных (SQL и не только)
Часть 1: Основы SQL (UNION, JOIN)
1. UNION vs UNION ALL vs JOIN

UNION: Объединяет результаты двух запросов вертикально (одна под другой). Убирает дубликаты (выполняет DISTINCT). Требует одинаковое количество и типы колонок.

UNION ALL: То же объединение, но без удаления дубликатов. Работает быстрее UNION.

JOIN: Объединяет таблицы горизонтально (добавляет колонки). Соединяет строки по условию (ключу).

Меткофап: UNION расширяет таблицу в высоту, JOIN — в ширину.

Часть 2: Транзакции и аномалии
2. Что такое Lost Update (Потерянное обновление)?

Суть: Классическая проблема конкурентности. Две транзакции читают одно значение, каждая его изменяет, и последняя запись перезаписывает первую, не учитывая ее изменение.

Пример (как в твоем конспекте): Счет 100$. Т1 вычитает 50, Т2 добавляет 10%. Без блокировок результат будет 110$ (проценты от старых 100) вместо 60$. Изменение Т1 потеряно.

Как бороться: Блокировки или уровни изоляции (об этом ниже).

3. Уровни изоляции транзакций (ACID)
   4 стандартных уровня (от слабого к строгому):

Read Uncommitted: Можно читать незакоммиченные данные других транзакций.

Аномалия: Грязное чтение (Dirty Read) — прочитал данные, которые потом откатились.

Read Committed (дефолт в PostgreSQL): Видим только закоммиченные данные.

Решает: Dirty Read.

Аномалии остаются: Неповторяющееся чтение, Фантомы.

Repeatable Read: Если прочитал строку дважды в одной транзакции — данные не изменятся.

Решает: Dirty Read, Non-repeatable Read.

Аномалии: Фантомы (в некоторых СУБД, в PostgreSQL на этом уровне фантомов тоже нет).

Serializable: Самый строгий. Транзакции идут так, как будто выполняются по очереди.

Решает: Все аномалии (Dirty Read, Non-repeatable Read, Phantom Read, Lost Update).

4. Non-repeatable Read vs Phantom Read (Ключевое отличие)

Неповторяющееся чтение (Non-repeatable Read): Одна и та же строка меняет свое содержимое (значение поля) между чтениями в рамках одной транзакции.

Пример: Прочитал имя пользователя = "Вася". Другая транзакция поменяла на "Петя". При повторном чтении — "Петя".

Фантомное чтение (Phantom Read): Меняется набор строк, удовлетворяющих условию. Появляются новые строки (фантомы) или исчезают старые.

Пример: Выбрал все заказы пользователя с суммой > 100. Получил 2 строки. Другая транзакция добавила новый заказ на 150. При повторном SELECT'е — 3 строки.

5. Как избежать Lost Update?

Атомарная операция: Вместо "прочитать -> вычислить -> записать" делать UPDATE accounts SET balance = balance - 50 WHERE id = 1. Это блокировка на уровне строки средствами БД.

Пессимистичная блокировка: Явно заблокировать строку.

Оптимистичная блокировка: Использовать версионность.

6. Пессимистичная блокировка (как наложить)

Синтаксис: SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

Что делает: Блокирует выбранные строки. Другая транзакция, попытавшаяся выполнить SELECT FOR UPDATE, UPDATE или DELETE этих строк, будет ждать окончания первой транзакции (COMMIT/ROLLBACK).

7. Оптимистичная vs Пессимистичная блокировка

Пессимистичная: "Я уверен, что кто-то захочет изменить эти данные прямо сейчас, поэтому я их заблокирую, пока работаю." (Блокировка на уровне БД, SELECT FOR UPDATE).

Плюс: Гарантирует целостность.

Минус: Может быть медленной (очереди), возможны дедлоки.

Оптимистичная: "Я надеюсь, что никто не изменит данные, пока я работаю. Но если изменил — переделаю." (Использует версионность — поле version).

Как работает: Читаем запись (version=1). Изменяем. Сохраняем: UPDATE ... SET version=2 WHERE id=1 AND version=1. Если affected rows == 0, значит кто-то изменил до нас — повторяем операцию.

Плюс: Нет блокировок, лучше для производительности при низкой конкуренции.

Минус: При высокой конкуренции много повторных попыток.

8. Приоритет уровня изоляции

Наиболее приоритетный: Уровень транзакции. Он переопределяет настройки сессии и базы.

9-10. Read Uncommitted в PostgreSQL

Есть ли? Формально — да, синтаксис принят. Но работает как Read Committed.

Почему? Архитектура Postgres не позволяет делать грязное чтение (слишком сложно реализовать без падения производительности, проще всегда читать закоммиченное).

Часть 3: Распределенные системы и паттерны
11. Что такое идемпотентность?

Суть: Свойство операции, при котором многократное выполнение дает тот же результат, что и однократное.

Зачем: В распределенных системах сообщения могут дублироваться (сеть, таймауты, ретраи). Если операция идемпотентна, повторный запрос не навредит.

Реализация: Передавать уникальный idempotency_key (UUID) в запросе и хранить результат выполнения по этому ключу. При повторном запросе с тем же ключом — возвращать закешированный результат.

12. API Gateway — для чего?

Суть: Единая точка входа (шлюз) для всех клиентов в микросервисной архитектуре.

Функции:

Маршрутизация: Перенаправляет запросы к нужным микросервисам (/users -> сервис пользователей, /orders -> сервис заказов).

Аутентификация/Авторизация: Проверяет токены до входа в систему.

Rate Limiting: Ограничивает количество запросов от клиента.

Логирование/Мониторинг: Собирает метрики по всем запросам.

Агрегация: Может сходить в несколько сервисов и собрать ответ для клиента (Backend For Frontend).

Часть 4: Типы баз данных
13. Колоночные базы данных (Columnar/Column-oriented)

Для чего нужны: Для аналитики (OLAP — Online Analytical Processing). Где нужно посчитать сумму, среднее, группировку по миллионам строк.

Принцип: Данные хранятся не строками, а колонками. Все значения одной колонны лежат рядом на диске.

Преимущество: Если нужно посчитать средний возраст всех пользователей, колоночная БД прочитает только данные колонки "возраст" (мегабайты), а строчная прочитает целиком все строки (гигабайты). Огромный выигрыш в скорости и сжатии.

14. Векторные и Графовые БД

Векторные:

Для чего: Для поиска по смыслу (семантический поиск), рекомендательные системы, поиск изображений, работа с LLM (большими языковыми моделями).

Как работают: Данные превращаются в вектор (массив чисел) с помощью ML-моделей. БД ищет "ближайшие" векторы (по косинусному расстоянию).

Графовые:

Для чего: Для данных с очень сложными и глубокими связями. Соцсети (друзья друзей), системы рекомендаций, выявление мошеннических схем, управление доступом.

Как работают: Хранят узлы (сущности) и ребра (связи). Запросы типа "найти кратчайший путь" или "проверить связь через 5 уровней" выполняются молниеносно, в отличие от SQL с 10 JOIN'ами.

Блок: Брокеры сообщений (RabbitMQ, Kafka)
Часть 1: Основы и мотивация
1. Что такое брокеры сообщений и зачем они нужны?

Суть: Это промежуточное ПО (middleware) для асинхронного обмена данными между сервисами. Сервисы не общаются напрямую, а через брокер.

Зачем: Чтобы отвязать отправителя от получателя. Сервис А кинул сообщение в брокер и забыл, занимается своими делами. Сервис Б заберет сообщение, когда будет готов.

Почему нельзя напрямую? Можно, но будет синхронная связь (HTTP/gRPC). Минусы: отправитель ждет ответа (блокировка), если получатель упал — запрос потерян, сложно балансировать пиковую нагрузку.

2. Минусы использования брокеров

Дополнительная задержка (latency): Сообщение теперь путешествует через промежуточное звено.

Оверхед: Усложнение архитектуры, нужно писать код для публикации и потребления, обрабатывать ошибки сети.

Дополнительная точка отказа: Сам брокер может упасть. Нужно обеспечивать его отказоустойчивость (кластеризация).

Сложность сопровождения: Нужно мониторить очереди, настраивать, обновлять.

Часть 2: RabbitMQ vs Kafka (Ключевые отличия)
3. Чем RabbitMQ отличается от Kafka?
   Это два разных философских подхода.

Характеристика	RabbitMQ	Kafka
Модель	Push (Брокер сам толкает сообщения потребителю)	Pull (Потребитель сам забирает сообщения, когда готов)
Хранение	Очереди в RAM (по умолчанию). Можно настроить персистентность на диск, но это не основная фича.	Все сообщения пишутся на диск и хранятся заданное время (retention), даже если прочитаны.
Маршрутизация	Сложная, гибкая. Есть Exchange, очереди, routing keys.	Простая. Пишем в Topic (который состоит из партиций).
Очередность	Не гарантирует строгую глобальную очередь (если несколько консюмеров).	Гарантирует порядок в рамках одной партиции.
Подход к сообщению	Сообщение удаляется после подтверждения (ack).	Сообщение не удаляется, двигается офсет (указатель чтения). Можно перечитать заново.
Масштабирование	Ограничено производительностью одной очереди.	Линейно растет с увеличением числа партиций.
4. Из чего состоит топик в Kafka?

Из партиций (Partitions). Это основная единица параллелизма и масштабирования.

Сообщения в топике распределяются по партициям (обычно по хэшу ключа или round-robin).

Порядок гарантируется внутри одной партиции, но не между партициями.

5. Гарантирует ли Kafka очередность сообщений?

Да, но только в рамках одной партиции.

Если нужна глобальная очередность для конкретного ключа (например, события по одному пользователю), нужно отправлять все сообщения с этим ключом в одну партицию.

Часть 3: Глубокое погружение в RabbitMQ (Exchange)
6. Что такое Exchange в RabbitMQ и какие они бывают?

Exchange (обменник) — это компонент, который принимает сообщения от продюсера и решает, в какую очередь (или очереди) его направить по определенным правилам.

Типы Exchange (детально):

Direct Exchange (Прямой)

Правило: Отправляет сообщение в очередь, у которой routing_key полностью совпадает с ключом сообщения.

Аналогия: Письмо с точным адресом (индекс + улица + дом).

Применение: Распределение задач по типу (лог с уровнем error идет в очередь ошибок).

Fanout Exchange (Веерный)

Правило: Копирует сообщение во все привязанные к нему очереди. Игнорирует routing_key.

Аналогия: Радиовещание. Все, кто включил приемник, слышат одно и то же.

Применение: Широковещательные уведомления (обновить кэш на всех серверах), события, которые интересны всем.

Topic Exchange (Тематический)

Правило: Маршрутизация по шаблону routing_key с использованием wildcards.

Символы:

* (звездочка) — заменяет ровно одно слово.

# (решетка) — заменяет ноль или более слов.

Аналогия: Подписка на теги новостей. sports.* — все новости спорта, #.weather — все новости о погоде где угодно.

Применение: Гибкая маршрутизация событий (логи по сервисам и уровням).

Headers Exchange (По заголовкам)

Правило: Игнорирует routing_key. Решение принимается на основе заголовков (headers) сообщения — это пары ключ-значение.

Доп. аргумент: x-match: all (нужны все указанные заголовки) или x-match: any (достаточно любого).

Аналогия: Сложный фильтр по атрибутам.

Применение: Маршрутизация по множеству параметров, когда ключ неудобен (например, тип контента + язык + версия).

Default Exchange (По умолчанию)

Это встроенный прямой exchange с пустым именем ("").

Правило: Брокер автоматически направляет сообщение в очередь, чье имя совпадает с routing_key.

Применение: Простейшие сценарии, когда не нужна сложная маршрутизация (прямо в очередь по имени).

Блок: Apache Kafka — глубокое погружение
Часть 1: Базовые понятия (Кратко для контекста)
1. Топик (Topic)

Категория или "канал" для сообщений .

Физически может быть разбит на несколько партиций.

2. Партиция (Partition)

Это: Единица параллелизма и масштабирования. Лог-файл, в который сообщения только дописываются в конец (commit log) .

Порядок: Гарантируется строгий порядок сообщений внутри одной партиции .

Офсет (Offset): У каждого сообщения в партиции есть уникальный номер (смещение), по которому его можно найти .

3. Брокер (Broker)

Это просто сервер в кластере Kafka . Хранит данные и обслуживает запросы.

4. Репликация

Зачем: Для отказоустойчивости. Каждая партиция может иметь копии (реплики) на разных брокерах .

Leader — Follower: Одна реплика является лидером (читает и пишет), остальные — последователи (синхронизируются с лидером) .

Часть 2: Устройство партиций и ключевые механизмы
5. Как партиции обеспечивают масштабирование?

Партиции — это ключ к параллелизму. Если у топика 10 партиций, то 10 потребителей (в одной группе) могут читать из них одновременно, каждый из своей партиции .

Количество партиций определяет максимальную степень параллелизма при потреблении. Потребителей (инстансов приложения) в группе может быть не больше, чем партиций. Остальные будут простаивать .

6. Как данные распределяются по партициям?

Продюсер сам решает, в какую партицию отправить сообщение.

По ключу (key): Если указан ключ, Kafka берет его хэш и по нему определяет номер партиции. Это гарантирует, что все сообщения с одним ключом (например, ID пользователя) попадут в одну и ту же партицию, сохраняя порядок обработки событий по этому пользователю .

Round-robin: Если ключа нет, сообщения распределяются по очереди для балансировки нагрузки.

7. Что такое ISR (In-Sync Replicas)?

Это: Список реплик (последователей), которые успели синхронизироваться с лидером и не отстают от него . Только реплики из этого списка могут стать новым лидером в случае сбоя.

Почему это важно: Если разрешить выборы лидера из отставшей реплики (которая не в ISR), данные, которые успел принять старый лидер, но не успели скопироваться, будут потеряны. Это контролируется параметром unclean.leader.election.enable (в проде его ставят в false) .

Часть 3: Гарантии и надежность (CRole)
Теперь про твою "кролю" — про гарантии доставки и надежность.

8. Гарантии при записи (Producer acks)
   Продюсер может выбирать уровень подтверждения:

acks=0: "Выстрелил и забыл". Самый быстрый, но риск потери данных максимальный (брокер упал — сообщение пропало) .

acks=1: Ждем подтверждения только от лидера партиции. Если лидер упадет сразу после ответа, но до того, как последователи скопировали данные, сообщение потеряется .

acks=all (или -1): Ждем подтверждения от всех реплик из ISR. Самый надежный режим .

Важно: Чтобы это работало, нужно настроить min.insync.replicas (например, =2). Если в ISR останется меньше реплик, чем указано, запись будет отклонена. Это защита от записи в ненадежное окружение .

9. Consumer groups и Offset (Смещение)

Consumer Group: Группа потребителей, которые вместе читают данные из топика. Каждое сообщение получает только один потребитель внутри группы (как очередь). Если групп несколько, каждая получит свою копию (как топик) .

Offset commit: Потребитель должен сообщать брокеру, какие сообщения он обработал, фиксируя смещение . Смещения хранятся в специальном внутреннем топике __consumer_offsets .

Опасность: Если коммитить смещение до обработки сообщения и упасть, сообщение будет потеряно (at most once).

Опасность: Если коммитить после обработки, но упасть до коммита, сообщение будет прочитано снова (at least once).

Идемпотентность на стороне потребителя помогает сделать at least once безопасным.

10. CRaC / Coordinated Restore at Checkpoint (если ты про это)

В контексте Kafka прямой связи нет, но есть схожая концепция управляемого состояния.

Если мы говорим про "кролю" как про механизм контрольных точек (checkpoint) для стейтфул-обработки (Kafka Streams), то там есть понятие закрепленных за задачами состояний (state stores). Они периодически снэпшотятся в специальные топики (changelog topics) . При сбое задача восстанавливает свое состояние из этих чейнджлогов перед возобновлением работы. Это и есть механизм отказоустойчивости для стейтфул-процессинга.

11. Гарантия порядка и идемпотентность

Порядок: Только в пределах одной партиции .

Идемпотентный продюсер: Начиная с версии 0.11, можно включить enable.idempotence=true. Kafka будет автоматически дедуплицировать сообщения, если продюсер по ошибке отправил дубликат (из-за ретраев). Это дает стройную гарантию точно один раз (exactly-once) при записи в одну партицию .

Бонус: Современный тренд — KRaft
12. Что такое KRaft и при чем тут ZooKeeper?

Раньше: Kafka для управления кластером (кто лидер, список брокеров) использовала ZooKeeper.

KRaft (Kafka Raft): Начиная с версии 2.8 (экспериментально) и 3.3 (продакшн), Kafka может сама управлять метаданными через встроенный протокол консенсуса Raft .

Зачем: Упрощение архитектуры (не надо тащить отдельный ZooKeeper-кластер), улучшение производительности при большом количестве партиций (миллионы), более быстрый failover контроллера .

Блок: Кэширование (полный разбор)
Часть 1: Основы и проблемы
1. Для чего используется кэширование?

Суть: Сохранение часто используемых данных в быстром хранилище (обычно in-memory) для ускорения доступа и снижения нагрузки на медленные источники (БД, API).

Инструменты кэширования:

In-memory (внутри сервиса): Простая map + sync.RWMutex, sync.Map, библиотеки типа bigcache, freecache (оптимизированы для GC).

Внешние хранилища: Redis (стандарт), Memcached (простой, только ключ-значение).

На границе сети: Varnish, Nginx (кэширование HTTP-ответов), CDN (для статики).

Проблемы кэширования (что нужно учитывать):

Инвалидация (устаревание данных): Как понять, что данные в кэше пора обновить? (Самая сложная проблема в CS).

Холодный старт (Cache Warming): Кэш пуст, первый запрос всегда медленный.

Протухание (TTL): Что делать с данными, которые больше не нужны?

Согласованность (Consistency): Данные в кэше и базе могут расходиться. Насколько это критично?

"Проблема собак" (Thundering Herd): Когда много запросов одновременно видят промах кэша и валят БД.

Размер кэша: Что вытеснять, когда память закончилась? (LRU, LFU, FIFO).

GC (для in-memory): Хранение миллионов объектов в куче Go может убить производительность сборщиком мусора.

Часть 2: Стратегии синхронизации кэша и базы
2. Проблемы синхронизации и стратегии

Cache-Aside (Lazy Loading) — Самый популярный

Как работает: Приложение сначала смотрит в кэш. Если нет (miss) — читает из БД, сохраняет в кэш и отдает.

Плюсы: Простота, кэш содержит только реально запрашиваемые данные.

Минусы: Промах всегда = 2 запроса (кэш + БД). Данные могут быть старыми (stale), если БД обновилась, а кэш нет.

Read-Through

Как работает: Кэш сам ходит в БД при промахе. Приложение общается только с кэшем.

Плюсы: Проще для приложения (меньше логики).

Минусы: Нужна библиотека/прокси, умеющая это делать.

Write-Through

Как работает: При записи данные пишутся синхронно и в кэш, и в БД.

Плюсы: Кэш всегда актуален (сильная согласованность).

Минусы: Запись становится медленнее (пишем в 2 места).

Write-Behind (Write-Back)

Как работает: Данные пишутся только в кэш, а в БД — асинхронно (пачками, по расписанию).

Плюсы: Очень быстрая запись, сглаживание пиков.

Минусы: Риск потери данных, если кэш упадет до синхронизации с БД.

Write-Around

Как работает: Данные пишутся сразу в БД, минуя кэш. Кэш обновится только при следующем чтении (по принципу Cache-Aside).

Плюсы: Кэш не засоряется данными, которые пишутся один раз и редко читаются.

Минусы: Первое чтение после записи будет промахом.

Refresh-Ahead

Как работает: Кэш предсказывает, какие данные скоро понадобятся, и обновляет их до истечения TTL.

Плюсы: Минимизация промахов для горячих данных.

Минусы: Сложно предсказывать, лишние запросы к БД.

Часть 3: Высокая нагрузка и защита БД
3. Самый быстрый вариант кэша

In-memory cache внутри сервиса (например, bigcache или обычная map с шардированием).

Почему: Нет сетевых вызовов (RTT = 0), нет сериализации/десериализации (если храним структуры).

Проблема: GC. Хранить миллионы мелких объектов в куче Go — больно. Решения:

Хранить данные вне кучи (off-heap) — bigcache, freecache.

Шардировать мапу на много мелких (уменьшение блокировок и GC-сканирования).

4. Защита БД при пропадании кэша (Thundering Herd)

Проблема: Лег спать кэш по ключу, 10 000 запросов видят MISS и летят в БД. БД падает.

Решение: Single Flight

Пакет golang.org/x/sync/singleflight.

Как работает: Несколько горутин, пытающихся получить один и тот же ключ, объединяются. Только одна идет в БД, остальные ждут ее результат и получают те же данные.

5. Проблема одинакового TTL (Кэш-лавина)

Проблема: Записали 1000 ключей с TTL = 3600 секунд. Через час они все одновременно протухнут. Сервис словит лавину запросов в БД.

Решение: Jitter (разброс)

Устанавливать TTL = базовое время + случайное число (например, 3600 + rand.Intn(600)). Тогда ключи будут протухать не одновременно, а растянуто по времени.

6. Зачем нужен TTL (Time To Live)?

Автоматическая инвалидация: Данные в источнике (БД) могли измениться. TTL гарантирует, что кэш рано или поздно обновится.

Экономия памяти: Устаревшие данные автоматически удаляются.

Решение проблемы "холодных" данных: То, что не спрашивают долго, не занимает место.

Часть 4: Кластеризация Redis
7. Варианты собрать кластер Redis

Вариант 1: Redis Sentinel

Что это: Master-Slave репликация + мониторинг (Sentinel-ноды).

Принцип: Один мастер (пишет), несколько реплик (читают). Если мастер падает, Sentinel выбирает нового мастера из реплик.

Плюсы: Автоматический фейловер, отказоустойчивость.

Минусы:

Нет шардинга! Все данные на одной ноде (мастере). Объем ограничен памятью одной машины.

Запись всегда в одну точку (мастер).

Вариант 2: Redis Cluster (нативный)

Что это: Решение для горизонтального масштабирования.

Принцип: Данные автоматически шардируются на 16384 слота. Каждая нода мастера отвечает за свой диапазон слотов. Есть реплики для отказоустойчивости.

Плюсы:

Автоматический шардинг (данные распределены по нодам).

Высокая доступность.

Можно масштабироваться, добавляя ноды (перераспределение слотов).

Минусы:

Клиенты должны понимать кластер (уметь переадресовывать запросы MOVED).

Нет транзакций/мульти-ключевых операций, если ключи в разных слотах (кроме хэш-тегов).

Сложнее в настройке.

Вариант 3: Прокси-решения (Twemproxy, Codis)

Исторически: Ставили прослойку между клиентом и Redis, которая делала шардинг. Сейчас Redis Cluster вытеснил это для большинства задач.
