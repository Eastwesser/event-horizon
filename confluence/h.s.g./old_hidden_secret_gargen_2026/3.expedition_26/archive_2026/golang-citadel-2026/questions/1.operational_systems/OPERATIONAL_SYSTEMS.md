Системные вызовы (syscalls)

Суть: Это единственный легальный способ для пользовательской программы (user space) попросить ядро (kernel space) что-то сделать от ее имени. Ядро — привилегированный режим, у него есть доступ к железу и памяти.

Механика: Программа кладет номер системного вызова и аргументы в регистры процессора, а затем вызывает инструкцию int 0x80 (на старых) или syscall (на новых x86_64). Процессор переключается в привилегированный режим, и ядро выполняет запрос.

Примеры: open(), read(), write(), close(), fork(), execve(), socket(), connect().

Это не просто метафора, это абстракция. Если ты можешь открыть это (open()), прочитать это (read()), записать это (write()), и закрыть это (close()), то это "файл" с точки зрения Unix.

Каталоги: Тоже файлы, содержащие список других файлов.

Устройства: /dev/sda (жесткий диск), /dev/tty (терминал). Чтение и запись в них взаимодействует с драйверами устройств.

Пайпы (Pipes): Межпроцессное взаимодействие.

Сокеты (Sockets): Сетевые соединения.

1. Системные вызовы (syscalls) — глубинная механика
   Твой текст:

Суть: Это единственный легальный способ для пользовательской программы (user space) попросить ядро (kernel space) что-то сделать от ее имени.

Разбираем (почему это вообще так):

Два режима процессора:

Ring 3 (User Mode): Здесь живут твои программы. Не имеют доступа к:

Регистрам управления (CR0, CR3...).

Портам ввода-вывода.

Специальным инструкциям (HLT, LGDT, MOV из/в CR3).

Физической памяти (только через виртуальную, которую выдало ядро).

Ring 0 (Kernel Mode): Здесь живет ядро. Имеет доступ ко всему.

Переключение между режимами:
Только через специальные инструкции:

int 0x80 (старый способ, прерывание).

sysenter / sysexit (Intel).

syscall / sysret (AMD, современный стандарт).

Механика syscall (шаг за шагом):

c
// Пользовательский код (libc)
ssize_t read(int fd, void *buf, size_t count) {
long ret;
// Кладем номер syscall (0 для read) в RAX
// fd в RDI, buf в RSI, count в RDX
__asm__ volatile (
"syscall"
: "=a"(ret)
: "a"(__NR_read), "D"(fd), "S"(buf), "d"(count)
: "rcx", "r11", "memory"
);
return ret;
}
Что происходит при syscall:

Процессор сохраняет текущий RIP (следующая инструкция) в RCX.

Сохраняет RFLAGS в R11.

Переключает CS (сегмент кода) на селектор ядра (Ring 0).

Переключает SS (сегмент стека) на стек ядра.

Переходит по адресу, записанному в MSR_LSTAR (специальный регистр, где ядро указало точку входа).

Ядро по номеру в RAX ищет в таблице sys_call_table нужную функцию.

Проверяет аргументы (валидность указателей, прав доступа).

Выполняет запрос.

Возвращает результат в RAX, переключает обратно в Ring 3.

bash

# или

3. Что еще важно в этом блоке (чего нет в твоем конспекте)
   3.1. User space vs Kernel space (граница)

User space: Каждый процесс имеет свое виртуальное адресное пространство (0 до 2^47 на x86_64). Не видит другие процессы.

Kernel space: Общая область памяти (выше ~0xffff800000000000), отображенная в адресное пространство каждого процесса.

Схема виртуальной памяти процесса (x86_64):

text
0x0000000000000000  ┌─────────────────┐
│                 │
│   User space    │
│   (текст, дан-  │
│    ные, куча,   │
│    стек, mmap)  │
│                 │
0x00007fffffffffff  ├─────────────────┤
│   (дыра)        │
0xffff800000000000  ├─────────────────┤
│                 │
│   Kernel space  │
│   (отображение  │
│    физической   │
│    памяти,      │
│    код ядра)    │
│                 │
0xffffffffffffffff  └─────────────────┘
Почему так:

При переключении в ядро (syscall или прерывание) не надо менять таблицы страниц.

Ядро всегда видно, но из user mode к нему нет доступа (страницы ядра помечены как "только kernel").

3.2. Передача данных между user и kernel space

copy_from_user() / copy_to_user() — специальные функции ядра.

Проверяют, что указатель пользователя валиден (не фейковый).

Аккуратно копируют байты, защищаясь от page fault.

3.3. Блокирующие vs неблокирующие операции

Блокирующий read: Если данных нет, процесс уходит в сон (ждет).

Неблокирующий read (O_NONBLOCK): Если данных нет, возвращает EAGAIN.

Это основа асинхронного I/O и epoll.

3.4. /proc и /sys — разговор с ядром через файлы

/proc — информация о процессах и системе:

bash

Блок 2: Процессы, Потоки и Память (Твой главный блок)
Тут самые интересные моменты, и есть пара неточностей, которые важно поправить, чтобы понимание стало кристальным.

Fork() и Copy-on-Write (CoW)
Ты правильно подметил про 2 гигабайта и указатели, но давай уточним механику.

Раньше (наивный Unix): fork() реально копировал всю память родителя в дочерний процесс. Это было дико медленно и жрало память.

Сейчас (современный Linux): fork() использует технику Copy-on-Write (CoW).

Когда процесс делает fork(), ядро не копирует страницы памяти. Оно просто делает так, что таблицы страниц дочернего процесса указывают на те же самые физические страницы памяти, что и родитель.
Эти страницы помечаются как "только для чтения" (read-only) для обоих процессов.
Если какой-то из процессов (родитель или ребенок) пытается записать данные на эту страницу, процессор генерирует исключение (page fault).
Ядро перехватывает это исключение, создает настоящую копию этой страницы для пишущего процесса, обновляет его таблицы страниц, чтобы он указывал на новую копию, и помечает обе страницы (оригинал и копию) как "чтение-запись".
После этого процесс спокойно пишет в свою копию.
Итог: Реальное копирование происходит только при записи. Если после fork() сразу вызывается exec() (замена образа программы), копирования страниц памяти может не произойти вообще! Это гениальная оптимизация.

Контекст процесса (Context)
Ты верно говоришь, что это "снэпшот". Это набор регистров процессора (включая Instruction Pointer, Stack Pointer, общие регистры), счетчики, информация о памяти (таблицы страниц). Именно это состояние сохраняется, когда процесс вытесняется, и загружается, когда он возобновляется.

Переключение контекста (Context Switch)
Да, это адски дорого.

Сохранение состояния: Регистры текущего процесса сохраняются в его структуру в ядре.

Переключение таблиц страниц: Это самый тяжелый момент. Таблицы страниц определяют, какая физическая память виртуально доступна процессу. При их смене:

TLB Flush: Сбрасывается Translation Lookaside Buffer (кэш виртуальных адресов в физические внутри процессора). Без этого кэша следующий процесс первое время будет постоянно промахиваться мимо кэша (cache miss), пока TLB снова не наполнится.

Кэш процессора (L1/L2/L3): Данные, которые были в кэше для предыдущего процесса, становятся невалидными для нового. Новому процессу придется заново подтягивать данные из оперативной памяти (или еще хуже). Это и есть охлаждение кэша.

Потоки (Threads)

В Linux потоки реализованы через тот же clone(). При создании потока флаги в clone() говорят: "Память (VM) и файловые дескрипторы (FILES) мы делим с родителем, а стек (STACK) пусть будет свой".

Благодаря разделению памяти и таблиц файлов, переключение между потоками одного процесса значительно дешевле, чем между процессами. Таблицы страниц не меняются, значит, TLB не сбрасывается полностью (но регистры все равно сохранять надо).

1. Fork() и Copy-on-Write (CoW) — дополнения
   Твой текст — отличный! Но добавлю несколько важных нюансов:

Нюанс 1: Кто помечает страницы read-only?
Ты правильно описал механику, но важно понимать: ядро не бегает по всем страницам и не меняет флаги. Вместо этого:

Таблицы страниц родителя и ребенка копируются (сами таблицы, а не страницы!).

При копировании ядро устанавливает флаг "только для чтения" для всех записываемых страниц в обеих таблицах.

Сами физические страницы остаются общими.

Нюанс 2: Что происходит с анонимными страницами?
CoW работает не только с памятью процесса, но и с:

Анонимными страницами (куча, стек) — да.

Файловыми страницами (mmap с MAP_PRIVATE) — тоже да, но там отдельная механика.

Нюанс 3: Page fault — это не всегда ошибка
Когда процесс пишет в read-only страницу, процессор генерирует page fault (#PF). Ядро в обработчике смотрит:

Это ошибка доступа (segfault)?

Или это CoW-ситуация?

Если это CoW, ядро:

Находит физическую страницу.

Выделяет новую физическую страницу.

Копирует содержимое старой в новую.

Обновляет таблицу страниц только пишущего процесса, чтобы указывала на новую страницу с правами RW.

Если на старую страницу больше никто не ссылается (счетчик ссылок = 1), можно сделать ее RW для оставшегося процесса.

Нюанс 4: vfork() — экстремальный случай
Был когда-то vfork() — вообще без копирования памяти. Ребенок использует память родителя напрямую, родитель блокируется, пока ребенок не сделает exec() или exit(). Сейчас почти не используется (CoW достаточно эффективен).

3. Переключение контекста — цена операции
   Твой текст про TLB и кэш — абсолютно верен. Добавлю цифры и детали:

Сколько это стоит в цифрах (приблизительно):

Почему context switch такой дорогой:

Сохранение/восстановление регистров (несколько десятков инструкций).

Переключение CR3 (таблицы страниц) — это одна инструкция, но...

Холодный кэш — следующий процесс будет промахиваться мимо L1/L2/L3, пока не нагреет их.

Спекулятивное выполнение — конвейер процессора сбрасывается.

Современные оптимизации:

PCID (Process Context Identifiers) — в новых процессорах TLB помечается тегом (ID процесса). Можно не сбрасывать TLB полностью, а только помечать записи как принадлежащие другому процессу.

INVPCID — инструкция для выборочной инвалидации TLB.

Как измерить контекстное переключение:

bash
# Инструмент perf
perf stat -e context-switches,cpu-migrations,page-faults ./myapp

# Или просто time
time ./myapp  # покажет количество context switch (если настроено)
4. Потоки (Threads) — углубление
   Твой текст:

В Linux потоки реализованы через тот же clone(). При создании потока флаги в clone() говорят: "Память (VM) и файловые дескрипторы (FILES) мы делим с родителем, а стек (STACK) пусть будет свой".

Это ключевой момент, который многие не понимают! Добавлю конкретики:

Как создать поток через clone() (минимальный пример):

c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

#define STACK_SIZE (1024 * 1024)

int thread_func(void *arg) {
printf("Thread: PID=%d, аргумент=%s\n", getpid(), (char*)arg);
return 0;
}

int main() {
void *stack = malloc(STACK_SIZE);
char *msg = "Привет из потока!";

    // Флаги для создания потока (а не процесса)
    int flags = CLONE_VM |          // разделяем память
                CLONE_FILES |        // разделяем файловые дескрипторы
                CLONE_SIGHAND |      // разделяем обработчики сигналов
                CLONE_THREAD;        // быть в одной thread group
    
    pid_t pid = clone(thread_func, stack + STACK_SIZE, flags, msg);
    
    if (pid == -1) {
        perror("clone");
        exit(1);
    }
    
    printf("Parent: создан поток с PID %d\n", pid);
    
    // Ждем поток (для thread'ов waitpid не работает!)
    // Нужна другая синхронизация
    sleep(1);
    
    free(stack);
    return 0;
}
Что реально делят потоки:

CLONE_VM — адресное пространство (таблицы страниц одни на всех).

CLONE_FILES — таблица открытых файлов (если один поток закрыл файл, другой это видит).

CLONE_FS — информация о файловой системе (umask, current directory).

CLONE_SIGHAND — таблица обработчиков сигналов.

CLONE_THREAD — поместить в одну thread group (все потоки имеют общий TGID = PID, который видит пользователь).

Что НЕ делят:

Стек (каждый поток имеет свой).

Регистры (свои на момент выполнения).

TLS (Thread Local Storage) — своя область для thread-local переменных.

TID, PID, TGID — путаница:

PID (Process ID) — то, что показывает ps. Для потоков это TGID (Thread Group ID).

TID (Thread ID) — уникальный идентификатор потока в ядре.

В однопоточной программе: PID = TID = TGID.

В многопоточной: у всех потоков одинаковый TGID (то, что мы называем PID), но разные TID.

bash
ps -eLf  # показать потоки (-L)
# UID   PID   LWP   C  ...
# root 12345 12345  0      (главный поток)
# root 12345 12346  0      (второй поток)
# LWP = LightWeight Process = TID
5. Чего не хватает в блоке (важные темы)
1. Виртуальная память и Page Tables

Как процесс видит память: виртуальные адреса -> физические страницы.

Многоуровневые таблицы страниц (4 уровня на x86_64: PGD, PUD, PMD, PTE).

Page faults: major (с диска), minor (CoW, zero-filled).

2. OOM Killer (Out-Of-Memory Killer)

Когда память заканчивается, ядро ищет жертву.

Выбирает процесс с наибольшим oom_score (кто больше всех жрет, тот и виноват).

Можно защитить процесс через /proc/pid/oom_score_adj.

3. Zombie и Orphan процессы

Зомби: процесс завершился, но родитель не прочитал код возврата (wait).

Сироты: родитель умер раньше ребенка — ребенка усыновляет init (PID 1).

4. nice и приоритеты

nice (-20 до 19) — чем меньше, тем выше приоритет.

Реальный планировщик (CFS) использует не nice напрямую, а "вес" (weight).

5. Реальные примеры утечек памяти

Не закрытые файловые дескрипторы (мы говорили).

Не освобожденная память (в Go с GC это реже, но в C/C++ — частая проблема).

Goroutine leak (горутина зависла на канале и не выходит).

Блок 3: Сети
Тут все отлично схвачено.

TCP Handshake: SYN -> SYN-ACK -> ACK. Это устанавливает соединение.

TCP Keep-Alive: "спрашивать о состоянии друг друга" — это про то, чтобы проверить, жив ли еще собеседник, если долго нет данных.

epoll vs poll vs select

select и poll: Когда ты передаешь им список из 10000 сокетов, ядро каждый раз должно пройти по всему списку, чтобы проверить, на каких произошли события. Это O(n). Неэффективно.

epoll (Event Poll): Работает по принципу "подписки", как ты и сказал.

Ты создаешь epoll экземпляр (epoll_create1).
Ты добавляешь в него интересующие тебя файловые дескрипторы (сокеты) с помощью epoll_ctl (это делается один раз).
Ядро само следит за ними.
Ты вызываешь epoll_wait и получаешь только те дескрипторы, на которых уже произошли события. Ядро возвращает их тебе готовым списком. Это O(1) или около того. Гениально.
Level-Triggered vs Edge-Triggered:

Level-Triggered (LT) - по умолчанию: Если в сокете есть данные для чтения, epoll_wait будет постоянно сообщать об этом, пока ты их не прочитаешь. Надежно и просто.

Edge-Triggered (ET): epoll_wait сообщит о событии только один раз, когда состояние изменилось (например, пришли новые данные). Ты должен прочитать все данные сразу, иначе больше не получишь уведомления. Это сложнее, но производительнее, так как ядро реже дергает. Nginx использует ET.

HTTP

HTTP/1.1: Текстовый протокол. Одно соединение — один запрос-ответ. Можно держать соединение открытым (Keep-Alive), но все равно последовательно.

HTTP/2: Бинарный, мультиплексирование (одно соединение, много потоков запросов), сжатие заголовков, сервер может сам "толкать" ресурсы.

HTTP/3: Использует UDP (протокол QUIC) вместо TCP, чтобы ускорить соединение и обойти проблему "Head-of-Line Blocking" на уровне TCP.

БЛОК 3: Сети (расширенный разбор)
1. TCP Handshake — SYN, SYN-ACK, ACK (детали)
   Твой текст:

TCP Handshake: SYN -> SYN-ACK -> ACK.

Разбираем (что реально происходит на уровне ядра и сокетов):

3-Way Handshake нужен, чтобы:

Клиент подтвердил, что он живой и может отправлять.

Сервер подтвердил, что готов принимать.

Обе стороны согласовали начальные порядковые номера (ISN — Initial Sequence Number) для надежности.

Что видит программист (на примере сокетов):

Сервер:

c
// 1. Создать сокет
int s = socket(AF_INET, SOCK_STREAM, 0);

// 2. Привязать к порту
bind(s, ...);

// 3. Перевести в режим прослушивания
listen(s, 128);   // backlog = 128

// 4. Принять соединение
int client = accept(s, ...);
// accept() возвращает ТОЛЬКО ПОСЛЕ того, как завершился handshake!
Клиент:

c
// 1. Создать сокет
int s = socket(AF_INET, SOCK_STREAM, 0);

// 2. Подключиться
connect(s, ...);
// connect() возвращает управление ТОЛЬКО ПОСЛЕ получения ACK от сервера!
Состояния сокетов (которые можно увидеть в netstat):

Этап	Состояние на клиенте	Состояние на сервере
Клиент отправил SYN	SYN_SENT	LISTEN
Сервер получил SYN, отправил SYN-ACK	SYN_SENT	SYN_RCVD
Клиент получил SYN-ACK, отправил ACK	ESTABLISHED	SYN_RCVD
Сервер получил ACK	ESTABLISHED	ESTABLISHED
Важно: Сервер может держать соединения в состоянии SYN_RCVD неограниченное время? Нет. Есть параметр tcp_synack_retries (сколько раз пересылать SYN-ACK, если ACK не пришел). После исчерпания попыток — соединение удаляется.

SYN Flood (атака):
Злоумышленник шлет тысячи SYN-пакетов с поддельных IP и не отвечает на SYN-ACK. Сервер заполняет очередь SYN_RCVD и не может принимать легитимные соединения.

Защита: SYN Cookies

Сервер не хранит состояние SYN_RCVD.

Вместо этого кодирует информацию о соединении в порядковом номере (Sequence Number) SYN-ACK.

Когда приходит ACK, сервер раскодирует номер и создает соединение, если оно валидно.

2. TCP Keep-Alive (детали)
   Твой текст:

TCP Keep-Alive: "спрашивать о состоянии друг друга" — это про то, чтобы проверить, жив ли еще собеседник, если долго нет данных.

Разбираем (подводные камни):

Keep-Alive — это опция, а не часть протокола.
Включается на сокете:

c
int keepalive = 1;
setsockopt(s, SOL_SOCKET, SO_KEEPALIVE, &keepalive, sizeof(keepalive));
Три параметра (системные, но можно менять на сокете):

tcp_keepalive_time (по умолч. 7200 сек = 2 часа) — через сколько бездействия начать проверку.

tcp_keepalive_intvl (75 сек) — интервал между повторными пробами.

tcp_keepalive_probes (9) — сколько раз послать пробу, прежде чем считать соединение мертвым.

Итог: Если соединение умерло (сетевая карта выдернута, сервер упал), приложение узнает об этом только через ~2 часа 11 минут (7200 + 9*75 сек)!

В реальных приложениях (веб-сервера, базы данных):
Не используют TCP Keep-Alive. Используют application-level heartbeats:

WebSocket: ping/pong.

gRPC: keepalive ping.

Свои протоколы: раз в N секунд отправлять служебное сообщение "я жив".

3. epoll vs poll vs select (углубленно)
   Твой текст хороший, добавлю детали реализации и нюансы.

Почему select() плох:

Максимальное количество FD ограничено FD_SETSIZE (обычно 1024).

При каждом вызове нужно копировать весь битовый массив из userspace в kernel и обратно.

Ядро линейно проверяет все FD (O(n)).

poll() лучше:

Нет лимита 1024.

Но все равно O(n) — ядро проходит по всем FD, переданным в массиве.

epoll() — прорыв:

Ядро хранит свой список отслеживаемых FD (красное дерево).

При epoll_ctl() мы добавляем/удаляем/меняем FD в этом дереве (один раз).

При epoll_wait() ядро отдает готовые FD из специального списка (двусвязный список).

Режимы:

Level-Triggered (LT): Если в FD есть данные, каждое epoll_wait() будет возвращать его, пока данные не прочитаны.

Edge-Triggered (ET): Событие генерируется только один раз при изменении состояния (нет данных -> есть данные). Нужно читать, пока read() не вернет EAGAIN.

Почему ET сложнее:

c
// ET-цикл (правильный)
while (1) {
int n = epoll_wait(epfd, events, MAX_EVENTS, -1);
for (i = 0; i < n; i++) {
if (events[i].events & EPOLLIN) {
// Читаем, пока не вернет EAGAIN
while ((len = read(events[i].data.fd, buf, sizeof(buf))) > 0) {
// обрабатываем
}
if (len == -1 && errno != EAGAIN) {
// ошибка
}
}
}
}
Производительность:

LT проще, но может генерировать много событий.

ET сложнее, но снижает количество переходов user<->kernel.

4. HTTP/1.1 vs HTTP/2 vs HTTP/3 (детали)
   HTTP/1.1:

Текстовый, человеко-читаемый.

Проблема head-of-line blocking: Одно соединение — один запрос в каждый момент времени. Если запрос медленный, следующие ждут.

Решение: Браузеры открывают 6 параллельных соединений к одному хосту (это костыль).

HTTP/2:

Бинарный протокол (не читается глазами).

Мультиплексирование: В одном TCP-соединении передаются потоки (streams). Потоки могут перемежаться.

Сжатие заголовков (HPACK): Повторяющиеся заголовки не шлются каждый раз.

Server Push: Сервер может сам отправить ресурсы (CSS, JS), не дожидаясь запроса (спорная фича, часто отключают).

Проблема HTTP/2:
TCP все равно гарантирует порядок пакетов. Если потерялся пакет одного потока — все потоки ждут его пересылки (TCP-level head-of-line blocking).

HTTP/3 (QUIC):

Использует UDP.

QUIC — это TCP, реализованный в userspace, но с мультиплексированием внутри.

Если потерялся пакет одного потока — остальные потоки продолжают работать.

Быстрое соединение (0-RTT handshake).

Уже используется в YouTube, Google, Cloudflare.

5. Что еще важно в сетях (но ты не упомянул)
   Socket buffers (очереди в ядре):

Когда данные приходят, ядро кладет их в recv buffer сокета.

read() копирует данные из буфера ядра в userspace.

Если приложение не читает, буфер переполняется — отправитель получает ENOBUFS или начинает тормозить (TCP window).

TCP Window и Congestion Control:

TCP регулирует скорость отправки: окно перегрузки (cwnd) и окно приема (rwnd).

Slow start, congestion avoidance, fast retransmit — это все про то, как не убить сеть.

TIME_WAIT (что это и почему много соединений в этом состоянии):

После закрытия соединения сокет уходит в TIME_WAIT.

Ждет 2*MSL (обычно 60 сек), чтобы убедиться, что все пакеты умерли.

Если сервер создает много коротких соединений — TIME_WAIT накапливается, порты заканчиваются.

Решение для высоконагруженных серверов:

Включать SO_REUSEADDR и SO_REUSEPORT.

Использовать HTTP Keep-Alive (не закрывать соединение после каждого запроса).

6. Итог по Блоку 3 (коротко)
   Тема	Суть
   TCP Handshake	SYN → SYN-ACK → ACK, установка порядковых номеров
   TCP Keep-Alive	Долгий таймаут (часы), лучше свой heartbeat
   select/poll	O(n), копирование списков, устарели
   epoll	O(1) (субъективно), подписка на события, ET/LT
   HTTP/1.1	Текстовый, одно соединение → один запрос
   HTTP/2	Бинарный, мультиплексирование, но TCP HOL
   HTTP/3 (QUIC)	UDP, нет TCP HOL, быстрый handshake
   TIME_WAIT	Ждет 60 сек, проблема для коротких соединений

БЛОК 4: Контейнеризация (полный разбор)
Вступление
Ты абсолютно правильно схватил суть: контейнеры — это просто процессы. Но с божественными правами изоляции. Давай разберем, что реально происходит, когда ты запускаешь docker run.

1. Контейнеры vs Виртуальные машины (чтобы понимать масштаб)
   Твой текст:

Контейнеры, в отличие от виртуальных машин, взаимодействуют с общим ядром. Виртуальные машины эмулируют всю систему.

Разбираем:

Виртуальная машина (VM):

Гипервизор (VirtualBox, VMware, KVM) эмулирует железо: CPU, память, диски, сетевую карту.

На этом эмулированном железе запускается гостевое ядро (своя ОС).

В гостевой ОС запускаются процессы.

Накладные расходы: огромные. Каждая VM — это полноценная ОС со своим ядром, памятью, процессами.

Контейнер:

Использует ядро хоста (то же самое, что и твоя основная ОС).

Контейнер — это просто набор процессов, изолированных от других процессов хоста.

Накладные расходы: почти нулевые. Это просто процессы.

Аналогия:

VM — это многоквартирный дом с отдельными входами. У каждой квартиры своя планировка (своя ОС).

Контейнеры — это квартиры в одном подъезде с общим входом (общее ядро), но с отдельными замками (изоляция).

2. Namespaces — "китайские стены" для процессов
   Твой текст:

Namespaces: Изолируют "видимость". Процесс в своем namespace видит свой список процессов (PID namespace), свои сетевые интерфейсы (NET namespace), свою точку монтирования (MNT namespace), своего пользователя root (USER namespace) и т.д.

Разбираем (как это работает под капотом):

Что такое namespace?
Это флаг, который говорит ядру: "Для этого процесса показывай не настоящие ресурсы, а виртуальные".

Когда создается namespace?
При системном вызове clone() (помнишь, мы говорили про fork и clone?). Флаги определяют, что изолировать:

c
// Создать процесс с новым PID и NET namespace
clone(child_func, stack, CLONE_NEWPID | CLONE_NEWNET, NULL);
В Docker это делает runc (низкоуровневая прослойка).

Основные namespace'ы (которые реально важны):

Namespace	Что изолирует	Зачем нужно
PID	PID процессов	В контейнере процесс видит только свои процессы (с PID 1 внутри). На хосте он может быть PID 12345.
NET	Сеть	У контейнера свои виртуальные интерфейсы (eth0), свои IP, свои таблицы маршрутизации.
MNT	Точки монтирования	Контейнер видит свою файловую систему (свои /, /usr, /etc). Не видит файлы хоста.
UTS	hostname	У контейнера может быть свое имя хоста (не совпадает с хостом).
IPC	Межпроцессное взаимодействие	Изоляция разделяемой памяти, семафоров (чтобы контейнеры не лазали в память друг друга).
USER	Пользователи	Root в контейнере не равен root на хосте (если настроено). Безопасность!
CGROUP	Cgroups	Изоляция информации о cgroups (чтобы контейнер не видел лимиты других контейнеров).
Детальный разбор PID namespace (самый понятный пример):

На хосте:

bash
ps aux | grep myapp
# root     12345  0.0  0.1  1000  400 ?  Ssl  10:00   0:00 /myapp
PID 12345.

В контейнере (заходим):

bash
docker exec -it container1 bash
ps aux
# root        1  0.0  0.1  1000  400 ?  Ssl  10:00   0:00 /myapp
В контейнере этот же процесс имеет PID 1!

Как это работает:

Ядро хранит для каждого процесса таблицу соответствия: "виртуальный PID" -> "реальный PID".

Процесс видит только то, что разрешено его namespace.

Важно: PID 1 в контейнере — это специальный процесс. Если он умрет, контейнер останавливается. Он отвечает за обработку сигналов (как init в Linux).

NET namespace (сеть контейнера):

bash
# На хосте
ip link show
# eth0, wlan0, docker0, veth...

# В контейнере
docker exec -it container1 bash
ip link show
# lo, eth0 (свой виртуальный интерфейс)
Как Docker создает сеть:

Создает виртуальный интерфейс veth (кабель с двумя концами).

Один конец кладет в контейнер (становится его eth0).

Другой конец подключает к мосту docker0 на хосте.

Контейнер получает IP из подсети моста (обычно 172.17.0.0/16).

На хосте настраивается NAT (iptables), чтобы контейнеры ходили в интернет.

Типы сетей в Docker:

bridge (по умолчанию) — изолированная сеть между контейнерами на одном хосте.

host — контейнер использует сеть хоста (без изоляции).

overlay — для кластеров (Swarm, Kubernetes), контейнеры на разных хостах видят друг друга.

USER namespace (безопасность):

Самая важная фича для безопасности.

Проблема: Если в контейнере процесс работает от root, и он сломает изоляцию — на хосте он тоже root (катастрофа).

Решение (USER namespace):

bash
# Запустить контейнер с ремаппингом пользователей
docker run --userns-remap="default" ubuntu bash
Как работает:

В контейнере пользователь root (UID 0) маппится на хосте в непривилегированного пользователя (UID 100000).

Если контейнерный root попытается писать в /etc хоста — у него нет прав (на хосте он nobody).

Проверить:

bash

# uid=0(root) gid=0(root)

# На хосте (найти процесс)
ps aux | grep bash
# 100000   12345  0.0  0.0   ...   (UID на хосте 100000, а не root!)
3. Cgroups — "клетка для ресурсов"
   Твой текст:

Cgroups (Control Groups): Ограничивают "ресурсы". Ты говоришь ядру: "Процессы в этой cgroup могут использовать не больше 2 ядер CPU и 1 ГБ RAM". Ядро следит за этим. Именно это спасает от OOM Killer'а внутри контейнера.

Разбираем:

Что такое cgroups?
Механизм ядра Linux для учета и ограничения ресурсов группы процессов.

Две версии:

cgroups v1 (старая) — разные подсистемы висят в разных иерархиях.

cgroups v2 (новая, с 2016) — единая иерархия, используется в systemd, Docker, Kubernetes.

Где живут cgroups?
Виртуальная файловая система /sys/fs/cgroup/.

bash
# Посмотреть cgroups
ls /sys/fs/cgroup/

# Найти свой процесс в cgroup
cat /proc/self/cgroup
# 0::/system.slice/ssh.service
Основные контроллеры cgroups:

Контроллер	Что ограничивает	Как задать в Docker
cpu	CPU (ядро-время, доли, квоты)	--cpus=1.5 (полтора ядра)
memory	Память (RAM+swap)	--memory=1g (1 ГБ RAM)
blkio	Дисковый ввод-вывод	--device-read-bps (скорость чтения)
cpuset	Привязка к конкретным ядрам CPU	--cpuset-cpus=0-3 (ядра 0-3)
pids	Количество процессов	--pids-limit=100 (макс 100 процессов)
net_cls	Теги для сетевых пакетов (для tc)	(реже используется)
Как работает CPU limit:

bash
# Запустить контейнер с ограничением в полтора ядра
docker run --cpus=1.5 ubuntu stress --cpu 4
Что реально происходит:

В cgroup создается параметр cpu.cfs_period_us (обычно 100000 мкс = 100 мс).

cpu.cfs_quota_us = 150000 (полтора ядра = 150% времени).

Ядро следит: за каждые 100 мс процесс в этой cgroup может суммарно работать не больше 150 мс на всех ядрах.

Проверить:

bash
cd /sys/fs/cgroup/cpu/docker/<container_id>/
cat cpu.cfs_period_us   # 100000
cat cpu.cfs_quota_us    # 150000
Как работает Memory limit и OOM Killer:

bash
# Ограничить память 1 ГБ
docker run --memory=1g ubuntu
Что происходит:

В cgroup создается memory.limit_in_bytes = 1073741824 (1 ГБ).

Ядро считает память, используемую процессами в этой cgroup (RSS + page cache).

Если сумма превышает лимит:

Ядро пытается вытеснить page cache.

Если не помогает — запускает OOM Killer внутри этой cgroup.

OOM Killer убьет один из процессов в контейнере.

OOM Score внутри cgroup:

bash
# Найти процесс в контейнере
ps aux | grep stress

# Посмотреть его oom_score (на хосте)
cat /proc/12345/oom_score
Если контейнер переполнил лимит — ядро убьет процесс с худшим (самым высоким) score.

Важно: В логах будет Killed или exit code 137 (128+9, где 9 — SIGKILL).

Запускает процесс (обычно с PID 1 в новом namespace).

1. Горутины — это не потоки! (Модель M:N)
   Твой текст:

Модель M: N: У тебя есть N горутин, которые бегут на M потоков ОС (обычно M = количество ядер процессора, задается GOMAXPROCS).

Разбираем:

Это ключевое отличие Go от Java/C++.

Потоки ОС (M): Тяжелые. Создаются ядром. Имеют большой стек (~1-8 МБ). Переключение контекста стоит дорого (мы говорили про context switch, TLB flush и т.д.).

Горутины (G): Легкие. Создаются runtime'ом Go. Имеют маленький стек (начинается с 2 КБ) и могут расти. Переключение между горутинами происходит в пользовательском пространстве — это в 100 раз быстрее, чем переключение потоков ОС.

Аналогия:
Представь, что потоки ОС (M) — это железнодорожные пути. Их количество ограничено железнодорожной компанией (ядром Linux). А горутины (G) — это поезда на этих путях. Планировщик Go решает, какой поезд сейчас поедет по какому пути.

GOMAXPROCS:

go
runtime.GOMAXPROCS(4) // Явно указать, что можно использовать 4 ядра
По умолчанию = количество ядер процессора. Это максимальное количество M (потоков ОС), которые одновременно могут выполнять код пользователя.

Твой текст:

Три Сущности:

G (Goroutine): Твоя легковесная задачка со своим стеком (который растет, 2КБ вначале!).

M (Machine): Это тот самый pthread (поток ОС), который реально выполняется на ядре Linux.

P (Processor): Контекст для планировщика. У него есть своя локальная очередь горутин (runqueue). Количество P = GOMAXPROCS.

Разбираем (это святая троица Go):

G (Goroutine):

Хранит: стек, указатель на текущую инструкцию, состояние (ждет, работает, в системе).

Стек динамический: начинается с 2 КБ, если нужно — runtime выделяет новый, больший стек и копирует данные (это дорого, но редко).

M (Machine):

Это настоящий поток ОС. Создается через системный вызов clone() (как мы обсуждали).

M крутится в бесконечном цикле: "взять G из очереди P -> выполнить G -> вернуть G".

P (Processor):

Это не ядро процессора! Это контекст планировщика.

У каждого P есть локальная очередь (runqueue) горутин (размером 256).

Количество P жестко = GOMAXPROCS.

Если у тебя 4 ядра и GOMAXPROCS=4, то одновременно могут выполняться только 4 горутины (по одной на P). Остальные ждут в очередях.

Схема:

text
OS Threads (M1, M2, M3)      OS Threads (M4, M5)
↑       ↑                    ↑
|       |                    |
┌───┴───┐ ┌─┴───┐            ┌──┴───┐
│  P1   │ │  P2 │   ...       │  P4  │  (GOMAXPROCS=4)
└───┬───┘ └──┬──┘            └──┬───┘
┌────┴────┐   │              ┌───┴────┐
│ G1 G2 G3│   │              │ G15 G16│  (локальные очереди)
└─────────┘   │              └────────┘
↓
Глобальная очередь (если локальные переполнены)
Твой текст:

Суть: Когда твоя горутина делает системный вызов (например, читает из сокета), M (поток ОС) блокируется. Чтобы не блокировать другие горутины, runtime отсоединяет этот M, отцепляет P и прикрепляет новый M (новый поток) к этому P.

Разбираем (Handoff):

Это гениальный механизм, который позволяет Go эффективно работать с блокирующими системными вызовами (как read() из файла).

Сценарий:

Горyтина G1 на M1 (привязанном к P1) вызывает syscall.Read(fd, buffer).

Данных в fd нет. Ядро переводит M1 в состояние ожидания (blocked).

Проблема: P1 бездействует, пока M1 спит. Горутины в очереди P1 не выполняются.

Решение (Handoff):

Runtime Go видит, что M1 заблокирован надолго.

M1 отцепляется от P1 (они расходятся).

Runtime создает новый M2 (или берет из спящего пула) и прикрепляет его к P1.

M2 начинает выполнять горутины из очереди P1.

Когда системный вызов завершается (данные пришли), M1 просыпается, но у него нет P. Он пытается украсть P или встает в очередь спящих M (в парк).

Итог: Пока один системный поток ждет, другой поток ОС работает. Процессорные ядра не простаивают.

2. Сетевой ввод-вывод (Netpoll — The Killer Feature)
   Твой текст:

Помнишь я рассказывал про epoll? В Go это реализовано настолько круто, что тебе даже думать не надо.
Ты пишешь conn.Read(buffer). Если данных нет, горутина засыпает (G переходит в waiting state). Она не жрет ресурсы.
Внизу, в runtime, есть штука netpoll. Она вызывает epoll_wait (в Linux) и мониторит дескрипторы.
Как только данные пришли, epoll будит runtime, runtime находит горутину, которая ждала этот сокет, и пихает ее обратно в очередь на выполнение (в P).

Разбираем (интеграция epoll в Go):

Это самое сладкое место Go.

Без Go (чистый C с epoll):

c
int epfd = epoll_create1(0);
epoll_ctl(epfd, EPOLL_CTL_ADD, sock, &ev);
while (1) {
int n = epoll_wait(epfd, events, MAX_EVENTS, -1);
for (int i = 0; i < n; i++) {
// Ручная обработка событий
if (events[i].events & EPOLLIN) handle_read(events[i].data.fd);
}
}
Код сложный, легко ошибиться.

В Go:

go
go func() {
buf := make([]byte, 1024)
conn.Read(buf)  // Просто и понятно
fmt.Println(string(buf))
}()
Что происходит под капотом:

Создание сетевого соединения:

conn, _ := net.Dial("tcp", "example.com:80")

Внутри: socket() -> connect() -> файловый дескриптор (FD) готов.

Вызов conn.Read():

Это не прямой системный вызов read()! Это вызов метода (*net.conn).Read().

Внутри — проверка: есть ли данные в буфере сокета (в ядре)? Если есть — читаем и отдаем.

Если данных нет:

Горутина упаковывается в структуру "ждун" (waiting).

FD сокета и горутина регистрируются в netpoll.

Горутина переводится в состояние _Gwaiting.

Планировщик Go переключается на следующую горутину.

Работа netpoll (отдельный системный поток/механизм):

В runtime есть цикл, который вызывает epoll_wait() (в Linux) или kqueue() (в BSD/macOS).

Он ждет события на всех зарегистрированных FD.

Когда данные приходят на сокет, epoll_wait() возвращает список готовых FD.

Пробуждение:

Runtime находит горутины, привязанные к этим FD.

Переводит их из _Gwaiting в _Grunnable.

Кладет их в локальные очереди P.

В следующий раз, когда P будет выбирать работу, горутина выполнится и получит свои данные.

Итог:

Ты пишешь синхронный код (линейный, легко читаемый).

Под капотом — асинхронный, событийно-ориентированный I/O (как в Node.js).

Нет коллбеков, нет ада промисов, нет async/await (хотя в Go 1.22+ появились свои фишки, но это другая тема).

3. Планировщик Go (Work Stealing)
   Твой текст:

Планировщик Go — это отдельный вид искусства. Он работает без участия ядра Linux (потоки ОС уже запланированы ядром, а поверх них Go планирует свои горутины).
Локальные очереди: У каждого P (логического процессора) своя очередь горутин. Это снижает конкуренцию за глобальные блокировки.
Воровство работы (Work Stealing): Если у P закончились горутины, он не идет спать. Он пытается украсть половину горутин из очереди соседнего P.
Handoff: Если M (поток) блокируется (из-за системного вызова или синхронизации), P отцепляется от этого M и находит другой M, чтобы продолжать крутить остальные горутины.

Разбираем (как планировщик реально работает):

Планировщик Go — это кооперативная вытесняющая многозадачность. Звучит противоречиво? Сейчас поймешь.

Когда горутина отдает управление (точки переключения):

Блокирующие системные вызовы (мы уже разобрали).

Синхронизация (каналы, мьютексы) — горутина уходит в ожидание.

Явный вызов runtime.Gosched() — "я добровольно отдаю процессор".

Таймеры и каналы времени (time.Sleep, time.After).

Вытеснение (preemption): С Go 1.14+ планировщик может вытеснять горутину, если она выполняется слишком долго без переключений (например, бесконечный цикл вычислений).

Алгоритм выбора горутины для P:

Проверить локальную очередь P (runnext — самая приоритетная).

Взять из начала локальной очереди.

Если локальная пуста — попытаться украсть (work stealing) из другой P.

Если украсть не удалось — проверить глобальную очередь.

Если и там пусто — P встает в спящий режим (процессор не жрет).

Work Stealing (как это реально работает):

P1 (без работы) выбирает случайный P2.

P1 пытается забрать половину горутин из очереди P2.

Это балансирует нагрузку и не дает простаивать ядрам.

Глобальная очередь:

Нужна, когда локальные очереди переполнены.

Также в нее попадают горутины после работы сетевого poll'ера.

4. Синхронизация по-гошному
   Твой текст:

Каналы (Channels): "Don't communicate by sharing memory; instead, share memory by communicating". Канал внутри — это структура в куче с блокировкой (hchan), но он учит тебя правильному дизайну.
sync.Pool: Очень крутая штука для временных объектов. Позволяет снизить нагрузку на GC.

Разбираем (каналы под капотом):

Структура канала (hchan):

go
type hchan struct {
qcount   uint           // количество элементов в буфере
dataqsiz uint           // размер буфера (для буферизированных)
buf      unsafe.Pointer // указатель на кольцевой буфер
elemsize uint16
closed   uint32
elemtype *_type         // тип элемента
sendx    uint           // индекс для отправки
recvx    uint           // индекс для получения
recvq    waitq          // очередь горутин, ждущих приема (канал пуст)
sendq    waitq          // очередь горутин, ждущих отправки (канал полон)
lock     mutex          // мьютекс (вся работа с каналом блокируется)
}
Что происходит при отправке в канал ch <- val:

Захватывается lock.

Проверяется, есть ли горутины в recvq (ждут чтения)?

Если есть: берем первую, передаем ей значение напрямую (без буфера), будим горутину, отпускаем lock.

Если нет ждущих, но есть место в буфере:

Кладем в буфер, обновляем индексы, отпускаем lock.

Если буфер полон и нет ждущих читателей:

Текущая горутина пакуется в структуру sudog, добавляется в sendq.

Вызывается gopark() — горутина засыпает (переходит в _Gwaiting).

Планировщик переключается на другую горутину.

Что происходит при получении val := <-ch:

Захватываем lock.

Есть горутины в sendq? (кто-то ждет отправки)

Если есть: забираем значение у них (или из буфера, если буферизированный), будим отправителя.

Нет отправителей, но есть в буфере:

Берем из буфера.

Буфер пуст и нет отправителей:

Текущая горутина встает в recvq и засыпает.

sync.Pool (чтобы GC не убивал производительность):

go
var pool = sync.Pool{
New: func() interface{} {
return make([]byte, 1024) // создаем новый объект, если пул пуст
},
}

// В обработчике запроса
buf := pool.Get().([]byte) // берем из пула
defer pool.Put(buf)        // возвращаем

// Используем buf
Как это работает:

У каждого P (логического процессора) есть свой локальный кэш объектов.

Сначала объект берется из локального кэша — без блокировок, быстро.

Put() кладет объект обратно в локальный кэш.

Важно: Во время сборки мусора (GC) объекты из пула могут быть удалены без предупреждения.

Блок 6: Вопросы, которые возникли
"От какого процесса форк будет происходить?" — Всегда от текущего. fork() вызывается внутри работающей программы. Тот, кто вызвал fork(), становится родителем. Копия становится ребенком. Если ребенок умирает, а родитель не ждал его статус (wait), ребенок становится "зомби". Если родитель умирает раньше ребенка, ребенка усыновляет init (PID 1).

"JSON в тело POST" — Абсолютно верно. Длинные и сложные структуры (как твой SQL-подобный фильтр) не лезут в URL (ограничения по длине, некрасиво). Их кладут в тело (body) HTTP-запроса, обычно в формате JSON, и используют метод POST (или иногда PUT/PATCH).

(ПОЛНЫЙ РАЗБОР)
Вопрос 1: "От какого процесса форк будет происходить?"
Короткий ответ:
fork() всегда вызывается из текущего (активного) процесса. Тот процесс, который выполнил системный вызов fork(), становится родительским (parent). Новый созданный процесс становится дочерним (child).

Длинный ответ (чтобы не осталось вопросов):

1. Механика fork()
   Когда процесс вызывает fork():

Ядро Linux создает точную копию вызывающего процесса (с учетом Copy-on-Write, о котором мы говорили).

Копируется: память, файловые дескрипторы, счетчики, контекст, окружение.

Разница: у нового процесса свой PID (идентификатор).

Важнейший нюанс:
fork() возвращает значение дважды:

В родительском процессе возвращается PID дочернего процесса (положительное число).

В дочернем процессе возвращается 0.

c
pid_t pid = fork();

if (pid == 0) {
// Это выполняется в ДОЧЕРНЕМ процессе
printf("Я ребенок! Мой PID = %d\n", getpid());
} else if (pid > 0) {
// Это выполняется в РОДИТЕЛЬСКОМ процессе
printf("Я родитель! Ребенок имеет PID = %d\n", pid);
}
2. Иерархия процессов в Linux
   В Linux все процессы образуют дерево:

text
init (PID 1)
├─ systemd/journald
├─ sshd
│  └─ bash (PID 1000)
│     └─ ./myapp (PID 1500)
│        └─ [fork()]→ дочерний процесс (PID 1501)
init (PID 1) — первый процесс, запускаемый ядром. Он является предком для всех остальных.

Каждый процесс знает своего родителя (PPID — Parent Process ID).

3. Жизненный цикл: зомби и сироты
   Зомби-процессы (defunct):

Когда дочерний процесс завершается (exit()), он не исчезает сразу.

Он становится зомби — остается запись в таблице процессов, чтобы родитель мог узнать код завершения.

Зомби не занимает память, но занимает запись в таблице процессов.

Проблема: если родитель не вызывает wait() или waitpid(), зомби висит вечно.

Сироты (orphans):

Если родитель умирает раньше ребенка, ребенок становится сиротой.

Ядро автоматически назначает нового родителя — процесс init (PID 1).

Init периодически вызывает wait(), поэтому сироты не становятся вечными зомби.

bash
# Посмотреть зомби
ps aux | grep defunct

# Посмотреть дерево процессов
pstree -p
4. fork() без exec()
   Обычно после fork() вызывают exec() — замену образа программы. Но если exec() не вызывать:

Родитель и ребенок выполняют один и тот же код.

Используется для многопоточности (в старых системах) или для распараллеливания задач внутри одной программы.

Пример (веб-сервер):

c
while (1) {
int client_fd = accept(server_fd, ...);
if (fork() == 0) {
// Дочерний процесс обрабатывает клиента
handle_client(client_fd);
exit(0);
}
// Родитель продолжает принимать новых клиентов
close(client_fd);
}
Это классическая модель preforking (Apache использовал так).

Вопрос 2: "JSON в тело POST. Длинные структуры в запросах"
Короткий ответ:
Да, сложные структуры (как SQL-подобные фильтры) кладут в тело (body) HTTP-запроса, обычно в формате JSON, и используют метод POST (или PUT/PATCH). В URL такое не суют из-за ограничений длины, небезопасности и некрасивости.

Длинный ответ:

1. Почему не в URL?
   HTTP-методы GET и URL:

GET предназначен для получения данных.

Параметры передаются в строке запроса: ?key1=value1&key2=value2

Ограничения:

Разные браузеры и серверы имеют лимиты на длину URL (обычно 2048 символов, но может быть меньше).

URL виден в истории браузера, логах сервера, реферерах — небезопасно для чувствительных данных.

Нельзя передавать вложенные структуры (массивы, объекты) без костылей.

Пример костыля для массива в GET:

text
/filter?users[]=1&users[]=2&users[]=3   // Некрасиво и нестандартно
2. Тело запроса (Request Body)
   POST / PUT / PATCH:

Предназначены для отправки данных на сервер.

Данные идут в теле запроса.

Нет ограничений по длине (кроме настроек сервера).

Можно передавать любые структуры: JSON, XML, бинарные данные.

Твой пример (SQL-подобный фильтр):

json
{
"Groups": [
{
"Field": "status_states.status_id",
"Value": "4"
}
],
"Where": {
"Conditions": {
"status_states.status_id": [
{
"Operator": "=",
"Value": 1
}
]
},
"ExpressionType": "AND"
}
}
Это идеальный кандидат для POST-запроса с JSON в теле.

3. Как это выглядит в HTTP
   Запрос:

text
POST /api/search HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 312

{
"Groups": [...],
"Where": {...}
}
Ответ:

text
HTTP/1.1 200 OK
Content-Type: application/json

{
"results": [...]
}
4. Альтернативы JSON
   XML: Был популярен в SOAP, сейчас реже.

Protocol Buffers (protobuf): Бинарный формат, быстрее JSON, меньше размер.

MessagePack: Тоже бинарный, похож на JSON.

form-data: Для отправки файлов (multipart/form-data).

5. Когда использовать GET, а когда POST?
   Критерий	GET	POST
   Цель	Получить данные	Отправить данные
   Безопасность	Данные в URL (видимы)	Данные в теле
   Идемпотентность	Да (повторный запрос безопасен)	Нет (может создать ресурс)
   Кеширование	Может кешироваться	Обычно не кешируется
   Длина	Ограничена	Без ограничений
   Пример	Поиск, пагинация	Создание заказа, сложный фильтр
   Итог по Блоку 6:
   fork():

Всегда от текущего процесса.

Возвращает PID ребенка в родителе, 0 — в ребенке.

Зомби = ребенок умер, родитель не забрал статус.

Сироты = родитель умер, ребенка усыновляет init (PID 1).

JSON в теле POST:

Сложные структуры — в тело, а не в URL.

POST — для отправки данных, GET — для получения.

Content-Type: application/json — стандарт для API.

БЛОК 7: Инструменты, безопасность и реальные кейсы (Новый блок)
Отлично! Раз ты хочешь выйти за рамки теории и посмотреть, как это все применяется на практике — давай создадим Блок 7. Это будет про инструменты, которые превращают знание в суперсилу, и про безопасность, которая в современном мире критична.

Вступление
Теория без практики мертва. Все эти syscall'ы, контексты, горутины и контейнеры — это круто, но когда твое приложение падает в проде или жрет 100% CPU, нужны инструменты, чтобы понять почему.

Часть 1. Инструменты для исследования системы
1. strace — трассировка системных вызовов
   Что делает: Показывает все syscall'ы, которые делает процесс.

Когда использовать:

Программа падает с загадочной ошибкой.

Хочешь понять, какие файлы открывает приложение.

Программа висит — на каком syscall'е?

Базовое использование:

bash
# Запустить программу под strace
strace ./myapp

# Присоединиться к работающему процессу
strace -p 12345

# Записывать в файл (если вывода много)
strace -o trace.log ./myapp

# Показать только определенные syscall'ы
strace -e trace=open,read,write ./myapp

# Показать время выполнения каждого syscall'а
strace -T ./myapp

# Показать относительное время между syscall'ами
strace -r ./myapp
Пример анализа:

bash
strace -e trace=network curl example.com
# connect(3, ...) = 0
# sendto(3, "GET / HTTP/1.1\r\nHost: ...", ...) = 74
# recvfrom(3, "HTTP/1.1 200 OK\r\n...", ...) = 1024
Что ты видишь:

Какие соединения открывает программа.

Какие файлы читает/пишет.

Где программа ждет (на каком syscall'е).

2. ltrace — трассировка библиотечных вызовов
   Что делает: Показывает вызовы библиотечных функций (malloc, printf, pthread_create), а не syscall'ов.

Пример:

bash

# malloc(1024) = 0x55a1e2c4b260
# printf("Hello, %s!\n", "world") = 13
# free(0x55a1e2c4b260) = <void>
Когда полезно:

Отладка утечек памяти (следить за malloc/free).

Понимание, что делает программа до того, как уйти в syscall.

3. perf — профилировщик производительности
   Что делает: Считает, где программа проводит время (на уровне CPU, кэша, инструкций).

Установка:

bash
sudo apt install linux-tools-common linux-tools-$(uname -r)
Базовое использование:

bash
# Собрать статистику по программе

# Пример вывода:

# 5,000      context-switches              # 0.500 K/sec
# 200        cpu-migrations                # 0.020 K/sec
# 1,000,000  page-faults                   # 0.100 M/sec
# 30,000,000 cycles                        # 2.997 GHz
# 15,000,000 instructions                   # 0.50  insn per cycle
Профилирование (горячие точки):

bash
# Записать профиль (30 секунд)

# Посмотреть отчет
perf report
# Покажет функции, где больше всего времени
Когда использовать:

Приложение жрет 100% CPU — где конкретно?

Сравнение производительности до и после оптимизации.

Поиск узких мест (блокировки, кэш-промахи).

Полезные события:

bash
# Список доступных событий

# Кэш-промахи
perf stat -e cache-misses,cache-references ./myapp

# Промахи TLB
perf stat -e dTLB-load-misses,iTLB-load-misses ./myapp
4. eBPF — супер-инструмент (современный стандарт)
   Что такое eBPF: Технология, позволяющая запускать безопасный код в ядре без перекомпиляции ядра.

Возможности:

Трассировка любого syscall'а с фильтрацией.

Мониторинг сети (пакеты в реальном времени).

Профилирование на лету.

Безопасность (обнаружение атак).

Инструменты на основе eBPF:

bcc (BPF Compiler Collection):

bash

bash

3. seccomp — ограничение syscall'ов
   Что делает: Запрещает процессу вызывать определенные syscall'ы.

Зачем:

Используется в Docker, Chrome, systemd.

Пример (в Go):

import "golang.org/x/sys/unix"

// Запретить все syscall'ы, кроме read, write, exit

Action: unix.SECCOMP_RET_ALLOW,
Syscalls: []unix.Syscall{
unix.SYS_READ,
unix.SYS_WRITE,
unix.SYS_EXIT,
},
}
unix.Seccomp(unix.SECCOMP_SET_MODE_FILTER, filter)
}

БЛОК 1: Фундамент (Сисколлы и "Всё есть файл")
Простыми словами:

Представь, что компьютер — это закрытый завод (ядро). Ты — обычный посетитель (программа). Зайти внутрь нельзя, но можно постучать в окошко и попросить что-то сделать.

Системный вызов (syscall) — это и есть то самое окошко. Ты говоришь: "Эй, открой мне файл" (open), "прочитай данные" (read), "запиши" (write). Ядро делает это за тебя, потому что у него есть доступ к станкам (железу).

"Всё есть файл" — это такая философия: если что-то можно открыть, прочитать и закрыть — называй это файлом. Неважно, что это:

Текстовый документ — ну ок, файл.

Папка — тоже файл (специальный, со списком внутри).

Веб-камера — файл (открыл, читаешь картинку).

Сетевое соединение — файл.

Даже информация о процессоре в папке /proc — это файл, который при чтении магическим образом генерирует данные.

Зачем? Чтобы программисту было просто: научился работать с файлами — умеешь работать со всем.

БЛОК 2: Процессы, Потоки и Память
Простыми словами:

Процесс — это запущенная программа. У нее есть своя комната (память), свои вещи, свой номерок (PID).

Форк (fork) — это когда процесс создает точную копию себя. Как клонирование. Раньше при клонировании тупо копировали всю комнату со всем хламом (медленно и жирно). Теперь умное ядро делает Copy-on-Write: "Чуваки, вы пока пользуйтесь одной комнатой на двоих. Как только один из вас захочет что-то переставить — тогда я сделаю копию стены, которую он трогает". Экономия памяти и времени.

Поток (thread) — это облегченная версия процесса. Представь, что процесс — это офис, а потоки — сотрудники в этом офисе. У них общий холодильник, общий принтер (память), но каждый работает за своим столом (свой стек). Создать нового сотрудника дешевле, чем арендовать новый офис.

Контекст процесса — это фотография состояния процесса в момент, когда его выгоняют из процессора. Где он остановился, что у него в руках (регистры), какой листок читал (таблицы страниц).

Переключение контекста — это когда процессор переключается с одной программы на другую. Очень дорогое удовольствие. Нужно сфоткать текущую программу, стереть ее следы в кэше (TLB flush), загрузить фотку новой программы, и только потом она начинает работать. Как смена бригады рабочих, но еще нужно выкинуть их инструменты и затащить новые.

БЛОК 3: Сети
Простыми словами:

TCP handshake — это как знакомство:

Ты: "Привет, я Вася" (SYN)

Сервер: "Привет, Вася, я Петя" (SYN-ACK)

Ты: "Ок, привет, Петя" (ACK)
После этого начинаете общаться.

Keep-Alive — проверка, жив ли еще собеседник. Если долго молчали, можно спросить: "Ты тут?" Если не отвечает — закрываем соединение.

select/poll — старый способ следить за кучей соединений. Ты каждый раз говоришь ядру: "Посмотри вон на те 10000 сокетов, может там что-то пришло?" Ядро тупо проходит по всем и отвечает. Медленно.

epoll — умный способ. Ты говоришь ядру: "Следи вот за этими сокетами сам, а когда что-то случится — сразу мне скажи". Ядро запоминает список и спит в засаде. Как только данные приходят — будит тебя и говорит: "Вот список тех, у кого есть данные". Быстро, современно.

Level-Triggered — пока в сокете есть данные, epoll будет долбить тебя каждую секунду: "Данные есть! Данные есть!". Надежно, но навязчиво.

Edge-Triggered — сказал один раз: "О, данные появились" — и заткнулся. Дальше сам читай, пока не кончатся, иначе больше не скажу. Эффективнее, но сложнее.

HTTP/1.1 — старый протокол. Одно соединение — один запрос. Как если бы для каждой покупки в магазине нужно было заново заходить, здороваться, платить и уходить.

HTTP/2 — новее. Можно в одном соединении пихать много запросов одновременно. Как зашел в магазин и сразу набрал полную тележку разного товара.

HTTP/3 — совсем новый. Использует UDP вместо TCP, чтобы не ждать, если один пакет потерялся. Все остальные запросы продолжают идти, не тормозят.

БЛОК 4: Контейнеризация
Простыми словами:

Контейнер — это просто процесс, которого обманули.

Ему кажется, что он главный (PID 1), что у него свой компьютер (сеть, диски), но на самом деле он сидит в песочнице, а снаружи — общий хост.

Namespaces — это "шоры для лошади". Процесс в контейнере видит только то, что ему разрешено:

PID namespace: он думает, что его PID = 1, а на самом деле может быть 12345.

NET namespace: у него свой IP, свои сетевые интерфейсы.

MNT namespace: он видит свою папку /, а не всю файловую систему хоста.

USER namespace: root в контейнере — не root на хосте (безопасно!).

Cgroups — это "будка для собаки". Можно сказать ядру: "Эти процессы (контейнер) могут жрать не больше 2 ядер CPU и 1 ГБ памяти". Ядро следит и бьет по рукам, если перебирают.

Итог: Контейнеры — это дешево (одно ядро на всех) и удобно (запаковал приложение со всем окружением и запустил где хочешь).

БЛОК 5: Go-специфика
Простыми словами:

Горутина — это супер-легкий поток. Создать поток в ОС — это как арендовать квартиру (дорого, долго). Создать горутину — как взять раскладушку в той же квартире (быстро, дешево).

Модель M:N — у тебя есть N горутин (легких задачек), и они бегают на M потоках ОС (обычно M = количество ядер). Планировщик Go сам решает, какую задачку на какое ядро поставить.

Три сущности:

G (Goroutine) — твоя задачка. Изначально с маленьким стежком (2 КБ), но если надо — растет.

M (Machine) — настоящий поток ОС (pthread). Рабочая лошадка.

P (Processor) — контекст планировщика. У каждого P своя очередь горутин. Количество P = сколько ядер используем.

Netpoll — это магия Go. Когда ты читаешь из сети (conn.Read), а данных нет, горутина засыпает. Под капотом Go сам вызывает epoll, ждет данные, а когда они приходят — будит горутину. Ты пишешь простой синхронный код, а получаешь скорость асинхронного.

Work Stealing — если у одного P кончились горутины, он не спит, а идет "воровать" работу у соседей. Забирает половину очереди и работает.

Каналы — способ передачи данных между горутинами. Не "делись памятью, а передавай данные через общение". Одна горутина кидает в канал, другая ловит.

sync.Pool — коробка с временными объектами. Чтобы не создавать новые каждый раз (GC замучает), берешь из коробки, используешь, кладешь обратно.

БЛОК 6: Вопросы, которые возникли
Простыми словами:

"От какого процесса форк?" — от того, который вызвал fork(). Он становится родителем. Копия — ребенком. Если ребенок умер, а родитель не забрал "справку о смерти" (wait), ребенок становится зомби — висит в таблице процессов, но ничего не делает. Если родитель умер раньше ребенка, ребенка усыновляет процесс init (PID 1) — главный папа всех процессов.

"JSON в тело POST" — когда данные сложные (вложенные структуры, массивы), их не пихают в URL (там место ограничено, да и некрасиво). Их кладут в тело запроса и отправляют методом POST. В теле может быть JSON, XML, что угодно. Сервер читает и радуется.

БЛОК 7: Инструменты и безопасность
Простыми словами:

strace — подсматривает, какие системные вызовы делает программа. Висит программа? strace покажет, на каком вызове она застряла.

perf — считает, где программа проводит время. Жрет CPU? perf покажет, какая функция виновата.

bpftrace — швейцарский нож для копания в ядре. Можно спросить: "Покажи все открытия файлов" — и ядро будет присылать уведомления в реальном времени.

/proc и /sys — папки-призраки. В них лежит информация о системе и процессах. Зашел в /proc/cpuinfo — узнал про процессор. Зашел в /proc/12345/fd — увидел, какие файлы открыты у процесса 12345.

Capabilities — выдать программе только часть прав root. Не хочешь давать полный root, чтобы слушать порт 80? Дай только CAP_NET_BIND_SERVICE — и программа сможет слушать порт, но не сможет ничего другого.

seccomp — запретить программе вызывать опасные системные вызовы. Если хакер взломает твою программу, он не сможет вызвать execve (запустить свою программу), потому что seccomp запретит.

Реальные кейсы:

Утечка памяти? → pprof покажет, кто жрет.

Высокий CPU? → perf укажет на горячую функцию.

Медленные запросы? → логи БД и iostat покажут, что диск тормозит.

Сеть не работает? → tcpdump покажет, уходят ли пакеты.

ИТОГ (одним абзацем)
Linux — это ядро, которое управляет железом и дает программам доступ через системные вызовы. Процессы и потоки — это способ запускать много всего сразу, а память виртуальная, чтобы не мешали друг другу. Сети — это сложно, но epoll и Go-горутины делают жизнь проще. Контейнеры обманывают процессы, создавая иллюзию отдельных компьютеров. А инструменты вроде strace, perf и bpftrace позволяют заглянуть под капот и понять, что сломалось. Всё это нужно, чтобы твоя программа работала быстро, не падала и не дырявила память.
