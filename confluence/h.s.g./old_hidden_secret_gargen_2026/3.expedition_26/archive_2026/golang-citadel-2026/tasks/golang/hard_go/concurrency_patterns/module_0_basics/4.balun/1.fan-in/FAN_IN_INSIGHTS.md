# Fan-In: Инсайты от Мусаси

## 🔑 Суть паттерна

**Fan-In (сбор данных)** — объединение данных из нескольких источников в один поток.

**Принцип:** Много каналов → один канал

## 📊 Когда использовать?

- Сбор метрик из нескольких сервисов
- Объединение результатов параллельных вычислений
- Агрегация данных из разных источников

## 🏗️ Архитектура

```
Канал 1 ──┐
Канал 2 ──┼──> MergeChannels ──> Один канал
Канал 3 ──┘
```

## ⚙️ Реализация

**Ключевые моменты:**

1. **WaitGroup для синхронизации:**
   - `wg.Add(len(channels))` — один раз перед циклом (проще, если знаешь количество)
   - Или `wg.Add(1)` в каждой итерации (гибче, если количество может меняться)
   - Каждая горутина вызывает `wg.Done()` один раз

2. **Закрытие канала:**
   - Отдельная горутина ждёт `wg.Wait()`
   - После завершения всех горутин закрывает выходной канал
   - Это гарантирует, что все данные записаны

3. **Неблокирующий возврат:**
   - Функция сразу возвращает канал
   - Горутины работают в фоне
   - Клиент не блокируется

## 🔒 Потокобезопасность

- Каждая горутина читает из своего канала (безопасно)
- Запись в выходной канал синхронизирована через сам канал
- WaitGroup гарантирует, что все горутины завершились перед закрытием

## ⚠️ Ловушки

1. **Замыкание в цикле:**
   - В Go 1.22+ каждая итерация создаёт свою переменную
   - Но передача параметром (`go func(ch <-chan T)`) — явнее и безопаснее

2. **wg.Add() в цикле:**
   - Если вызывать `wg.Add(len(channels))` в каждой итерации → счётчик будет неправильным
   - Правильно: один раз перед циклом или `wg.Add(1)` в каждой итерации

3. **Закрытие канала:**
   - Закрывать должен только отправитель
   - Закрывать нужно после завершения всех горутин

## 🎯 Связь с другими паттернами

- **Fan-Out** — противоположность (один канал → много каналов)
- **Pipeline** — можно комбинировать: fan-out → обработка → fan-in
