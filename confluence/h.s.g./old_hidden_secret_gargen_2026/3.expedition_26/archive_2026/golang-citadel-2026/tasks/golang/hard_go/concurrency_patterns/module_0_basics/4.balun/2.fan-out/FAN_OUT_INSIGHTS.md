# Fan-Out: Инсайты от Мусаси

## 🔑 Суть паттерна

**Fan-Out (распределение данных)** — разделение потока данных из одного источника на несколько приёмников.

**Принцип:** Один канал → много каналов

## 📊 Когда использовать?

- Распределение задач по нескольким воркерам
- Шардирование данных в кластер БД (каждый канал = узел)
- Балансировка нагрузки между сервисами
- Параллельная обработка одного потока данных

## 🏗️ Архитектура

```
Один канал ──> SplitChannel ──┬──> Канал 1
                              ├──> Канал 2
                              └──> Канал 3
```

## ⚙️ Реализация: Round Robin

**Round Robin** — последовательное распределение по кругу.

**Как работает:**
```go
idx := 0
for value := range inputCh {
    outputChannels[idx] <- value
    idx = (idx + 1) % n  // Круг: 0→1→2→...→(n-1)→0→1...
}
```

**Пример с 2 каналами:**
- Значение 0 → канал[0] (idx=0)
- Значение 1 → канал[1] (idx=1)
- Значение 2 → канал[0] (idx=0, круг замкнулся)
- Значение 3 → канал[1] (idx=1)
- И так далее...

**Модуль `%` создаёт круг:**
- `(idx + 1) % n` — остаток от деления
- При `n=2`: 0→1→0→1→0...
- При `n=3`: 0→1→2→0→1→2→0...

## 🔄 Round Robin vs "Какой пуст"

### Round Robin (твой код)
- **Последовательное распределение:** всегда по порядку
- **Равномерное:** каждый канал получает одинаковое количество
- **Простое:** не нужно проверять состояние каналов
- **Не учитывает нагрузку:** распределяет независимо от того, занят канал или нет

**Когда использовать:**
- Все каналы/сервисы равны по скорости
- Нужна предсказуемость
- Простота важнее оптимизации

### "Какой пуст" (альтернатива)
- **Запись в первый доступный канал**
- **Учитывает нагрузку:** быстрый канал получит больше
- **Может быть неравномерным**
- **Требует неблокирующей записи** (через `select`)

**Реализация:**
```go
// Записываем в первый доступный канал
for i := 0; i < n; i++ {
    select {
    case outputChannels[i] <- value:
        break  // Записали, выходим
    default:
        // Этот канал занят, пробуем следующий
    }
}
```

**Когда использовать:**
- Каналы/сервисы обрабатывают с разной скоростью
- Нужна балансировка по нагрузке
- Готовы к более сложной логике

## 🔗 Связь с Load Balancer

**Fan-Out — это Load Balancer на уровне каналов:**

- **Round Robin в fan-out** = Round Robin в load balancer
- **"Какой пуст" в fan-out** = Least Connections в load balancer

**Принцип тот же, уровень другой:**
- Load Balancer: распределяет запросы по сервисам
- Fan-Out: распределяет данные по каналам

## ⚠️ Ловушки

1. **Блокирующая запись:**
   - `outputChannels[idx] <- value` блокируется, если канал полон
   - Если один канал не читается → вся горутина зависнет
   - Решение: неблокирующая запись через `select` с `default`

2. **Однонаправленные каналы:**
   - Возвращаем `[]<-chan T` (только чтение)
   - Защищает от записи снаружи
   - Явность лучше неявности

3. **Закрытие каналов:**
   - Закрываем все выходные каналы после завершения входного
   - Это сигнал читателям, что данных больше не будет

## 🎯 Связь с другими паттернами

- **Fan-In** — противоположность (много каналов → один канал)
- **Load Balancer** — тот же принцип на уровне сервисов
- **Worker Pool** — можно комбинировать: fan-out → worker pool → fan-in
