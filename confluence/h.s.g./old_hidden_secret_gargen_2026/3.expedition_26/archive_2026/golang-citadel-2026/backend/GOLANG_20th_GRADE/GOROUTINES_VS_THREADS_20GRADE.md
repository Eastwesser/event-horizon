## ДОПОЛНЕНИЕ к 18 грейду:

| Характеристика | Горутина | Поток ОС |
|----------------|----------|----------|
| **Размер стека** | 2KB стартовый, растёт до 1GB в куче | 1-8MB фиксированный (обычно), может расти но с лимитом |
| **Количество** | Миллионы (при 2KB/каждая) | Тысячи (при 8MB/каждый) |
| **Шедулинг** | User-space (Go runtime, cooperative + preemptive) | Kernel-space (вытесняющий, кванты времени) |
| **Переключение контекста** | Сохраняет ~10 регистров, не переключает режимы | Сохраняет все регистры + FPU, переход user↔kernel |
| **Создание** | ~0.5-1 мкс (malloc + инициализация G) | ~10-50 мкс (clone + выделение стека) |

**Важно:** 1 млн горутин ≠ 2GB RAM, если они активно работают — стек растёт. На практике 100k — безопасный лимит.

**Ключевое отличие:** горутины планируются Go-рантаймом в одном потоке ОС (или нескольких, ограниченных GOMAXPROCS). Потоки ОС планируются ядром, каждому нужен свой M.

**И ещё важное отличие**: переключение между горутинами происходит на границах вызовов функций (или при принудительном прерывании с Go 1.14), а не по кванту времени как в потоках ОС. Это делает переключение предсказуемым и дешёвым, но требует, чтобы горутины добровольно отдавали управление (например, при вызове channel, time.Sleep, runtime.Gosched или системном вызове).

1. Разница между fork и clone
   Это не просто «fork для процессов, clone для потоков». В современном Linux fork тоже реализован через clone.

fork()	clone()
Что делает	Создаёт копию процесса	Создаёт процесс или поток с контролируемым разделением ресурсов
Разделение памяти	Нет (COW — копирование при записи)	Опционально (CLONE_VM — общая память)
Стек	Копирует родительский	Требует выделить отдельный стек
Точка входа	Продолжает с того же места	Начинает с fn(arg) (как pthread)
Где используется	Стандартное создание процессов	pthread_create, Go runtime для создания M
Как работает clone (сигнатура):

c
int clone(int (*fn)(void *), void *stack, int flags, void *arg, ...);
Ключевые флаги:

CLONE_VM — общая память (главный для потоков)

CLONE_FS — общая файловая система (umask, cwd)

CLONE_FILES — общие файловые дескрипторы

CLONE_SIGHAND — общие обработчики сигналов

CLONE_THREAD — один PID для всех нитей (показывает ps -eLf)

CLONE_VFORK — приостановить родителя до execve в ребёнке

Пример из Go runtime (упрощённо):

go
// runtime/os_linux.go
func newosproc(mp *m) {
var sigset sigset
sigprocmask(_SIG_SETMASK, &sigset, nil)
ret := clone(cloneFlags, stk, unsafe.Pointer(mp), unsafe.Pointer(mp.g0))
}
// cloneFlags = _CLONE_VM | _CLONE_FS | _CLONE_FILES | _CLONE_SIGHAND | _CLONE_THREAD
Почему это важно для Go: M (OS thread) создаётся через clone с флагом CLONE_VM → память общая, это нить, а не отдельный процесс. Иначе каждый M жил бы в своём адресном пространстве — никакой общей кучи не было бы .

Итог:

fork = clone( SIGCHLD, 0 ) (только сигнал, без разделения)

pthread_create = clone( CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD, stack )

Go M = clone( ...CLONE_VM..., stack )

2. Как работает morestack (ассемблерные трюки для роста стека горутины)
   Это магия, которая делает стек горутины динамическим (2KB → до 1GB).

Проблема: Стек растёт вниз (на x86). Как узнать, что места мало?
Решение: В начале каждой функции — пролог, который сравнивает SP (stack pointer) с границей.

Упрощённый пролог функции (на ассемблере x86-64):

asm
TEXT runtime·myfunc(SB), 0, $0-0
MOVQ    (TLS), CX        // загружаем текущий g
MOVQ    g_stackguard(CX), SI  // граница стека
CMPQ    SP, SI
JBE     need_more         // если SP <= граница → мало места
// ... тело функции ...
RET
need_more:
CALL    runtime·morestack(SB)
JMP     start             // перезапуск функции с начала
Что делает morestack (упрощённо):

Сохраняет контекст текущей горутины (регистры) в g.sched

Выделяет новый сегмент стека (в куче!) — размером 2× текущего

Копирует старый стек в новый

Обновляет указатели стека в g

Возвращается в пролог, который перезапускает функцию с начала

Ассемблерный трюк с JMP start: В исходниках Go этот JMP не исполняется напрямую CPU. Вместо этого morestack модифицирует сохранённый PC так, чтобы возврат шёл на метку start, а не на следующую инструкцию. Это называется "перемотка" (rewind) точки возврата .

Пример из реального исходника Go (asm_amd64.s):

asm
TEXT runtime·morestack(SB),7,$0-0
// ... проверки ...
CALL    runtime·newstack(SB)  // реальное выделение нового стека
// сюда не возвращаемся — newstack вызывает schedule()
Обратный процесс — lessstack: Когда горутина завершается, рантайм может уменьшить стек (но на практике редко — проще оставить как есть для следующей горутины).

Итог: Горутна не имеет "своего" стека в смысле ОС. Её стек — это кусок памяти в куче, который умеет переезжать при росте. Пролог в каждой функции — цена за эту гибкость (~5-10 инструкций на вызов).

3. Алгоритм Work Stealing в планировщике Go
   Это то, что позволяет P без работы не простаивать, а воровать задачи у других P.

Базовый цикл schedule():

go
// runtime/proc.go (упрощённо)
func schedule() {
_g_ := getg()
gp := runqget(_g_.m.p.ptr())  // 1. взять из локальной очереди P
if gp == nil {
gp = findrunnable()        // 2. нет работы → красть/глобальная
}
execute(gp)                    // 3. выполнить
}
findrunnable() — логика воровства:

Проверить глобальную очередь (sched.runq)

Проверить netpoll (готовые сетевые горутины)

Work stealing: перебрать все остальные P (по кругу) и украсть у них задачи

Если ничего не нашёл — уйти в спящий режим (futex)

Оптимизация: не воруем у idle P (патч 2014 года):

go
// Не пытаемся воровать у P, которые idle
if !idlepMask.read(uint32(id)) {
if gp := runqsteal(_p_, p2, stealRunNextG); gp != nil {
return gp, false
}
}
Раньше проверяли каждый P (O(N) по GOMAXPROCS), что при 1024 ядрах было дорого. Теперь — битмаска idle P .

Алгоритм воровства (runqsteal):

go
func runqsteal(_p_, p2 *p, stealRunNextG bool) *g {
// 1. Пытаемся украсть последнюю G из очереди p2 (LIFO — хорошая локальность)
// 2. Если неудача — украсть половину очереди (batch stealing)
// 3. Минимум: 1, максимум: len(p2.runq)/2, но не более 32
n := p2.runqsize / 2
if n > 32 {
n = 32
}
// атомарно забираем n штук
}
Почему половина и не больше 32?

Баланс: не оголять ворующего P

32 — эмпирически найденный предел, чтобы не тратить время на копирование

Схема работы:

```graph TD
A[P1: локальная очередь пуста] --> B{findrunnable}
B --> C[проверить глобальную очередь]
C --> D{есть работа?}
D -->|да| E[взять глобальную]
D -->|нет| F[воровать у других P]
F --> G{нашли?}
G -->|да| H[украсть половину очереди]
G -->|нет| I[idle, парковка через futex]
H --> J[выполнять G]
```

Результат оптимизации (из коммита Go):
При GOMAXPROCS=1024 производительность выросла на 22% (1.38k ms → 1.07k ms) .

Итог: Work stealing — не просто "украсть задачу". Это:

Сначала локальная очередь (LIFO — хорошая локальность кэша)

Потом глобальная (FIFO — справедливость)

Потом воровство у других P (половина очереди, не более 32)

Потом сон через futex

Без этого механизма один P мог бы простаивать, пока другие перегружены — и весь параллелизм встал бы.

4. netpoll — сетевой поллер (как Go делает неблокирующий I/O)
   Это механизм, который позволяет тысячам горутин ждать данные на сокетах, не блокируя при этом OS threads.

Проблема: Если бы каждая горутина, ждущая чтения из сокета, занимала поток ОС — мы бы вернулись к модели 1:1 (как в Java). Это убило бы всю лёгкость.

Решение: Go использует интерфейс netpoll, который на Linux реализован через epoll, на BSD через kqueue, на Windows через IOCP .

Как работает (упрощённо):
go
// runtime/netpoll_epoll.go
func netpoll(block bool) *g {
var waitms int32
if block {
waitms = -1  // бесконечно ждать
} else {
waitms = 0   // не блокироваться
}

    // epoll_wait — системный вызов
    n := epollwait(epfd, &events, 128, waitms)
    
    var gpList *g
    for i := 0; i < n; i++ {
        gp := *(**g)(unsafe.Pointer(&events[i].data))
        gpList = append(gpList, gp)
    }
    return gpList
}
Ключевая магия: В epoll_data хранится указатель на структуру goroutine (*g), которая ждёт этот сокет. Когда epoll возвращает готовый fd — мы сразу знаем, какую именно горутину будить .

Схема работы с горутиной:

graph TD
A[Горутина вызывает conn.Read] --> B{данные есть в буфере?}
B -->|да| C[немедленный возврат]
B -->|нет| D[gopark → парковка горутины]
D --> E[регистрация fd в epoll]
E --> F[вызов epoll_wait в findrunnable]
F --> G[появление данных → ядро пробуждает epoll]
G --> H[netpoll возвращает *g]
H --> I[горутина становится _Grunnable]
I --> J[Read завершается с данными]
Почему это гениально:

Один M (поток) может обслуживать тысячи горутин через epoll_wait

Гортина ждёт не в потоке, а в очереди epoll — это структура ядра, но без занятия потока

Поток, который вызывает findrunnable, заходит в netpoll и может запарковаться, если нет готовых горутин

Важно: netpoll вызывается из findrunnable при поиске работы для P. Если есть готовые сетевые горутины — они возвращаются и выполняются, не создавая новых M .

Пример с практикой: Когда вы пишете:

go
conn, _ := net.Dial("tcp", "google.com:80")
go func() {
buf := make([]byte, 1024)
conn.Read(buf)  // здесь горутина паркуется
}()
В этот момент горутина уходит в netpoll, поток освобождается, а через 50ms, когда приходит ответ, sysmon или findrunnable вызывает netpoll и будит горутину.

5. sysmon — системный монитор (тот, кто всех контролирует)
   Это специальный поток, который работает вне модели GMP — у него нет P .

Как создаётся:

go
// runtime/proc.go
func main() {
// ...
newm(sysmon, nil)  // создаёт M без P!
// ...
}
Почему без P? Потому что sysmon должен работать даже тогда, когда все P заняты или заблокированы. Он не подчиняется планировщику — он над ним.

Что делает sysmon (основные задачи):
Задача	Частота	Что делает
Проверка сетевого поллера	каждые 10ms	вызывает netpoll для пробуждения горутин, готовых к чтению/записи
Запуск таймеров	при необходимости	проверяет, не истекло ли время у time.After, time.Sleep
Вытеснение долгих горутин	каждые 10ms	если горутина бежит больше 10ms без вызова — ставит флаг preempt
Форсированный GC	раз в 2 минуты	если GC не запускался давно — запускает принудительно
Retake P из syscall	постоянно	если P долго в syscall — отбирает его и передаёт другому M
Код (упрощённо):
go
// runtime/proc.go
func sysmon() {
for {
// 1. Проверяем таймеры
if poll := timeSleepUntil(); poll < now {
// есть таймеры, которые пора запустить
}

        // 2. Проверяем сеть (каждые 10ms)
        if lastpoll != 0 && lastpoll+10*1000*1000 < now {
            netpoll(0)  // non-blocking, пробуждаем готовые горутины
        }
        
        // 3. Вытесняем долгие горутины (retake)
        retake(now)
        
        // 4. Принудительный GC (раз в 2 минуты)
        if gcwaiting == 0 && lastgc+2*60*1e9 < now {
            forcegchelper()
        }
        
        usleep(delay)  // спим 10-20ms
    }
}
Retake — ключевая функция:
go
func retake(now int64) {
for i := 0; i < gomaxprocs; i++ {
p := allp[i]
if p.status == _Prunning && p.sysmontick < now-10*1e6 {
// горутина на P бежит больше 10ms → прерываем
preemptone(p)
}
if p.status == _Psyscall {
// P в системном вызове больше 10μs? Забираем!
handoffp(p)
}
}
}
Итог: sysmon — это "надзиратель", который не даёт системе зависнуть:

Если горутина зависла в бесконечном цикле — sysmon её вытеснит (preemption)

Если P ушёл в syscall на диске — sysmon заберёт P и отдаст другому M

Если сетевые события пришли — sysmon разбудит netpoll

6. handoffp — передача P при блокировке
   Когда M (поток) блокируется на системном вызове (например, read от файла), он не может тащить с собой P — иначе все остальные горутины этого P встанут.

Процесс:

M вызывает блокирующий syscall

M вызывает entersyscall() — помечает, что уходит

Когда syscall затягивается, sysmon вызывает handoffp

handoffp передаёт P другому M (или создаёт новый M)

Старый M просыпается и пытается вернуться:

Если его P свободен — забирает

Если нет — сам становится без P и ищет работу

Код (из исходников Go):
go
// runtime/proc.go
func handoffp(p *p) {
// Проверяем, есть ли работа
if !runqempty(p) || sched.runqsize != 0 {
startm(p, false)  // запускаем M для этого P
return
}
// Если есть GC работа — обязательно запускаем M
if gcBlackenEnabled != 0 && gcMarkWorkAvailable(p) {
startm(p, false)
return
}
// Нет работы — P уходит в idle
pidleput(p)
}
Важный патч (2016 год): Раньше handoffp мог положить P в idle, даже когда была GC-работа. Это приводило к дедлоку. Починили так: теперь если есть GC-работа — обязательно стартуем новый M .

Пример дедлока, который починили:

text
1. Одна горутина вызвала LockOSThread
2. GC начал работу
3. Гортина уснула, а P ушёл в handoffp
4. Раньше: P шёл в idle → нет M для GC → дедлок
5. Теперь: handoffp видит GC work → стартует M → GC работает

Абсолютный максимум (20+ грейд)
7. g0 и m0 — нулевые горутина и поток
   Это фундамент, без которого ничего не работает.

Сущность	Описание
m0	Первый поток ОС (main thread), созданный ядром при старте процесса. Не создаётся через clone, он уже существует.
g0	Первая горутина. У неё огромный стек (64KB на 64-bit системах), потому что она выполняет системные операции (создание других M, выделение памяти). У неё нет обычного "динамического стека как у G" — это скорее гибрид.
Ключевая разница: g0 не подчиняется планировщику так же, как обычные G. Она не переключается в том же смысле. У неё своя, особая роль.

Где используется g0:

Создание новых M через newm (требует стабильный стек)

mcall(fn) — переключение с текущей G на g0 для выполнения системной функции

exitsyscall — выход из системного вызова

scavenge — возврат памяти ОС

mcall — ключевая функция переключения:

go
// runtime/asm_amd64.s
TEXT runtime·mcall(SB), NOSPLIT, $0-8
MOVQ    fn+0(FP), DI      // сохраняем функцию для вызова на g0
MOVQ    SP, (g_sched+gobuf_sp)(g)  // сохраняем стек текущей G
MOVQ    g, (g_sched+gobuf_g)(g)    // сохраняем саму G
MOVQ    g0, g             // переключаемся на g0
MOVQ    (g_sched+gobuf_sp)(g0), SP // восстанавливаем стек g0
CALL    DI                // вызываем функцию на g0
// сюда никогда не возвращаемся
Почему это важно: mcall — это единственный безопасный способ переключиться с пользовательского стека G на системный стек g0. Без этого мы бы не могли выполнять schedule() или park горутины.

8. Алгоритм findrunnable — полная версия
   Это сердце планировщика. Вот полный порядок действий, когда P ищет работу:

go
func findrunnable() (gp *g, inheritTime bool) {
// ========== УРОВЕНЬ 0: Проверки на завершение ==========
if sched.gcwaiting != 0 {
gcstopm()  // останавливаемся, если GC ждёт
}

    // ========== УРОВЕНЬ 1: Локальная очередь ==========
    if gp, inheritTime := runqget(_p_); gp != nil {
        return gp, inheritTime
    }
    
    // ========== УРОВЕНЬ 2: Глобальная очередь ==========
    if sched.runqsize != 0 {
        lock(&sched.lock)
        gp := globrunqget(_p_, 0)  // берём 1 горутину
        unlock(&sched.lock)
        if gp != nil {
            return gp, false
        }
    }
    
    // ========== УРОВЕНЬ 3: Netpoll (неблокирующий) ==========
    if netpollinited() && lastpoll != 0 {
        if list := netpoll(0); !list.empty() {  // non-blocking
            gp := list.pop()
            injectglist(&list)  // остальные в глобальную очередь
            return gp, false
        }
    }
    
    // ========== УРОВЕНЬ 4: Work Stealing (попытка 1) ==========
    for i := 0; i < 4; i++ {  // 4 попытки кражи
        for _, p2 := range allp {
            if p2 == _p_ || p2.status != _Prunning {
                continue
            }
            if gp := runqsteal(_p_, p2, true); gp != nil {
                return gp, false
            }
        }
    }
    
    // ========== УРОВЕНЬ 5: Проверка idle-шности ==========
    if sched.gcwaiting != 0 {
        // GC ждёт, мы единственный P → паркуемся
        if sched.npidle == gomaxprocs-1 {
            gcstopm()
        }
        goto top
    }
    
    // ========== УРОВЕНЬ 6: Netpoll (блокирующий) ==========
    if netpollinited() {
        if list := netpoll(-1); !list.empty() {  // blocking!
            gp := list.pop()
            injectglist(&list)
            return gp, false
        }
        lastpoll = nanotime()  // обновляем время последнего опроса
    }
    
    // ========== УРОВЕНЬ 7: Ничего нет → парковка ==========
    _p_.status = _Pidle
    pidleput(_p_)
    
    // Финальная проверка перед сном
    if sched.runqsize != 0 {
        _p_.status = _Prunning
        goto top  // кто-то добавил работу в последний момент
    }
    
    // Спим через futex
    notesleep(&sched.note)
    
    // Проснулись — ищем работу заново
    _p_.status = _Prunning
    goto top
}
Ключевые константы:

4 попытки кражи — эмпирически найденное число

32 максимум задач при воровстве — баланс между локальностью и амортизацией

-1 в netpoll — блокировка до появления события

9. sched — глобальная структура планировщика
   Это "сердце" рантайма, общая для всех M и P.

go

type schedt struct {

Почему это важно: Все P обращаются к sched за глобальной очередью и для синхронизации. sched.lock — горячая точка, но Go оптимизировал так, что в 99% случаев P работают с локальными очередями и не трогают глобальный мьютекс.

10. preempt — как именно работает вытеснение (кооперативное + некооперативное)
    Go использует гибридный подход. До Go 1.14 было только кооперативное (на границах функций). С 1.14 добавили асинхронное вытеснение для долгих циклов.

А. Кооперативное (на границах функций):
Пролог функции вызывает morestack (как мы уже видели)

morestack проверяет флаг stackguard0, который sysmon выставляет через preemptone

Если флаг взведён — горутина вызывает gosched и уступает место

Б. Асинхронное (для циклов, Go 1.14+):
go
// runtime/signal_unix.go
func sighandler(sig uint32, info *siginfo, ctxt unsafe.Pointer, gp *g) {
if sig == _SIGURG {
// Специальный сигнал для прерывания
if gp.preempt {
// Прерываем горутину прямо сейчас!
gopreempt_m(gp)
}
}
}
Как это работает:

sysmon видит горутину, работающую больше 10ms

Вызывает preemptM(mp) — посылает сигнал SIGURG потоку M

Обработчик сигнала сохраняет контекст и вызывает gopreempt_m

Гортуна вытесняется прямо из цикла без её согласия

Границы:

Не работает на Windows (там SuspendThread)

Не работает на планете (Fuchsia) без поддержки сигналов

Может вызвать проблемы с CGO (C-функции не прерываются)

11. injectglist — возврат краденых горутин в глобальную очередь
    Когда netpoll возвращает несколько готовых горутин, их нельзя просто вернуть в локальную очередь текущего P (может быть переполнена).

Алгоритм:

go
func injectglist(glist *gList) {
// Если P есть и очередь не переполнена
if pp := getg().m.p.ptr(); pp != nil && !runqputfull(pp) {
for {
gp := glist.pop()
if gp == nil {
return
}
runqput(pp, gp, false)  // кладём в локальную очередь
}
}

    // Иначе — в глобальную (под sched.lock)
    lock(&sched.lock)
    for {
        gp := glist.pop()
        if gp == nil {
            break
        }
        globrunqput(gp)
    }
    unlock(&sched.lock)
}
Почему не всегда в глобальную:

Локальная очередь быстрее (без lock)

Если есть место — используем локальную

Если нет — глобальная, но это дороже (мьютекс)

12. wakep — пробуждение спящих M
    Когда появляется работа (например, netpoll разбудил горутину), нужно разбудить спящие M.

go
func wakep() {
// Проверяем, нужно ли будить
if atomic.Load(&sched.npidle) == 0 {
return  // нет свободных P — нечего будить
}
if atomic.Load(&sched.nmspinning) != 0 {
return  // уже кто-то крутится в поиске работы
}

    // Запускаем новый M или будим существующий
    startm(nil, false)
}
Кто вызывает wakep:

ready() — когда горутина становится готовой после goready

netpoll — когда появились сетевые события

timer — когда сработал таймер

unlock — при освобождении мьютекса (может разбудить ждущую горутину)
