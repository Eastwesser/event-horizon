GC в Go: от "как это работает" до "почему write barrier не жрёт CPU"
Записывай. Это будет абсолютный максимум по сборщику мусора. То, что спрашивают на позицию, где ты сам будешь GC настраивать.

1. Что такое GC и почему он вообще нужен
   Проблема: В C/C++ ты сам вызываешь free(). Забыл → memory leak. Вызвал не вовремя → use-after-free → segfault.

Решение Go: GC сам определяет, когда память больше не нужна, и освобождает её.

Цена: Программа иногда "замирает" (STW — Stop The World). Задача Go-разработчика — сделать эти паузы незаметными.

2. Триколорный алгоритм (основа всего)
   Это не магия. Это просто.

Три цвета:

Цвет	Что значит	Как туда попадают
Белый	Не достижим (кандидат на удаление)	Все объекты начинают белыми
Серый	Достижим, но его дети ещё не просмотрены	Становится серым при обнаружении
Чёрный	Достижим, и все дети просмотрены	После обхода всех ссылок
Алгоритм одной строкой:

Корни (глобальные переменные, стек, регистры) → серые

Пока есть серые: взять серый, покрасить его детей в серый, сам → чёрный

В конце: все белые → удалить

Аналогия: Ты красишь комнату. Серый — стена, которую ты начал красить, но не закончил. Чёрный — готово. Белый — не трогал. Убираешь только белые стены.

3. Write Barrier — почему GC не ломается при записи в память
   Проблема: GC идёт параллельно с твоим кодом. Ты можешь изменить указатель после того, как GC уже пометил объект.

Пример (как ломается без барьера):

GC пометил объект A (чёрный), потом пошёл дальше

Твой код: a.next = b (b — белый)

GC никогда не вернётся к A (он уже чёрный), поэтому b никогда не станет серым

GC удалит b, хотя на него есть ссылка от A → segfault

Решение — Write Barrier: При каждой записи указателя Go вызывает функцию, которая говорит GC: "Эй, этот объект теперь достижим, не удаляй его".

На Go это выглядит так (упрощённо):

go
// То, что ты пишешь
a.next = b

// То, что реально делает Go
gcWriteBarrier(&a.next, b)
Что делает барьер (Dijkstra-style):

go
func gcWriteBarrier(ptr **Object, new *Object) {
if gcPhase == _GCmark {
// GC идёт, надо помочь
if new != nil && isWhite(new) {
// Сделай new серым, чтобы GC его не удалил
greyObject(new)
}
}
// Сама запись
*ptr = new
}
Почему это быстро: Барьер срабатывает только во время фазы маркировки. Всё остальное время — просто проверка флага (одна инструкция).

А что с производительностью: Каждая запись в указатель (а это любое присваивание полю структуры) теперь дороже на 1-2 наносекунды. Плата за безопасность.

4. STW (Stop The World) — когда программа замирает
   GC не может работать полностью параллельно. В некоторые моменты нужна остановка всех горутин.

Фазы GC с STW:

Фаза	Длительность (типичная)	Что делает
Mark Start	10-30 μs	Включает write barrier, определяет корни (глобальные переменные, стеки горутин)
Marking	0 (параллельно)	Сама маркировка (работает на всех P)
Mark Termination	20-50 μs	Останавливает все P, завершает маркировку, включает write barrier для sweep
Sweeping	0 (параллельно)	Удаляет белые объекты (лениво, при аллокациях)
Важно: Основная работа (маркировка) происходит параллельно твоему коду. STW только на короткие фазы.

Почему так мало STW: Go использует write barrier и позволяет твоему коду работать, пока GC бежит рядом.

5. Pacing — как GC решает, когда запускаться
   GC не запускается "каждые 2 минуты". Он запускается, когда есть работа.

Правило (упрощённо):

text
Если выделено памяти > target процента от живой памяти → запустить GC
Target по умолчанию: 100% (то есть при удвоении живой памяти)

Пример:

Живая память: 50MB

Target = 100% → GC запустится при 100MB выделенной памяти (с учётом того, что было удалено)

После GC: живых объектов, допустим, 55MB

Следующий GC: при ~110MB

Параметр GOGC:

bash
export GOGC=200  # запускать при 200% (реже, но дольше паузы)
export GOGC=50   # запускать при 50% (чаще, но короче паузы)
export GOGC=off  # выключить GC (не делай этого)
Как GC считает "живую память": Во время маркировки считает, сколько объектов осталось чёрными.

6. Write Barrier — два типа (Dijkstra и Yuasa)
   Go использует два барьера в разных фазах.

Фаза маркировки: Dijkstra (insertion barrier)
go
// При записи ptr = new
if new != nil && isWhite(new) {
greyObject(new)  // делаем new серым
}
*ptr = new
Проблема: Может сохранять мусор (белый объект, на который больше нет ссылок, но он стал серым и не удалится до следующего GC).

Фаза завершения маркировки: Yuasa (deletion barrier)
go
// При записи ptr = new
old := *ptr
if old != nil && isWhite(old) {
greyObject(old)  // делаем old серым (тот, на который больше не ссылаемся)
}
*ptr = new
Проблема: Тоже может сохранять мусор, но другого рода.

Почему два барьера: Dijkstra хорош для параллельной маркировки (не требует перепросмотра чёрных объектов). Yuasa нужен для финальной синхронизации, чтобы не потерять ссылки при завершении.

С Go 1.8+: Используется гибридный барьер (Dijkstra во время маркировки, Yuasa в Mark Termination). Это снизило STW с 10-100ms до 10-50μs.

7. Какие объекты вообще смотрит GC
   GC не смотрит на каждый байт. Только на:

Указатели (явные и скрытые внутри срезов, мапов, интерфейсов)

Строки (как указатели на данные)

Срезы (указатель на массив + длина + ёмкость)

Что GC игнорирует:

int, float64, bool — не содержат ссылок

[1024]byte — сплошные данные без указателей

Как Go узнаёт, где в структуре указатели: Информация хранится в бинарнике (в секции .gopclntab). GC при обходе объекта читает эту таблицу и знает: "смещение 8 байт — указатель, смещение 16 — нет".

8. Sweeping — удаление объектов
   Маркировка нашла белые объекты. Теперь их надо удалить.

Как это работает:

Белые объекты помещаются в список "на удаление"

Когда нужна память для нового объекта (make, new), аллокатор сначала проверяет этот список

Если есть подходящий по размеру белый объект — переиспользует его

Если нет — выделяет новую память через mmap

Почему лениво (sweep on demand): Не нужно останавливать мир и удалять всё сразу. Программа может работать, а память освобождается постепенно.

Что такое "память не вернулась ОС": Go редко возвращает память ядру (через munmap). Он держит её в своём heap, потому что завтра она может снова понадобиться. Вернуть можно через debug.FreeOSMemory() или надеяться на scavenger (отдельная горутина, которая спит и иногда вызывает madvise(MADV_DONTNEED)).

9. Пример: что происходит в реальной программе
   go
   type Node struct {
   next *Node
   data [1024]byte
   }

func main() {
for i := 0; i < 1000; i++ {
n := &Node{}          // аллокация
n.next = &Node{}      // ещё одна аллокация
// n уходит из области видимости
}
runtime.GC()              // принудительный GC
}
Что делает GC:

Останавливает все P (Mark Start STW, ~20μs)

Находит корни: глобальные переменные (нет), стеки горутин (main)

Из стека main видит, что переменная n больше не существует (переиспользована в цикле)

Маркирует все Node, на которые есть ссылки из стека (их 0)

Все 2000 объектов становятся белыми

Mark Termination STW (~20μs)

При следующей аллокации sweep вернёт эту память

Итог: Все объекты удалены.

10. Как оптимизировать GC в своём коде
    Правила (от создателей Go):

Меньше указателей → меньше работы GC

Плохо: []*int

Хорошо: []int

Пул объектов (sync.Pool) → переиспользуй, не создавай новые

go
var bufPool = sync.Pool{
New: func() interface{} { return make([]byte, 4096) },
}
buf := bufPool.Get().([]byte)
defer bufPool.Put(buf)
Не храни ссылки на короткоживущие объекты → они не станут чёрными

Следи за GOGC: для сервисов с большим количеством долгоживущих объектов можно увеличить до 200-400

Профилируй:

bash
GODEBUG=gctrace=1 ./myapp
# gc 1 @0.012s 2%: 0.031+1.2+0.045 ms clock, 0.25+0.87/1.5/2.1+0.36 ms cpu
