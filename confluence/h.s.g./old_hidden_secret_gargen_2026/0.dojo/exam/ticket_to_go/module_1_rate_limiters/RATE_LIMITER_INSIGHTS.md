# Rate Limiter: Инсайты от Мусаси

## 🔑 Ключевые концепции

### Worker Pool vs Rate Limiter

**Worker Pool (Semaphore)** — ограничивает **количество одновременно выполняющихся горутин**.
- "Максимум 5 горутин работают одновременно"
- Это ограничение **параллельности (concurrency)**
- Пример: "50 URL, ≤5 одновременно" — это Worker Pool

**Rate Limiter** — ограничивает **частоту запросов**.
- "Максимум 50 запросов в секунду"
- Это ограничение **частоты (rate)**
- Пример: "Token Bucket Rate Limiter" — это Rate Limiter

### Разница на практике

**Worker Pool на 5 горутин:**
- Приходит 100 запросов одновременно
- Сразу обработается **5 запросов** (по одному на горутину)
- Остальные 95 ждут в очереди
- Если каждый запрос обрабатывается 0.1 сек → все 100 запросов обработаются за **2 секунды** (100 запросов / 5 горутин × 0.1 сек)

**Rate Limiter на 50 запросов/сек:**
- Приходит 100 запросов одновременно
- Пропустит **50 запросов в первую секунду**
- Остальные 50 пропустит во **вторую секунду**
- Всего займёт **2 секунды**, но это ограничение частоты, а не параллельности

**Важно:** Можно запустить 100 горутин, но Rate Limiter пропустит только 50 запросов в секунду. Остальные будут отклонены или подождут.

Вода (Принцип и Вопрос):

Про Worker Pool:
Твой ответ: "5 горутин, каждая рандомно отработает свой пул задач, но всего задач будет 50."
Нет. Если Worker Pool на 5 горутин и приходит 100 запросов:
    Сразу обработается 5 запросов (по одному на горутину).
    Остальные 95 ждут в очереди.
    Если каждый запрос обрабатывается 0.1 сек → все 100 запросов обработаются за 2 секунды (100 запросов ÷ 5 горутин × 0.1 сек = 2 сек).

Про Rate Limiter:
Твой ответ: "Выполнятся только 50 запросов, остальные повиснут."
Нет. Rate Limiter на 50 запросов/сек:
    В первую секунду пропустит 50 запросов.
    Во вторую секунду пропустит ещё 50.
    Всего займёт 2 секунды, но это ограничение частоты, а не количества.
Вопрос: в чём разница? Worker Pool ограничивает параллельность (сколько одновременно), Rate Limiter — частоту (сколько в секунду).

## 🔒 Замыкания в Go

### Проблема замыкания в циклах

**Старый код (до Go 1.22):**
```go
for i := 0; i < 3; i++ {
    go func() {
        fmt.Println(i)  // ❌ Все горутины увидят i=3 (последнее значение)
    }()
}
```

**Правильное решение:**
```go
for i := 0; i < 3; i++ {
    go func(i int) {  // ✅ Передаём i как параметр
        fmt.Println(i)  // Каждая горутина получит своё значение
    }(i)
}
```

### Почему важно понимать замыкания?

1. В старых версиях Go это ломало код
2. В других местах (не в `for`) замыкание работает по-старому
3. На собеседованиях спрашивают про **понимание**, а не про версию

**Суть замыкания:** Функция захватывает переменную из внешней области видимости. Если переменная меняется, функция видит новое значение. Передача параметра создаёт **копию значения** на момент вызова.

## 📡 Каналы: Буферизованные vs Небуферизованные

### Небуферизованный канал
```go
ch := make(chan int)  // без буфера
```
- **Синхронизация:** Отправка блокируется, пока кто-то не прочитает
- Отправитель **ждёт** получателя
- Это как рукопожатие: оба должны быть готовы одновременно

### Буферизованный канал
```go
ch := make(chan int, 3)  // буфер на 3 элемента
```
- **Очередь:** Можно отправить до N значений без блокировки
- Отправитель не ждёт, если в буфере есть место
- Это как почтовый ящик: можно положить письма, даже если получателя нет

### Пример из кода

```go
ch1 := make(chan string, 3)  // буфер на 3
data := []string{"a", "b", "c"}

for i := 0; i < len(data); i++ {
    go func(i int) {
        ch1 <- data[i]  // Не блокируется, т.к. буфер есть
    }(i)
}
```

**Зачем буфер на 3?** В данном случае не критично, но:
- Без буфера: каждая горутина будет блокироваться, пока не прочитают
- С буфером: горутины могут отправить все 3 значения и завершиться

**Будет ли работать без буфера?** Да, но горутины будут ждать чтения.

## 🪣 Типы Rate Limiter'ов

### 1. Fixed Window (Фиксированное окно)
- **Принцип:** Считаем запросы в фиксированных временных окнах
- **Пример:** "100 запросов в минуту" → окна: 0:00-0:59, 1:00-1:59...
- **Реализация:** Счётчик запросов + время начала окна
- **Проблема:** На границе окна возможен всплеск (в конце одного окна + начало следующего = 200 запросов за 2 секунды!)
- **Когда использовать:** Когда допустимы всплески на границах

### 2. Sliding Window Log (Скользящее окно с логом)
- **Принцип:** Храним время каждого запроса, считаем запросы в скользящем окне
- **Пример:** "100 запросов в минуту" → храним все времена запросов, считаем за последние 60 секунд
- **Реализация:** Массив/список времён запросов
- **Плюс:** Точное ограничение, нет всплесков
- **Минус:** Память растёт с количеством запросов
- **Когда использовать:** Когда нужна точность и память не критична

### 3. Sliding Window Counter (Скользящее окно со счётчиком)
- **Принцип:** Делим окно на подокна, считаем запросы в каждом
- **Пример:** "100 запросов в минуту" → делим на 6 подокон по 10 сек, считаем взвешенно
- **Реализация:** Массив счётчиков для каждого подокна
- **Плюс:** Более равномерное ограничение, меньше памяти чем Log
- **Минус:** Менее точный чем Log (приблизительный)
- **Когда использовать:** Компромисс между точностью и памятью

### 4. Token Bucket (Ведро токенов) ⭐
- **Принцип:** Ведро с токенами, которые пополняются со временем
- **Пример:** Ведро на 10 токенов, пополнение 1 токен/сек
- **Реализация:** Счётчик токенов + горутина пополнения или расчёт по времени
- **Плюс:** Позволяет "накопить" токены в периоды простоя (burst)
- **Метод:** `Allow() bool` — проверяет, есть ли токен, и забирает его
- **Когда использовать:** Когда нужны burst'ы (всплески) после простоя

### 5. Leaky Bucket (Протекающее ведро)
- **Принцип:** Запросы капают с фиксированной скоростью
- **Пример:** Ведро на 10 запросов, обработка 1 запрос/сек
- **Отличие от Token Bucket:** Запросы накапливаются в очереди, а не токены
- **Когда использовать:** Когда нужна равномерная обработка без burst'ов

## 🔍 Сравнение типов

| Тип | Точность | Память | Burst | Сложность |
|-----|----------|--------|-------|-----------|
| Fixed Window | Низкая | O(1) | Да (на границе) | Простая |
| Sliding Window Log | Высокая | O(n) | Нет | Средняя |
| Sliding Window Counter | Средняя | O(k) | Нет | Средняя |
| Token Bucket | Средняя | O(1) | Да | Средняя |
| Leaky Bucket | Средняя | O(n) | Нет | Средняя |

**Burst** — возможность сделать больше запросов после простоя

## 🎯 Что строим?

**Token Bucket Rate Limiter** с методом `Allow() bool`:
- Структура с токенами
- Пополнение токенов со временем
- Метод `Allow()` проверяет и забирает токен
- Thread-safe (потокобезопасный)

## ✅ Практика: Token Bucket в действии

### Тест: 5 токенов, пополнение 1/сек, запросы каждые 200ms

**Результат:**
```
Запрос 0: разрешён  (токенов: 5 → 4)
Запрос 1: разрешён  (токенов: 4 → 3)
Запрос 2: разрешён  (токенов: 3 → 2)
Запрос 3: разрешён  (токенов: 2 → 1)
Запрос 4: разрешён  (токенов: 1 → 0)
Запрос 5: разрешён  (токенов: 0 → 0, но пополнился 1 токен на 1000ms!)
Запрос 6: отклонён  (токенов: 0)
Запрос 7: отклонён  (токенов: 0)
Запрос 8: отклонён  (токенов: 0)
Запрос 9: отклонён  (токенов: 0)
```

### Почему запрос 5 разрешён?

**Временная линия:**
- 0ms: Запрос 0 → токенов: 5→4
- 200ms: Запрос 1 → токенов: 4→3
- 400ms: Запрос 2 → токенов: 3→2
- 600ms: Запрос 3 → токенов: 2→1
- 800ms: Запрос 4 → токенов: 1→0
- **1000ms: Пополнение! → токенов: 0→1** (тикер сработал)
- 1000ms: Запрос 5 → токенов: 1→0 (успел взять пополнившийся токен!)
- 1200ms: Запрос 6 → токенов: 0 (отклонён)
- 1400ms: Запрос 7 → токенов: 0 (отклонён)
- 1600ms: Запрос 8 → токенов: 0 (отклонён)
- 1800ms: Запрос 9 → токенов: 0 (отклонён)
- 2000ms: Пополнение! → токенов: 0→1 (но уже поздно, тест закончился)

### Выводы

1. **Burst эффект:** Первые 5 запросов прошли сразу (ведро было полным)
2. **Пополнение работает:** На 1000ms тикер пополнил токен, поэтому запрос 5 прошёл
3. **Ограничение работает:** После исчерпания токенов запросы отклоняются
4. **Частота пополнения:** 1 токен/сек означает, что после исчерпания нужно ждать секунду

### Когда использовать Token Bucket?

✅ **Подходит:**
- Когда нужны burst'ы (всплески) после простоя
- Когда допустима некоторая неравномерность
- Когда нужна простота реализации

❌ **Не подходит:**
- Когда нужна строгая равномерность (лучше Leaky Bucket)
- Когда нужна высокая точность (лучше Sliding Window)
