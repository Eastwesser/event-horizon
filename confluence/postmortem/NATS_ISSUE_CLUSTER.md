📝 Заметка для собеса: Эпопея с NATS (баг no response from stream)
Проблема:
После релиза v1.1.3.3 Billing начал спамить в логи ошибкой:

text
ERROR billing outbox: publish event_type=balance.updated err="nats: no response from stream"
При этом:

Стрим EVENTS существует, лидер выбран, balance.updated есть в Subjects.

nats pub из CLI работает без ошибок.

Консьюмеров-фантомов нет, nc.Subscribe на balance.updated нигде не зарегистрирован.

Что проверяли:

nats stream info EVENTS — subject на месте, лидер nats-2/nats-3.

nats consumer ls EVENTS — старых консьюмеров нет.

grep -r "nc.Subscribe" services/ — обычных подписок нет.

nats pub из CLI — сообщение уходит успешно.

Причина (баг NATS):
В issue #6391 описана ситуация: лидер стрима «залипает» и перестаёт принимать сообщения на конкретный subject, хотя стрим существует и другие subject работают. Причина — сбой в Raft-консенсусе при переизбрании лидера. js.Publish в Go-клиенте по умолчанию ждёт PubAck 250 мс и делает 2 ретрая — этого мало, если лидер «залип» навсегда.

Решение (двухуровневое):

Клиентский ретрай + пересоздание стрима. В outbox_worker.go добавили цикл из 5 попыток с nats.RetryWait(1s), nats.RetryAttempts(3), nats.AckWait(10s). Если ловим no response from stream — вызываем forceStreamRecreation(): StreamInfo → DeleteStream → AddStream с теми же настройками. Это «встряхивает» Raft и сбрасывает залипший subject.

Анти-спам + идемпотентность. В Billing добавили SetNX в Redis с ключом score_lock:{user_id}:{game_id}:{score} и TTL 30 секунд. Повторное сохранение того же счёта игнорируется. reference_id для наград теперь берётся из event.Timestamp, а не из time.Now().UnixNano(), чтобы избежать двойного начисления при redelivery.

Что сказали бы на собесе:

«Мы столкнулись с багом NATS JetStream, когда лидер стрима «залипает» на одном subject. CLI работает, а клиент из Go — нет. Мы проверили всё: конфиг стрима, консьюмеров, обычные подписки. В итоге нашли issue #6391 и поняли, что это баг Raft-консенсуса. Решили двумя уровнями: добавили ретраи с пересозданием стрима на клиенте и защиту от двойного начисления через Redis SetNX и event.Timestamp. Это классический пример, когда распределённая система ведёт себя не так, как ожидаешь, и нужно копать до уровня протокола».

Ключевой вывод: NATS — отличная штука, но в кластере он иногда «залипает» на subject, и это лечится только пересозданием стрима или переизбранием лидера. Клиентский retry — обязателен.
