1. «Надёжно, но долго» vs «быстро, но с багами» — нет, это ложная дихотомия
Правильная формулировка: «сериализация на одном ресурсе» vs «параллелизм на разных ресурсах».

Твой items FOR UPDATE — это сериализация на одном item. Пока один purchase держит items[X], второй purchase того же X ждёт. Это не «плата за надёжность», это плата за то, что мы не разделили «зарезервировать» и «оплатить».

Классическое решение (все крупные e-commerce так делают): двухфазный резерв.

Фаза 1 (быстро, короткий лок): UPDATE items SET stock = stock - 1 WHERE id = $1 AND stock >= 1 RETURNING stock — одна строка, атомарно, без SELECT FOR UPDATE. Держит лок микросекунды.

Фаза 2 (долго, без лока): Billing gRPC, INSERT purchases, outbox — вне лока на items. Если фаза 2 упала — компенсация: UPDATE items SET stock = stock + 1.

Фаза 3 (если нужно): purchases INSERT — свой лок, короткий.

Так работает Shopify, Stripe, Amazon. Резерв — мгновенный, оплата — асинхронная. Клиент видит «заказ принят» за 50ms, а фактическое списание идёт фоном. Если не хватило денег — отмена с уведомлением.

У нас purchase держит items FOR UPDATE всю транзакцию — включая Billing.SpendCurrency (gRPC, 100–500ms), INSERT inventory, INSERT purchases, INSERT outbox. Это 2+ секунды. И cancel ждёт всё это время.

Вывод: это не «фундаментально», это наша реализация. Можно разделить — резерв items короткий, оплата — вне лока.

2. Про 1000 юзеров / 1000 товаров vs 1000 юзеров / 1 товар
Ты абсолютно прав — это два разных кейса.

Кейс A: 1000 юзеров, 1000 товаров, каждый свой
purchase(user1, item1), purchase(user2, item2), ... — разные items.

items FOR UPDATE не пересекается — каждый держит свой.

Параллелизм = 1000. Latency = latency одной транзакции.

Всё хорошо. Никакой сериализации.

Кейс B: 1000 юзеров, 1 товар
purchase(user1, itemX), purchase(user2, itemX), ... — один items[X].

items FOR UPDATE сериализует всех — 1 держит, 999 ждут.

Параллелизм = 1. Latency = 1000 × latency одной транзакции (если транзакция 2с — 2000с = 33 минуты).

Кто-то получит, кто-то нет (stock = 1, остальные 999 — out of stock).

Но — в кейсе B никто не ждёт 33 минуты. Первые несколько получают out of stock быстро (stock = 1 → после первого purchase, остальные сразу stock <= 0 → fail). То есть реальная latency для 999 — 2 секунды (первый purchase), потом мгновенный out of stock. Не 33 минуты.

Вот это ключ. FOR UPDATE сериализует только тех, кто реально конкурирует за ресурс. Если stock = 1, конкурируют все, но выигрывает один, остальные получают быстрый fail (stock = 0).

Проблема — если все пытаются купить, и все проходят (stock = 1000), то FOR UPDATE сериализует все 1000. Это реальный сценарий для «айфон за миллион билетиков» — если stock = 100, 1000 юзеров, все хотят, все проходят до stock = 0. Тогда 900 ждут 900 × 2с = 30 минут. Это плохо.

Решение — не держать FOR UPDATE всю транзакцию. Резерв — мгновенный (UPDATE ... WHERE stock >= 1), оплата — вне лока. Тогда 1000 юзеров параллельно делают резерв (1000 UPDATE, каждый микросекунды), 100 получают stock, 900 — out of stock мгновенно. Дальше 100 параллельно платят. Latency = max(резерв, оплата) = 2с для 100, 0с для 900. Не 30 минут.

Вывод: твой сценарий неизбежен только если FOR UPDATE держится всю транзакцию. Если резерв короткий — неизбежности нет.

3. Redis, батчинг — не для покупок
Ты правильно заметил: Redis — для чтения. Для покупок — ACID в Postgres. Redis не даёт ACID (если не Redis Cluster с WAIT, но это другой уровень сложности).

Батчинг — для записи логов, метрик, не для денег. Нельзя «батчить» 1000 SpendCurrency в один — потому что каждый должен знать, прошёл он или нет. Батч вернёт «1000 прошло», а если один упал — какой? Не разберёшь.

Для денег — только поштучно, ACID. Это фундаментально. Redis/батчинг не помогут.

4. ORDER-сервис — не сейчас, но идея правильная
Корзина, заказы, обработка — это следующий уровень. Сейчас у нас прямая покупка: POST /shop/purchase → сага → всё. ORDER-сервис добавит:

Корзина (несколько items за раз) — батчинг покупок, один SpendCurrency на сумму.

Заказ — статус (created → paid → fulfilled → shipped → delivered), отдельная сущность.

Резерв — items FOR UPDATE на время корзины, не на время оплаты.

Это правильно для маркетплейса. Но сейчас — overkill. У нас нет корзины, нет заказов, нет доставки. ORDER — это v1.2+, не v1.1.3.7.

Но — резерв можно добавить сейчас, без ORDER. Просто разделить purchase на «резерв» (короткий UPDATE) + «оплата» (вне лока). Это Шаг 3.5 (после bulkhead, до индексов).

## Фундаментальный вопрос: «надёжно, но долго» vs «быстро, но с багами»

Нет, это ложная дихотомия. Правильно: «сериализация на одном ресурсе» vs
«параллелизм на разных ресурсах».

- 1000 юзеров / 1000 товаров — параллелизм = 1000, latency = latency одной
  транзакции. Всё хорошо.
- 1000 юзеров / 1 товар — параллелизм = 1, но **только если FOR UPDATE держится
  всю транзакцию**. Если резерв короткий (UPDATE ... WHERE stock >= 1) — 
  параллелизм = 1000, 100 получают stock, 900 — быстрый out-of-stock.

Наш `PurchaseItemWithStock` держит `items FOR UPDATE` всю транзакцию, включая
Billing gRPC (100–500ms). Это **наша** реализация, не фундамент. Классическое
решение — двухфазный резерв (Shopify, Stripe, Amazon): резерв мгновенный,
оплата вне лока, компенсация при сбое. Шаг 3.5.

Redis и батчинг — не для денег. ACID только в Postgres, поштучно.

1. Про кейс Б: 1000 юзеров, 1 товар, stock = 1000
Да, сериализация. Но не потому, что БД не тянет, а потому что мы сами её сериализовали FOR UPDATE.

Что реально произойдёт с текущим кодом:

1000 purchase(userN, itemX) — все хотят один items[X].

SELECT ... FOR UPDATE — первый берёт лок, 999 ждут.

Первый: Billing gRPC (100–500ms) + INSERT inventory + INSERT purchases + INSERT outbox → 2с, commit, лок отпущен.

Второй: берёт лок, 2с, commit.

...

1000-й: 2000с = 33 минуты.

Но — это с текущим кодом. С коротким резервом (Шаг 3.5):

UPDATE items SET stock = stock - 1 WHERE id = $1 AND stock >= 1 RETURNING stock — микросекунды, лок держится только на UPDATE.

1000 параллельно: 1000 UPDATE, каждый 1ms. Параллелизм = 1000, потому что Postgres сам сериализует только строку items[X] на время UPDATE, а не на всю транзакцию.

Итого: 1000 UPDATE × 1ms = 1 секунда (не 33 минуты), все получают stock, дальше 1000 параллельно платят (Billing gRPC) — вне лока, 2с параллельно.

Latency: 1–3 секунды для всех.

Это ключ. FOR UPDATE на всю транзакцию — 33 минуты. UPDATE ... WHERE stock >= 1 (без SELECT FOR UPDATE) — 1 секунда. Разница в 2000 раз — не потому, что БД медленная, а потому что мы сами держим лок дольше, чем нужно.

Вывод: кейс Б не неизбежен. Сериализация на строке (UPDATE) — микросекунды. Сериализация на транзакции (FOR UPDATE) — секунды. Это наша реализация, не фундамент.

Шаг 3.5 — это правильный фикс. Он не про ORDER, он про разделение лока и оплаты. 30 минут. После bulkhead — сразу увидим эффект (contention на 10 items упадёт).
