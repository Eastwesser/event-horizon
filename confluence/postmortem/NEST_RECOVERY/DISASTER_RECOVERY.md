# 🚨 Event Horizon — Disaster Recovery Plan (DRP)

> **Цель:** Описать процедуры восстановления после катастрофических сбоев (потеря датацентра, физическое уничтожение серверов, ransomware).
> **Метрики:** RTO (время восстановления) = 4 часа. RPO (потеря данных) = 24 часа.

## 1. Классификация инцидентов

| Уровень | Описание | Пример | Действие |
|---------|----------|--------|----------|
| **L1** | Отказ одного сервиса | Упал Gateway | Kubernetes/Docker перезапускает под |
| **L2** | Отказ узла (Node) | Упала VM | Балансировщик перенаправляет трафик на живые ноды |
| **L3** | Отказ датацентра | Пожар, наводнение | **Активация DRP** (этот документ) |
| **L4** | Катастрофа | Ядерный взрыв, война | Восстановление из off-site бэкапов |

## 2. Что мы теряем при L3/L4

1. **Инфраструктура:** Все VM, Docker-контейнеры, сети.
2. **Данные на дисках:** Postgres (13 баз), ClickHouse (аналитика), NATS (сообщения в полете).
3. **Секреты:** JWT_SECRET, пароли БД (если не вынесены в Vault).
4. **DNS:** Если домен привязан к IP старого сервера.

## 3. Стратегия бэкапов (Off-site)

| Компонент | Метод | Частота | Хранение | RPO |
|-----------|-------|---------|----------|-----|
| **Postgres** (13 баз) | `pg_dump` + gzip | Раз в 24 часа | S3 (другой регион) | 24 часа |
| **ClickHouse** | `clickhouse-backup` | Раз в 24 часа | S3 (другой регион) | 24 часа |
| **S3 (uploads)** | Cross-Region Replication | Real-time | Второй бакет в другом регионе | ~0 |
| **Код** | Git | При каждом коммите | GitHub / GitLab | 0 |
| **Секреты** | Vault / Sealed Secrets | При изменении | Вне сервера | 0 |

## 4. План восстановления (Playbook)

### Шаг 1: Поднятие инфраструктуры (T+0 — T+1 час)
1. Развернуть новые VM через Terraform (или вручную у нового провайдера).
2. Установить Docker, k3s, Ansible.
3. Настроить сеть и firewall (UFW).

### Шаг 2: Восстановление кода и секретов (T+1 — T+2 часа)
1. `git clone git@github.com:Eastwesser/event-horizon.git`
2. Восстановить `.env` из Vault (или из защищенного хранилища).
3. Проверить, что все секреты на месте (JWT_SECRET, POSTGRES_PASSWORD, GRAFANA_ADMIN_PASSWORD).

### Шаг 3: Восстановление данных (T+2 — T+3 часа)
1. Скачать последние дампы из S3:
   ```bash
   aws s3 cp s3://eh-backups/postgres/ /tmp/restore/ --recursive
Поднять Postgres, применить миграции (make migrate-all).

Восстановить дампы:

bash
for db in auth game billing leaderboard shop inventory profile payment authors history notification; do
  psql -U eventhorizon -d eventhorizon_$db < /tmp/restore/$db.sql
done
Восстановить ClickHouse (если нужно).

Восстановить S3 (uploads) — синхронизировать из реплики.

Шаг 4: Запуск приложения (T+3 — T+4 часа)
make deploy

Проверить make status (все контейнеры healthy).

Прогнать смоук-тесты (make test-smoke).

Шаг 5: Переключение трафика (T+4 часа)
Поменять A-запись в Cloudflare на новый IP.

Дождаться TTL (300 сек).

Проверить, что сайт открывается.

5. Что НЕ делать при восстановлении
Не восстанавливать старые бинарники — пересобрать из исходников.

Не использовать старые IP — поднять новые.

Не забывать про миграции — сначала make migrate-all, потом дампы.

6. Тестирование DRP (Game Day)
Раз в квартал проводить учения:

Взять последний бэкап.

Развернуть копию в изолированной среде (staging).

Проверить, что данные консистентны.

Замерить RTO.
