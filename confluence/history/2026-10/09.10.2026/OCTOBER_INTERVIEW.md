Generics: чем дженерики отличаются от интерфейсов
Методы и интерфейсы Middle+ / Senior
ВОПРОС Работал ли с дженериками? В чём отличие от интерфейсов?
ЭТАЛОННЫЙ ОТВЕТ
Дженерики (type parameters, с Go 1.18) позволяют параметризовать функции и типы по типу, а
множество допустимых типов ограничивается constraint — специальным интерфейсом,
описывающим либо набор методов, либо набор типов ( type set ). Принципиальное отличие от
обычных интерфейсов — в моменте разрешения и механике вызова. Дженерики разрешаются на
этапе компиляции: компилятор Go использует GC shape stenciling — генерирует не отдельную
копию на каждый тип, а одну инстанциацию на «форму» типа (одинаковое представление в
памяти/способ работы GC), передавая в неё словарь (dictionary) с метаданными конкретного типа.

Интерфейс же разрешается в рантайме: вызов метода идёт косвенно через таблицу методов
(itable), а значение хранится в боксированном виде.
Практический итог: дженерики дают типобезопасность без приведений ( any + type assertion не
нужны) и обычно лучше с точки зрения аллокаций — конкретные типы не боксируются в
интерфейс. Интерфейсы дают динамический полиморфизм — одна переменная может в рантайме
держать разные типы, что для дженериков невозможно (тип фиксируется при инстанциации).
ЧАСТАЯ ОШИБКА Говорят «дженерики — это синтаксический сахар над интерфейсами» или
утверждают, что Go генерирует отдельную копию кода на каждый тип (как шаблоны C++). На
деле это GC shape stenciling со словарями, а не полная мономорфизация, и это именно про
compile-time типобезопасность, а не про runtime-полиморфизм.
02 Неявная реализация интерфейсов
Методы и интерфейсы Middle
ВОПРОС Что означает неявная реализация интерфейсов в Go? Как реализовать интерфейс?
ЭТАЛОННЫЙ ОТВЕТ
В Go интерфейс реализуется структурно и неявно: тип удовлетворяет интерфейсу автоматически,
если обладает полным набором методов с нужными сигнатурами. Никакого ключевого слова
implements нет — связь между типом и интерфейсом устанавливает компилятор по факту наличия
методов. Это даёт «структурную типизацию» (часто называют duck typing), но с полной проверкой
на этапе компиляции, а не в рантайме.
Ключевое следствие проектирования — интерфейсы можно объявлять после реализации и на
стороне потребителя: правило «accept interfaces, return structs». Зависимости описываются
минимальными интерфейсами там, где они используются, что снижает связанность и упрощает
тестирование (моки реализуют интерфейс просто наличием методов). Важно помнить про набор
методов: если методы объявлены на pointer receiver, то интерфейсу удовлетворяет *T , а не T .
GO
import "cmp"
// Дженерик: тип T известен на компиляции, нет боксинга и приведений.
func Min[T cmp.Ordered](a, b T) T {
if a < b {
return a
}
return b
}
// Аналог через интерфейс: значения боксируются, нужен type switch/assertion,
// компилятор не гарантирует, что a и b одного типа.
func MinIface(a, b any) any { /* ... сравнение через рефлексию/switch ... */ }
ЧАСТАЯ ОШИБКА Кандидаты с фоном Java/C# ищут явный implements и путают неявную
реализацию с динамической. Также забывают, что при методах на pointer receiver значение
T интерфейсу не удовлетворяет — присвоить можно только &T .
03 Value receiver vs pointer receiver
Методы и интерфейсы Middle / Middle+
ВОПРОС В чём отличие метода для указателя от метода для значения структуры?
ЭТАЛОННЫЙ ОТВЕТ
Метод с value receiver ( func (s T) M() ) работает с копией значения — мутации полей внутри
метода в оригинал не попадают. Метод с pointer receiver ( func (s *T) M() ) работает с оригиналом
через указатель — изменения сохраняются. Кроме семантики мутаций важна и стоимость: value
receiver копирует всю структуру при каждом вызове, что для больших структур дороже, чем
передать 8-байтовый указатель.
Практические правила выбора: pointer receiver обязателен, если метод изменяет состояние;
желателен для больших структур и для типов, чьё значение нельзя безопасно копировать
(содержат sync.Mutex , sync.WaitGroup и т.п. — копирование мьютекса — это баг). Для
консистентности набор методов одного типа делают однородным: если хотя бы один метод на
указателе, обычно все делают на указателе. Тонкость: метод-сет T включает только value-
методы, а *T — и value-, и pointer-методы; поэтому интерфейсу с pointer-методом удовлетворяет
только *T .
GO
type Stringer interface {
String() string
}
type Point struct{ X, Y int }
func (p Point) String() string { return fmt.Sprintf("(%d,%d)", p.X, p.Y) }
var s Stringer = Point{1, 2} // Point неявно удовлетворяет Stringer
GO
type Counter struct{ n int }
func (c Counter) IncValue() { c.n++ } // мутация теряется (копия)
func (c *Counter) IncPtr() { c.n++ } // мутация сохраняется
c := Counter{}
c.IncValue() // c.n == 0
c.IncPtr() // c.n == 1 (Go автоматически берёт &c)
ЧАСТАЯ ОШИБКА Считают, что value receiver на «маленькой» структуре всё равно как-то
меняет оригинал, либо копируют структуры с мьютексом внутри через value receiver. Также
забывают про влияние выбора receiver на метод-сет и удовлетворение интерфейсов.
04 nil-интерфейс vs typed nil (iface/eface)
Методы и интерфейсы Senior
ВОПРОС Что будет выведено при сравнении nil-интерфейса с typed nil?
ЭТАЛОННЫЙ ОТВЕТ
Под капотом интерфейсное значение — это пара слов. Для интерфейса с методами это
iface{ tab *itab, data unsafe.Pointer } , для пустого interface{} —
eface{ _type *_type, data unsafe.Pointer } . Интерфейс равен nil тогда и только тогда, когда
оба слова пусты — нет ни типа, ни значения. Как только в интерфейс кладётся значение
конкретного типа (пусть даже nil-указатель этого типа), слово типа становится ненулевым, и
интерфейс перестаёт быть nil .
Отсюда классическая ловушка: nil-указатель конкретного типа, положенный в интерфейс, даёт
(type=*T, data=nil) — это «typed nil», и сравнение с nil даёт false . Чаще всего это стреляет с
error : функция возвращает конкретный тип ошибки ( *MyError ), который оказался nil , но в
вызывающем коде err != nil неожиданно истинно, потому что в интерфейсе записан тип.
Правильно — объявлять переменную сразу как интерфейс ( var err error ) и возвращать nil без
типа, а не возвращать nil-указатель конкретного типа.
ЧАСТАЯ ОШИБКА Уверенно отвечают « true , ведь значение nil». Не знают про двухсловное
представление и про различие iface / eface , из-за чего не могут объяснить, почему
err != nil срабатывает там, где «ошибки нет».
GO
type MyError struct{}
func (*MyError) Error() string { return "boom" }
func do() error {
var e *MyError = nil
return e // в интерфейс error попадает (type=*MyError, data=nil)
}
err := do()
fmt.Println(err == nil) // false — typed nil, не nil-интерфейс!

Внутреннее устройство map: бакеты и эвакуация
Составные типы Middle+ / Senior
ВОПРОС Расскажи про map. Почему к элементу map нельзя взять указатель? Что такое
эвакуация?
ЭТАЛОННЫЙ ОТВЕТ
Классическая (до Go 1.24) реализация map — хеш-таблица из бакетов, где каждый бакет хранит до
8 пар ключ/значение плюс массив старших байтов хеша ( tophash ) для быстрого отсева при
поиске. Хеш ключа (с рандомизированным seed, чтобы защититься от hash-flooding) делится на
две части: младшие биты выбирают бакет, старший байт ускоряет сравнение внутри бакета.
Коллизии внутри бакета разрешаются линейным просмотром восьми слотов; при переполнении
бакета подцепляется overflow-бакет (то есть chaining на уровне бакетов, а не отдельных
элементов).
Когда заполнение растёт (load factor выше ~6.5 на бакет) или накапливается слишком много
overflow-бакетов, таблица удваивается и начинается эвакуация — инкрементальное, по мере
операций, перераспределение пар из старых бакетов в новые. Именно поэтому нельзя взять
адрес элемента map ( &m[k] не компилируется): рантайм вправе физически переместить пары
при эвакуации/росте, и любой сохранённый указатель стал бы висячим. По той же причине map
нельзя сделать потокобезопасной «бесплатно» — конкурентная запись ловится детектором и
роняет программу. Сама map — ссылочный тип: переменная хранит указатель на внутренний
hmap , поэтому копия map делит данные с оригиналом. (В Go 1.24 реализация переведена на Swiss
Tables — другая раскладка и группы по 8 слотов, но семантика address-safety и отсутствия
потокобезопасности та же.)
ЧАСТАЯ ОШИБКА Объясняют коллизии «как в учебнике» — связные списки на каждый
элемент, тогда как в Go chaining идёт overflow-бакетами по 8 слотов. И не связывают запрет
на &m[k] с тем, что эвакуация перемещает данные.

Слайсы: header, len/cap, append и шаринг массива
Составные типы Middle+ / Senior
ВОПРОС Что такое слайс? Зачем указывать capacity в make? Как работает append и почему
он O(1) амортизированно? Изменится ли оригинал при передаче слайса в функцию?
ЭТАЛОННЫЙ ОТВЕТ
Слайс — это header из трёх полей: указатель на начало окна в базовом массиве, длина ( len ) и
ёмкость ( cap ). При передаче слайса в функцию header копируется по значению, но указатель в
копии ведёт на тот же базовый массив. Поэтому изменение существующего элемента по индексу
( s[i] = x ) видно снаружи — массив общий. А append меняет len (и, возможно, указатель)
только у локальной копии header: если ёмкости хватало, новый элемент запишется в общий
массив, но внешний слайс его «не увидит», так как его len не изменился; если ёмкости не
хватило — выделяется новый массив, копия начинает указывать на него, и связь с оригиналом
теряется полностью.
make([]T, len, cap) с заранее известной ёмкостью убирает лишние реаллокации: при росте
append , когда len == cap , выделяется новый массив (примерно ×2 для маленьких слайсов, затем
рост замедляется до ~×1.25) и копируются все элементы — это O(n) в худшем случае. Но за счёт
геометрического роста суммарная стоимость n вставок — O(n), то есть амортизированно O(1) на
вставку. Отсюда же вытекают тонкие баги шаринга: два слайса от одного make / s[a:b] делят
массив, и append в один может затереть данные другого, пока не произошла реаллокация.
ЧАСТАЯ ОШИБКА Говорят «слайс передаётся по ссылке» и ждут, что append внутри функции
всегда виден снаружи. Путаница в том, что общий — массив, а len / cap — локальные копии;
поведение append зависит от того, хватило ли cap .

Конкурентный доступ к map: потокобезопасность
Составные типы / Практика Middle+ / Senior
ВОПРОС Code review: глобальная map с конкурентным доступом, 80% чтений, 20% записей.
Найди проблемы и предложи решение.
ЭТАЛОННЫЙ ОТВЕТ
map в Go не потокобезопасна: конкурентная запись (или чтение одновременно с записью) — это
data race, который рантайм специально детектирует и аварийно завершает процесс с
fatal error: concurrent map ... . Типичные дефекты в таком ревью: (1) мьютекс объявлен
локально/копируется и фактически не защищает общую map; (2) Unlock вызывается вручную, а не
через defer , из-за чего паника между Lock и Unlock оставит мьютекс захваченным (deadlock); (3)
неатомарный getOrCreate — классический check-then-act race: между «проверил, что ключа нет»
и «вставил» другой горутиной значение уже могло появиться.
Базовое решение — инкапсулировать map и sync.RWMutex в одну структуру: RLock / RUnlock на
чтениях (а их здесь 80%), Lock / Unlock на записи, причём вся операция get-or-create под одним
эксклюзивным Lock , чтобы исключить гонку. Для read-heavy паттернов с редко меняющимся
набором ключей подходит sync.Map ; при очень высокой конкуренции на запись — шардирование
(массив [N]struct{mu; m} с выбором шарда по хешу ключа), чтобы снизить contention на одном
мьютексе.
GO
func modify(s []int) {
s[0] = 99 // видно снаружи — общий массив
s = append(s, 7) // снаружи не видно, если меняется только локальный header
}
ЧАСТАЯ ОШИБКА Защищают только запись, забывая, что одновременное чтение+запись —
тоже гонка. И реализуют getOrCreate через RLock на проверке и отдельный Lock на
вставке, оставляя окно гонки между ними.

Указатели: *p = v против p = &v (value vs reference семантика)
Основы языка Middle
ВОПРОС Функция setAge принимает *Person и внутри создаёт новый Person . Как это
повлияет на оригинал? Что выведет код?
ЭТАЛОННЫЙ ОТВЕТ
В Go всё передаётся по значению, включая указатели — в функцию копируется сам адрес. Дальше
всё решает разница между разыменованием и переназначением. *p = Person{...} пишет по
адресу, на который указывает p , то есть перезаписывает оригинальную структуру в main —
изменение видно снаружи ( Age станет новым). А p = &Person{...} переназначает локальную
копию указателя: оригинал в main не затрагивается, и после возврата из функции ничего не
изменится.
GO
type Cache struct {
mu sync.RWMutex
m map[string]int
}
func (c *Cache) GetOrCreate(k string, make func() int) int {
c.mu.Lock()
defer c.mu.Unlock() // defer обязателен — защита от паники
if v, ok := c.m[k]; ok {
return v
}
v := make()
c.m[k] = v
return v
}
Это и есть суть value-семантики Go: чтобы функция изменила данные вызывающего, нужно
передать указатель и писать через него ( *p = ... или p.Field = ... ), а не переназначать сам
указатель.
ЧАСТАЯ ОШИБКА Считают, что «раз передан указатель — любое изменение p внутри
функции видно снаружи», и не различают запись по адресу ( *p = ... ) и переприсваивание
локальной копии указателя ( p = ... ). Рисунок памяти с двумя стрелками снимает путаницу
мгновенно.

Горутина против OS-потока
Goroutines vs threads Middle
ВОПРОС Как бы ты описал, что такое горутина? Чем горутина отличается от потока ОС?
ЭТАЛОННЫЙ ОТВЕТ
Горутина — это легковесная единица выполнения, которой управляет планировщик рантайма Go, а
не ядро ОС. Запускается ключевым словом go перед вызовом функции. Принципиальные отличия
от потока ОС:
GO
type Person struct {
Name string
Age int
}
func setAge(p *Person, age int) {
*p = Person{Name: p.Name, Age: age} // запись по адресу — оригинал меняется
// p = &Person{Name: p.Name, Age: age} // переназначение копии — оригинал НЕ меняется
}
func main() {
pers := Person{Name: "Ann", Age: 25}
setAge(&pers, 27)
fmt.Println(pers.Age) // 27
}
КОНКУРЕНТНОСТЬ: ГОРУТИНЫ, КАНАЛЫ,
СИНХРОНИЗАЦИЯ
Стек. Горутина стартует с маленьким стеком (~2 КБ) и растёт/сжимается динамически (copyon-
grow), тогда как поток ОС резервирует фиксированный стек (обычно 1–8 МБ).
Стоимость переключения. Контекст горутины переключается в user-space самим рантаймом
(сохраняется минимум регистров), без перехода в ядро. Переключение потока ОС требует
syscall и сброса кэшей — на порядок дороже.
Мультиплексирование. Множество горутин мультиплексируется на небольшое число потоков
ОС. Поэтому сотни тысяч горутин — норма, а столько же потоков положат систему.
Важно: горутина — это про конкурентность (структуру программы), а реальный параллелизм даёт
планировщик, раскладывая горутины по потокам на доступных ядрах.
ЧАСТАЯ ОШИБКА Кандидаты называют горутину «потоком» и не могут объяснить разницу в
цене переключения и стека; путают «легковесность» с «бесплатностью» — забывают, что
миллион горутин — это всё равно ~2 ГБ только под стеки.
10 Конкурентность vs параллелизм vs асинхронность
Concurrency model Middle
ВОПРОС Чем отличается асинхронное исполнение от параллельного? А конкурентность от
параллелизма?
ЭТАЛОННЫЙ ОТВЕТ
Три разных понятия, которые часто смешивают:
Цитируя Роба Пайка: «Concurrency is not parallelism». Конкурентная программа на одном ядре даёт
чередование без параллелизма; при GOMAXPROCS>1 рантайм может исполнять конкурентные
горутины параллельно. То есть конкурентность — необходимое условие, чтобы получить
параллелизм, но не гарантия его.
ЧАСТАЯ ОШИБКА Кандидаты ставят знак равенства между конкурентностью и параллелизмом
и считают, что go func() автоматически означает «на отдельном ядре». На самом деле это
лишь возможность параллельного исполнения, которую решает планировщик.

Каналы: буферизованные, небуферизованные, закрытые, nil
Каналы Middle+
ВОПРОС Какие бывают каналы? Чем отличаются буферизованные и небуферизованные? Как
ведёт себя запись/чтение для закрытого и nil-канала?
GO
go worker(ctx, jobs) // запуск горутины: дешёвый, неблокирующий
Конкурентность (concurrency) — это структура программы: способ декомпозировать задачу
на независимые единицы, которые могут выполняться в произвольном порядке и чередоваться.
Это свойство кода, а не железа.
Параллелизм (parallelism) — это исполнение: несколько единиц физически работают
одновременно на разных ядрах CPU.
Асинхронность — это про неблокирующий запуск: инициируем операцию и продолжаем
работу, не дожидаясь её завершения (типично для I/O).
ЭТАЛОННЫЙ ОТВЕТ
Небуферизованный ( make(chan T) ) синхронен: отправка блокируется, пока другой стороной не
будет выполнено чтение, — это точка рандеву (happens-before между отправителем и
получателем). Буферизованный ( make(chan T, N) ) асинхронен в пределах буфера: отправка
блокируется только когда буфер полон, чтение — когда буфер пуст. Буфер развязывает скорости
producer и consumer.
Семантика крайних случаев — её и спрашивают:
Операция Открытый Закрытый nil
send ch <- v блок/успех паника блокировка навсегда
recv <-ch блок/успех zero value, ok=false (после вычитки буфера) блокировка навсегда
close(ch) ок паника (двойное закрытие) паника
Из закрытого канала сначала вычитываются оставшиеся в буфере значения, и лишь потом
приходит zero, false . Закрывать должен писатель, не читатель. nil-канал блокируется навсегда
— это используется намеренно: занулив case-канал в select , можно динамически его
«выключить».
ЧАСТАЯ ОШИБКА Запись в закрытый канал и повторный close — паника, а не no-op; на этом
сыпались. Также путают «чтение из закрытого канала» (безопасно, отдаёт zero+false) с
«записью в закрытый» (паника).

select: семантика, default, nil-каналы, таймаут
select Middle+
ВОПРОС Как работает select ? Что меняет default ? Что будет, если один из каналов — nil?
ЭТАЛОННЫЙ ОТВЕТ
select ждёт готовности нескольких канальных операций и выполняет ровно один готовый case.
Если готовы несколько — выбирается псевдослучайно (важно для честности, чтобы не было
голодания одного канала). Если ни один не готов — select блокируется до первой готовой
операции.
Канонический таймаут и отмена:
default делает select неблокирующим: при отсутствии готовых case-ов сразу выполняется
default . Это паттерн try-send / try-recv.
nil-канал в case никогда не готов — операция над ним эффективно «отключена». Приём:
динамически зануляем канал, чтобы исключить ветку из выбора.
Пустой select{} блокирует горутину навсегда.
ЧАСТАЯ ОШИБКА for { select { ... default: } } без полезной работы в default — это busyloop,
который жжёт CPU и не уступает планировщику. default нужен для non-blocking
операции, а не как «иначе подождём».

context: назначение и правила использования
context Middle+
ВОПРОС Для чего нужен context , какие проблемы он решает?
ЭТАЛОННЫЙ ОТВЕТ
context.Context управляет жизненным циклом операции через границы API и горутин: отмена,
дедлайны/таймауты и передача request-scoped значений. Конструкторы:
Отмена распространяется по дереву: отменили родителя — отменились все потомки. Горутина
обязана слушать <-ctx.Done() и завершаться, иначе отмена бессмысленна и получаем утечку.
Правила: контекст — первый параметр функции ( ctx context.Context ); его не хранят в
структурах; не передают nil (передавайте context.TODO() ); cancel всегда вызывают (обычно
defer cancel() ), даже при таймауте — иначе течёт таймер контекста.
ЧАСТАЯ ОШИБКА Создают WithTimeout / WithCancel и не вызывают cancel() — утечка
ресурсов контекста. И второе: воспринимают отмену как «волшебную» — забывают, что
горутина сама должна проверять ctx.Done() , иначе она не остановится.

Паттерн «первый результат + отмена остальных»
context (отмена) Senior
ВОПРОС Реализуй обёртку: запустить поиск по нескольким источникам параллельно,
вернуть первый успешный результат, остальные отменить через context.
GO
select {
case res := <-work:
return res, nil
case <-time.After(timeout): // или <-ctx.Done()
return zero, ctx.Err()
}
context.Background() / TODO() — корень дерева контекстов;
WithCancel(parent) — ручная отмена через возвращаемый cancel ;
WithTimeout / WithDeadline — автоматическая отмена по времени;
WithValue — request-scoped значения (трейс-ID, auth), но не для передачи опциональных
параметров.
ЭТАЛОННЫЙ ОТВЕТ
Создаём дочерний контекст с WithCancel , общий канал результатов, и в каждой горутине через
select гарантируем выход по отмене (чтобы не зависнуть на отправке в канал, который уже никто
не читает):
Ключевое: defer cancel() обрывает проигравшие горутины; буфер размера N (или select -
обёртка отправки) защищает от leak писателей, которые иначе навсегда залипнут на ch <- r .
Этот же скелет годится для варианта «выполнить все с таймаутом и собрать ошибки» — там
вместо первого результата собираем все через WaitGroup .
ЧАСТАЯ ОШИБКА Небуферизованный ch без select на отправке — проигравшие горутины
навсегда виснут на ch <- r (классическая утечка горутин), потому что главная читает канал
ровно один раз. И забывают defer cancel() — тогда search у проигравших не прерывается.
15 Mutex vs RWMutex
sync.Mutex / RWMutex Middle+
ВОПРОС Расскажи про sync.Mutex . Что такое RWMutex и когда он выигрывает у обычного
Mutex ?
ЭТАЛОННЫЙ ОТВЕТ
sync.Mutex — взаимное исключение: Lock() / Unlock() защищают критическую секцию, держать
его может только одна горутина. Правила: defer mu.Unlock() сразу после Lock() ; нельзя
GO
func searchFirst(ctx context.Context, urls []string) (Result, error) {
ctx, cancel := context.WithCancel(ctx)
defer cancel() // отменяет всех проигравших
ch := make(chan Result, len(urls)) // буфер = N: писатели не залипнут
for _, u := range urls {
go func(u string) {
r, err := search(ctx, u)
if err != nil {
return
}
select {
case ch <- r:
case <-ctx.Done():
}
}(u)
}
select {
case r := <-ch:
return r, nil // defer cancel() остановит остальных
case <-ctx.Done():
return Result{}, ctx.Err()
}
}
копировать мьютекс после использования (копируется и его внутреннее состояние — go vet это
ловит); рекурсивный re-lock в той же горутине — дедлок (мьютекс не реентрантен). Внутри есть
normal/starvation режимы для защиты от голодания ожидающих.
sync.RWMutex различает два режима: RLock() (много читателей одновременно) и Lock() (один
писатель, эксклюзивно — блокирует и читателей, и писателей). Выигрывает на профиле много
чтений / редкие записи, давая параллелизм читателям. Но он тяжелее обычного мьютекса
(больше учёта), поэтому при коротких критических секциях и сбалансированном read/write
обычный Mutex нередко быстрее. RLock использовать только для чтения — модификация под
RLock это data race.
ЧАСТАЯ ОШИБКА Считают RWMutex «всегда лучше» — на самом деле под низкой долей чтений
или коротком теле он проигрывает Mutex . Также модифицируют данные, держа RLock , и
копируют структуру с мьютексом внутри.

Data race, atomic vs Mutex, флаг -race
Атомики vs мьютексы Senior
ВОПРОС 1000 горутин конкурентно обновляют общую переменную max . Как убрать data
race и гарантировать корректный результат? Когда брать sync/atomic вместо мьютекса?
ЭТАЛОННЫЙ ОТВЕТ
Две независимые проблемы: (1) data race на max , (2) нужно дождаться всех горутин.
Mutex берём на всю операцию «прочитать-сравнить-записать»: если защитить только запись,
между чтением и записью встрянет другая горутина (race-окно). WaitGroup гарантирует, что
главный читает max после завершения всех.
atomic vs mutex. sync/atomic подходит для одной машинной ячейки (счётчик, флаг, указатель) и
read-modify-write через CompareAndSwap . Он быстрее (нет блокировки), но не атомизирует
составные инварианты из нескольких полей — там нужен Mutex . Для «максимума» атомарно
делается CAS-циклом:
GO
var mu sync.Mutex
var wg sync.WaitGroup
max := math.MinInt64
for _, v := range data {
wg.Add(1)
go func(v int) {
defer wg.Done()
mu.Lock()
if v > max { // и чтение, и запись — под одним lock
max = v
}
mu.Unlock()
}(v)
}
wg.Wait()
Любой data race — UB, и его надо ловить детектором: go test -race / go run -race .
ЧАСТАЯ ОШИБКА Берут lock только вокруг присваивания, оставляя сравнение снаружи, — race
остаётся. Думают, что WaitGroup синхронизирует доступ к данным (он лишь ждёт
завершения). И не запускают -race в CI, считая, что «у меня и так работает».

Примитивы синхронизации и sync.Once
sync.Once / sync пакет Senior
ВОПРОС Какие примитивы синхронизации ты знаешь? Как устроен sync.Once и почему
двойная проверка важна с точки зрения memory model?
ЭТАЛОННЫЙ ОТВЕТ
Арсенал пакета sync и около: Mutex / RWMutex (критические секции), WaitGroup (ожидание
группы горутин), Once (однократное выполнение), Cond (условные переменные), Pool
(переиспользование объектов), sync/atomic (атомарные операции), плюс каналы и select , и
context для отмены. Go-пословица: «Don’t communicate by sharing memory; share memory by
communicating» — каналы для передачи владения данными, мьютексы/атомики для защиты
разделяемого состояния.
sync.Once гарантирует, что функция выполнится ровно один раз, даже при гонке горутин. Идея
реализации — double-checked locking на атомарном флаге + мьютексе:
GO
for {
old := atomic.LoadInt64(&max)
if int64(v) <= old || atomic.CompareAndSwapInt64(&max, old, int64(v)) {
break
}
}
GO
type Once struct {
done atomic.Uint32
m sync.Mutex
}
func (o *Once) Do(f func()) {
if o.done.Load() == 0 { // быстрый путь без блокировки
o.doSlow(f)
}
}
func (o *Once) doSlow(f func()) {
o.m.Lock()
defer o.m.Unlock()
if o.done.Load() == 0 { // повторная проверка под мьютексом
defer o.done.Store(1)
f()
}
}
Тонкость про memory model / happens-before: флаг done ставится в 1 после f() (через defer
после вызова). Атомарная запись done устанавливает happens-before с атомарным чтением в
быстром пути, поэтому горутина, увидевшая done==1 , гарантированно видит все записи,
сделанные внутри f() . Если поставить флаг до f() или читать его не-атомарно, другая горутина
может увидеть done==1 , но ещё не увидеть инициализированные данные.
ЧАСТАЯ ОШИБКА Реализуют Once через простой bool без атомиков/мьютекса — это data
race и нет гарантии видимости результата f() . Не понимают, что флаг обязан выставляться
после f , и не связывают это с happens-before.
18 Deadlock и утечка горутин
deadlock / goroutine leak Senior
ВОПРОС Что такое deadlock и goroutine leak? Детектит ли их рантайм? Есть ли смысл
создавать миллион горутин?
ЭТАЛОННЫЙ ОТВЕТ
Deadlock — все участники заблокированы навсегда. Рантайм Go детектит только глобальный
дедлок — когда все горутины спят и продвинуться некому: паника
fatal error: all goroutines are asleep - deadlock! . Локальный дедлок (часть горутин зависла,
остальные работают) рантайм не ловит — его видно только через профилировщик. Типичные
источники: захват двух мьютексов в разном порядке, отправка в небуферизованный канал без
читателя, WaitGroup.Wait() при недостающем Done() .
Goroutine leak — горутина, которая никогда не завершится: висит на канале без второй стороны,
забыт Done() , бесконечный цикл без ctx.Done() . Каждая такая горутина держит минимум ~2 КБ
стека и ссылки на объекты — постепенная деградация по памяти и числу горутин. Детекция:
runtime.NumGoroutine() , pprof goroutine-профиль, в тестах — go.uber.org/goleak .
Миллион горутин: технически реально (~2 ГБ под стеки), но обычно бессмысленно. Параллелизм
CPU-bound работы упирается в GOMAXPROCS ; для I/O лучше ограничить число одновременных
операций (worker pool / семафор), чем плодить горутины без счёта.
ЧАСТАЯ ОШИБКА Считают, что Go «всегда поймает дедлок». Локальный дедлок и зависший
писатель на канале рантайм пропустит, и это превратится в leak. Также не связывают
забытую отмену контекста с накоплением висящих горутин.

ВОПРОС Нужно обойти большой список URL. Запускать горутину на каждый — плохо. Какие

Семафор на буферизованном канале — минималистично:
Worker pool — фиксированное число воркеров читает задачи из общего канала jobs ; число

20 Fan-in / fan-out и pipeline
Паттерны (fan-in/out, pipeline) Senior
ВОПРОС Реализуй joinChannels , сливающую произвольное число каналов в один (fan-in).
Как из этого строится pipeline и где типичные дедлоки/паники?
ЭТАЛОННЫЙ ОТВЕТ
Fan-in: на каждый входной канал — своя горутина-читатель, все пишут в общий out ; отдельная
горутина закрывает out после завершения всех писателей.
GO
sem := make(chan struct{}, limit) // не более limit одновременно
var wg sync.WaitGroup
for _, u := range urls {
wg.Add(1)
sem <- struct{}{} // занять слот (блок, если limit достигнут)
go func(u string) {
defer wg.Done()
defer func() { <-sem }() // освободить слот
fetch(u)
}(u)
}
wg.Wait()
Из таких «звеньев» строится pipeline: каждая стадия принимает входной канал, возвращает
выходной, стадии соединяются ( stage1 -> stage2 -> stage3 ). Fan-out — несколько горутин
читают из одного входа (распараллеливание стадии); fan-in собирает их обратно в один поток. Для
корректного завершения через все стадии прокидывают ctx / done -канал, а закрытие выходного
канала делает только производящая сторона.
ЧАСТАЯ ОШИБКА close(out) вызывают внутри читающих горутин или раньше wg.Wait() —
получают панику «send on closed channel» или гонку закрытий. Зеркальная ошибка — не
закрыть out вообще: потребитель с range зависает навсегда (deadlock/leak).

21 Модель планировщика GMP и work stealing
Runtime & Scheduler Middle+ / Senior
ВОПРОС Объясни модель планировщика Go (GMP). Какую проблему она решает, как
происходит переключение горутин и в чём преимущество горутин перед OS-потоками?
ЭТАЛОННЫЙ ОТВЕТ
GMP — это три сущности рантайма. G (goroutine) — единица выполнения: стек, указатель
инструкции, состояние. M (machine) — поток ОС, на котором реально исполняется код. P
(processor) — логический процессор, контекст планирования: он владеет локальной runqueue
готовых горутин и набором ресурсов для аллокаций (mcache). Ключевое правило: чтобы M
исполнял Go-код, ему нужен привязанный P. Число P по умолчанию равно GOMAXPROCS , и именно P
ограничивает реальный параллелизм исполнения Go-кода, а не число M.
Проблема, которую решает модель, — мультиплексирование тысяч дешёвых горутин на
небольшое число потоков ОС с минимальными накладными расходами и хорошей локальностью.
Каждый P держит свою локальную очередь (LRQ, до 256 G); есть ещё одна глобальная очередь
GO
func joinChannels[T any](chans ...<-chan T) <-chan T {
out := make(chan T)
var wg sync.WaitGroup
wg.Add(len(chans))
for _, ch := range chans {
go func(ch <-chan T) {
defer wg.Done()
for v := range ch { // выйдет, когда ch закроют
out <- v
}
}(ch)
}
go func() { wg.Wait(); close(out) }() // close ровно один раз, после всех писателей
return out
}
РАНТАЙМ И ПЛАНИРОВЩИК (GMP)
(GRQ). Балансировка идёт через work stealing: когда у P опустела локальная очередь, он сначала
заглядывает в глобальную очередь и в netpoller, а затем «крадёт» половину горутин у случайного
другого P. Это снижает контеншн на общих структурах и держит ядра загруженными.
Переключение горутин — это user-space context switch: рантайм сохраняет регистры (SP/PC и
др.) текущей G и восстанавливает их для следующей, не уходя в ядро. Поэтому оно на порядок
дешевле переключения потоков ОС. Дополнительный выигрыш — стек: горутина стартует с ~2 KB
и растёт/сжимается динамически (copying stacks), тогда как поток ОС резервирует фиксированный
стек порядка мегабайта. Итог: на одной машине можно держать сотни тысяч горутин.
ЧАСТАЯ ОШИБКА Путают роли M и P и считают, что параллелизм определяется числом
потоков. На самом деле потолок одновременно исполняемого Go-кода задаёт число P (=
GOMAXPROCS ), а M может быть значительно больше — лишние M простаивают или сидят в
syscall. Также часто забывают про глобальную очередь и про то, что work stealing крадёт
именно половину чужой очереди.

Синхронные syscall и hand-off P
Runtime & Scheduler Senior
ВОПРОС Приведи пример синхронного (блокирующего) системного вызова и объясни, что
происходит с G, M и P в рамках GMP-модели.
ЭТАЛОННЫЙ ОТВЕТ
Типичный пример — блокирующее чтение с диска или вызов, который не проходит через netpoller
(например, файловый read , многие операции с устройствами). Перед входом в такой syscall
рантайм вызывает entersyscall : M вместе с текущей G уходит в ядро и там блокируется, поэтому
P отвязывается от этого M (переходит в состояние _Psyscall ).
Дальше есть два пути освобождения P. Быстрый: если syscall возвращается достаточно быстро, на
выходе ( exitsyscall ) M пытается снова забрать свой прежний P и продолжить ту же G без
переключения — это дешёвый happy path. Медленный: если M «завис» в syscall, фоновый поток-
монитор sysmon замечает, что P слишком долго в _Psyscall , и выполняет hand-off — отбирает P
у заблокированного M и отдаёт его другому M (свободному из пула или вновь созданному). Этот
новый M с P немедленно продолжает крутить остальные горутины из локальной очереди. Когда
исходный syscall наконец завершится, его M уже не имеет P; он пытается захватить любой
свободный P, и если не находит — паркует свою G в runnable-очередь и сам уходит в пул
простаивающих M.
Смысл механизма: один блокирующий вызов «съедает» только M (поток ОС), но не P. P остаётся
доступным для выполнения других горутин, поэтому пул логических процессоров не простаивает
из-за блокировок.
CODE
G ── M ── P // исполнение
G ── M P (_Psyscall) // entersyscall: M в ядре, P отвязан
G ── M M' ── P // sysmon hand-off: P уходит к новому M'
ЧАСТАЯ ОШИБКА Кандидаты говорят, что «P сам ищет новый M», и упускают, что hand-off в
медленном случае инициирует именно sysmon, а в быстром — P вообще не передаётся, M
забирает его обратно. Ещё путают блокировку: блокируется M (поток), а не P, и тем более не
«весь планировщик».
23 Netpoller и асинхронный сетевой I/O
Runtime & Scheduler Senior
ВОПРОС Что такое netpoller? Чем сетевой I/O в Go отличается от блокирующего syscall и
почему он не «съедает» потоки?
ЭТАЛОННЫЙ ОТВЕТ
Netpoller — это подсистема рантайма, которая интегрируется с механизмами событийного I/O
ядра: epoll на Linux, kqueue на BSD/macOS, IOCP на Windows. Сетевые файловые дескрипторы
рантайм переводит в неблокирующий режим, поэтому сетевая операция в Go только выглядит как
синхронный блокирующий вызов ( conn.Read ), но под капотом работает асинхронно.
Когда горутина делает Read / Write , а данные ещё не готовы (ядро вернуло EAGAIN ), рантайм
регистрирует дескриптор в netpoller и паркует горутину ( gopark ) — она уходит в состояние
ожидания, а её M и P освобождаются и продолжают исполнять другие горутины. Поток ОС при
этом не блокируется, в отличие от настоящего синхронного syscall. Готовность дескриптора
отслеживается двумя способами: на каждом витке планировщика ( schedule / findrunnable )
делается неблокирующий опрос netpoller, плюс sysmon периодически опрашивает его с
таймаутом. Как только I/O готов, netpoller возвращает список «разбуженных» горутин — они
помечаются runnable и ставятся обратно в очереди P.
Именно поэтому Go держит десятки тысяч сетевых соединений без пула потоков и без явного
событийного цикла в коде: цикл epoll_wait спрятан в рантайме, а разработчик пишет линейный
блокирующий код. Контраст с разделом про синхронные syscall: файловый read блокирует M и
требует hand-off P, тогда как сетевой read через netpoller освобождает и M, и P, не тратя поток ОС.
ЧАСТАЯ ОШИБКА Считают, что netpoller обрабатывает любой I/O, включая файловый. На
большинстве платформ обычные файлы не интегрированы с epoll/kqueue, поэтому дисковый
I/O идёт как блокирующий syscall с hand-off, а не через netpoller. Также путают: netpoller не
«крутит поток на ожидании», он именно паркует горутину и освобождает M.
24 GOMAXPROCS и asynchronous preemption
Runtime & Scheduler Senior
ВОПРОС Что задаёт GOMAXPROCS и как планировщик вытесняет горутину, которая долго не
возвращает управление (например, тугой цикл без вызовов функций)?
ЭТАЛОННЫЙ ОТВЕТ
GOMAXPROCS задаёт число P — то есть верхнюю границу горутин, исполняющих Go-код
одновременно. По умолчанию он равен числу доступных CPU; начиная с Go 1.25 рантайм также
учитывает CPU-лимиты cgroups в контейнерах. Менять его можно через runtime.GOMAXPROCS(n)
или переменную окружения. Важно: GOMAXPROCS ограничивает параллелизм Go-кода, но не число
потоков M — потоки, сидящие в блокирующих syscall, не считаются и могут существовать сверх
GOMAXPROCS .
Вытеснение (preemption) эволюционировало. Долгое время оно было кооперативным: точки
переключения вставлялись компилятором в прологи функций (проверка stackguard ), поэтому
планировщик мог отобрать горутину только когда она вызывала функцию или аллоцировала.
Горутина с тугим циклом без вызовов ( for { i++ } ) монополизировала P и могла, например,
задерживать STW-фазу GC. Начиная с Go 1.14 появился asynchronous preemption: sysmon
замечает, что G исполняется на P дольше ~10 мс, и помечает её к вытеснению. Реализовано это
через сигнал ОС ( SIGURG на Unix): обработчик сигнала прерывает горутину в безопасной точке,
рантайм аккуратно сохраняет её состояние и возвращает в очередь, отдавая P другим. Это
сделало планировщик по-настоящему вытесняющим и убрало целый класс «зависаний» из-за
CPU-bound циклов.
ЧАСТАЯ ОШИБКА Считают, что GOMAXPROCS ограничивает число потоков/горутин (на деле —
только число P) и что Go всегда умел вытеснять любые циклы. До 1.14 тугой цикл без вызовов
функций мог намертво занять P и затормозить STW; асинхронное вытеснение через сигналы
— относительно недавняя возможность, и про неё на собеседованиях вспоминают редко.

Трёхцветный конкурентный mark-sweep и его фазы
GC & Memory Senior
ВОПРОС Объясните, как работает трёхцветный алгоритм сборки мусора в Go.
ЭТАЛОННЫЙ ОТВЕТ
GC в Go — это непоколенный (non-generational), неперемещающий (non-moving) конкурентный
mark-sweep сборщик. «Трёхцветность» — это инвариант, который позволяет вести разметку
параллельно с работающей программой. Все объекты логически делятся на три множества: белые
— ещё не достигнутые (кандидаты на удаление), серые — достигнутые, но их поля ещё не
просканированы, чёрные — достигнутые и полностью просканированные (на них больше не
смотрят).
Цикл идёт так: сначала все объекты белые. Корни (стеки горутин, глобалы, регистры) красятся в
серый и кладутся в рабочую очередь. Дальше worker'ы GC берут серый объект, сканируют его
поля, перекрашивают найденных белых детей в серый, а сам объект — в чёрный. Когда серых не
осталось — граф достижимости полностью обойдён, и всё, что осталось белым, — мусор. Фаза
sweep освобождает белые спаны; она тоже конкурентная и часто выполняется лениво, по мере
новых аллокаций.
СБОРКА МУСОРА И ПАМЯТЬ
Ключевой момент: разметка идёт одновременно с мутатором (пользовательскими горутинами),
которые могут переписывать указатели. Чтобы не потерять живой объект, поддерживается
инвариант (в Go — гибридный, на базе слабого трёхцветного инварианта): чёрный объект не
должен ссылаться на белый без посредника. Обеспечивает это write barrier (см. вопрос про
барьер записи). GC ничего не перемещает, поэтому адреса объектов стабильны и нет фазы
compaction.
ЧАСТАЯ ОШИБКА Кандидаты называют GC Go «поколенным» или «перемещающим/
компактящим» (путают с JVM). В Go он непоколенный и не двигает объекты. Также часто
забывают про роль write barrier и не могут объяснить, зачем вообще нужны три цвета, а не
два.
26 Тюнинг GOGC и GOMEMLIMIT
GC & Memory Senior
ВОПРОС Что такое GOGC? Как он работает и сколько ресурсов резервирует GC? Чем
помогает GOMEMLIMIT?
ЭТАЛОННЫЙ ОТВЕТ
GOGC задаёт целевой рост кучи между циклами в процентах от объёма живых данных после
прошлой сборки. Формула таргета: target_heap ≈ live_heap * (1 + GOGC/100) . По умолчанию
GOGC=100 — новый цикл стартует, когда куча вырастет примерно вдвое относительно живого
набора. GOGC=200 откладывает сборку (куча должна вырасти втрое: реже GC, но больше RSS),
GOGC=off полностью отключает сборщик. Регулируется через переменную окружения или
debug.SetGCPercent .
По CPU работает механизм GC pacing: цель — тратить на конкурентную разметку около 25% CPU
(примерно 1 из 4 P при GOMAXPROCS=4 ) в виде фоновых mark-worker'ов. Если pacer видит, что при
таком темпе разметка не успеет до достижения таргета, он подключает mark assist — заставляет
аллоцирующую горутину «доплатить» разметкой пропорционально объёму аллокаций, что
подтормаживает именно те горутины, что мусорят активнее всего.
С Go 1.19 есть GOMEMLIMIT ( debug.SetMemoryLimit ) — мягкий лимит на общий объём памяти
рантайма. Он приоритетнее GOGC: при приближении к лимиту GC начинает сборки чаще, не
дожидаясь GOGC-таргета, что защищает от OOM. Типовая прод-конфигурация в контейнере:
оставить GOGC дефолтным, а GOMEMLIMIT выставить чуть ниже лимита памяти пода (например,
90%). Лимит «мягкий»: рантайм будет жечь CPU на сборки, но память приоритетнее. Диагностика
— GODEBUG=gctrace=1 .
ЧАСТАЯ ОШИБКА Считают, что GOGC задаёт абсолютный размер кучи в мегабайтах, а не
процент роста от живых данных. Многие не знают про GOMEMLIMIT или путают его с жёстким
лимитом, а также не упоминают mark assist, думая, что GC всегда укладывается ровно в 25%
CPU.

Write barrier — зачем нужен барьер записи
GC & Memory Senior
ВОПРОС Что такое write barrier в Go GC и зачем он нужен?
ЭТАЛОННЫЙ ОТВЕТ
Write barrier — это небольшой код, который компилятор вставляет перед записью указателя в кучу.
Он нужен только во время активной фазы разметки, когда GC и мутатор работают одновременно.
Без него возможна потеря живого объекта: если мутатор запишет указатель на ещё белый объект
в уже чёрный (просканированный) объект и при этом сотрёт единственную серую ссылку на этот
белый, сборщик никогда до него не дойдёт и ошибочно освободит живую память.
Барьер поддерживает трёхцветный инвариант. В Go (начиная с 1.8) используется гибридный
барьер Yuasa + Dijkstra: при записи указателя в серый/чёрный объект он подкрашивает и старое, и
новое значение указателя так, чтобы они не остались белыми (грубо: «затеняет» затираемый
старый указатель и записываемый новый). Главный практический выигрыш гибридного барьера —
он позволил не делать повторное STW-пересканирование стеков в конце цикла: стек горутины,
ставший чёрным, остаётся чёрным, а барьер ловит все опасные записи. Это и сократило паузы до
десятков-сотен микросекунд.
Важно: барьер стоит денег на каждой записи указателя, поэтому он активен не всегда, а
включается на время фазы mark и выключается вне её. Также для скаляров (не-указателей)
барьер не нужен — он работает только на запись указателей.
ЧАСТАЯ ОШИБКА Кандидаты либо вообще не знают про барьер, либо называют его «read
barrier», либо думают, что он работает постоянно. Почти никто не может объяснить
конкретный сценарий гонки (чёрный объект → белый), из-за которого барьер вообще
понадобился.
28 STW в Go GC: где именно мир останавливается
GC & Memory Middle+
ВОПРОС Когда в цикле GC происходит Stop the World и почему паузы короткие? Использует
ли GC отдельные потоки?
ЭТАЛОННЫЙ ОТВЕТ
В современном Go (concurrent mark-sweep) STW происходит дважды за цикл, и обе паузы очень
короткие — обычно десятки-сотни микросекунд, а не «весь GC»:
Вся тяжёлая работа — сканирование графа (mark) и освобождение памяти (sweep) —
выполняется конкурентно, без остановки мира, параллельно с пользовательскими горутинами.
Поэтому длительность пауз почти не зависит от размера кучи.
Sweep Termination / Mark Setup — короткая остановка в начале: завершить ленивый sweep
прошлого цикла, включить write barrier, перевести GC в фазу маркировки.
1
Mark Termination — короткая остановка в конце разметки: убедиться, что серых объектов не
осталось, выключить барьер, зафиксировать статистику и пересчитать pacing.
2
Отдельных «GC-потоков» нет: разметку ведут обычные фоновые горутины-worker'ы GC, которые
планировщик запускает на тех же M/P, что и пользовательский код, забирая под себя около 25%
CPU. Дополнительно нагруженные аллокациями горутины подключаются к разметке через mark
assist. То есть GC конкурирует за общие процессоры рантайма, а не имеет выделенный пул
потоков ОС.
ЧАСТАЯ ОШИБКА Главное заблуждение — что «Stop the World останавливает программу на
всё время сборки» (модель старых JVM/учебников). В Go STW — это две микропаузы, а mark
и sweep идут конкурентно. Также путают STW-паузы с «GC работает в 25% CPU» — это
разные вещи.
29 sync.Pool и его взаимодействие с GC
GC & Memory Senior
ВОПРОС Как sync.Pool взаимодействует с GC? Что такое victim pool и почему sync.Pool
нельзя использовать как кэш?
ЭТАЛОННЫЙ ОТВЕТ
sync.Pool — это пул временных объектов для снижения числа аллокаций и давления на GC
(типичный кейс — переиспользование буферов в hot path). Устроен по-шардово: у каждого P свой
локальный набор, что даёт почти lock-free Get / Put ; есть и shared-часть, из которой другие P
могут «украсть» объект (work stealing). Именно поэтому pool безопасен для конкурентного
доступа без явных мьютексов.
Ключевая особенность — пул очищается сборщиком мусора, причём в два этапа через механизм
victim cache. На каждом цикле GC текущее содержимое пула не выбрасывается сразу, а
перемещается в «victim»-набор; объекты же, которые уже лежали в victim с прошлого цикла,
окончательно отбрасываются и становятся мусором. Фактически объект переживает один цикл GC
после того, как им перестали пользоваться, и удаляется на следующем. Это сглаживает потерю
пула на границе циклов, но не делает хранение долгоживущим.
Отсюда вывод: sync.Pool нельзя использовать как кэш или хранилище состояния —
содержимое может быть удалено в любой момент без уведомления, поэтому в нём нельзя
держать данные, которые обязаны сохраниться (соединения, результаты, которые дорого
пересоздавать с гарантией). Для кэша нужен LRU/TTL-кэш, а не пул.
ЧАСТАЯ ОШИБКА Считают sync.Pool надёжным кэшем и удивляются «пропаже» данных. Не
знают про victim cache и потому думают, что GC чистит пул мгновенно за один цикл. Также
частая ошибка — класть в пул объекты с указателями на большие графы, продлевая им
жизнь.

unsafe ).

MVCC в PostgreSQL: зачем и как
MVCC в PostgreSQL Middle+
ВОПРОС Зачем в Postgres нужен MVCC? Что такое MVCC вообще?
ЭТАЛОННЫЙ ОТВЕТ
MVCC (Multi-Version Concurrency Control) — модель управления конкурентным доступом, в
которой читатели не блокируют писателей, а писатели не блокируют читателей. Достигается это за
счёт хранения нескольких версий одной строки: при UPDATE Postgres не перезаписывает строку
на месте, а вставляет новую версию (новый tuple), помечая старую как «истёкшую». DELETE лишь
помечает версию удалённой. У каждого tuple есть служебные поля xmin (id транзакции-
создателя) и xmax (id транзакции, которая его удалила/обновила).
Видимость версий определяется снимком (snapshot): транзакция видит те версии, чей создающий
xid уже закоммичен и попадает в её снимок, а удаляющий — нет. Момент захвата снимка зависит
от уровня изоляции: при READ COMMITTED новый снимок берётся на каждый оператор, при
REPEATABLE READ / SERIALIZABLE — один снимок на всю транзакцию. Так обеспечивается
консистентное чтение без блокировок читателей.
Платой за это являются «мёртвые» версии (dead tuples), которые накапливаются и приводят к
раздуванию таблиц и индексов (bloat). Их вычищает VACUUM /autovacuum, освобождая место под
новые версии и продвигая «горизонт» (datfrozenxid) для защиты от переполнения счётчика
транзакций (transaction ID wraparound).
ЧАСТАЯ ОШИБКА Говорят «MVCC = строки не блокируются», но забывают, что записи в одну и
ту же строку всё равно сериализуются через блокировку строки ( SELECT ... FOR UPDATE ,
конкурирующий UPDATE ). Также путают MVCC с уровнями изоляции — это разные слои:
MVCC лишь механизм, на котором изоляция реализована.

Связь прямая. Блокировка ( SELECT ... FOR UPDATE , конкурирующий UPDATE ) живёт ровно до

Repeatable Read — нет грязных и неповторяющихся чтений; фантомы по стандарту допустимы.

Покрывающий индекс (covering index)

ВОПРОС Что такое покрывающий индекс (covering index) в PostgreSQL и какие виды
индексов ты знаешь?
ЭТАЛОННЫЙ ОТВЕТ
Покрывающий индекс — это индекс, содержащий все столбцы, нужные для ответа на запрос, так
что планировщик может выполнить Index Only Scan, не обращаясь к heap (основной таблице). В
Postgres есть два способа: добавить столбцы в ключ индекса либо вынести их в INCLUDE (с версии
11) — последнее предпочтительнее, когда столбцы нужны только для возврата, а не для поиска/
сортировки:
Важный нюанс: Index Only Scan в Postgres срабатывает не всегда. Из-за MVCC индекс не хранит
информацию о видимости версий, поэтому Postgres сверяется с visibility map; если страница не
помечена как «all-visible» (давно не было VACUUM ), произойдёт обращение в heap, и выигрыш
теряется. Поэтому покрывающие индексы любят свежий autovacuum.
Типы индексов в Postgres: B-tree (по умолчанию, для равенства и диапазонов, сортировки), Hash
(только равенство), GIN (множества значений: массивы, jsonb, полнотекстовый поиск), GiST
(геометрия, диапазоны, ближайшие соседи), SP-GiST (несбалансированные структуры), BRIN
(огромные таблицы с естественной упорядоченностью, очень компактный). Только B-tree
поддерживает INCLUDE и Index Only Scan в полной мере.
ЧАСТАЯ ОШИБКА Считают, что покрывающий индекс «всегда» даёт Index Only Scan, и
забывают про visibility map — на таблице с активной записью и редким vacuum скан всё равно
лезет в heap. И недооценивают цену: широкий INCLUDE раздувает индекс и замедляет
INSERT / UPDATE .

Шардирование — горизонтальное распределение данных по нескольким независимым инстансам

1024 логических шарда, размещённых на кольце, и маппят их на физические узлы. При
добавлении/удалении узла переезжает лишь доля ключей (≈ 1/N ), а не все. Виртуальные шарды
также позволяют балансировать неравномерную нагрузку, перераспределяя логические шарды
между машинами без рехеширования данных.
Celebrity-проблема (hotspot) — когда отдельный «горячий» товар (топовый бестселлер)
генерирует непропорциональную нагрузку, и его шард становится узким местом, хотя данные
распределены равномерно. Решения: кешировать горячие сущности (Redis) перед БД; реплики на
чтение для горячего шарда; для крайних случаев — дробление ключа (например, добавление
суффикса к ключу горячей записи, чтобы размазать запись по нескольким шардам). Здесь же
важно не выбирать ключом шардирования заведомо перекошенное поле (категория, продавец) —
иначе hotspot гарантирован.
Решардинг — изменение числа/состава шардов. Делается обычно без даунтайма через
directory/lookup-таблицу (карта «логический шард → физический узел»), двойную запись на время
миграции и переключение чтений после догона данных.
ЧАСТАЯ ОШИБКА Предлагают hash(id) % N как финальное решение, не понимая, что это
превращает добавление шарда в полную перетасовку данных. И путают celebrity-проблему
(перекос нагрузки на равномерных данных) с перекосом самих данных по плохому ключу
шардирования.

Полнотекстовый поиск: Postgres FTS vs Elasticsearch
Полнотекстовый поиск Senior
ВОПРОС Как реализовать полнотекстовый поиск? Какой движок выбрать? Как работает
индексация?
ЭТАЛОННЫЙ ОТВЕТ
В основе любого полнотекстового поиска лежит инвертированный индекс: для каждого терма
(нормализованного слова) хранится список документов, где он встречается. Текст перед
индексацией проходит через analyzer: токенизация → приведение к нижнему регистру →
отбрасывание стоп-слов → стемминг/лемматизация. Благодаря нормализации запрос «подушка»
находит «подушки» и «подушке».
В PostgreSQL это tsvector (нормализованный документ) и tsquery (запрос), а ускоряет поиск
GIN-индекс по tsvector (GiST — реже, для динамичных данных). Этого достаточно для
умеренных объёмов и когда поиск — вторичная функция, и большой плюс — отсутствие отдельной
системы и транзакционная согласованность с данными. Минусы: ограниченное ранжирование
( ts_rank ), слабее по релевантности, тяжело масштабируется горизонтально.
Elasticsearch/OpenSearch — специализированный движок: горизонтально масштабируется
шардами, даёт ранжирование по BM25 (а не устаревшему TF-IDF), фасеты, агрегации, fuzzy/
префиксный поиск, подсветку. Цена — отдельная инфраструктура и то, что ES не источник истины
и eventually consistent.
Типовая продакшн-архитектура: Postgres как source of truth + ES как индекс для поиска.
Синхронизация — через CDC (Debezium читает WAL → Kafka → индексатор в ES); это
предпочтительнее application-level dual-write, потому что dual-write легко рассинхронизируется
при сбое одной из записей. Выбор движка: если поиск простой и нагрузка средняя — хватит
Postgres FTS; если поиск — ключевая фича с релевантностью и масштабом — ES.
ЧАСТАЯ ОШИБКА Сразу тянут Elasticsearch, недооценивая стоимость эксплуатации отдельного
кластера и проблему синхронизации, хотя GIN-индекс в Postgres закрыл бы задачу. Обратная
крайность — dual-write «в коде» в две системы без CDC, что неизбежно ведёт к
рассинхронизации при частичных сбоях.

39 Партиционирование и гарантии порядка в Kafka
Message Brokers Middle+ / Senior
ВОПРОС Сколько consumer'ов имеет смысл держать в группе при 3 партициях? Где хранятся
offset'ы? Что произойдёт с порядком сообщений, если на работающем топике увеличить
число партиций?
ЭТАЛОННЫЙ ОТВЕТ
Единица параллелизма в Kafka — партиция. Внутри одной consumer group каждая партиция в
каждый момент времени закреплена ровно за одним consumer'ом, поэтому при 3 партициях
полезную работу делают максимум 3 consumer'а. Четвёртый войдёт в группу, но при rebalance не
получит ни одной партиции и будет простаивать как горячий резерв (он подхватит партицию, если
один из активных consumer'ов отвалится). Вывод: число consumer'ов в группе разумно держать
<= числу партиций; чтобы масштабироваться дальше, нужно увеличивать число партиций, а не
consumer'ов.
Offset'ы фиксируются не на брокере "за consumer'а", а самим consumer'ом — он коммитит
позицию во внутренний компактируемый топик __consumer_offsets (ключ — group.id + топик +
БРОКЕРЫ СООБЩЕНИЙ (KAFKA)
партиция, значение — последний закоммиченный offset). Именно поэтому новая группа может
независимо перечитать топик с начала, а старая продолжит с сохранённой позиции.
Порядок Kafka гарантирует строго в пределах одной партиции, а распределение по партициям
идёт по ключу: partition = hash(key) % partitions . Как только вы меняете partitions , формула
меняется — и сообщения с тем же ключом, которые раньше шли в партицию A, начнут попадать в
партицию B. Старые записи остаются в A, новые ложатся в B, и две партиции вычитываются
параллельно разными consumer'ами. Глобальный (per-key) порядок при этом нарушается: события
одной сущности могут обработаться вперемешку. Безопасно увеличивать число партиций можно
либо при дизайне топика заранее (с запасом), либо остановив producer'ов и дождавшись полной
вычитки уже накопленных сообщений перед переключением.
ЧАСТАЯ ОШИБКА Считать, что добавление партиций "на лету" безболезненно и автоматически
ускоряет обработку. На деле оно ломает per-key ordering и не перераспределяет уже
лежащие в старых партициях сообщения.

Быстрое устранение лага в Kafka
Message Brokers Middle+ / Senior
ВОПРОС Топик с 3 партициями, накопился лаг в 1 млн сообщений. Как разгрести его
максимально быстро?
ЭТАЛОННЫЙ ОТВЕТ
Сначала надо понять, во что мы упёрлись, потому что от этого зависит решение. Если узкое место
— сам consumer (тяжёлая обработка каждого сообщения), а не пропускная способность чтения, то
дешевле всего распараллелить обработку внутри consumer'а: читать батчами и раздавать
сообщения в worker pool из горутин, коммитя offset только после успешной обработки батча. При
этом партиционный порядок придётся либо пожертвовать, либо сохранить, шардируя задачи
между worker'ами по ключу. Параллельно стоит подкрутить fetch.min.bytes / max.poll.records ,
чтобы увеличить размер батча и снизить накладные расходы на сетевые round-trip'ы.
Ключевое ограничение: число активных consumer'ов в группе ограничено числом партиций (3),
поэтому просто "добавить четвёртый под" не поможет — он встанет в простой. Увеличение
партиций на этом же топике тоже не разгребёт лаг: старые сообщения останутся в исходных трёх
партициях, новое распределение коснётся только свежих записей.
Если же упёрлись в параллелизм чтения, рабочий приём — temporary fan-out: поднять
промежуточный топик с бóльшим числом партиций (например, 12), быстрым "перекладчиком"
перегнать в него накопленный лаг и обрабатывать его отдельной consumer group с нужным числом
consumer'ов. Если per-key порядок важен — сохраняем тот же partition key при переносе, чтобы
события одной сущности остались в одной партиции нового топика. После разбора лага
возвращаемся к штатному топику.
ЧАСТАЯ ОШИБКА Первая реакция многих — "добавим партиций / добавим consumer'ов".
Кандидаты упускают, что ретроспективно лаг так не ребалансируется, и не отделяют
bottleneck чтения от bottleneck обработки, хотя лечатся они по-разному.

DLQ и Outbox: зачем нужны и чем платим
Message Brokers Senior
ВОПРОС Зачем нужен Dead Letter Queue? Что такое Outbox-паттерн и почему DBA его
недолюбливают?
ЭТАЛОННЫЙ ОТВЕТ
DLQ (Dead Letter Queue) — отдельный топик, куда отправляют сообщения, которые не удалось
обработать после N повторов. Без него "ядовитое" сообщение (poison message) блокирует
партицию: consumer не может закоммитить offset за битым сообщением, бесконечно ретраит его и
тормозит обработку всего, что лежит за ним. DLQ позволяет признать сообщение
непереработанным здесь и сейчас, сдвинуть offset и разобрать его потом — вручную или
отдельным процессом. Плата за это — нарушение исходного порядка: проблемное событие
"выпадает" из потока, что критично для event sourcing. Частично смягчается версионированием
событий и тем, что в DLQ кладут полный контекст (исходный топик/партиция/offset, заголовки,
причину ошибки) для воспроизведения.
Outbox решает другую задачу — атомарность бизнес-операции и публикации события. Нельзя в
одной транзакции и записать в БД, и гарантированно отправить в Kafka (это два разных ресурса,
классический dual-write). Поэтому в рамках той же транзакции пишут и в основную таблицу, и в
таблицу outbox . Отдельный процесс — relay или CDC-коннектор (Debezium, читающий WAL/binlog)
— забирает строки из outbox и публикует их в Kafka хотя бы один раз (at-least-once). Из-за at-leastonce
на стороне потребителя нужна идемпотентность или Inbox-паттерн (дедупликация по
message-id).
DBA не любят Outbox потому, что это интенсивный поток мелких insert'ов и delete'ов в горячую
OLTP-базу: таблица и её индексы пухнут, vacuum/чистка не успевает, а главное — растёт write-
нагрузка и лаг репликации, что деградирует продуктовую нагрузку. Лечится партиционированием
outbox-таблицы и своевременной архивацией/очисткой, выносом outbox в отдельную БД либо
переходом на CDC прямо из лога транзакций, минуя промежуточную таблицу.
ЧАСТАЯ ОШИБКА Подавать Outbox как бесплатную "гарантию доставки" и забывать про два
следствия: доставка получается at-least-once (нужна идемпотентность/Inbox на потребителе)
и реальную цену по нагрузке на запись и репликацию.

Стратегии кеширования и инвалидация
System Design / Кеширование Middle+ / Senior
ВОПРОС Где должен стоять кеш в архитектуре? Что кешировать и по какому ключу? Как
инвалидировать кеш — в том числе для агрегированных лент и поисковых запросов?
SYSTEM DESIGN И РАСПРЕДЕЛЁННЫЕ СИСТЕМЫ
ЭТАЛОННЫЙ ОТВЕТ
Кеш (обычно Redis) ставится между сервисом и БД, и работает по одному из паттернов. Cache-
Aside (lazy): приложение само читает из кеша, при промахе идёт в БД, кладёт результат обратно и
ставит TTL — это дефолт для read-heavy нагрузки. Write-Through: запись идёт одновременно в кеш
и БД (консистентно, но дороже на запись). Write-Behind: запись сначала в кеш, асинхронно в БД
(быстро, но риск потери данных). Для лент и каталогов почти всегда выбирают Cache-Aside,
потому что читается гораздо чаще, чем пишется.
Кешировать стоит то, что дорого вычислять и часто читается: агрегированные ленты, профили,
результаты тяжёлых JOIN. Ключ должен быть детерминированным и включать все параметры,
влияющие на результат: для ленты — feed:{user_id} , для поиска — нормализованный запрос
плюс фильтры и страница, например search:{hash(query+filters)}:page:{n} . Значение —
сериализованный список ID или сами данные.
Инвалидация — самое сложное. Базовый приём — TTL (например, 60 с для ленты, 5 мин для
каталога): просто, но даёт окно несвежих данных. Event-based invalidation: при публикации поста
инвалидируем/обновляем feed:* затронутых пользователей (fan-out на запись для активных
авторов). Для поиска точечная инвалидация почти невозможна — один новый товар влияет на
сотни запросов, поэтому здесь полагаются на короткий TTL плюс асинхронное обновление
поискового индекса (Elasticsearch), а не на ручную чистку. Redis при этом запускается в кластере с
шардированием и репликами для масштабирования.
ЧАСТАЯ ОШИБКА Кандидаты называют «поставим Redis» и TTL, но не знают именованных
паттернов (Cache-Aside / Write-Through) и не понимают, что инвалидацию поисковых
запросов точечно сделать нельзя — путь только через TTL и переиндексацию. Также
забывают про распределённый кеш (один инстанс Redis — не масштабируется и SPOF).
43 CQRS и разделение чтения/записи
System Design / Архитектура Middle+ / Senior
ВОПРОС Как спроектировать сервисы для обработки записи и чтения товаров при 100K RPS
(20% запись, 80% чтение)? Как называется паттерн разделения и какие у него trade-offs?
ЭТАЛОННЫЙ ОТВЕТ
Паттерн называется CQRS (Command Query Responsibility Segregation): операции записи
(Commands) и чтения (Queries) разносятся в разные модели, чтобы масштабировать и
оптимизировать каждую сторону независимо. При 100K RPS это ~20K write и ~80K read — нагрузки
несимметричные, и держать их на одной модели расточительно.
Есть две степени разделения. Лёгкая: один сервис, но read- и write-endpoints вынесены в
отдельные деплойменты/пулы подов, которые масштабируются независимым HPA; чтение идёт с
read-реплик БД. Полная CQRS: разные хранилища под разные задачи — запись в
нормализованный Postgres (source of truth, ACID), а чтение из денормализованного, заточенного
под запросы стора (Elasticsearch для поиска, или денормализованные read-модели/
материализованные представления). Синхронизация между write- и read-моделью идёт
асинхронно — через CDC (Debezium) или поток событий.
Главный trade-off — eventual consistency: read-модель отстаёт от write-модели на время
репликации события, поэтому только что записанный товар может на доли секунды не находиться
в поиске. Это допустимо для каталога, но недопустимо, например, для баланса кошелька. Второй
trade-off — выросшая сложность: два хранилища, конвейер синхронизации, обработка дубликатов
и порядка событий. Поэтому полную CQRS вводят только когда профиль нагрузки реально
асимметричен; иначе достаточно read-реплик. Декомпозицию сервисов при этом ведут по
bounded contexts (DDD), а не механически по «чтение/запись».
ЧАСТАЯ ОШИБКА Низкий балл ставили за то, что кандидат предлагает «два сервиса»
интуитивно, но не называет паттерн CQRS и не проговаривает его цену — eventual consistency
и сложность синхронизации. Частое заблуждение: считать, что CQRS обязательно требует
Event Sourcing и отдельных БД, тогда как минимальная реализация — это просто раздельное
масштабирование read/write на одной БД с репликами.
44 Transactional Outbox для надёжной доставки событий
System Design / Reliable Messaging Senior
ВОПРОС Как реализовать надёжную отправку уведомлений (или событий) при создании
заказа, чтобы не потерять сообщение и не отправить его без сохранённого заказа?
ЭТАЛОННЫЙ ОТВЕТ
Проблема — dual write: нельзя атомарно записать заказ в БД и отправить сообщение в брокер,
потому что это два разных хранилища. Если упасть между ними, получим заказ без уведомления
или уведомление без заказа. Решает это паттерн Transactional Outbox: в той же транзакции, что и
заказ, мы пишем событие в таблицу outbox той же БД. Раз транзакция атомарна — либо есть и
заказ, и запись в outbox, либо ничего.
Дальше отдельный процесс публикует события из outbox в брокер:
Ключевой момент — доставка получается at-least-once, поэтому потребитель обязан быть
идемпотентным: дедупликация по event_id / idempotency_key . Retry публикации — с exponential
backoff и jitter; после исчерпания попыток событие уходит в dead-letter. Симметричный паттерн на
стороне приёма — Inbox: фиксируем обработанные event_id , чтобы повторная доставка не
выполнила бизнес-логику дважды.
Polling Publisher — воркер периодически делает
SELECT ... FROM outbox WHERE status='pending' FOR UPDATE SKIP LOCKED , отправляет в брокер и
помечает строку как done (или удаляет). SKIP LOCKED позволяет нескольким воркерам
безопасно разбирать таблицу параллельно.
CDC (Change Data Capture) — Debezium читает WAL/binlog и стримит вставки в outbox прямо в
Kafka. Это эффективнее polling и не нагружает БД запросами, но требует инфраструктуры CDC.
SQL
-- внутри одной транзакции с INSERT INTO orders ...
INSERT INTO outbox (id, aggregate_id, type, payload, status)
VALUES (gen_random_uuid(), :order_id, 'OrderCreated', :json, 'pending');
ЧАСТАЯ ОШИБКА Кандидаты предлагают «сохранить заказ, потом отправить в Kafka» и не
видят проблему dual write и потери сообщения при падении между шагами. Те, кто знает
Outbox, часто забывают, что доставка at-least-once и потребитель обязан быть
идемпотентным (Inbox/дедупликация), а также используют обычный SELECT FOR UPDATE без
SKIP LOCKED , из-за чего воркеры блокируют друг друга.

45 Виртуальная и физическая память, OOM Killer, swap
ОС: управление памятью Senior
ВОПРОС Как процессу может быть выделено, скажем, 1.4 ТБ виртуальной памяти, если
физической памяти в системе меньше? На что смотрит OOM Killer в Linux — на виртуальную
или физическую память? Что изменится, если включён swap?
ЭТАЛОННЫЙ ОТВЕТ
Виртуальная память — это абстракция, которую ядро предоставляет каждому процессу: процесс
видит собственное непрерывное виртуальное адресное пространство и работает с виртуальными
адресами, которые MMU транслирует в физические через таблицы страниц. У 64-битного
процесса это пространство огромно, поэтому VIRT (как его показывает top ) легко достигает
сотен гигабайт или терабайт — туда входят зарезервированные, но ещё не использованные
регионы mmap , шаренные библиотеки, стек, куча. Физическая страница (RSS) выделяется лениво
— только когда процесс реально обращается к адресу: происходит page fault, и ядро подкладывает
физическую страницу (demand paging). Поэтому 1.4 ТБ виртуального адресного пространства при
16 ГБ RAM — это нормально: «выделено» виртуально не значит «занято физически».
OOM Killer смотрит на физическую память, а не на виртуальную. Когда система не может
удовлетворить запрос на физические страницы (и swap исчерпан или отключён), ядро выбирает
жертву по oom_score — он считается в первую очередь от объёма реально занятой памяти
процесса (RSS + swap) и корректируется через oom_score_adj (-1000..+1000). Процесс с
наибольшим score завершается сигналом SIGKILL — его нельзя перехватить, поэтому graceful
shutdown невозможен. Swap не увеличивает физическую память: он позволяет вытеснять
неактивные (anonymous) страницы на диск, освобождая RAM и откладывая OOM. Платой
становится резкое падение производительности при swap-in/swap-out (диск на порядки
медленнее RAM), вплоть до thrashing.
Для Go-сервисов это прямо влияет на эксплуатацию в контейнерах. В Kubernetes лимит памяти
задаёт cgroup-лимит на RSS, и при его превышении срабатывает cgroup-OOM — под убивается с
OOMKilled , при этом сборщик мусора Go не успевает помочь, так как реагирует на рост кучи, а не
на физическое давление cgroup. Поэтому важно задавать GOMEMLIMIT (soft memory limit рантайма)
ниже cgroup-лимита, чтобы GC начинал агрессивнее освобождать память до того, как ядро дёрнет
OOM Killer. Высокий VIRT у Go-процесса (рантайм резервирует адресное пространство под арены
кучи) — это ожидаемо и само по себе не повод для тревоги; смотреть нужно на RSS.
ОПЕРАЦИОННЫЕ СИСТЕМЫ И COMPUTER SCIENCE
ЧАСТАЯ ОШИБКА Кандидаты говорят, что OOM Killer «смотрит на виртуальную память», и
пугаются большого VIRT, путая зарезервированное адресное пространство с реальным
потреблением. Также забывают, что swap не добавляет «памяти», а лишь обменивает её на
latency, и что OOM-сигнал нельзя перехватить.
46 Почему создание потока ОС — дорогая операция
ОС: процессы, потоки, контекст-свитчинг Middle+
ВОПРОС Почему создание потока операционной системы — дорогая операция, помимо
размера стека? И почему это важно в контексте Go?
ЭТАЛОННЫЙ ОТВЕТ
Большой стек (обычно ~1–8 МБ, фиксированный, выделяется виртуально) — лишь одна из причин.
Главное, что создание потока требует системного вызова ( clone / pthread_create ), а значит
перехода в режим ядра и обратно. Ядро должно создать и проинициализировать свои структуры
(task_struct, дескриптор потока, отдельный стек ядра), зарегистрировать поток в планировщике,
настроить отображения памяти. Стоимость этих операций не константна: она зависит от текущей
загрузки системы, количества потоков, состояния аллокаторов ядра. Поэтому создание тысяч
потоков ОС плохо масштабируется.
Отдельная и часто более значимая статья расходов — context switch между потоками.
Переключение требует ухода в ядро, сохранения/восстановления регистров и состояния, прохода
через планировщик. Косвенная цена ещё выше: при смене потока (особенно с другим адресным
пространством) сбрасывается часть TLB и вымываются кеши процессора (L1/L2), из-за чего после
переключения растут кеш-промахи. На горячих путях именно это, а не сам syscall, бьёт по
throughput.
Ровно поэтому Go использует горутины. Горутина — это объект рантайма, а не поток ОС:
стартовый стек всего ~2–8 КБ, растёт сегментами по мере надобности, создаётся без syscall.
Планировщик Go (модель M:N) мультиплексирует множество горутин (G) на небольшое число
потоков ОС (M), привязанных к логическим процессорам (P, по числу GOMAXPROCS ). Переключение
между горутинами происходит в user-space на точках планирования (вызовы функций, операции с
каналами, блокирующие операции) и обходится в десятки наносекунд — без перехода в ядро и без
сброса TLB. Это позволяет держать сотни тысяч горутин там, где сопоставимое число потоков ОС
положило бы систему.
ЧАСТАЯ ОШИБКА Сводят всю дороговизну к размеру стека и забывают про syscall, работу
планировщика ядра и про эффект на TLB/кеши при контекст-свитче. Многие также не могут
связать это с горутинами и моделью M:N, хотя именно эта связь — суть вопроса.

Системный вызов: синхронный и асинхронный, и как Go их обрабатывает
ОС: системные вызовы, ввод-вывод Senior
ВОПРОС Что такое системный вызов? Приведи пример синхронного и асинхронного syscall.
Как с этим работает рантайм Go?
ЭТАЛОННЫЙ ОТВЕТ
Системный вызов (syscall) — это контролируемая точка входа в ядро, через которую процесс из
user-space запрашивает привилегированную операцию: ввод-вывод, работу с памятью, сетью,
процессами. Технически это переход с понижением уровня привилегий (на x86-64 — инструкция
syscall ), с передачей номера вызова и аргументов и обязательной валидацией их ядром. Прямой
доступ к железу из user-space запрещён, поэтому любое реальное взаимодействие с диском,
сетью или другими процессами идёт через syscalls.
Синхронный (блокирующий) syscall не возвращает управление, пока операция не завершится:
классический read() по дисковому файлу заблокирует поток до готовности данных. Асинхронная
(неблокирующая) модель устроена иначе: дескриптор переводится в неблокирующий режим,
вызов сразу возвращает «данных пока нет» (EAGAIN), а готовность отслеживается через механизм
мультиплексирования событий — epoll в Linux, kqueue в BSD/macOS, IOCP в Windows, либо
современный io_uring . Поток не простаивает на каждом дескрипторе, а ждёт события сразу по
тысячам соединений.
В Go это спрятано за синхронным API, но реализовано неблокирующе через netpoller. Сетевые
дескрипторы переводятся в неблокирующий режим и регистрируются в epoll/kqueue. Когда
горутина делает conn.Read() и данных нет, рантайм не блокирует поток ОС — он паркует горутину
и переключает поток (M) на другую готовую горутину, а netpoller разбудит её, когда дескриптор
станет готов. За счёт этого десятки тысяч соединений обслуживаются горстью потоков. Важное
исключение — обычный файловый и большинство «настоящих» блокирующих syscalls: epoll на них
в общем случае не работает, поэтому Go выполняет их на занятом потоке, а планировщик
отвязывает P от заблокированного M (через монитор sysmon ) и при необходимости поднимает
новый поток, чтобы остальные горутины продолжали исполняться. Поэтому большое число
одновременно блокирующих syscalls (например, синхронный дисковый I/O или вызовы cgo) может
неожиданно раздуть число потоков ОС.
ЧАСТАЯ ОШИБКА Думают, что «асинхронный» в Go означает, что код не блокируется на
уровне горутины, — на самом деле API синхронное, неблокирующая магия только под
капотом через netpoller. И почти все упускают, что файловый I/O и cgo идут мимо netpoller,
занимая поток ОС, — отсюда рост числа потоков под нагрузкой.

Восстановление бинарного дерева по preorder и inorder
Алгоритмы / Деревья Middle+
ВОПРОС Постройте бинарное дерево по обходам preorder и inorder. Верните корень дерева.
ЭТАЛОННЫЙ ОТВЕТ
Ключевая идея — связать два обхода. В preorder корень всегда стоит первым, поэтому
preorder[0] — это корень всего дерева. Находим этот элемент в inorder: всё, что слева от него, —
это inorder левого поддерева, всё справа — inorder правого. Размер левой части ( k элементов)
подсказывает, как разрезать preorder: следующие k элементов после корня — preorder левого
поддерева, остаток — правого. Дальше рекурсия по тем же правилам; базовый случай — пустой
диапазон возвращает nil .
Наивная реализация ищет индекс корня в inorder линейно на каждом шаге — это O(N) поиск
внутри O(N) узлов, итого O(N^2) по времени. Правильный приём — один раз построить
map[int]int (значение → индекс в inorder) и обращаться к нему за O(1) . Тогда вся сборка —
O(N) по времени и O(N) по памяти (хэш-таблица плюс стек рекурсии до O(N) на вырожденном
дереве). Передавать срезы по значению не нужно — достаточно работать индексами в исходных
массивах.
АЛГОРИТМЫ И СТРУКТУРЫ ДАННЫХ
GO
type TreeNode struct {
Val int
Left, Right *TreeNode
}
func buildTree(preorder, inorder []int) *TreeNode {
idx := make(map[int]int, len(inorder))
for i, v := range inorder {
idx[v] = i
}
pre := 0
var build func(inL, inR int) *TreeNode
build = func(inL, inR int) *TreeNode {
if inL > inR {
return nil
}
rootVal := preorder[pre]
pre++
node := &TreeNode{Val: rootVal}
mid := idx[rootVal]
node.Left = build(inL, mid-1) // важно: сначала левое — оно идёт раньше в preorder
node.Right = build(mid+1, inR)
return node
}
return build(0, len(inorder)-1)
}
ЧАСТАЯ ОШИБКА Кандидаты останавливаются на O(N^2) , заново сканируя inorder на каждом
узле, и не вспоминают про хэш-таблицу для индексов. Второй провал — порядок: правое
поддерево нельзя строить раньше левого, потому что общий указатель pre должен идти по
preorder именно слева направо.
49 Оценка сложности алгоритмов: Big O, время и память
Алгоритмы и сложность Middle / Middle+
ВОПРОС Что такое временная и пространственная сложность? Как оценивается через Big O,
как складываются сложности, что растёт быстрее — N или N log N ? Чем O отличается от
Ω и Θ ?
ЭТАЛОННЫЙ ОТВЕТ
Сложность алгоритма — это мера того, как растут затраты ресурсов при увеличении размера
входа N . Временная сложность описывает рост числа операций, пространственная — рост
дополнительной памяти (не считая самого входа). Big O — это асимптотическая оценка сверху для
худшего случая: нас интересует не точное число операций, а характер роста при больших N .
Поэтому при оценке отбрасывают константы и младшие члены: 3N^2 + 100N + 7 → O(N^2) . При
последовательном выполнении блоков сложности складываются, и доминирует старший член
( O(N) + O(N log N) → O(N log N) ); при вложенных циклах — перемножаются.
Иерархия роста, которую важно держать в голове:
O(1) < O(log N) < O(N) < O(N log N) < O(N^2) < O(2^N) < O(N!) . Ключевой момент, на котором
проверяют понимание: N log N растёт быстрее линейного N , но существенно медленнее N^2 .
Практический ориентир — сравнительные сортировки имеют нижнюю границу O(N log N) , а
наивная сортировка вставками или пузырьком — O(N^2) , и разница на N = 10^6 это разница
между секундами и часами. Помимо O есть Ω — нижняя оценка (лучший случай) и Θ — точная
оценка, когда верхняя и нижняя границы совпадают; на собеседовании обычно говорят про O , но
упоминание Θ показывает глубину.
Несколько канонических примеров на массиве в Go. Поиск максимума в неотсортированном
массиве — O(N) , придётся посмотреть каждый элемент. В отсортированном массиве максимум
— это последний элемент, доступ за O(1) , а поиск произвольного значения — бинарный,
O(log N) . По памяти оба этих алгоритма работают «на месте» — O(1) дополнительной памяти,
потому что мы не аллоцируем структуру, растущую вместе с входом.
ЧАСТАЯ ОШИБКА Путают N и N log N («это почти одно и то же») и не чувствуют, что
логарифмический множитель — всё равно медленнее линейного. Второй частый провал —
забывают про пространственную сложность: рекурсия добавляет O(глубины) на стек, а
решение «через дополнительный срез/map» — это O(N) памяти, даже если по времени всё
красиво.

символы. Никакого реверса и лишних аллокаций: O(n) по времени, O(1) по памяти. Для строк с

// O(N) по времени, O(1) по памяти — каждый элемент смотрим один раз
func maxVal(a []int) int {
best := a[0]
for _, v := range a[1:] {
if v > best {
best = v
}
}
return best
}
// O(log N) по времени, O(1) по памяти — на отсортированном массиве
func binarySearch(a []int, target int) int {
lo, hi := 0, len(a)-1
for lo <= hi {
mid := lo + (hi-lo)/2 // так не переполнится, в отличие от (lo+hi)/2
switch {
case a[mid] == target:
return mid
case a[mid] < target:
lo = mid + 1
default:
hi = mid - 1
}
}
return -1
}
