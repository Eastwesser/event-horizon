Auth — полный разбор для собеса
Ниже — всё, что известно по services/auth из твоих файлов. Это ответ на вопрос «А как у вас работает сервис аутентификации?» с учётом паттернов из EVENT_HORIZON_PATTERNS_15.10.2026.md.

1. Одна фраза (elevator pitch)
Auth — единственный сервис, который знает пароль. Регистрация и логин, bcrypt cost 12, пара JWT (access 15 мин + refresh 7 дней), обе подписаны HMAC-SHA256. jti каждого токена лежит в Redis — пока ключ есть, сессия жива. Gateway на каждом закрытом запросе не разбирает подпись сам, а зовёт Auth по gRPC ValidateToken. Redis упал — 503, а не «токен жив».

4. Как работает (по шагам)
Регистрация
Gateway принимает POST /api/v1/auth/register, валидирует DTO.

Зовёт Auth по gRPC Register.

Auth проверяет: email не занят, пароль ≥ 8 символов.

bcrypt cost 12 → хеш в users.password_hash (Postgres :5460).

Роль — только user. Самостоятельно author/admin не поставить (заблокировано в Auth).

Возвращает пару JWT.

Логин
POST /api/v1/auth/login → Gateway → gRPC Login.

Auth достаёт password_hash из Postgres, сверяет bcrypt.

Выпускает пару:

access — 15 минут, claims: user_id, email, role, тип access, jti

refresh — 7 дней, claims: то же + тип refresh, свой jti

Оба подписаны HMAC-SHA256 общим секретом из env (JWT_SECRET).

jti access → Redis на 15 мин. jti refresh → Redis на 7 дней.

Возвращает {access_token, refresh_token, expires_in}.

Проверка на каждом закрытом запросе
Gateway RequireAuth вырезает Authorization: Bearer ….

Зовёт Auth по gRPC ValidateToken.

Auth проверяет:

подпись HMAC,

тип access (не refresh),

jti есть в Redis.

Нет ключа → Unavailable / «сессия отозвана» → Gateway отдаёт 401.

Роль кладётся в контекст запроса. RequireRole после этого пускает только нужную роль.

Необычный кейс: Gateway не разбирает подпись сам. Каждый закрытый запрос — это gRPC-вызов в Auth. Это осознанный trade-off: отзыв сессии работает мгновенно (logout → удалили jti из Redis → следующий запрос 401), но цена — лишний сетевой хоп на каждый запрос.

Refresh (одноразовый)
POST /api/v1/auth/refresh → gRPC Refresh.

Auth проверяет подпись refresh, тип refresh, jti в Redis.

Удаляет старый jti refresh из Redis.

Выпускает новую пару, роль перечитывает из Postgres.

Новые jti → Redis.

Почему одноразовый: смена роли подхватывается без вечного старого access. Старый refresh больше не работает.

Logout
POST /api/v1/auth/logout → gRPC Logout.

Auth удаляет jti из Redis.

Подпись токена остаётся верной до exp, но проверка сессии его больше не пускает.

Redis упал
На ValidateToken: Auth возвращает gRPC Unavailable, Gateway отвечает 503 session store unavailable.

На Refresh: то же.

Подпись без живого Redis больше не считается сессией. Это осознанно: лучше 503, чем «токен жив, но мы не знаем, отозван ли он».

Rate limit (на Gateway, не в Auth)
Ограничение	Лимит	При ошибке Redis
Login с одного IP	5 req/s	fail-closed (пускать перестаёт)
Общий на пользователя/IP	~100 req/s	fail-open (API остаётся открытым)
WebSocket с IP	100 conn/мин	—
Почему login fail-closed, а общий fail-open: брутфорс важнее не пустить, чем сохранить доступность логина. Общий лимит — наоборот, чтобы лимитер не погасил весь вход.

Необычные кейсы (стоит рассказать)
1. Session Store в Redis — не «просто JWT».
Обычный JWT stateless: подпись верна — токен жив. Здесь наоборот: подпись верна, но jti нет в Redis — токен мёртв. Это даёт мгновенный отзыв (logout, смена роли, компромат), но цена — Redis в hot path каждого запроса.

2. Gateway не разбирает подпись сам.
Каждый закрытый запрос — gRPC ValidateToken. Это делает Auth единственной точкой правды о сессии. Минус — лишний хоп. Плюс — нельзя обойти проверку, даже если Gateway скомпрометирован.

3. Refresh одноразовый.
Старый jti refresh удаляется, пара выпускается заново, роль перечитывается из Postgres. Это защита от replay refresh-токена.

4. Login fail-closed, общий лимит fail-open.
Осознанный trade-off: брутфорс важнее не пустить, чем сохранить доступность логина. Общий лимит — наоборот.

5. bcrypt cost 12.
Медленно намеренно: ~100–300ms на хеш. Поэтому 500 VU login blast в k6 «краснеет» by design. Это не баг, это защита от брутфорса.

9. Что спросят на собесе (готовые ответы)
«Почему JWT, а не сессии в cookie?»
JWT в Authorization: Bearer — не cookie. Чужой сайт не подставит этот заголовок, поэтому CSRF не применим. Если бы JWT лёг в cookie, понадобились бы SameSite и CSRF-токен. Сейчас этого не нужно.

«Почему jti в Redis, а не просто JWT?»
Обычный JWT stateless: подпись верна — токен жив. Logout невозможен без чёрного списка. Я храню jti каждого токена в Redis: logout удаляет ключ, следующий запрос — 401. Смена роли подхватывается через refresh (роль перечитывается из Postgres). Цена — Redis в hot path каждого запроса, но это осознанный trade-off ради мгновенного отзыва.

«Почему Gateway не разбирает подпись сам?»
Gateway зовёт Auth по gRPC ValidateToken на каждом закрытом запросе. Это делает Auth единственной точкой правды о сессии. Минус — лишний хоп. Плюс — нельзя обойти проверку, даже если Gateway скомпрометирован.

«Почему refresh одноразовый?»
Старый jti refresh удаляется, пара выпускается заново, роль перечитывается из Postgres. Это защита от replay refresh-токена. Если refresh украли и использовали — старый перестанет работать, а новый у жертвы не появится.

«Что если Redis упал?»
Auth возвращает gRPC Unavailable, Gateway отвечает 503 session store unavailable. Подпись без живого Redis больше не считается сессией. Лучше 503, чем «токен жив, но мы не знаем, отозван ли он».

«Почему bcrypt cost 12?»
Медленно намеренно: ~100–300ms на хеш. Это защита от брутфорса. Поэтому 500 VU login blast в k6 «краснеет» by design. Это не баг, это защита. Если нужно быстрее — bcrypt cost 10 или argon2, но тогда слабее защита.

«Почему login fail-closed, а общий лимит fail-open?»
Брутфорс важнее не пустить, чем сохранить доступность логина. Если Redis на лимите логина упал — пускать перестаём. Общий лимит — наоборот, чтобы лимитер не погасил весь вход при падении Redis.

«Как тестируешь Auth?»
Unit-тесты на service layer с hand-written mock репозитория (auth_service_test.go). Converter layers — package tests. Интеграционные — testcontainers (Postgres + Redis). k6 CORE — browse.js (20 VU), purchase.js (1–5 VU). Legacy 500 VU login blast — не pass/fail, а демонстрация защиты.

«Что было бы при 10k DAU?»
Модель 10k DAU ≈ десятки RPS avg, пик ~×2. Auth write path — узкое место: bcrypt 12 + rate limit 5/s. Read path (ValidateToken) держится на Redis. Для 10k DAU хватит текущего thin-стека. Для 10k одновременных логинов — нет, и это by design.

«Что улучшил бы?»
Ротация JWT_SECRET (сейчас нет)

Argon2id вместо bcrypt (современнее)

Refresh rotation с reuse detection (сейчас просто одноразовый)

WAF перед Gateway (сейчас нет)

Полный AuthZ matrix «каждая ручка × роль» (сейчас baseline)

10. Связи с другими сервисами
Auth — фундамент. От него зависят все:

Кто	Как использует Auth
Gateway	ValidateToken на каждом закрытом запросе
Inventory	gRPC interceptor читает x-user-role из metadata (роль от Gateway)
Authors	RequireRole(author|admin) на ручках записи
Admin ручки	RequireRole(admin) на analytics, users, applications
Все остальные	user_id из токена — общий человек для Profile, Billing, Shop, History
Деньги — Billing: игра начисляет билетики и лампы по score.updated, буст списывает лампы синхронно, магазин списывает билетики синхронно. Auth тут не участвует, но user_id — из Auth.

11. Что важно не перепутать
Auth — не «просто JWT». Это Session Store в Redis. Подпись верна, но jti нет — токен мёртв.

Gateway не разбирает подпись сам. Каждый запрос — gRPC в Auth.

bcrypt 12 — by design медленно. 500 VU login blast краснеет намеренно.

Login fail-closed, общий лимит fail-open. Осознанный trade-off.

Refresh одноразовый. Старый jti удаляется, роль перечитывается.

Redis упал — 503, не «токен жив». Лучше отказ, чем сомнительная сессия.

Auth — единственный сервис, который знает пароль. Остальные видят только user_id и role из токена.
