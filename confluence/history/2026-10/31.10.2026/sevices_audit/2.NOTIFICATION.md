1. Одна фраза (elevator pitch)
Notification — in-app колокольчик и Telegram. Два независимых сервиса в одном процессе: InboxService (in-app) + Notifier (Telegram). Два шины одновременно: NATS primary, Kafka fallback (Dual-Bus Consumer). Потребляет score.updated, purchase.paid, purchase.fulfilled, payment.completed, record_beaten. Fan-Out: одно событие → N уведомлений. Idempotency Key через source_event: ON CONFLICT (user_id, source_event) DO NOTHING — повтор не создаёт дубль. In-app bell soft-fail при logout (без цикла 401). 16 паттернов.

4. Как работает (по шагам)
Потребление событий
Durable consumer подписан на:

score.updated — Game (достижения, рекорд)

purchase.paid — Shop (покупка начата)

purchase.fulfilled — Fulfillment (покупка собрана)

payment.completed — Payment (подписка активирована)

record_beaten — Leaderboard (ваш рекорд побили)

author.upserted? (в некоторых источниках — да)

Для каждого события:

Fan-Out: одно событие → N уведомлений (например, record_beaten → уведомление тому, кого побили).

Idempotency Key через source_event: INSERT INTO notifications (...) ON CONFLICT (user_id, source_event) DO NOTHING. Повтор события не создаёт дубль.

Notifier (Telegram): если пользователь подписан на Telegram — отправка. Если нет — in-app только.

Ack при успехе. Nak при ошибке.

Если Redis (rate limit / кэш) упал — Graceful Degradation: in-app работает, Telegram может тормозить.

Необычный кейс: Fan-Out. Одно событие record_beaten → N уведомлений (всем, кого побили? нет — тому, кого побили, одно). Fan-Out — это когда одно событие порождает несколько уведомлений (например, score.updated → уведомление о достижении + уведомление о новом рекорде). Это может быть N уведомлений на одно событие.

Dual-Bus Consumer (NATS + Kafka)
NATS primary: Notification подписан на purchase.paid (и др.) через NATS JetStream.

Kafka fallback: если JetStream не подключён — Notification читает из Kafka (purchase.paid, purchase.fulfilled).

В FINISHERS.md: «Fulfillment и notification читают Kafka только когда JetStream не поднят».

Это Dual-Bus Consumer: два брокера, primary/fallback. В обычном make deploy — NATS. В make deploy-heavy — Kafka.

Необычный кейс: в EVENT_HORIZON_PATTERNS_15.10.2026.md отмечено: «Notifier (Telegram) в Handle для Kafka падает без Ack при unmarshal error. Решение: Poison message → Ack» (пункт 13 в техдолге). То есть если Kafka прислал битое сообщение, Notification не делает Ack — бесконечный retry. Это техдолг.

In-app bell (soft-fail)
FE NotificationBell компонент.

GET /api/v1/notifications — список.

Если пользователь не залогинен — soft-fail: нет цикла 401, просто пусто.

В INTERVIEW_PATTERNS.md: «In-app bell; soft-fail when logged out (без цикла 401)».

Telegram Notifier
Отдельный сервис Notifier в том же процессе.

Если пользователь подписан на Telegram — отправка через Telegram Bot API.

Retry with Fixed Delay: при ошибке Telegram — retry с фиксированной задержкой (не exponential backoff). В каталоге отмечено: «Retry with Fixed Delay — notification».

Если пользователь не подписан — пропуск.

Важно: в INTERVIEW_PATTERNS.md: «Players should not get Telegram spam for routine events (identity/Telegram = future / optional)». То есть Telegram — опционально, не для всех событий.

MarkRead
POST /api/v1/notifications/:id/read.

UPDATE notifications SET read_at = now() WHERE id = $1 AND user_id = $2.

user_id из JWT — нельзя отметить чужое.

Идемпотентно: повтор не двигает read_at (или двигает, но результат тот же).

Необычные кейсы (стоит рассказать)
1. Два независимых сервиса в одном процессе.
InboxService (in-app колокольчик) + Notifier (Telegram). Один процесс, два сервиса. Это не два deployment, а два логических сервиса в одном бинарнике. Плюс — меньше deployment’ов. Минус — если Telegram тормозит, in-app тоже (общий процесс).

2. Два шины одновременно — Dual-Bus Consumer.
NATS primary, Kafka fallback. В обычном make deploy — NATS. В make deploy-heavy — Kafka. В FINISHERS.md: «Fulfillment и notification читают Kafka только когда JetStream не поднят». Это защита от двойной доставки.

3. Fan-Out.
Одно событие → N уведомлений. record_beaten → уведомление тому, кого побили. purchase.paid → уведомление покупателю + уведомление автору (если есть). Fan-Out — это не broadcast всем, а N адресных уведомлений.

4. Idempotency Key через source_event.
INSERT INTO notifications (...) ON CONFLICT (user_id, source_event) DO NOTHING. source_event — уникальный id события (например, score.updated:user:123:game:hexagon:score:150). Повтор не создаёт дубль. Это защита от at-least-once.

5. In-app bell soft-fail.
Если пользователь не залогинен — FE NotificationBell не делает запрос, нет цикла 401. В INTERVIEW_PATTERNS.md: «In-app bell; soft-fail when logged out (без цикла 401)».

6. Retry with Fixed Delay для Telegram.
Не exponential backoff, а фиксированная задержка. В каталоге отмечено. Плюс — проще. Минус — при долгом сбое Telegram нагрузка постоянная.

7. Известные проблемы (техдолг):
«Notifier (Telegram) в Handle для Kafka падает без Ack при unmarshal error. Решение: Poison message → Ack» (пункт 13). То есть битое сообщение из Kafka — бесконечный retry.

9. Что спросят на собесе (готовые ответы)
«Почему два сервиса в одном процессе?»
InboxService (in-app колокольчик) + Notifier (Telegram). Один процесс, два логических сервиса. Плюс — меньше deployment’ов, общий код. Минус — если Telegram тормозит, in-app тоже (общий процесс). Честно: знаю про минус.

«Почему Dual-Bus Consumer?»
NATS primary, Kafka fallback. В обычном make deploy — NATS. В make deploy-heavy — Kafka. В FINISHERS.md: «Fulfillment и notification читают Kafka только когда JetStream не поднят». Это защита от двойной доставки: если оба брокера живы — Notification читает только NATS.

«Что такое Fan-Out?»
Одно событие → N уведомлений. record_beaten → уведомление тому, кого побили. purchase.paid → уведомление покупателю + уведомление автору (если есть). Fan-Out — это не broadcast всем, а N адресных уведомлений. notification_fanout_size (histogram) — размер.

«Почему Idempotency Key через source_event?»
INSERT INTO notifications (...) ON CONFLICT (user_id, source_event) DO NOTHING. source_event — уникальный id события (например, score.updated:user:123:game:hexagon:score:150). Повтор не создаёт дубль. At-least-once + idempotent consumer. Без этого Boosty повторил бы вебхук — два уведомления.

«Почему In-app bell soft-fail?»
Если пользователь не залогинен — FE NotificationBell не делает запрос, нет цикла 401. В INTERVIEW_PATTERNS.md: «In-app bell; soft-fail when logged out (без цикла 401)». Это UX: лучше пусто, чем бесконечный цикл 401.

«Почему Retry with Fixed Delay для Telegram?»
Не exponential backoff, а фиксированная задержка. Плюс — проще. Минус — при долгом сбое Telegram нагрузка постоянная. Честно: знаю про минус. Exponential backoff был бы лучше.

«Что если Telegram API упал?»
notification_telegram_failed_total растёт. Retry with Fixed Delay — повторяем. Если долго — алерт. In-app при этом работает (не зависит от Telegram).

«Что если битое сообщение из Kafka?»
Техдолг: «Notifier (Telegram) в Handle для Kafka падает без Ack при unmarshal error. Решение: Poison message → Ack». То есть битое сообщение — бесконечный retry. Честно: знаю, надо делать Ack и логировать poison.

«Почему GET /api/v1/notifications только свои?»
user_id из JWT, не из query. Чужие уведомления посмотреть нельзя. Защита от IDOR. Если бы user_id был в query — можно было бы посмотреть чужие.

«Почему :50063, а не :50056?»
В HOW_DOES_EH_WORK.md (v1.0.7) был :50056. В README v1.1.0 и MIRO_STICKERS_PASTE.md — :50063. Актуальный — :50063. Старый — из ранней версии.

«Как тестируешь Notification?»
Unit — мок InboxStore, мок Telegram клиента, Idempotency (повтор с тем же source_event). Integration — testcontainers (реальный PG). Dual-Bus — тест с NATS и Kafka (проверка, что читает только один). Fan-Out — тест с N уведомлениями.

«Что улучшил бы?»
Poison message → Ack (сейчас бесконечный retry)

Retry с exponential backoff для Telegram (сейчас fixed delay)

Фильтрация PII в уведомлениях (сейчас нет)

Алерт на notification_telegram_failed_total резко растёт

Алерт на notification_poison_messages_total растёт
