Balancer — полный разбор для собеса
Разбираю так же, как предыдущие. Всё, что известно по services/balancer из твоих файлов. 15 паттернов. Least Connections, самописный, ~10 МБ Go-бинарник.

1. Одна фраза (elevator pitch)
Balancer — самописный L7-балансировщик. Алгоритм Least Connections: выбирает backend с наименьшим числом активных соединений. Atomic Counter для ActiveConns — без mutex на hot path. Reverse Proxy через httputil.ReverseProxy. Prometheus Gauge — единственный сервис с Gauge (balancer_active_connections). ~10 МБ Go-бинарник, не NGINX. Знает про 3 Gateway-реплики (:8081–8083). 15 паттернов. Известные проблемы: пустые пакеты backend/, proxy/ (мёртвый код), /ready не проверяет бэкенды, static registry (нет service discovery), нет health checks бэкендов.

4. Как работает (по шагам)
Request lifecycle (HTTP)
Клиент → Balancer :8079 (HTTP или WS upgrade).

Least Connections: Balancer смотрит ActiveConns всех бэкендов (atomic load), выбирает минимальный.

Reverse Proxy: httputil.ReverseProxy проксирует запрос в выбранный Gateway.

ActiveConns выбранного бэкенда инкрементируется (atomic add).

Ответ от Gateway → клиенту.

ActiveConns декрементируется (atomic add).

Необычный кейс: Least Connections с atomic counter. Не mutex, не lock-free queue — просто atomic.LoadInt32 / atomic.AddInt32. На горячем пути (каждый запрос) — это критично. В SYSTEM_DESIGN.md код:

go
func (lb *LeastConnBalancer) getLeastConnBackend() *Backend {
    var selected *Backend
    var minConns int32 = 2147483647

    for _, b := range lb.backends {
        conns := atomic.LoadInt32(&b.ActiveConns)
        if conns < minConns {
            minConns = conns
            selected = b
        }
    }
    return selected
}
WebSocket (sticky)
Клиент → Balancer :8079/ws/leaderboard?ticket=....

Balancer выбирает backend least-connections.

Sticky: WS-соединение держится на этом backend до конца. Все кадры идут в одну Gateway-реплику.

Balancer не разбирает WS-кадры — просто проксирует байты.

ActiveConns — WS считается как одно активное соединение на всё время жизни.

Важно: без sticky WS-кадры прыгали бы между репликами, Hub на каждой реплике — свой. Клиент видел бы разные табло. Sticky решает.

Необычные кейсы (стоит рассказать)
1. Least Connections + Atomic Counter.
Не mutex, не lock-free queue — atomic.LoadInt32 / AddInt32. На горячем пути (каждый запрос) — это критично. В SYSTEM_DESIGN.md код: цикл по бэкендам, atomic.LoadInt32, выбрать минимальный.

2. Reverse Proxy через httputil.ReverseProxy.
Не свой HTTP-клиент, а стандартный httputil.ReverseProxy. Плюс — проверенный код, поддержка WS upgrade, keep-alive. Минус — меньше контроля (нельзя легко вставить свою логику).

3. Prometheus Gauge — единственный сервис с Gauge.
balancer_active_connections{backend="gateway"} — Gauge, не Counter. Значение может расти и падать. В каталоге: «единственный сервис с Gauge».

4. X-Balancer-Backend Header.
Balancer добавляет заголовок X-Balancer-Backend: gateway-2 в ответ. Это debug: видно, какая реплика обработала. В каталоге: «X-Balancer-Backend Header — balancer».

5. Sticky для WS.
WS-соединение держится на одной Gateway-реплике. Без sticky — кадры прыгали бы между репликами, Hub на каждой реплике свой. Клиент видел бы разные табло.

6. Static registry — нет service discovery.
Список бэкендов — статический. Нет Consul, нет etcd, нет Kubernetes DNS. Техдолг: «Интегрировать с etcd/consul/k8s».

7. Нет health checks бэкендов.

8. /ready не проверяет бэкенды.

9. Что спросят на собесе (готовые ответы)
«Почему самописный Balancer, а не NGINX?»
Гибкость: мы сами решаем, как распределять нагрузку (Least Connections). Метрики: собираем свои метрики прямо в балансировщике (Prometheus Gauge). Легковесность: ~10 МБ Go-бинарник. Минус: NGINX проверен годами, наш — самописный. Но для MVP это допустимо.

«Что такое Least Connections?»
Алгоритм: выбирает backend с наименьшим числом активных соединений. Лучше round-robin, когда запросы разной длительности: длинный запрос на одном backend — round-robin перегрузит его, least-connections — нет.

«Почему Atomic Counter, а не Mutex?»
На горячем пути (каждый запрос) — atomic.LoadInt32 / AddInt32 дешевле mutex. Не нужен lock, не нужен contention. ActiveConns — просто int32, atomic операции.

«Что такое Reverse Proxy?»
httputil.ReverseProxy — стандартный Go-прокси. Проксирует HTTP (и WS upgrade) в backend. Плюс: проверенный код, поддержка WS, keep-alive. Минус: меньше контроля (нельзя легко вставить свою логику).

«Почему Prometheus Gauge, а не Counter?»
balancer_active_connections — текущее число активных соединений. Может расти и падать. Counter только растёт. Gauge — единственный сервис с Gauge.

«Что такое X-Balancer-Backend Header?»
Balancer добавляет заголовок X-Balancer-Backend: gateway-2 в ответ. Debug: видно, какая реплика обработала. Не для production, для отладки.

«Почему WS sticky?»
WS-соединение держится на одной Gateway-реплике. Без sticky — кадры прыгали бы между репликами, Hub на каждой реплике свой. Клиент видел бы разные табло. Sticky решает.

«Почему static registry, а не service discovery?»
Техдолг: «Static registry — нет service discovery. Интегрировать с etcd/consul/k8s». Сейчас список бэкендов статический. Плюс: просто. Минус: не масштабируется автоматически.

«Почему нет health checks бэкендов?»
Техдолг: «Нет health checks бэкендов. Периодический ping /health каждого backend». Сейчас если Gateway-2 упал — Balancer всё равно может выбрать его. Запрос уйдёт, получит ошибку, Balancer вернёт 502. Честно: знаю, надо health checks.

«Почему /ready не проверяет бэкенды?»
Техдолг: «/ready не проверяет бэкенды — всегда ready. Реальная проверка доступности хотя бы одного backend». Сейчас даже если все 3 Gateway упали — Balancer говорит «ready». Честно: знаю.

«Почему пустые пакеты backend/, proxy/?»
Техдолг: «Пустые пакеты backend/ и proxy/ — мёртвый код. Удалить или наполнить». Сейчас — мёртвый код. Честно: знаю.

«Почему log.Printf в hot path?»
Техдолг: «log.Printf в hot path». Не structured logging. В hot path — каждое соединение логируется. Честно: знаю.
