Leaderboard — полный разбор для собеса
Разбираю так же, как Auth, Game, Billing. Всё, что известно по services/leaderboard из твоих файлов.

1. Одна фраза (elevator pitch)
Leaderboard — табло. Потребляет score.updated из NATS, пишет в Redis Sorted Set (ZAddArgs{GT: true} — только улучшение рекорда) и в Postgres как бэкап. Читает топ из Redis. При старте — warm-up из Postgres. Внутри consumer’а — Event Chaining: если чей-то рекорд побит, публикует record_beaten. Подтверждения NATS собираются в Ack Batcher — батчем, не по одному. 20 паттернов.

4. Как работает (по шагам)
Потребление score.updated
Game публикует score.updated через outbox worker.

Leaderboard — durable consumer с именем (позиция сохраняется между перезапусками).

Для каждого события:

Max-Only Write: ZAddArgs{GT: true} — пишет в Redis Sorted Set только если новый счёт больше текущего. Не перезаписывает рекорд худшим.

Write-Through Cache: параллельно пишет в Postgres (leaderboard_backup) — бэкап, не источник правды для чтения.

Event Chaining: если чей-то рекорд побит — публикует record_beaten с user_id, game_id, level, new_score.

Ack Batcher: подтверждения NATS собираются в батч, не по одному. Меньше нагрузки на NATS.

Чтение топа
Gateway → gRPC GetLeaderboard.

Leaderboard читает из Redis Sorted Set: ZREVRANGE key 0 limit-1 WITHSCORES.

Возвращает топ с очками.

Необычный кейс: чтение — только из Redis. Postgres не читается для топа (он бэкап). Это быстро (Redis Sorted Set — O(log N) на вставку, O(log N + M) на чтение).

Warm-up при старте
Leaderboard стартует.

Restore-on-Startup: читает leaderboard_backup из Postgres, заливает в Redis Sorted Set.

Если Postgres упал при старте — leaderboard пустой. Это известная проблема (пункт 25 в техдолге): «Retry / exponential backoff».

Event Chaining (record_beaten)
Leaderboard потребляет score.updated.

Если новый счёт больше текущего рекорда другого игрока — публикует record_beaten.

record_beaten содержит user_id (кого побили), game_id, level, new_score.

Notification потребляет record_beaten → in-app bell «Ваш рекорд побили».

FE — deep-link на /leaderboard?game=X&level=Y&highlight=me.

Важно: «один рекорд — одно уведомление». Не спамить. Это в roadmap (FUTURE_EVENT_HORIZON.md): «Проверить: не спамить. Один рекорд — одно уведомление».

Необычные кейсы (стоит рассказать)
1. ZAddArgs{GT: true} — Max-Only Write.
В Redis Sorted Set пишется только если новый счёт больше текущего. GT: true — это флаг «Greater Than». Не перезаписывает рекорд худшим. Если игрок сыграл хуже — рекорд остаётся. Это атомарно на уровне Redis.

2. Ack Batcher.
Подтверждения NATS собираются в батч, не по одному. Меньше нагрузки на NATS. Это оптимизация: 100 событий → 1 Ack вместо 100. Важно при высоком RPS.

3. Event Chaining.
Внутри consumer’а score.updated Leaderboard публикует record_beaten. Это chaining: одно событие порождает другое. Не прямой вызов Notification, а событие. Notification потребляет record_beaten → in-app bell.

4. Restore-on-Startup.
При старте Leaderboard читает leaderboard_backup из Postgres, заливает в Redis. Если Postgres упал — leaderboard пустой. Известная проблема (техдолг): «Retry / exponential backoff».

5. Write-Through Cache.
Параллельно пишет в Redis и в Postgres. Redis — для чтения, Postgres — бэкап. Не Cache-Aside (где промах → БД), а Write-Through: пишем в оба сразу.

6. Multi-Level Key.
Ключ включает game_id, level. Сейчас все доски — level=1 (кроме Flappy). Уровни 2–3 — в roadmap.

7. Известная проблема (техдолг):
«RestoreFromPostgres при старте — если Postgres упал, leaderboard пустой. Решение: Retry / exponential backoff».

9. Что спросят на собесе (готовые ответы)
«Почему Redis Sorted Set, а не Postgres ORDER BY score DESC?»
Redis Sorted Set — O(log N) на вставку, O(log N + M) на чтение топа. Postgres ORDER BY score DESC LIMIT 10 на большой таблице — Seq Scan или Index Scan, но всё равно медленнее. Плюс Redis держит топ в памяти. Postgres — бэкап, не источник правды для чтения.

«Что такое ZAddArgs{GT: true}?»
Max-Only Write. В Redis Sorted Set пишется только если новый счёт больше текущего. GT: true — флаг «Greater Than». Не перезаписывает рекорд худшим. Если игрок сыграл хуже — рекорд остаётся. Атомарно на уровне Redis.

«Почему Write-Through, а не Cache-Aside?»
Пишем в Redis и в Postgres параллельно. Redis — для чтения, Postgres — бэкап. Cache-Aside был бы «промах → БД», но для топа мы всегда читаем из Redis, не ходим в Postgres. Write-Through даёт бэкап без задержки.

«Что такое Ack Batcher?»
Подтверждения NATS собираются в батч, не по одному. Меньше нагрузки на NATS. 100 событий → 1 Ack вместо 100. Важно при высоком RPS.

«Что такое Event Chaining?»
Внутри consumer’а score.updated Leaderboard публикует record_beaten. Одно событие порождает другое. Не прямой вызов Notification, а событие. Notification потребляет record_beaten → in-app bell «Ваш рекорд побили». FE — deep-link на /leaderboard?game=X&level=Y&highlight=me.

«Почему record_beaten — событие, а не прямой вызов?»
Развязка. Leaderboard не знает про Notification. Если Notification упал — record_beaten лежит в NATS, доставится позже. Leaderboard не блокируется. Это event-driven архитектура.

«Что если Postgres упал при старте?»
RestoreFromPostgres не сработает — leaderboard пустой. Известная проблема (техдолг): «Retry / exponential backoff». Честно: знаю, надо чинить.

«Почему /api/v1/leaderboard публичный?»
Табло видят все. Это осознанно. Но WS — через одноразовый билет, не JWT в query. Это защита от утечки токена через query-параметры (логи, прокси).

«Как работает WS?»
Клиент делает POST /api/v1/ws-ticket с Authorization: Bearer. Gateway кладёт в Redis ключ ws:ticket:{id} на 30 секунд и отдаёт {ticket, expires_in}. Сокет открывается как GET /ws/leaderboard?ticket=. Билет удаляется первым GETDEL, второй раз недействителен. Origin проверяется.

«Как тестируешь Leaderboard?»
Unit — мок репозитория. Integration — testcontainers (реальный PG + Redis). k6 — browse.js (20 VU) читает топ. Legacy 500 VU login blast — не pass/fail. WS — wscat с билетом.

«Что улучшил бы?»
RestoreFromPostgres: Retry / exponential backoff

«Один рекорд — одно уведомление»: не спамить record_beaten
