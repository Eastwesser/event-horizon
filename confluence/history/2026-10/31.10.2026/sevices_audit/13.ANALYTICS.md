4. Как работает (по шагам)
Потребление событий
Пять субъектов (durable consumer analytics-*):

score.updated (durable analytics-score-updated)

user.registered

shop.purchased

payment.completed

author.upserted

Для каждого события:

Parameterized Query через ClickHouse-параметры: не fmt.Sprintf("INSERT INTO events VALUES (%s)", payload), а INSERT INTO events (...) VALUES ({user_id:String}, {event_type:String}, ...).

INSERT INTO clickhouse.events (батчами, не по одной строке).

Батчинг: события копятся в памяти (буфер), раз в N секунд или N событий — INSERT пачкой. ClickHouse не любит мелкие INSERT (too many parts).

Ack при успехе. Nak при ошибке (ClickHouse недоступен, timeout).

Необычный кейс: Parameterized Query через ClickHouse-параметры. ClickHouse HTTP-интерфейс поддерживает named params: {name:Type} в SQL, param_name=value в URL или теле. Это защита от SQL injection. Не конкатенация строк.

Батчинг в ClickHouse
Событие → буфер в памяти.

Раз в 1 секунду (или N событий) — INSERT INTO clickhouse.events VALUES (...), (...), ... пачкой.

ClickHouse создаёт part на каждый INSERT. Мелкие INSERT → too many parts → ошибка.

Батчинг решает: один INSERT = один part. MergeTree фоново сливает parts.

Важно: при Nak — событие вернётся, буфер не теряет. At-least-once.

GetDAU / GetMAU / GetRetention
Gateway → gRPC GetDAU / GetMAU / GetRetention. RequireRole(admin).

Analytics → HTTP-клиент ClickHouse → SELECT ... FROM clickhouse.events WHERE ....

Cohort Retention Analysis: для retention — классический SQL: SELECT cohort, day, count(DISTINCT user_id) ... GROUP BY cohort, day.

Возвращает результат.

Важно: ClickHouse не поддерживает UPDATE / DELETE как Postgres. Только ALTER TABLE ... DELETE (асинхронно, дорого) или ReplacingMergeTree (дедуп при merge). Analytics пишет append-only, не обновляет.

Read-only
Analytics — read-only сервис. Только INSERT (ingest) и SELECT (analytics).

Нет POST, PUT, DELETE публично.

Это осознанно: Analytics — не CRUD, а агрегатор.

Необычные кейсы (стоит рассказать)
1. ClickHouse — единственный сервис с аналитической БД.
В HOW_DOES_EH_WORK.md: «ClickHouse: OLAP column store; not on checkout path». Analytics — единственный, кто пишет в ClickHouse. Остальные — Postgres. Это осознанный split: OLTP (Postgres) vs OLAP (ClickHouse).

2. Cohort Retention Analysis.
Классический SQL: SELECT cohort, day, count(DISTINCT user_id) ... GROUP BY cohort, day. Когорта — день регистрации. Retention — сколько из когорты вернулись на день N. Это стандарт для продуктовой аналитики.

3. Parameterized Query через ClickHouse-параметры.
INSERT INTO events (...) VALUES ({user_id:String}, {event_type:String}, ...). ClickHouse HTTP-интерфейс поддерживает named params. Не конкатенация — защита от SQL injection. В EVENT_HORIZON_PATTERNS_15.10.2026.md отмечено как отдельный паттерн.

4. Батчинг в ClickHouse.
События копятся в памяти, раз в N секунд — INSERT пачкой. ClickHouse не любит мелкие INSERT (too many parts). Батчинг решает. Это не паттерн из каталога, но важная деталь реализации.

5. Adapter для ClickHouse.
HTTP-клиент ClickHouse — Adapter. Не native driver (порт 9000), а HTTP (8123). Это осознанно: HTTP проще, не нужен native protocol. Минус — чуть медленнее.

9. Что спросят на собесе (готовые ответы)
«Почему ClickHouse, а не Postgres?»
ClickHouse — колоночный OLAP: сжатие по колонкам, огромные сканы, GROUP BY на миллиардах строк за секунды. Postgres — OLTP: строчные транзакции, JOIN, ACID. Аналитика (DAU/MAU/retention) — это сканы и агрегаты, ClickHouse лучше. В HOW_DOES_EH_WORK.md: «ClickHouse: OLAP column store; not on checkout path».

«Почему Analytics без Postgres?»
Единственный сервис с ClickHouse. Не нужен Postgres: события append-only, агрегаты — из ClickHouse. Postgres был бы лишним.

«Что такое Cohort Retention Analysis?»
Классический SQL: SELECT cohort, day, count(DISTINCT user_id) ... GROUP BY cohort, day. Когорта — день регистрации. Retention — сколько из когорты вернулись на день N. Стандарт для продуктовой аналитики.

«Почему Parameterized Query через ClickHouse-параметры?»
ClickHouse HTTP-интерфейс поддерживает named params: {name:Type} в SQL, param_name=value в URL или теле. Не конкатенация строк — защита от SQL injection. В EVENT_HORIZON_PATTERNS_15.10.2026.md отмечено как отдельный паттерн.

«Что такое батчинг в ClickHouse?»
События копятся в памяти, раз в N секунд — INSERT пачкой. ClickHouse не любит мелкие INSERT (too many parts). Батчинг решает: один INSERT = один part. MergeTree фоново сливает parts. Если батчинг сломан — clickhouse_parts_current растёт, merge не справляется.

«Почему HTTP-клиент ClickHouse, а не native driver?»
HTTP проще: не нужен native protocol (порт 9000), не нужен отдельный driver. Минус — чуть медленнее. Adapter — HTTP-клиент. Это осознанно: аналитика не latency-critical.

«Почему все ручки — только admin?»
DAU/MAU/retention — бизнес-метрики. Обычный пользователь не должен их видеть. RequireRole(admin) на Gateway. Это защита от утечки.

«Почему Analytics — read-only?»
Только INSERT (ingest) и SELECT (analytics). Нет POST/PUT/DELETE публично. Analytics — агрегатор, не CRUD. В FINISHERS.md: «Три чтения, не CRUD».

«Что если ClickHouse упал при ingest?»
Nak — событие вернётся. Consumer повторит. analytics_nak_total растёт. Алерт на резкий рост. Graceful Degradation: ingest не теряет, но тормозит.

«Что если sql := fmt.Sprintf(...) с %s для db name?»
Техдолг: fmt.Sprintf для имени базы — потенциальная SQL injection, если имя станет user input. Сейчас — не user input, но в техдолге: «Параметризовать db name». Честно: знаю.

«Как тестируешь Analytics?»
Unit — мок AnalyticsStore, Parameterized Query (проверка, что нет конкатенации). Integration — testcontainers (реальный ClickHouse). Batching — тест с N событиями, проверка размера батча. Retention — тест с фиктивными событиями.
