Shop — полный разбор для собеса
Разбираю так же, как Auth, Game, Billing, Leaderboard. Всё, что известно по services/shop из твоих файлов. Самый богатый сервис: 30 паттернов.

1. Одна фраза (elevator pitch)
Shop — витрина и покупка. Сага на две базы: списание билетиков в Billing (Postgres billing), склад и строка покупки в Shop (Postgres shop). Общей транзакции нет. purchase_sagas — строка-оркестратор: started → spent → stocked, либо spent → compensating → compensated. Ключ списания один на цикл: shop:{user}:{item}:{cycle} — два клика делят один ключ, второго списания нет. Если процесс умер после списания, воркер resumeSagas через 30 секунд дочитывает строку и делает один идемпотентный шаг. purchase.paid пишется в outbox в той же транзакции, что склад и purchases; воркер публикует FOR UPDATE SKIP LOCKED после commit. 30 паттернов.

4. Как работает (по шагам)
PurchaseItem (покупка)
Gateway → gRPC PurchaseItem.

Merch gate: если category=merch — синхронно зовёт Payment CanPurchaseMerch. Нет подписки → 403 subscription_required, покупка не начинается.

Saga started: Shop пишет строку purchase_sagas с ключом spend_ref = shop:{user}:{item}:{cycle}. cycle берётся из purchase_claims.

Списание: Shop зовёт Billing SpendCurrency синхронно:

UPDATE … WHERE balance >= amount

INSERT transactions с уникальным spend_ref

INSERT outbox(balance.updated)

commit

Успех или «такой ключ уже был» → сага spent. Отказ Billing (нет баланса) → сага aborted.

Транзакция Shop:

SELECT stock FOR UPDATE

stock - 1 с проверкой version (optimistic lock)

INSERT inventory (primary key (user_id, item_id) — второй раз тот же скин не вставить)

INSERT purchases с заранее известным id, статус COMPLETED, refundable_until = now + 7 days

INSERT outbox(shop.purchased) и INSERT outbox(purchase.paid) с этим же purchases.id

commit

Сага stocked.

Outbox worker забирает строки FOR UPDATE SKIP LOCKED, публикует в NATS, помечает обработанными только после успешного Publish.

Если шаг 6 упал (склад не записался)
Сага compensating.

Shop пишет billing.refund в outbox с ключом refund:shop:{user}:{item}:{cycle}.

Зовёт Billing AddCurrency с этим ключом — возврат.

Если возврат прошёл — сага compensated, cycle сдвигается, следующая покупка получит новый ключ.

Если возврат упал — счётчик shop_purchase_refund_failures_total растёт, строка outbox остаётся, воркер повторяет.

Если процесс умер после списания (между шагами 5 и 6)
Воркер resumeSagas берёт строки spent / compensating старше 30 секунд FOR UPDATE SKIP LOCKED.

Нашёл purchases.id → ставит stocked, ничего не возвращает.

Не нашёл → вызывает тот же возврат, что и outbox billing.refund, сдвигает cycle, ставит compensated.

Необычный кейс: лок строки снимается до RPC в Billing. Иначе долгий RPC держит лок и блокирует другие саги.

CancelPurchase (отмена)
Gateway → gRPC CancelPurchase.

Одна транзакция Shop:

блокировка покупки

отказ, если окно 7 дней вышло или физический товар уже fulfilled_at

статус REFUNDED

удаление из shop.inventory

stock + 1

commit

Потом AddCurrency с ключом cancel-{purchaseID}.

Повтор отмены делает тот же вызов — уникальный ключ не задваивает деньги.

Чтение каталога
Gateway → gRPC GetItems.

Shop читает из Redis (Cache-Aside). Промах → Postgres, запись в Redis.

Инвалидация после мутации (inventory.item.created, обновление карточки).

Inventory → Shop (каталог автора)
Inventory создаёт карточку → outbox inventory.item.created.

NATS → Shop durable consumer shop-inventory-sync.

Shop создаёт строку shop.items.

Каталог обновляется. Прямого gRPC Inventory → Shop нет.

Необычные кейсы (стоит рассказать)
1. Saga на две базы — без 2PC.
Списание в Billing (Postgres billing), склад и purchases в Shop (Postgres shop). Общей транзакции нет и не будет: двухфазный коммит ломает доступность ради иллюзии одной базы. Вместо этого — строка purchase_sagas как оркестратор. Состояния: started → spent → stocked, либо started → aborted, либо spent → compensating → compensated.

2. Spend Cycle — оригинальный приём для идемпотентности.
Ключ списания shop:{user}:{item}:{cycle}. Два клика делят один cycle и один ключ — второго списания нет. После возврата cycle растёт, следующая покупка получает новый ключ. Это не UUID с наносекундами (как было до v1.1.1) — это стабильный ключ на цикл.

3. Saga Resume Worker — фоновое доведение.
Если процесс умер после списания, воркер resumeSagas через 30 секунд берёт строку spent / compensating FOR UPDATE SKIP LOCKED. Нашёл purchases.id → stocked. Не нашёл → возврат, cycle сдвинут, compensated. Лок снимается до RPC в Billing.

4. Pessimistic + Optimistic Lock в одной транзакции.
SELECT stock FOR UPDATE (pessimistic) + version (optimistic). Две защиты: блокировка строки + проверка версии. Это редкий кейс — обычно выбирают одно.

5. Outbox → Compensate Callback.
При отказе склада Shop пишет billing.refund в outbox в той же транзакции, что и попытка склада. Воркер публикует в NATS. Потребитель billing.refund → AddCurrency с ключом refund:.... Если и это упало — счётчик shop_purchase_refund_failures_total растёт, строка outbox остаётся, воркер повторяет.

6. purchase.paid с настоящим purchases.id.
До v1.1.1 purchase.paid нёс случайные 16 байт, fulfilled_at не находил строку покупки. После — PurchaseUUID = purchases.id, записанный в той же транзакции. Это исправление в v1.1.1 (FINISHERS.md).

7. Прямого gRPC Game → Shop нет.
Общий человек — user_id из Auth. Общие деньги — Billing. Скин лежит в shop-inventory. Каталог автора живёт в Inventory и событием появляется в Shop. Прямого gRPC Game → Shop нет.

9. Что спросят на собесе (готовые ответы)
«Почему saga, а не 2PC?»
Две базы: Billing (Postgres billing) и Shop (Postgres shop). 2PC ломает доступность ради иллюзии одной базы — координатор блокирует обе базы на всё время. Saga даёт eventual business consistency: локальные транзакции + компенсации. В нашем случае строка purchase_sagas — оркестратор: started → spent → stocked, либо spent → compensating → compensated.

«Что такое Spend Cycle?»
Ключ списания shop:{user}:{item}:{cycle}. Два клика делят один cycle и один ключ — второго списания нет. После возврата cycle растёт, следующая покупка получает новый ключ. Это не UUID с наносекундами (как было до v1.1.1) — это стабильный ключ на цикл.

«Что если процесс умер после списания, но до записи покупки?»
Воркер resumeSagas через 30 секунд берёт строку spent / compensating FOR UPDATE SKIP LOCKED. Нашёл purchases.id → ставит stocked, ничего не возвращает. Не нашёл → вызывает тот же возврат, что и outbox billing.refund, сдвигает cycle, ставит compensated. Лок снимается до RPC в Billing.

«Почему лок снимается до RPC?»
Долгий RPC держит лок и блокирует другие саги. Лучше снять лок, сделать RPC, потом обновить строку. Если процесс умрёт между — воркер resumeSagas дочитает.

«Почему Pessimistic + Optimistic Lock в одной транзакции?»
SELECT stock FOR UPDATE (pessimistic) + version (optimistic). Две защиты: блокировка строки + проверка версии. Это редкий кейс — обычно выбирают одно. Но для денег и склада — обе.

«Почему purchase.paid пишется в outbox, а не публикуется напрямую?»
До v1.1.1 purchase.paid публиковался после commit, мимо outbox. Если процесс умирал между commit и publish — событие терялось. После — shop.purchased и purchase.paid пишутся в outbox в той же транзакции, что склад и purchases. Воркер публикует FOR UPDATE SKIP LOCKED после commit. Строка помечается processed только после успешного Publish. Дубликаты возможны — consumer идемпотентный.

«Что если S3 принял файл, а событие готово не ушло?»
Это про AdTime, не про Event Horizon. В EH S3 нет. Но паттерн тот же: воркер не подтверждает job, либо есть сверка «файл есть, события нет». Клиенту не говорят ready раньше объекта.

«Почему мерч без подписки — 403?»
Мерч-гейт: синхронный CanPurchaseMerch в Payment. Нет подписки → 403 subscription_required, покупка не начинается. Это бизнес-правило: физический мерч требует активной подписки. CanPurchaseMerch сам по себе — 200 probe, но PurchaseItem возвращает 403.

«Почему purchases.id заранее известный?»
До v1.1.1 purchase.paid нёс случайные 16 байт, fulfilled_at не находил строку покупки. После — PurchaseUUID = purchases.id, записанный в той же транзакции. purchase.fulfilled от Fulfillment находит строку по этому id и ставит fulfilled_at.

«Что если paymentClient nil?»
Мерч-гейт деградирует — покупка мерча проходит без проверки подписки. Это известная проблема (техдолг): нужна метрика merch_gate_disabled. Сейчас нет.

«Что если kafkaProd создаётся, но не используется?»

Shop — единственный сервис с явной сагой. purchase_sagas — оркестратор.

Spend Cycle — shop:{user}:{item}:{cycle}. Не UUID с наносекундами.

Saga Resume Worker — resumeSagas через 30 секунд FOR UPDATE SKIP LOCKED.

Pessimistic + Optimistic Lock в одной транзакции — редкий кейс.

purchase.paid в outbox, не прямой publish.

purchases.id заранее известный — fulfilled_at находит строку.

Мерч-гейт — синхронный CanPurchaseMerch, 403 subscription_required.

/api/v1/shop/inventory — купленные скины. /api/v1/inventory/items — каталог автора (другой домен).
