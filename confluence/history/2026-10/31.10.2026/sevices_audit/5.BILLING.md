Billing — полный разбор для собеса
Разбираю так же, как Auth и Game. Всё, что известно по services/billing из твоих файлов.

1. Одна фраза (elevator pitch)
Billing — единственный сервис, который двигает деньги (внутреннюю валюту). Две валюты: лампы (буст) и билетики (магазин). Списание — условным UPDATE WHERE balance >= $1, вставка в transactions с уникальным reference_id, outbox balance.updated — в одной транзакции. Повтор с тем же reference_id упирается в уникальный ключ и не списывает второй раз. Это double-entry ledger: каждая транзакция с balance_after. 24 паттерна.

4. Как работает (по шагам)
AddCurrency (начисление)
Вызывается из Game (daily gift), Leaderboard consumer (награда за рекорд), Shop (возврат при отмене).

В одной транзакции:

Atomic Upsert-Increment: INSERT … ON CONFLICT DO UPDATE SET balance = balance + $amount

INSERT transactions с уникальным reference_id и balance_after

INSERT outbox(balance.updated)

Commit.

Инвалидация кэша: redisRepo.DeleteBalance(ctx, userID, currency).

Возвращает новый баланс.

SpendCurrency (списание)
Вызывается из Game (буст), Shop (покупка).

В одной транзакции:

Conditional UPDATE: UPDATE user_currencies SET balance = balance - $1 WHERE user_id = $2 AND currency = $3 AND balance >= $1

Если 0 rows — недостаточно средств → откат.

INSERT transactions с reference_id и balance_after

INSERT outbox(balance.updated)

Commit.

Инвалидация кэша.

Возвращает новый баланс.

Необычный кейс: Conditional UPDATE — атомарная проверка «хватает ли» и списание в одном запросе. Не SELECT потом UPDATE — это lost update. WHERE balance >= $1 защищает от отрицательного баланса на уровне БД.

Идемпотентность
transactions.reference_id уникален.

Повтор AddCurrency / SpendCurrency с тем же ключом не проходит второй вставкой — упирается в уникальный ключ.

Ключи из Shop: shop:{user}:{item}:{cycle} (покупка), cancel-{purchaseID} (отмена), refund:shop:{user}:{item}:{cycle} (компенсация).

Ключ из Game: daily-gift:{user}:{date} (daily gift), boost:{user}:{cycle} (буст).

Double-Entry Ledger
Каждая транзакция в transactions имеет balance_after — баланс после операции. Это не просто лог, это ledger: можно восстановить историю и проверить, что баланс сходится.

Race Condition Test
В каталоге паттернов отмечен Race Condition Test — есть тест на конкурентное списание. Это важно: два параллельных SpendCurrency на один счёт не должны увести баланс в минус.

Необычные кейсы (стоит рассказать)
1. Conditional UPDATE вместо SELECT + UPDATE.
UPDATE … WHERE balance >= $1 — атомарная проверка «хватает ли» и списание в одном запросе. Не SELECT потом UPDATE — это lost update. WHERE balance >= $1 защищает от отрицательного баланса на уровне БД.

2. Double-Entry Ledger с balance_after.
Каждая транзакция в transactions имеет balance_after. Это не просто лог, это ledger: можно восстановить историю и проверить, что баланс сходится. Классика финансового учёта.

3. Batch INSERT через COPY.
Для массовых начислений (например, награда за рекорд всем игрокам) — COPY вместо INSERT. Быстрее на порядки.

4. Check-Only Mode.
Режим проверки баланса без записи. Используется, когда нужно узнать «хватает ли», но не списывать (например, перед показом кнопки «Купить»).

5. Race Condition Test.
Есть тест на конкурентное списание. Два параллельных SpendCurrency на один счёт не должны увести баланс в минус. Это критично для денег.

6. Reward Consumer.
Billing потребляет score.updated и начисляет билетики за игру. Это event-driven: Game не зовёт Billing синхронно для награды, а публикует событие, Billing потребляет. Асинхронно, at-least-once, идемпотентно по reference_id.

7. Известная проблема (техдолг):
В каталоге паттернов отмечено: «RewardConsumer использует time.Now().UnixNano() для reference_id — при повторной доставке события может начислить дважды. Решение: использовать event.ReferenceID из события». На собесе честно: «Знаю, что надо брать reference_id из события, а не генерировать из времени».

9. Что спросят на собесе (готовые ответы)
«Почему Conditional UPDATE, а не SELECT + UPDATE?»
UPDATE … WHERE balance >= $1 — атомарная проверка «хватает ли» и списание в одном запросе. Не SELECT потом UPDATE — это lost update: два параллельных запроса прочитали balance=100, оба списали 10, баланс 90 вместо 80. WHERE balance >= $1 защищает от отрицательного баланса на уровне БД.

«Почему reference_id уникален?»
Идемпотентность. Повтор AddCurrency / SpendCurrency с тем же ключом не проходит второй вставкой — упирается в уникальный ключ. Клиент может ретраить, брокер может доставить повторно — деньги не удвоятся. Ключи из Shop: shop:{user}:{item}:{cycle}. Из Game: daily-gift:{user}:{date}.

«Что такое Double-Entry Ledger?»
Каждая транзакция в transactions имеет balance_after — баланс после операции. Это не просто лог, это ledger: можно восстановить историю и проверить, что баланс сходится. Классика финансового учёта. Если баланс разошёлся — можно найти, где.

«Почему outbox, а не просто publish после commit?»
Dual-write проблема: commit в БД + publish в NATS раздельно → потеря или дубль события. Outbox пишет событие в ту же транзакцию, что и движение денег. Воркер публикует после commit. Дубликаты возможны — consumer идемпотентный по reference_id.

«Почему Redis, если есть Postgres?»
Cache-Aside: чтение баланса из Redis, промах → Postgres, запись в Redis. Инвалидация после мутации. Баланс читается часто (при каждом заходе в магазин), а меняется реже. Redis снимает нагрузку с Postgres. Но единственная копия баланса — в Postgres, Redis — только кэш.

«Что если Redis упал?»
Чтение идёт в Postgres. Медленнее, но работает. Запись всегда в Postgres, Redis только инвалидируется. Баланс не теряется.

«Почему Race Condition Test?»
Деньги — критичная штука. Два параллельных SpendCurrency на один счёт не должны увести баланс в минус. Тест проверяет, что Conditional UPDATE + version держат. Это не «на всякий случай», это обязательно для денег.

«Что такое Check-Only Mode?»
Режим проверки баланса без записи. Используется, когда нужно узнать «хватает ли», но не списывать (например, перед показом кнопки «Купить»). Не двигает деньги, только читает.

«Почему Batch INSERT через COPY?»
Для массовых начислений (например, награда за рекорд всем игрокам) — COPY вместо INSERT. Быстрее на порядки. COPY — это потоковая вставка, Postgres не парсит каждую строку как отдельный INSERT.

«Что за проблема с RewardConsumer?»
Честно: RewardConsumer использует time.Now().UnixNano() для reference_id. При повторной доставке события может начислить дважды — time.Now() каждый раз новый. Правильно — брать event.ReferenceID из события. Знаю, в техдолге. Это как раз тот случай, когда at-least-once + неидемпотентный consumer = двойное начисление.

«Как тестируешь Billing?»
Unit — мок репозитория. Integration — testcontainers (реальный PG + Redis). Race Condition Test — конкурентное списание. k6 CORE — browse.js (20 VU), purchase.js (1–5 VU). Legacy 500 VU login blast — не pass/fail.

«Что улучшил бы?»
RewardConsumer: reference_id из события, не из time.Now()

GetBalance возвращает -1 при cache miss — можно спутать с реальным -1. Использовать (int, bool)

Алерт на deadlocks > 0

Алерт на billing_outbox_pending растёт
