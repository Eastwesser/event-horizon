1. Одна фраза (elevator pitch)
Authors — кабинет автора: карточка, заявка на роль, продажи. Заявка проходит через State Machine: pending → approved / rejected. Approve меняет роль в Auth через gRPC и создаёт карточку автора в одной транзакции с approve. Если что-то упало — Compensating Action (Revert): RevertApplication откатывает. Idempotent Application Submission с обработкой race: повторная заявка не создаёт вторую. Pessimistic Lock (FOR UPDATE) в бизнес-логике: два админа не апрувят одну заявку одновременно. Role Check (Privilege Escalation): только admin может approve/reject. Outbox author.upserted в той же транзакции. 20 паттернов.

4. Как работает (по шагам)
Apply (заявка на автора)
Gateway → gRPC Apply. RequireAuth → user_id в контекст.

Idempotent Application Submission: проверка, есть ли уже активная заявка (pending или approved) у этого user_id. Если есть — возвращает её, не создаёт вторую.

Создаёт строку author_applications со статусом pending.

Возвращает {application_id, status: "pending"}.

Необычный кейс: Idempotent Submission с обработкой race. Если два запроса Apply пришли одновременно — unique constraint на (user_id, status='pending') или SELECT FOR UPDATE на user_id. Второй видит pending и возвращает существующую заявку.

Approve (admin)
Gateway → gRPC Approve. RequireRole(admin) на Gateway.

Pessimistic Lock: SELECT … FROM author_applications WHERE id=$1 FOR UPDATE. Два админа не апрувят одну заявку одновременно.

State Machine: проверка, что текущий статус — pending. Если уже approved / rejected — AlreadyExists / FailedPrecondition.

В одной транзакции Authors:

UPDATE author_applications SET status='approved'

INSERT authors (карточка автора) или UPSERT

INSERT outbox(author.upserted)

commit

Синхронно: Authors → Auth gRPC UpdateRole(user_id, "author").

Если Auth упал — Compensating Action (Revert): RevertApplication откатывает author_applications в pending, удаляет authors (или soft-delete). Это в services/authors есть.

Cache Invalidation: DeleteAuthor(ctx, user_id).

Необычный кейс: Compensating Action (Revert). Если Auth не смог сменить роль — Authors откатывает approve. Это не полная saga, а простая компенсация. В EVENT_HORIZON_PATTERNS_15.10.2026.md отмечено: «RevertApplication удаляет authors — если там есть заказы, FK упадёт. Решение: Soft delete + check FKs» (пункт 24 в техдолге).

Reject (admin)
Gateway → gRPC Reject. RequireRole(admin).

Pessimistic Lock на заявке.

Необычные кейсы (стоит рассказать)
1. State Machine для заявок.
pending → approved / rejected. Approve/reject проверяет текущий статус. Если уже approved — AlreadyExists / FailedPrecondition. Idempotent State Transition: повтор не двигает статус.

2. Pessimistic Lock в бизнес-логике.
SELECT … FROM author_applications WHERE id=$1 FOR UPDATE. Два админа не апрувят одну заявку одновременно. Без FOR UPDATE оба прошли бы проверку pending, оба сделали бы approve, оба вызвали Auth UpdateRole — двойной вызов, но роль всё равно одна. Но authors могло бы создаться дважды (если нет unique constraint). FOR UPDATE защищает.

3. Compensating Action (Revert).
Если Auth упал при approve — RevertApplication откатывает author_applications в pending, удаляет authors. Это не полная saga, а простая компенсация. В техдолге: «RevertApplication удаляет authors — если там есть заказы, FK упадёт. Решение: Soft delete + check FKs».

4. Idempotent Application Submission с обработкой race.
Два Apply одновременно — unique constraint на (user_id, status='pending') или SELECT FOR UPDATE на user_id. Второй видит pending и возвращает существующую заявку. Не создаёт вторую.

5. Role Check (Privilege Escalation).
Только admin может approve/reject. RequireRole(admin) на Gateway + gRPC interceptor. Это защита от privilege escalation: user не может сам себе поставить author.

6. Outbox author.upserted.
После approve или upsert карточки — INSERT outbox(author.upserted) в той же транзакции. History и Analytics потребляют. Прямого gRPC Authors → History нет.

9. Что спросят на собесе (готовые ответы)
«Почему State Machine для заявок?»
pending → approved / rejected. Approve/reject проверяет текущий статус. Если уже approved — AlreadyExists / FailedPrecondition. Idempotent State Transition: повтор не двигает статус. Без State Machine два админа могли бы approve → reject → approve, и роль прыгала бы.

«Почему Pessimistic Lock, а не Optimistic?»
SELECT … FOR UPDATE на заявке. Два админа не апрувят одну заявку одновременно. Optimistic Lock (version) тоже возможен, но при approve есть побочный эффект — вызов Auth gRPC. Если два approve пройдут проверку pending, оба вызовут Auth, оба создадут authors. FOR UPDATE защищает до вызова Auth.

«Что такое Compensating Action (Revert)?»
Если Auth упал при approve — RevertApplication откатывает author_applications в pending, удаляет authors. Это не полная saga, а простая компенсация. Знаю про техдолг: RevertApplication удаляет authors — если там есть заказы, FK упадёт. Решение — soft delete + check FKs.

«Почему Idempotent Application Submission с обработкой race?»
Два Apply одновременно — unique constraint на (user_id, status='pending') или SELECT FOR UPDATE на user_id. Второй видит pending и возвращает существующую заявку. Не создаёт вторую. Без этого можно было бы накликать 10 заявок.

«Почему только admin может approve?»
Role Check (Privilege Escalation). user не может сам себе поставить author. Только admin через RequireRole(admin). Это защита от privilege escalation: без этого любой мог бы стать автором и продавать мерч.

«Почему после approve JWT старый?»
UX gap. Approve меняет роль в Auth DB, но JWT пользователя уже выпущен с role=user. JWT не перевыпускается автоматически. Нужен refresh (роль перечитывается из Postgres) или re-login. В API_ROUTES.md отмечено: «Whoami may already show author while inventory RBAC uses JWT». То есть Auth DB уже author, а JWT ещё user. Inventory не пустит писать, пока JWT старый.

«Почему GET /api/v1/authors публичный?»
Список авторов — витрина. Любой может посмотреть, кто продаёт. Это осознанно. Карточка автора — тоже публичная. А /me, /me/sales, /apply — только auth.

«Почему Authors — не Mongo?»
MIRO_STICKERS_PASTE.md явно: «Authors PG+Redis only · no Mongo». Карточка автора — структурированные данные (имя, bio, портфолио), Postgres лучше. Mongo — для гибких атрибутов (Inventory) или чата (AdTime deschat).

«Что если Auth упал при approve?»
RevertApplication откатывает: author_applications обратно в pending, authors удаляется. Клиент получает ошибку. Admin может повторить. authors_revert_total растёт — алерт.

«Что если два админа approve одновременно?»
Pessimistic Lock: первый берёт FOR UPDATE, второй ждёт. Первый проходит, статус approved. Второй видит approved, получает AlreadyExists. Второго approve нет.

«Как тестируешь Authors?»
Unit — мок репозитория и Auth клиента, State Machine (переходы pending → approved / rejected). Integration — testcontainers (реальный PG). Idempotency — повтор Apply, повтор Approve. Revert — Auth мок падает, проверяем RevertApplication.

«Что улучшил бы?»
RevertApplication — soft delete + check FKs (сейчас hard delete, FK падает)

UX gap: после approve — автоперевыпуск JWT или инструкция «перелогиньтесь»

Алерт на authors_revert_total резко растёт

Алерт на pg_stat_database_deadlocks > 0
