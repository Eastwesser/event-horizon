4. Как работает (по шагам)
Checkout
Gateway → gRPC CreateCheckout. RequireAuth → user_id в контекст.

Payment создаёт строку payments со статусом pending, amount (200₽ present / 300₽ future).

Возвращает URL Boosty для редиректа.

Клиент платит в Boosty.

Boosty шлёт webhook на /api/v1/payment/webhook с HMAC-подписью.

Webhook (подтверждение)
Gateway принимает POST /api/v1/payment/webhook без auth (внешний провайдер).

Payment проверяет HMAC-SHA256 подпись через subtle.ConstantTimeCompare — защита от timing attack.

Dual Auth Path: если HMAC не совпал — проверяет shared secret (для YooKassa stub).

Если подпись неверна — 401, платёж не двигается.

В одной транзакции:

блокировка платежа (SELECT … FOR UPDATE)

проверка: если уже completed — 200, не открывать подписку второй раз (Idempotent Payment Completion)

закрытие платежа (status = completed)

гашение старой подписки (expires_at = now())

новая подписка на 30 дней

INSERT outbox(payment.completed)

INSERT revenue_splits: автору amount * 85 / 100 (170₽ из 200, 255₽ из 300), платформе остаток (30₽, 45₽)

commit

Возвращает 200.

Необычный кейс: revenue_splits — это журнал, не перевод. В FINISHERS.md сказано: «Это журнал. Денег на карту автора код не отправляет: живая касса по-прежнему Boosty, своего эквайринга с автосплитом нет». То есть 85/15 записаны, но рубль приходит в Boosty, не на расчётный счёт автора.

CanPurchaseMerch (мерч-гейт)
Shop → gRPC CanPurchaseMerch (синхронно, перед покупкой мерча).

Payment проверяет: есть ли активная подписка (expires_at > now()).

Возвращает {allowed: true} или {allowed: false, reason: "subscription_required"}.

Shop: allowed=false → 403 subscription_required на POST /shop/purchase.

Важно: CanPurchaseMerch — probe, 200. PurchaseItem в Shop — 403. Разные коды.

Subscription Expiry
При новом платеже старая подписка гасится (expires_at = now()), создаётся новая.

Cache TTL based on Expiry — кэш подписки живёт не дольше expires_at.

Если подписка истекла — CanPurchaseMerch вернёт allowed=false.

Cache TTL based on Expiry
Подписка кэшируется в Redis :6386.

TTL кэша — не дольше expires_at. Когда подписка истекает, кэш тоже.

Это Cache TTL based on Expiry — TTL вычисляется из данных, не константа.

Необычные кейсы (стоит рассказать)
1. HMAC-SHA256 + subtle.ConstantTimeCompare — защита от timing attack.
Подпись вебхука Boosty проверяется HMAC-SHA256. Сравнение — subtle.ConstantTimeCompare, а не ==. Обычное == сравнивает байты и останавливается на первом несовпадении — по времени можно подобрать подпись. ConstantTimeCompare всегда сравнивает все байты — время не зависит от содержимого.

2. Dual Auth Path — HMAC + shared secret.
Boosty шлёт HMAC. YooKassa stub (для локальной разработки) — shared secret. Payment проверяет сначала HMAC, если не совпал — shared secret. Это позволяет работать с двумя провайдерами.

3. Subscription Expiry + Cache TTL based on Expiry.
При новом платеже старая подписка гасится (expires_at = now()). Кэш подписки в Redis имеет TTL, вычисленный из expires_at, — не константа. Когда подписка истекает, кэш тоже. Это защита от «кэш говорит, что подписка жива, а она истекла».

4. Revenue Split 85/15 — журнал, не перевод.
INSERT revenue_splits: автору amount * 85 / 100 (170₽ из 200, 255₽ из 300), платформе остаток (30₽, 45₽). Это журнал, не перевод. Денег на карту автора код не отправляет: живая касса — Boosty, своего эквайринга с автосплитом нет.

5. Idempotent Payment Completion.
Повторный вебхук видит status = completed и не открывает подписку второй раз. Возвращает 200. Это защита от «Boosty прислал вебхук дважды — подписка продлилась на 60 дней вместо 30».

6. Мерч-гейт — probe 200, покупка 403.
GET /payment/can-purchase-merch — probe, 200 + {allowed, reason}. POST /shop/purchase для мерча без подписки — 403 subscription_required. Разные коды: probe не двигает деньги, покупка — двигает.

9. Что спросят на собесе (готовые ответы)
«Почему HMAC, а не просто shared secret?»
HMAC-SHA256 — подпись тела вебхука. Если shared secret утёк — злоумышленник может подписать любое тело. HMAC защищает от подмены тела. subtle.ConstantTimeCompare — защита от timing attack: обычное == останавливается на первом несовпадении, по времени можно подобрать подпись.

«Что такое Dual Auth Path?»
Boosty шлёт HMAC. YooKassa stub (для локальной разработки) — shared secret. Payment проверяет сначала HMAC, если не совпал — shared secret. Это позволяет работать с двумя провайдерами. Для production — только HMAC.

«Почему Revenue Split — журнал, не перевод?»
Живая касса — Boosty. Рубль приходит в Boosty, не на расчётный счёт с автосплитом. revenue_splits — журнал: автору 85%, платформе 15%. Но денег на карту автора код не отправляет. Своего эквайринга с автосплитом нет. Это честно: знаю, что журнал, а не перевод.

«Почему Idempotent Payment Completion?»
Boosty может прислать вебхук дважды. Повторный вебхук видит status = completed и не открывает подписку второй раз. Возвращает 200. Без этого подписка продлилась бы на 60 дней вместо 30.

«Почему Cache TTL based on Expiry?»
Кэш подписки в Redis имеет TTL, вычисленный из expires_at, — не константа. Когда подписка истекает, кэш тоже. Это защита от «кэш говорит, что подписка жива, а она истекла».

«Почему мерч-гейт probe 200, а покупка 403?»
GET /payment/can-purchase-merch — probe, 200 + {allowed, reason}. Он не двигает деньги, поэтому 200. POST /shop/purchase для мерча без подписки — 403 subscription_required. Он двигает деньги, поэтому 403. Разные коды — разная семантика.

«Почему SELECT … FOR UPDATE на платеже?»
При вебхуке мы блокируем строку платежа, чтобы два параллельных вебхука не открыли две подписки. FOR UPDATE держит лок до commit. Второй вебхук ждёт, видит completed, возвращает 200 без изменений.

«Что если HMAC не совпал?»
401, платёж не двигается. payment_webhook_invalid_total растёт. Алерт на резкий рост — либо конфиг сломан, либо брутфорс.

«Что если Boosty прислал вебхук с неверной суммой?»
Честно: в текущем коде проверка суммы — на стороне Boosty. Payment доверяет HMAC-подписи и сумме из тела. Если нужно строже — сверять amount с payments.amount перед завершением. Это в техдолге.

«Почему subscriptionDays default 30?»
Техдолг: subscriptionDays в Config — defaults 30. Проверить, что 30 корректно. Сейчас — 30 дней.

«Как тестируешь Payment?»
Unit — HMAC-проверка (тест с неверной подписью, тест с timing), мок репозитория. Integration — testcontainers (реальный PG). Webhook — симуляция с openssl dgst. Idempotency — повтор вебхука с тем же payment_id.
