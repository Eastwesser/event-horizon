Profile — полный разбор для собеса
Разбираю так же, как предыдущие. Всё, что известно по services/profile из твоих файлов. 14 паттернов.

1. Одна фраза (elevator pitch)
Profile — агрегатор анкеты игрока и достижений. Потребляет score.updated и event.user.registered из NATS. Rule Engine EvaluateAchievements — чистая функция вычисления кодов достижений. Achievement Unlock Pipeline EvaluateAndUnlock → UnlockCodes → Unlock — трёхшаговый пайплайн разблокировки. Пишет в Postgres :5464 и кэширует в Redis :6385 (Cache-Aside). В отличие от Auth, Profile подключён к Redis. 14 паттернов.

4. Как работает (по шагам)
GetProfile (чтение)
Gateway → gRPC GetProfile. RequireAuth → ValidateToken в Auth → user_id в контекст.

Cache-Aside: ключ profile:{user_id}, промах → Postgres, запись в Redis.

Профиль собирается из:

Auth — email, nickname

Game — total_score, best scores

Billing — lamps, tickets (через Billing gRPC)

Profile — достижения (achievements table)

Возвращает агрегат.

Важно: GET /api/v1/profile может вернуть _partial — если один из источников (Billing, Game) недоступен, Profile отдаёт то, что есть, с флагом _partial. Это Graceful Degradation. В OCTOBER EXTRACTION.txt сказано: «Gateway: response cache + _partial profile».

Потребление score.updated
Game публикует score.updated через outbox worker.

Profile — durable consumer score.updated.

Для каждого события:

Rule Engine EvaluateAchievements — чистая функция: вход (score, game_id, level, user_stats), выход — список кодов достижений, которые разблокированы.

Achievement Unlock Pipeline:

EvaluateAndUnlock — вычисляет коды
UnlockCodes — фильтрует уже разблокированные
Unlock — INSERT … ON CONFLICT DO NOTHING (Idempotent Write)
Обновление total_score (best score) в Postgres.

Cache Invalidation: DeleteProfile(ctx, user_id).

Ack в NATS.

Необычный кейс: Rule Engine — чистая функция. Не зависит от БД, не делает IO. Легко тестировать. Это отделяет бизнес-правила от инфраструктуры.

Потребление event.user.registered
Gateway публикует event.user.registered после регистрации.

Profile — durable consumer event.user.registered.

Создаёт строку профиля для нового пользователя (email, nickname из события).

Cache Invalidation.

Важно: в MIRO_STICKERS_PASTE.md сказано: «History ingest: NATS user.registered and event.user.registered (normalized)». Profile потребляет event.user.registered (нормализованное). History — оба.

Необычные кейсы (стоит рассказать)
1. Rule Engine EvaluateAchievements — чистая функция.
Вход: (score, game_id, level, user_stats). Выход: список кодов достижений. Не зависит от БД, не делает IO. Легко тестировать. Это отделяет бизнес-правила от инфраструктуры. Классика функционального ядра.

2. Achievement Unlock Pipeline — три шага.
EvaluateAndUnlock → UnlockCodes → Unlock.

EvaluateAndUnlock — вычисляет коды (Rule Engine)

UnlockCodes — фильтрует уже разблокированные (читает из PG)

Unlock — INSERT … ON CONFLICT DO NOTHING (Idempotent Write)
Три шага вместо одного метода — читаемо и тестируемо по отдельности.

3. Idempotent Write (ON CONFLICT).
INSERT … ON CONFLICT DO NOTHING для достижений. Повторное событие score.updated не создаёт дубль. At-least-once + idempotent consumer.

4. Graceful Degradation.
Если Redis упал — Profile читает из Postgres. Медленнее, но работает. Профиль не теряется.

5. _partial profile.
GET /api/v1/profile может вернуть _partial, если один из источников (Billing, Game) недоступен. Profile отдаёт то, что есть, с флагом. Это Graceful Degradation на уровне агрегата.

6. UpdateProfile (gRPC) наружу не открыт.
Умеет переписать total_score — поэтому наружу не открыт. Имя меняется через Auth update-nickname. Это защита от подмены счёта.

7. Известные проблемы (техдолг):

9. Что спросят на собесе (готовые ответы)
«Почему Rule Engine — чистая функция?»
Легко тестировать. Вход (score, game_id, level, user_stats), выход — список кодов. Не зависит от БД, не делает IO. Бизнес-правила отделены от инфраструктуры. Классика функционального ядра.

«Почему Pipeline из трёх шагов?»
EvaluateAndUnlock → UnlockCodes → Unlock. Три шага вместо одного метода — читаемо и тестируемо по отдельности. EvaluateAndUnlock вычисляет коды (Rule Engine). UnlockCodes фильтрует уже разблокированные (читает из PG). Unlock — INSERT … ON CONFLICT DO NOTHING (Idempotent Write).

«Почему Idempotent Write?»
INSERT … ON CONFLICT DO NOTHING для достижений. Повторное событие score.updated не создаёт дубль. At-least-once + idempotent consumer. Если consumer перезапустится и прочитает событие заново — достижение не задвоится.

«Почему Profile — агрегатор, а не CRUD?»
Анкета собирается из Auth (ник), Game (рекорды), Billing (баланс), Profile (достижения). Profile — агрегатор, не владелец этих данных. UpdateProfile наружу не открыт: умеет переписать total_score. Имя меняется через Auth.

«Что такое _partial?»
GET /api/v1/profile может вернуть _partial, если один из источников (Billing, Game) недоступен. Profile отдаёт то, что есть, с флагом _partial: true. Это Graceful Degradation: лучше частичный ответ, чем 500.

«Почему Profile подключён к Redis, а Game нет?»
Профиль читается часто (при каждом заходе в профиль), а меняется реже. Redis снимает нагрузку с Postgres. Game не читается так часто — Redis ему не нужен (в текущем compose redis-game поднят, но Game к нему не подключён).

«Что если Redis упал?»
Profile читает из Postgres. Медленнее, но работает. Профиль не теряется. Graceful Degradation.

«Почему UpdateProfile наружу не открыт?»
Умеет переписать total_score. Если открыть — клиент может подменить счёт. Имя меняется через Auth update-nickname. Если понадобится редактирование профиля — нужен отдельный gRPC без total_score.

«Что если Billing недоступен при GetProfile?»
Profile отдаёт _partial: true, lamps: null, tickets: null. Остальное (email, nickname, total_score, achievements) — из PG и кэша. Graceful Degradation.

«Как тестируешь Profile?»
Unit — Rule Engine EvaluateAchievements (чистая функция, легко тестировать), мок репозитория. Integration — testcontainers (реальный PG + Redis). k6 CORE — browse.js (20 VU) читает профиль.

«Что улучшил бы?»
Отдельный gRPC для редактирования профиля без total_score

Алерт на profile_partial_responses_total резко растёт

Алерт на profile_achievements_unlocked_total резко растёт (Rule Engine разблокирует всё подряд)
