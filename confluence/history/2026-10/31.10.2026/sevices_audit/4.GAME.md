Game — полный разбор для собеса
Разбираю так же, как Auth. Всё, что известно по services/game из твоих файлов.

1. Одна фраза (elevator pitch)
Game — игровое ядро. Принимает счёт от клиента, валидирует ходы по правилам конкретной игры (Strategy по game_id), пишет рекорд и строку outbox score.updated в одной транзакции. Буст за лампы списывает Billing синхронно, бустнутый забег в лидерборд не идёт. Публикация — отдельным воркером после commit, FOR UPDATE SKIP LOCKED, чтобы два процесса не слали один рекорд дважды. 20 паттернов.

4. Как работает (по шагам)
SubmitScore (обычный забег)
Gateway принимает POST /api/v1/game/submit, RequireAuth → ValidateToken в Auth → user_id + role в контекст.

Gateway зовёт Game по gRPC SubmitScore.

Game определяет игру по game_id — Strategy по играм (switch req.GameID на 8 игр: Flappy, Pancaker/Hexagon, Builder/Towers, Memonia, Hanoi, 2048, Gears, Tamagotchi).

Domain Validators — для Hexagon и Memory есть свои валидаторы (проверка ходов, seed, score).

Если буст активен — забег не ранжируется (в лидерборд не идёт, магазин с него не получает прибыль).

В одной транзакции:

INSERT/UPDATE highscores (рекорд, ON CONFLICT обновляет лучший счёт)

INSERT outbox(score.updated) — событие в ту же транзакцию

Commit.

Outbox worker (services/game/internal/worker/outbox_worker.go):

SELECT … FROM outbox WHERE processed = false ORDER BY created_at LIMIT 20 FOR UPDATE SKIP LOCKED

Два процесса берут разные строки — один рекорд не публикуется дважды.

Publish в NATS JetStream.

Строка помечается processed = true только после успешного Publish.

Если JetStream не подключён — строка остаётся необработанной, уйдёт со следующей попытки.

NATS score.updated → Leaderboard (Redis Sorted Set + PG), Profile (достижения), Billing (начисление), History, Analytics, Gateway → WebSocket.

StartBoost (буст за лампы)
Gateway → gRPC StartBoost.

Game зовёт Billing по gRPC SpendCurrency синхронно (лампы списываются до старта).

Если активный буст уже есть — лампы второй раз не списываются (идемпотентность).

Бустнутый забег не идёт в лидерборд, магазин с него не получает прибыль.

DailyGift (Tamagotchi)
Gateway → gRPC DailyGift.

Game проверяет, не забирал ли уже сегодня.

Если нет — зовёт Billing AddCurrency (+1000 билетиков), идемпотентно по reference_id.

Необычные кейсы (стоит рассказать)
1. Strategy по играм — switch на 8 игр.
SubmitScore — god-function switch на 8 игр. Это антипаттерн по мнению каталога: «Вынести в per-game strategy» (пункт 23 в «Средней важности»). На собесе честно: «Сейчас switch, знаю что надо вынести в strategy-интерфейс».

2. Outbox worker с FOR UPDATE SKIP LOCKED.
Два процесса берут разные строки. Строка помечается processed только после успешного Publish. Если JetStream не подключён — строка остаётся необработанной. Это защита от «потеряли событие» и «опубликовали дважды».

3. Бустнутый забег не ранжируется.
Буст за лампы — не pay-to-win. Бустнутый забег в лидерборд не идёт, магазин с него не получает прибыль. Это осознанный дизайн.

4. Domain Validators для Hexagon и Memory.
Не все игры валидируются одинаково. Для Hexagon и Memory есть чистые функции проверки ходов/seed/score. Для остальных — базовая проверка.

5. user_id из токена, не из тела.
SubmitScore использует user_id из JWT. Подменить нельзя.

9. Что спросят на собесе (готовые ответы)
«Почему outbox, а не просто publish после commit?»
Dual-write проблема: commit в БД + publish в NATS раздельно → потеря или дубль события. Outbox пишет событие в ту же транзакцию, что и рекорд. Воркер публикует после commit. Строка помечается processed только после успешного Publish. Дубликаты возможны — consumer идемпотентный. Так избегаем dual-write.

«Почему FOR UPDATE SKIP LOCKED?»
Два процесса-воркера берут разные строки. Без SKIP LOCKED они бы блокировали друг друга. С ним — каждый берёт свою пачку, никто не ждёт. Это стандартный паттерн для outbox poller’а.

«Что если JetStream упал?»
Строка остаётся processed = false. Воркер повторяет со следующей попытки. Рекорд в БД уже записан — клиент получил ответ. Событие уйдёт, когда NATS оживёт. Это at-least-once, consumer должен терпеть повтор.

«Почему бустнутый забег не в лидерборд?»
Буст за лампы — не pay-to-win. Иначе богатый игрок покупает лампы и всегда в топе. Бустнутый забег не ранжируется, магазин с него не получает прибыль. Это осознанный дизайн.

«Почему switch на 8 игр — не strategy?»
Честно: сейчас switch req.GameID — god-function. В каталоге паттернов это отмечено как антипаттерн (пункт 23): «Вынести в per-game strategy». Знаю, что надо. Для Hexagon и Memory уже есть Domain Validators — чистые функции. Для остальных — базовая проверка.

«Как валидируешь ходы?»
Для Hexagon и Memory — Domain Validators: чистые функции проверки ходов, seed, score. Для остальных — базовая проверка (score не отрицательный, game_id известен). Полная anti-cheat для всех 8 игр — в техдолге.

«Почему user_id из токена, не из тела?»
Защита от подмены. Клиент не может отправить рекорд за другого. Gateway кладёт user_id из JWT в контекст, Game берёт оттуда.

«Что если Billing упал при старте буста?»
StartBoost зовёт SpendCurrency синхронно. Billing упал — буст не стартует, клиент получает ошибку. Обычный SubmitScore при этом работает — Game не зависит от Billing для обычного забега. Это graceful degradation.

«Как тестируешь Game?»
Unit — мок репозитория, Domain Validators (чистые функции, легко тестировать). Integration — testcontainers (реальный PG). Есть Failover Test — проверка отказа. k6 CORE — browse.js (20 VU), purchase.js (1–5 VU). Legacy 500 VU login blast — не pass/fail.
