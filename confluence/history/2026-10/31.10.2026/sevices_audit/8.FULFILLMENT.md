Fulfillment — полный разбор для собеса
Разбираю так же, как предыдущие. Всё, что известно по services/fulfillment из твоих файлов. 15 паттернов. Dual-Transport Consumer, Idempotency Guard, эмуляция сборки.

1. Одна фраза (elevator pitch)
Fulfillment — эмуляция сборки заказа. Потребляет purchase.paid из NATS (primary) или Kafka (fallback). Ждёт 10 секунд (delay-based simulation), публикует purchase.fulfilled с тем же purchase_id. Shop ставит fulfilled_at, Notification пишет в колокольчик. Dual-Transport Consumer: NATS primary, Kafka fallback. Idempotency Guard на уровне транспорта: повтор purchase.paid не запускает вторую сборку. Manual DI (без контейнера). Нет gRPC — только NATS/Kafka + HTTP для health/metrics. 15 паттернов.

4. Как работает (по шагам)
Потребление purchase.paid
Shop публикует purchase.paid через outbox worker (NATS) или напрямую (Kafka, heavy).

Dual-Transport Consumer:

NATS primary: если JetStream подключён — Fulfillment читает из NATS.

Kafka fallback: если JetStream не подключён — Fulfillment читает из Kafka.

В FINISHERS.md: «Fulfillment и notification читают Kafka только когда JetStream не поднят».

Idempotency Guard (transport level): проверка, не обрабатывали ли уже этот purchase_id. Если да — Ack, skip.

Delay-Based Simulation: time.After(10 * time.Second) — эмуляция сборки.

Публикация purchase.fulfilled с тем же purchase_id в тот же транспорт (NATS или Kafka).

Ack при успехе. Nak при ошибке.

Необычный кейс: Delay-Based Simulation. time.After(10s) — эмуляция сборки. Не реальный WMS API. В README: «Fulfillment — эмуляция сборки заказа (delay 10s). По факту наличия товара, я просто ищу его, достаю из коробки и упаковываю для отправки. Заменится на реальный WMS API в будущем. См. FUTURE_EVENT_HORIZON.md → Tech Debt».

Dual-Transport Consumer
NATS primary: js.Subscribe("purchase.paid", handler, nats.Durable("fulfillment-durable")).

Kafka fallback: kafka.Consumer на топик purchase.paid.

Transport Selection в Service: сервис выбирает транспорт по env (NATS_URL / KAFKA_BROKERS).

Если оба живы — читает только NATS (primary). Kafka — fallback.

В FINISHERS.md: «Если JetStream подключён, Kafka-consumer у fulfillment и notification не стартует».

Необычный кейс: Dual-Transport Consumer — это не «читаем из обоих», а «читаем из одного, второй — fallback». В EVENT_HORIZON_PATTERNS_15.10.2026.md: «Dual-Transport Consumer — fulfillment (NATS primary, Kafka fallback)».

Idempotency Guard (transport level)
При получении purchase.paid — проверка purchase_id в памяти (map с TTL) или в отдельном хранилище.

Если уже обработан — Ack, skip.

Если нет — обработка, потом запись в map.

В каталоге паттернов: «Idempotency Guard (transport) — fulfillment».

Важно: Idempotency Guard на уровне транспорта — это не ON CONFLICT в БД (у Fulfillment нет БД), а map в памяти с TTL. При рестарте map теряется — повторная сборка возможна. Это техдолг (не явно, но подразумевается).

Публикация purchase.fulfilled
После time.After(10s) — публикация purchase.fulfilled с тем же purchase_id.

В тот же транспорт, из которого читали (NATS → NATS, Kafka → Kafka).

Shop потребляет purchase.fulfilled → ставит fulfilled_at по purchases.id.

Notification потребляет purchase.fulfilled → in-app bell.

Важно: purchase.fulfilled содержит purchase_id (настоящий purchases.id из Shop). Shop находит строку по этому id и ставит fulfilled_at. Это было исправлено в v1.1.1 (FINISHERS.md): «Покупка пишет purchase.paid в outbox с настоящим purchases.id».

Manual DI (без контейнера)
В отличие от других сервисов (DI Container), Fulfillment — Manual DI.

main.go вручную создаёт NATS-клиент, Kafka-клиент, сервис, handler.

В каталоге: «Manual DI (без контейнера) — fulfillment, balancer, nats-hub».

Плюс — проще, меньше зависимостей. Минус — больше кода в main.go.

Известные проблемы (техдолг)
«Заглушка time.After(10s) вместо реального WMS. Заменить на вызов warehouse/delivery API. Добавить Outbox для гарантии» (пункт 1).

«Нет Outbox — если сервис упадёт между purchase.paid и purchase.fulfilled, событие потеряется. Внедрить Transactional Outbox» (пункт 2).

«newUUID (crypto/rand) vs uuid.NewString() (google/uuid) — несогласованность» (пункт 30).

Важно: Fulfillment — единственный сервис без Outbox. Если упадёт между purchase.paid и purchase.fulfilled — событие потеряется. Shop не поставит fulfilled_at, Notification не отправит уведомление. Это критично. В техдолге: «Внедрить Transactional Outbox».

9. Что спросят на собесе (готовые ответы)
«Почему Fulfillment без gRPC?»
Единственный «вход» — purchase.paid, «выход» — purchase.fulfilled. HTTP только для /health и /metrics. Это осознанно: Fulfillment — чистый consumer, не сервис с API. В EVENT_HORIZON_PATTERNS_15.10.2026.md: «Нет gRPC — только NATS/Kafka + HTTP».

«Почему Manual DI, а не контейнер?»
Проще, меньше зависимостей. main.go вручную создаёт NATS-клиент, Kafka-клиент, сервис, handler. В каталоге: «Нет DI-контейнера — manual DI». Честно: знаю, что для большого сервиса контейнер лучше, но для Fulfillment — ручной DI достаточен.

«Что такое Dual-Transport Consumer?»
NATS primary, Kafka fallback. Не «читаем из обоих», а «читаем из одного, второй — fallback». В FINISHERS.md: «Если JetStream подключён, Kafka-consumer у fulfillment и notification не стартует». Это защита от двойной доставки.

«Что такое Idempotency Guard?»
Проверка purchase_id перед сборкой. Map в памяти с TTL. Повтор purchase.paid не запускает вторую сборку. В каталоге: «Idempotency Guard (transport) — fulfillment». Честно: при рестарте map теряется — повторная сборка возможна. Это техдолг.

«Что такое Delay-Based Simulation?»
time.After(10s) — эмуляция сборки. Не реальный WMS API. В README: «Заменится на реальный WMS API в будущем». Честно: это заглушка, в техдолге — заменить на реальный API.

«Почему Crypto-Secure UUID?»
newUUID (crypto/rand) для purchase.fulfilled. UUID непредсказуем. В каталоге: «Crypto-Secure UUID — fulfillment». Минус: newUUID (crypto/rand) vs uuid.NewString() (google/uuid) — несогласованность (пункт 30 в техдолге).

«Что если Fulfillment упадёт между purchase.paid и purchase.fulfilled?»
Техдолг: «Нет Outbox — если сервис упадёт между purchase.paid и purchase.fulfilled, событие потеряется. Внедрить Transactional Outbox». То есть Shop не поставит fulfilled_at, Notification не отправит уведомление. Честно: знаю, надо Outbox.

«Что если NATS упал?»
Graceful Degradation: Kafka fallback. Если JetStream не подключён — Fulfillment читает из Kafka. Это Dual-Transport Consumer.

«Почему purchase.fulfilled содержит purchase_id?»
Shop находит строку по этому id и ставит fulfilled_at. Было исправлено в v1.1.1: «Покупка пишет purchase.paid в outbox с настоящим purchases.id». Без этого fulfilled_at не находил строку.

«Как тестируешь Fulfillment?»
Unit — мок NATS/Kafka, Idempotency (повтор purchase.paid). Integration — testcontainers (реальный NATS/Kafka). Delay — тест с time.After. Dual-Transport — тест с NATS и Kafka (проверка, что читает только один).
