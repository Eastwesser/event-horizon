1. Одна фраза (elevator pitch)
NATS Hub — не игровой сервис, а bootstrap JetStream. Создаёт stream EVENTS со всеми субъектами (score.updated, user.registered, shop.*, purchase.*, payment.completed, inventory.item.*, author.upserted, balance.updated, event.>) и конфигом (FileStorage, MaxAge 7 дней, MaxBytes 1 ГБ). Idempotent Stream Creation: AddStream → если AlreadyExists → UpdateStream. Stream Config as Code — конфиг в Go, не в UI. Wildcard Subscription event.> — логирует все события. Реальный health check через nc.IsConnected(). 11 паттернов. Игровой логики нет.

4. Как работает (по шагам)
Bootstrap / Initializer
NATS Hub стартует.

Подключается к NATS-кластеру (nats-1:4222, nats-2:4223, nats-3:4224).

Idempotent Stream Creation:

js.AddStream(&nats.StreamConfig{...}) — попытка создать stream EVENTS.

Если AlreadyExists — js.UpdateStream(&nats.StreamConfig{...}) — обновить конфиг.

Если создать не удалось — ошибка, сервис падает (не может работать без stream).

Wildcard Subscription event.> — подписка на все события с префиксом event.. Логирует их (debug).

Реальный health check через nc.IsConnected() — если NATS-клиент отвалился, /health вернёт ошибку.

Необычный кейс: Idempotent Stream Creation. AddStream → если AlreadyExists → UpdateStream. Это защита от «stream уже создан, сервис упал при рестарте». В отличие от AddStream без проверки, UpdateStream не падает, если stream уже есть.

Stream Config as Code
Конфиг stream EVENTS — в Go-коде, не в NATS UI.

Name: "EVENTS", Subjects: []string{...}, Storage: FileStorage, MaxAge: 7 * 24 * time.Hour, MaxBytes: 1 * 1024 * 1024 * 1024 (1 ГБ).

Subjects:

score.updated

user.registered

event.>

shop.purchased

purchase.paid

purchase.fulfilled

payment.completed

inventory.item.*

author.upserted

balance.updated

Stream Config as Code — версионируется вместе с кодом, не в UI. Изменения — через PR.

Важно: в HOW_DOES_EH_WORK.md: «NATS Hub — Bootstrap / Initializer — единственный сервис, создающий инфраструктуру». То есть NATS Hub — единственный, кто создаёт stream. Остальные только публикуют/потребляют.

Wildcard Subscription event.>
NATS Hub подписан на event.> — все события с префиксом event..

Логирует их (debug): event.user.registered, event.score.updated, etc.

Это не для бизнес-логики, а для отладки: видно все события.

В каталоге: «Wildcard Subscription — nats-hub».

Реальный health check
/health — nc.IsConnected(). Если NATS-клиент отвалился — ошибка.

В отличие от многих сервисов (где /health всегда ok), NATS Hub проверяет реальное соединение.

В каталоге: «Реальный health check через nc.IsConnected()».

Важно: MaxAge: 7 дней — retention stream. В 00_METRICS.md: «Сырые события: 7 дней там, где так сказано в резюме (AdTime заказы, Roolz Kafka), 30 дней в модели EH». Для NATS stream — 7 дней, не 30. Для History — 30 дней (другое хранилище).

Кластер
NATS-кластер из 3 нод: nats-1:4222, nats-2:4223, nats-3:4224.

NATS Hub подключается к одному, NATS-клиент находит кластер.

Если нода упала — клиент переподключается к другой.

Stream EVENTS — реплицируется на все ноды (FileStorage + репликация).

В INTERVIEW_PATTERNS.md (nats.md): «NATS кластер (3 ноды) автоматически переизбирает лидера».

9. Что спросят на собесе (готовые ответы)
«Почему NATS Hub — отдельный сервис?»
Единственный, кто создаёт stream EVENTS. Остальные только публикуют/потребляют. Если бы каждый создавал stream — race condition, дублирование. Один Bootstrap / Initializer — проще. В HOW_DOES_EH_WORK.md: «NATS Hub — Bootstrap / Initializer — единственный сервис, создающий инфраструктуру».

«Почему Idempotent Stream Creation?»
AddStream → если AlreadyExists → UpdateStream. Защита от «stream уже создан, сервис упал при рестарте». AddStream без проверки упал бы, UpdateStream не падает.

«Что такое Stream Config as Code?»
Конфиг stream EVENTS — в Go-коде, не в NATS UI. Версионируется вместе с кодом. Изменения — через PR. Это infrastructure-as-code, но в Go, не в Terraform.

«Почему Wildcard Subscription event.>?»
NATS Hub подписан на event.> — все события с префиксом event.. Логирует их (debug). Не для бизнес-логики, а для отладки: видно все события.

«Почему реальный health check?»
/health — nc.IsConnected(). В отличие от многих сервисов (где /health всегда ok), NATS Hub проверяет реальное соединение. Если NATS-клиент отвалился — /health вернёт ошибку.

«Почему MaxAge 7 дней, а не 30?»
В 00_METRICS.md: «Сырые события: 7 дней там, где так сказано в резюме (AdTime заказы, Roolz Kafka), 30 дней в модели EH». Для NATS stream — 7 дней (retention), не 30. Для History — 30 дней (другое хранилище). Разные сроки для разных хранилищ.

«Почему MaxBytes 1 ГБ?»
Потолок. Если stream превысит 1 ГБ — старые сообщения удаляются раньше MaxAge. Защита от неограниченного роста. В 00_METRICS.md: «Диск событий за 7 дней при ~1 КБ на событие заказа: 106 × 86400 × 7 × 1 КБ ≈ 60 ГБ». То есть 1 ГБ — это мало, но для учебного контура достаточно.

«Что если NATS-кластер упал?»
NATS Hub не имеет Graceful Degradation. Если NATS-клиент отвалился — /health возвращает ошибку, сервис падает. Это осознанно: без stream EVENTS публикация не работает. Но NATS-кластер из 3 нод — если одна упала, клиент переподключается к другой.

«Почему 3 ноды NATS?»
Кластер: nats-1:4222, nats-2:4223, nats-3:4224. Stream EVENTS реплицируется на все ноды. Если нода упала — клиент переподключается к другой. В INTERVIEW_PATTERNS.md (nats.md): «NATS кластер (3 ноды) автоматически переизбирает лидера».

«Почему :9097 на хосте — NATS Hub, а не Gateway-3?»
В MIRO_STICKERS_PASTE.md: «nats-hub host :9097 — Collides with gateway-3 internal metrics port only on host map. Host curl :9097 ≠ gateway-3». То есть :9097 на хосте — это NATS Hub. Gateway-3 слушает :9097 внутри контейнера. Prometheus ходит по именам nats-hub:9097 и gateway-3:9097 внутри docker-сети.

«Как тестируешь NATS Hub?»
Unit — мок NATS-клиента, Idempotent Stream Creation (AddStream → UpdateStream), Stream Config (проверка subjects/MaxAge/MaxBytes). Integration — testcontainers (реальный NATS). Health check — nc.IsConnected().

«Что улучшил бы?»
