# Game — Redis anti-cheat (решение от 27.10.2026)

> Статус: **принято**. `redis-game :6380` не удаляем — подключаем для anti-cheat.
> Закрывает техдолг P2 (пункт 32: «`redis-game` не подключён — подключить/убрать»).
> Почему не «просто убрать»: в текущей реализации `SubmitScore` защищён только
> rate limit на Gateway (10 req/s на user). Этого мало: 10 валидных submit/с
> проходят валидацию и пишутся в PG → лавина outbox → лавина `score.updated`
> в NATS → 10 `ZADD` в Leaderboard, хотя рекорд мог не измениться.
> Redis решает три вещи: бизнес-лимит на submit, дедупликация, кэш рекорда.

| Что | Статус |

| Техдолг P2 (пункт 32) | «`redis-game` не подключён — подключить/убрать» |
| Rate limit на Gateway | 10 req/s на user (общий, не бизнес-лимит) |
| Leaderboard защита | `ZAddArgs{GT: true}` — хуже не перезаписывает (но событие всё равно идёт) |
| PG нагрузка от submit | Каждый валидный submit = INSERT `highscores` + INSERT `outbox` |

**Проблема:** игрок с валидным seed/moves может слать 10 submit/с. Все пройдут валидацию, все запишутся в PG, все попадут в outbox → NATS → 6 потребителей. Leaderboard отбросит худшие через `GT: true`, но событие уже прошло по всей цепочке. Это лишняя нагрузка на PG, NATS, outbox worker, consumers.

**Решение:** Redis в Game для anti-cheat / дедупликации / кэша рекорда.

## 2. Что делаем (три функции)

### 2.1. Бизнес-лимит на submit (`INCR`)

**Ключ:** `submit:{user_id}:{game_id}:{minute}` (minute = `time.Now().Unix() / 60`).
**TTL:** 60 секунд.
**Лимит:** N в минуту (например, 30 — с запасом на нормальную игру).

```go
func (s *GameService) checkSubmitRate(ctx context.Context, userID, gameID string) error {
    minute := time.Now().Unix() / 60
    key := fmt.Sprintf("submit:%s:%s:%d", userID, gameID, minute)
    count, err := s.rdb.Incr(ctx, key).Result()
    if err != nil {
        // Redis упал — fail-open: не блокируем игру
        return nil
    }
    if count == 1 {
        s.rdb.Expire(ctx, key, time.Minute)
    }
    if count > submitRateLimit {
        return status.Error(codes.ResourceExhausted, "too many submits")
    }
    return nil
}
Почему fail-open: если Redis упал, лучше пропустить submit, чем сломать игру. Rate limit Gateway (10 req/s) остаётся как первый барьер.

2.2. Дедупликация submit (SETNX)
Ключ: dedup:{user_id}:{game_id}:{sha256(seed + moves)}.
TTL: 5 минут.
Зачем: защита от replay — тот же submit с тем же seed/moves не пройдёт второй раз.

go
func (s *GameService) checkSubmitDedup(ctx context.Context, userID, gameID, seed string, moves []Move) error {
    hash := sha256.Sum256([]byte(seed + fmt.Sprint(moves)))
    key := fmt.Sprintf("dedup:%s:%s:%x", userID, gameID, hash)
    ok, err := s.rdb.SetNX(ctx, key, 1, 5*time.Minute).Result()
    if err != nil {
        // Redis упал — fail-open
        return nil
    }
    if !ok {
        return status.Error(codes.AlreadyExists, "duplicate submit")
    }
    return nil
}
Почему fail-open: если Redis упал — пропускаем, дубль возможен (at-least-once), но игра не ломается.

2.3. Кэш рекорда (GET / SETEX)
Ключ: score:{user_id}:{game_id}:{level}.
TTL: 5 минут.
Зачем: если новый счёт <= кэш — не писать в PG, не создавать outbox. Экономит INSERT и лавину событий.

go
func (s *GameService) checkHighscoreCache(ctx context.Context, userID, gameID string, level int32, score int64) (bool, error) {
    key := fmt.Sprintf("score:%s:%s:%d", userID, gameID, level)
    cached, err := s.rdb.Get(ctx, key).Int64()
    if err == redis.Nil {
        // miss — пишем, обновим кэш после успешной записи
        return true, nil
    }
    if err != nil {
        // Redis упал — fail-open: пишем в PG
        return true, nil
    }
    if score <= cached {
        // не рекорд — не пишем
        return false, nil
    }
    return true, nil
}

func (s *GameService) updateHighscoreCache(ctx context.Context, userID, gameID string, level int32, score int64) {
    key := fmt.Sprintf("score:%s:%s:%d", userID, gameID, level)
    s.rdb.SetEX(ctx, key, score, 5*time.Minute)
}
Почему fail-open: если Redis упал — пишем в PG (как раньше). Кэш — оптимизация, не источник правды.

3. Где встраивать (в SubmitScore)
Порядок важен: rate limit → dedup → validation → cache → PG.

go
func (s *GameService) SubmitScore(ctx context.Context, req *pb.SubmitScoreRequest) (*pb.SubmitScoreResponse, error) {
    // 1. Валидация входа
    if req.UserId == "" || req.GameId == "" {
        return nil, status.Error(codes.InvalidArgument, "user_id and game_id are required")
    }

    // 2. Бизнес-лимит на submit (Redis INCR, fail-open)
    if err := s.checkSubmitRate(ctx, req.UserId, req.GameId); err != nil {
        return nil, err
    }

    // 3. Дедупликация (Redis SETNX, fail-open)
    if err := s.checkSubmitDedup(ctx, req.UserId, req.GameId, req.Seed, req.Moves); err != nil {
        return nil, err
    }

    // 4. Domain Validator (чистая функция)
    if err := s.validate(req); err != nil {
        return nil, status.Error(codes.InvalidArgument, err.Error())
    }

    // 5. Кэш рекорда (Redis GET, fail-open)
    shouldWrite, err := s.checkHighscoreCache(ctx, req.UserId, req.GameId, req.Level, req.Score)
    if err != nil {
        // fail-open: пишем в PG
        shouldWrite = true
    }
    if !shouldWrite {
        return &pb.SubmitScoreResponse{
            Success:      true,
            NewHighscore: req.Score, // не рекорд
            Ranked:       false,
        }, nil
    }

    // 6. TX: highscores + outbox
    if err := s.repo.SaveScoreAndOutbox(ctx, req); err != nil {
        return nil, status.Errorf(codes.Internal, "save score: %v", err)
    }

    // 7. Обновить кэш рекорда (после успешной записи)
    s.updateHighscoreCache(ctx, req.UserId, req.GameId, req.Level, req.Score)

    return &pb.SubmitScoreResponse{
        Success:      true,
        NewHighscore: req.Score,
        Ranked:       !isBoostActive,
    }, nil
}
Важно: кэш рекорда обновляется после успешной записи в PG. Если PG упал — кэш не обновится, следующий submit перечитает из PG.

8. Что НЕ делать
Не fail-closed. Redis упал → не блокируем игру (fail-open). Иначе Redis — единая точка отказа для submit.

Не кэшировать всё подряд. Только score:{user}:{game}:{level}, TTL 5 мин. Не кэшировать highscores целиком.

Не убирать rate limit Gateway. Он остаётся первым барьером (10 req/s). Redis — второй барьер (бизнес-лимит 30/мин).

Не путать с Leaderboard. Leaderboard ZADD GT: true — защита от перезаписи худшим. Redis в Game — защита от лавины submit.

Не убирать redis-game из compose. Он теперь задействован.
