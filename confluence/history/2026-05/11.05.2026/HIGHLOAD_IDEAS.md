# Инсайты нагрузочного тестирования — 11 мая 2026

**Время:** 13:00 — 20:00  
**Инструмент:** bombardier  
**Цель:** POST /api/game/submit

## Что было сделано

1. Настройка мониторинга (логи, NATS varz, системные метрики)
2. Тестирование от 10 до 6000 пользователей
3. Оптимизация узких мест:
   - Leaderboard: убрали лишний `ZREVRANK`
   - Gateway: добавили кеш с TTL 2 секунды
   - NATS: batch ack сообщений
   - Billing: batch insert транзакций

## Что узнали про NATS

| Показатель | До оптимизации | После оптимизации |
|------------|----------------|-------------------|
| Макс RPS | ~3,500 | ~21,000 |
| P95 latency | 940ms | 340ms |
| Slow consumers | при 2000+ | при 6000+ |

**Вывод:** NATS может дать 20k+ RPS на одном узле, если правильно настроить durable subscriptions и batch ack.

## Что узнали про PostgreSQL

- Одновременные записи — узкое место
- Batch insert (COPY) ускорил вставку транзакций в 5-10 раз
- Пул соединений (max_connections) нужно увеличивать под нагрузку

## Что узнали про Redis

- Sorted Set отлично держит топ-10 даже при 6000 запросов/сек
- `ZADD` ~5-10ms, `ZREVRANK` добавляет ещё столько же
- Вынос `ZREVRANK` из hot path дал +30% производительности

## Что узнали про Go сервисы

- Goroutines не текут (спасибо graceful shutdown)
- Память растёт линейно с нагрузкой (~50KB на пользователя)
- CPU упирается в NATS и сериализацию protobuf

## Лимиты одного сервера

| Лимит | Значение | Как повысить |
|-------|----------|--------------|
| open files | 1024 | `ulimit -n 65535` |
| TCP порты | 28,000 | `sysctl net.ipv4.ip_local_port_range` |
| backlog | 128 | `sysctl net.core.somaxconn 4096` |
| память | 8GB | Физически добавить |
| CPU | 4 ядра | Физически добавить |

## Что бы сделали иначе

1. **Сразу сделали бы batch ack** — это дало +50% пропускной способности
2. **Вынесли бы `ZREVRANK` из NATS subscriber** — уменьшило latency на 200ms
3. **Стартовали с k6 вместо bombardier** — k6 даёт больше метрик, но сложнее
4. **Добавили бы tracing (Jaeger)** — легче найти медленные места

## Что сделали правильно

1. Graceful shutdown с самого начала
2. Раздельные БД на каждый микросервис
3. NATS как основная шина событий
4. Полная валидация игры на сервере
5. Документирование каждого этапа
