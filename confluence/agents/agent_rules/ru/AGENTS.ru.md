# EventHorizon — Правила для AI-агентов

## Назначение

Этот файл — операционное руководство для AI-агентов (включая меня, Хохо), работающих в репозитории EventHorizon.

Агент должен:

- понимать архитектуру микросервисной платформы;
- следовать принятым соглашениям;
- знать, куда класть код;
- уметь поднимать и тестировать систему;
- избегать небезопасных и разрушительных изменений;
- спрашивать, когда не уверен.

## Принципы работы агента

Агент должен:

- предпочитать минимальное безопасное изменение;
- сохранять существующую архитектуру (микросервисы, NATS, gRPC);
- обновлять документацию при изменениях API или конфигурации;
- проверять работу перед завершением;
- не делать рефакторинги без запроса.

### Что оптимизируем

1. **Правильность** — игра не должна врать игроку (манифест).
2. **Поддерживаемость** — код должен быть понятен через год.
3. **Скорость** — но не в ущерб первым двум.

### Что запрещено по умолчанию

- Добавлять FOMO-механики (искусственный дефицит, сгорание прогресса).
- Менять архитектуру без обсуждения.
- Добавлять новые зависимости без необходимости.
- Игнорировать падающие тесты.

## Архитектура

- **Стиль:** Микросервисы с событийной шиной (NATS)
- **Сервисы:**
  - `auth` (50051) — JWT, регистрация, логин
  - `game` (50052) — валидация, подсчёт очков
  - `billing` (50053) — лампочки, билетики
  - `leaderboard` (50054) — топ-10, Redis
  - `gateway` (8080) — HTTP + WebSocket

### Поток данных
Фронтенд → Gateway → Game → NATS → Leaderboard → Redis
↓
Billing → PostgreSQL

text

### Архитектурные правила

- Сервисы общаются через gRPC (синхронно) или NATS (асинхронно).
- База данных у каждого сервиса своя (database per service).
- Фронтенд НЕ считает очки — только сервер (честная валидация).
- Никаких FOMO-механик (см. манифест).

Эскалация

Спросить человека перед:

изменением JWT логики;
изменением правил начисления очков;
удалением данных;
изменением deployment конфигов.
Когда агент должен остановиться и спросить

Задача противоречит этическому манифесту (FOMO, скрытое обнуление).
Нужно изменить архитектуру (например, добавить новый сервис).
Документация и код расходятся.
Тесты падают по непонятной причине.
Известные подводные камни

user_id в localStorage — иногда не сохраняется, нужен fallback из токена.
WebSocket — закрывается при монтировании/размонтировании компонента.
NATS — при перезапуске может не подписаться (нужен durable consumer).
Leaderboard — очки должны суммироваться, а не заменяться.
