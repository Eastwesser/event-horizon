# Roolz — легенда проекта для рассказа на собесе

> **Честный дисклеймер:** это **легенда для рассказа** (narrative framework), не верифицированная внутренняя вики Roolz. Используйте как каркас: подставляйте только те технологии и цифры, которые вы реально трогали. Если опыт косвенный — так и скажите: «разбирал архитектуру / участвовал в модуле X».

## Elevator pitch (30 сек)

Roolz — продуктовая платформа с упором на **правила, роли и пользовательские сценарии** (rule engine / collaboration / domain workflows). Типичный контур: аккаунты и RBAC → доменные сущности → движок правил или бизнес-процессов → уведомления и аудит → интеграции наружу.

Формулировка на собесе: «мультиарендное SaaS-ядро с гибкими правилами доступа и автоматизациями, а не простой CRUD».

## Проблематика

- Сложный **RBAC/ABAC**: роли, ресурсные политики, делегирование.
- Версионирование правил: кто изменил condition, когда применилось.
- Идемпотентные webhooks наружу и внутрь.
- Поиск и фильтры по большим спискам сущностей (пагинация, индексы).
- Наблюдаемость: почему правило сработало / не сработало (explainability).

## Стек (типичный каркас рассказа)

- Backend на Go или Node; PostgreSQL как source of truth.
- Redis: сессии, rate limit, короткие кеши ACL.
- Очередь (NATS/Kafka/Rabbit) для async уведомлений и side-effects правил.
- Audit log / event store для «кто что поменял».
- Feature flags для постепенного раската правил.

Мост к EH: «в Event Horizon я делал RBAC `user|author|admin` на Gateway + gRPC metadata, Outbox для побочных эффектов, Redis sessions — тот же класс задач».

## Роль и задачи (STAR-шаблон)

1. **Ситуация:** гонки при одновременном обновлении сущности / правила; дыры в авторизации на отдельных эндпоинтах.
2. **Задача:** закрыть IDOR, сделать предсказуемые side-effects.
3. **Действие:** единый middleware авторизации; optimistic locking `version`; side-effects только через outbox после commit; тесты на 401 vs 403.
4. **Результат:** регресс по security checklist, меньше «тихих» дублей уведомлений — *без выдуманных %*.

## Доменные talking points

- **Policy decision point** vs enforcement в каждом хендлере.
- Разница role-based и attribute-based доступа.
- Dry-run правила перед publish в прод.
- Compensating actions, если downstream notification упал.
- Мультитенантность: `tenant_id` в каждом запросе и индексе.

## Масштаб — честно

Говорите про сложность домена (число типов правил, интеграций), а не про фантастический RPS, если его не было. Для SaaS часто важнее correctness ACL и аудит, чем «миллион RPS».

## Чего не выдумывать

- Внутренние метрики выручки Roolz.
- «Я с нуля спроектировал всю платформу», если был фокус на одном сервисе.
- Секреты/клиентов — только обобщённо.

## Как связать с завтрашним интервью red_mad_robot

Покажите системное мышление: границы сервисов, контракты событий, security by default, тестирование политик. Roolz-легенда = рассказ про **сложные инварианты**; EH = доказательство, что вы это кодировали руками.

1. Как проектировать RBAC, чтобы не размазать проверки по всем хендлерам?
2. Чем 401 отличается от 403 в вашем API?
3. Как версионировать бизнес-правила без даунтайма?
4. Как обеспечить идемпотентность webhook-доставки?
5. Optimistic locking vs pessimistic для карточки сущности?
6. Как дебажить «правило не сработало» в проде?
7. Что класть в audit log, а что нельзя (PII)?
8. Как тестировать ACL: unit на policy engine vs e2e через gateway?
