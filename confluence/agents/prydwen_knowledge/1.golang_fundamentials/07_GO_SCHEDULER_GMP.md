# Go: планировщик GMP

Модель рантайма Go: **G** (goroutine), **M** (OS thread), **P** (processor / контекст планирования). Нужно, чтобы объяснить, почему «горутины дешёвые», что такое work stealing и preemption.

## Буквы GMP

- **G (Goroutine):** сущность выполнения — стек, PC, статус (runnable / running / waiting).
- **M (Machine):** OS thread, на котором реально крутится код. Может парковаться, уходить в syscall.
- **P (Processor):** логический процессор; держит **локальную очередь** runnable G, кэш аллокатора (mcache). Число P = `GOMAXPROCS`.

Выполнение: M должен владеть P, чтобы исполнять Go-код. Связка: `M` + `P` берут `G` из очереди.

## Очереди и work stealing

1. У каждого P — локальная run queue (ограниченного размера).
2. Глобальная очередь — overflow / балансировка.
3. Если локальная пуста — P **ворует** половину очереди у другого P (work stealing) или берёт из global.
- Новые `go` обычно кладутся в локальную очередь текущего P → лучше cache locality.

Netpoller: блокирующий I/O (сеть) паркует G без удержания M+P надолго; когда сокет готов — G снова runnable.

## Syscall и блокировки

- При syscall M может отпустить P (hand off), чтобы другой M продолжил Go-код; после syscall M пытается найти свободный P.
- `LockOSThread` — привязка к OS thread (cgo, thread-local); дорого, не для hot path.
- Долгий CPU-loop без вызовов рантайма раньше мог не отдать процессор — см. preemption.

## Preemption (вытеснение)

- **Кооперативная (старая):** безопасные точки — вызовы функций, аллокации. Чистый цикл без вызовов мог крутиться вечно на P.
- **Асинхронная (Go 1.14+):** сигнал/метаданные для прерывания долгих G; fairer scheduling, меньше «stop-the-world голодания» из-за одного CPU hog.
- GC тоже опирается на преемпцию и safe points для STW-фаз.

На собесе: «с 1.14 горутину в tight loop могут вытеснить, но всё равно не пишите busy-spin без `runtime.Gosched`/канала/таймера».

## GOMAXPROCS снова

- Больше P ≠ всегда быстрее: contention на shared structures, cache thrashing.
- В контейнере: выставляйте по CPU quota (`go.uber.org/automaxprocs` или runtime cgroup detection), иначе oversubscribe.
- EH микросервисы: часто упираются в DB pool (25) и сеть, а не в число P.

## Связь с latency

- Слишком много runnable G → очереди, хвосты latency.
- Блокировки на Mutex под P — другие G на этом P ждут; держите локи короткими.
- cgo / тяжёлый syscall — отбирает M; следите за thread count в pprof/threadcreate.
