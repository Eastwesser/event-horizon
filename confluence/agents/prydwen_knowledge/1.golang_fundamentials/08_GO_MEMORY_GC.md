# Go: память и GC

Стек vs куча, escape analysis, сборщик мусора и pprof — must-have для разбора latency и RSS в проде.

## Стек и куча

- **Стек горутины:** локальные переменные, если не «убежали»; растёт/сжимается сегментами. Дёшево, без GC давления.
- **Куча (heap):** объекты, живущие дольше фрейма, разделяемые, большие, или чьи адреса ушли наружу. Учитываются GC.

Правило: меньше аллокаций в hot path → меньше GC CPU и пауз (у современного GC паузы малы, но CPU scavenger/mark не бесплатен).

## Escape analysis

Компилятор решает: стек или куча.

Типичные причины escape:

- возврат указателя на локальную переменную;
- сохранение указателя в heap-структуру / interface / channel;
- `append` с неизвестным cap, большие слайсы;
- замыкание, захватившее переменную;
- аргументы `fmt`/`interface{}` (часто боксинг).

Смотреть: `go build -gcflags='-m=2'`. Оптимизировать только по профилю, не «на глаз».

## Аллокации и слайсы

- `make([]T, 0, n)` — одна аллокация capacity, меньше ресайзов.
- `sync.Pool` для буферов в JSON/сериализации.
- Избегайте `string` ↔ `[]byte` в цикле.
- protobuf/json decode — главный источник alloc в gRPC сервисах EH; кэшируйте размеры, переиспользуйте buffers где безопасно.

## Garbage Collector (обзор)

- Concurrent mark-and-sweep (tri-color), цель — короткие STW.
- `GOGC` (дефолт 100): рост кучи на X% относительно live → следующий цикл. Больше GOGC → реже GC, выше RSS.
- `GOMEMLIMIT` (Go 1.19+): soft limit памяти — лучше для контейнеров, чем крутить только GOGC.
- Finalizers (`runtime.SetFinalizer`) — не для ресурсного менеджмента (предпочитайте `defer Close` / closer в EH).

## pprof

Базовые профили:

| Профиль | Зачем |
|---------|--------|
| `heap` | allocs, inuse — кто держит память |
| `allocs` | кумулятивные аллокации |
| `cpu` | горячие функции |
| `goroutine` | утечки / блокировки |
| `block` / `mutex` | contention (нужен `SetBlockProfileRate`) |

Поднять: `net/http/pprof` на metrics HTTP (не публичный gateway без auth), или `go tool pprof`.

**EH:** `/health` и `/ready` на metrics-порту; pprof обычно рядом в dev/staging, в prod — за сетью/флагом.

## Типичные симптомы

- Пилы RSS + CPU на mark — много короткоживущих объектов.
- Медленный steady alloc — утечка ссылок (глобальный slice, кэш без TTL, subslice leak).
- Рост goroutines — не GC, а concurrency bug.
