--- name: grill-me description: Builds a complete task brief before any code is written. Interrogates the user to fill goal, scope, constraints and acceptance criteria, then produces TASK_BRIEF.md from the embedded template. Use when the user gives a raw or vague task intention, says "grill me", asks for a task brief or spec, or makes an underspecified feature request like "add support for X". --- # Grill Me - build a task brief through interrogation ## Overview Turn a raw intention into a complete TASK_BRIEF.md through a short, structured interrogation. The brief transfers responsibility for understanding the task from the user to the agent. No code is written until the brief is approved. ## Phase 1 - Infer (no questions yet) Study the repo first: stack, conventions, affected modules, how to run and test. Never ask about anything that can be read from the repo. Asking about the stack is a failure of this skill. ## Phase 2 - Grill (one message, then wait) Ask 3-7 questions in a single batch. Two rounds maximum. Rules: - Every question maps to an empty section of the embedded template below. - Every question offers options and a default, so "yes" is a valid answer. Not "which UI kit?" but "the template uses Tailwind - shadcn/ui, or something else?" - Always ask about negative scope and propose candidates: "I will NOT touch CI, NOT bump major versions - correct?" - If the answer would not change the plan or the diff, do not ask. ## Phase 3 - Brief Fill the embedded template completely and save it as TASK_BRIEF.md next to the task. The stop criterion is formal: every section has content - not "it feels clear enough". Output the brief and a step-by-step plan. Wait for explicit approval before writing any code. ## When NOT to grill If the task is a well-defined single edit, say so: "this does not need a brief - it is one edit" - and handle it as a normal edit. ## Embedded template (TASK_BRIEF.md) # TASK_BRIEF.md ## Task What needs to be done, in one paragraph. ## Context Why it is needed and where it lives in the project. ## Scope ### In scope - ### Out of scope - ## Files / modules Zones expected to be touched: - ## Acceptance criteria - [ ] - [ ] - [ ] ## Constraints - Do not change: - Do not break: - Do not use: ## Verification - Tests: - Manual check: - Edge cases: ## Plan for the agent 1. Study the context first. 2. Propose a plan. 3. Wait for approval. 4. Make the minimal diff. 5. Explain the changes. 6. Suggest tests.
