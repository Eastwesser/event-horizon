# 📈 Архитектура и поток пользователя (для контекста)

У нас локальная песочница, но мы можем смоделировать эти цифры, исходя из архитектуры и заложенных лимитов, и главное — зафиксировать, где и как мы будем их смотреть, когда проект взлетит.

Погнали разбирать твой список по косточкам.

Прежде чем говорить о цифрах, утвердим «карту боя». Вот как выглядит типичный путь пользователя в Event Horizon:

## Ключевые моменты:

- Синхронный путь (REST/gRPC): Клиент → Балансировщик → Gateway → Сервис → БД/Кеш → Ответ.
- Асинхронный путь (События): Game → NATS → Leaderboard (и подписанные Gateway).
- Real-time путь: Leaderboard → WebSocket → Клиент.

## 7. Бизнес-метрики (Что мы считаем важным)
Это то, чего нам сейчас не хватает. Нужен отдельный сервис Analytics для подсчета.

- Популярность игр: Считаем количество событий score.updated по полю game_id. Самая популярная игра — Hexagon.

- Активность: DAU = количество уникальных user_id, отправивших рекорд за день.

- Retention: Смотрим, возвращается ли пользователь на следующий день.

## 🚨 «Куда смотреть в 3 часа ночи?» (SOS-дашборд)
Если сервис упал, я открываю одну панель в Grafana и смотрю на 4 графика:

- P99 Latency (для Gateway и Auth). Если растет — сервис тормозит.

- NATS Consumer Lag. Смотрим, сколько сообщений не обработано в Leaderboard или Billing. Если лаг > 1000 — проблема с подпиской.

- HTTP Error Rate (5xx). Смотрим gateway_requests_total со статусом 500. Если резко пошел вверх — что-то сломалось в бизнес-логике или БД.

- Free Memory (RAM). Если память на сервере заканчивается — K8s/Docker убьет под.
